### Lifecycle of the KV Cache: Prefill vs. Decode

In a decoder-only model (e.g., Llama, Mistral), the KV cache lifecycle is strictly segregated between the **Prefill** phase and the **Decode** phase.

1.  **Prefill Phase (Prompt Processing):**
    During the initial few tokens sent by the user, the GPU computes attention scores for all $N_{prompt}$ tokens against the entire vocabulary. The resulting attention scores are reduced to logits (probabilities) and stored in the **KV cache**.
    *   **Action:** All $N_{prompt} + N_{out}$ tokens are processed.
    *   **Storage:** The full KV cache (containing $N_{prompt}$ keys and $N_{out}$ values) is loaded from system RAM into the GPU's VRAM.

2.  **Decode Phase (Token-by-Token):**
    Once the prompt is processed, the model enters decoding mode. For each generated token $t_i$, the model attends to the **entire context** (previous prompt + generated tokens).
    *   **Action:** Only the relevant $N_{out}$ tokens from the current generation are processed.
    *   **Storage:** The KV cache is **not** recomputed from scratch. Instead, it is **reused** (cached) from the VRAM. Only the new $N_{out}$ values are written to VRAM, while the keys associated with the existing context remain cached.

**Hardware Implication:**
If the VRAM is insufficient for the current context size, the system must page the KV cache to system RAM. This forces the model to read from system RAM and write to GPU VRAM for each generated token, introducing memory bandwidth contention.

---

### Hardware Stress Discrepancy: Prompt Throughput vs. Latency

The user's observation is a classic symptom of **prefill vs. decode resource partitioning**.

*   **Prompt Processing Stress:** Dominated by **Compute (FP16/BF16)**. The GPU's high tensor cores are utilized to process the massive attention matrix across the entire context. High prompt-tokens-per-second (pt/s) indicates strong compute capacity, meaning the GPU can crunch the math very quickly.
*   **Interactive Latency Stress:** Dominated by **Memory Bandwidth and Compute**. Decoding requires high memory bandwidth to stream data from system RAM to the GPU and compute per-token. While the compute per-token might be low (due to small context size), the **latency** is high because the system spends time moving data across the PCIe bus rather than computing.

**Why high pt/s does not imply low interactive latency:**
Even if the GPU can compute 50 tokens per millisecond, if the system spends 10ms fetching the KV cache from RAM for every single generated token, the total time will be dominated by the I/O bound decoding step, not the compute step. The "excellent pt/s" masks a "slow decode" bottleneck.

---

### Impact of Scaling Context from 2,000 to 8,000 Tokens

Increasing context size from 2k to 8k tokens fundamentally changes the memory profile:

1.  **KV Cache Size Explosion:**
    The VRAM required is roughly proportional to $N_{context} \times N_{out}$.
    *   At 2k tokens: Cache size $\approx$ $2k \times 300$ tokens.
    *   At 8k tokens: Cache size $\approx$ $8k \times 300$ tokens (a **4x increase** in VRAM demand).

2.  **Prefill Behavior:**
    *   **Load Time:** The time to load the initial KV cache from system RAM increases significantly as the total size grows.
    *   **Throughput:** The prefill time will increase, likely reducing the *initial* prompt throughput. However, since the *per-token* latency is primarily a decoding issue, the *overall* inference time per token might not improve much, but the *per-token latency* will degrade due to the longer prefill duration.

3.  **Decode Behavior (The Critical Bottleneck):**
    *   **Page Faults:** As the cache exceeds VRAM, the model must load the KV cache from system RAM for every token.
    *   **Bandwidth Saturation:** Fetching $N_{context}$ keys and $N_{out}$ values from system RAM for every generated token creates a severe bandwidth bottleneck.
    *   **Result:** Per-token latency spikes dramatically. Even if compute speed is unchanged, the system spends the majority of the generation time moving data, not calculating.

### Truth vs. Implementation-Specific Claims

| Claim | Verdict | Reasoning |
| :--- | :--- | :--- |
| **KV cache is recomputed for every generated token.** | **False** (Generally) | Modern FP16/BF16 implementations use **caching** (reusing old keys/values) rather than recomputation. Recomputing would be $O(N_{context}^2)$, which is prohibitive. |
| **System RAM is always used to cache the KV cache.** | **Dependent** | This depends on **Cache Precision**. If the KV cache is stored as 32-bit floats (FP32), it fits in system RAM. If it is 16-bit (BF16) or 8-bit (INT8), it may exceed system RAM, requiring VRAM or offloading to CPU. |
| **Moving KV cache to system RAM reduces latency.** | **Dependent** | Only if the system RAM has sufficient bandwidth and the page-transaction cost is low enough to offset the data movement latency. Often, transferring data from system RAM to GPU is slower than reading from system RAM directly. |
| **Offloading KV cache to CPU eliminates VRAM pressure.** | **Dependent** | Only if the CPU has sufficient bandwidth and the offload kernel support is efficient. Not all CPUs support efficient KV offloading. |
| **Paging (dynamic memory management) adds latency.** | **Dependent** | Paging is required for dynamic sizing. It adds overhead but is necessary for fitting large contexts in small VRAM. |

### Three Measurements to Distinguish Bottlenecks

To isolate which component is causing the slowdown, run controlled experiments while holding other variables constant:

1.  **KV-Cache Traffic (Memory Bandwidth Benchmark):**
    *   *Setup:* Run the model with 2k tokens. Measure the time to fetch the full KV cache from system RAM to VRAM during the **Prefill** phase.
    *   *Expected Result:* Linear scaling with context size. A large increase here indicates **prefill memory bandwidth** is the bottleneck.

2.  **Weight Bandwidth (Compute Bandwidth Benchmark):**
    *   *Setup:* Run the model with 8k tokens. Measure the time to process the full KV cache from system RAM to VRAM during the **Decode** phase.
    *   *Expected Result:* Linear scaling with context size. A large increase here indicates **compute bandwidth** is saturated (or the VRAM size is too small to fit the cache, forcing offload).

3.  **CPU-GPU Transfer (I/O Bandwidth Benchmark):**
    *   *Setup:* Run the model with 8k tokens. Measure the time to move the KV cache from System RAM to GPU VRAM during the **Decode** phase.
    *   *Expected Result:* This isolates the PCIe bus and host system RAM. If this is the bottleneck, the system is **paging** the cache to system RAM and the transfer speed is the limiting factor, regardless of CPU speed.

### Numerical Example: Dominance of Prefill vs. Decode

**Scenario:**
*   **Prompt Tokens ($N_{prompt}$):** 250
*   **Output Tokens ($N_{out}$):** 300
*   **System RAM:** 32 GB (holds $\approx 32 \text{ GB} \times 16 \text{ bits} = 5.1 \text{ TB}$)
*   **VRAM:** 24 GB (holds $\approx 4.8 \text{ GB} \times 16 \text{ bits}$)
*   **Context:** 2,000 tokens.

**Calculation:**
1.  **KV Cache Size:** $2,000 \times 300 = 600,000$ tokens.
    *   VRAM Required: $600,000 \text{ tokens} \times 16 \text{ bits} = 9.6 \text{ GB}$.
    *   System RAM Available: 5.1 TB $\gg$ 9.6 GB.
2.  **Situation:** The system fits in VRAM.
3.  **Latency Dominance:**
    *   **Prompt Processing:** The GPU crunches attention on 250 tokens.
    *   **Decode Latency:** For each of 300 generated tokens, the model attends to the *entire* context (2,000 tokens).
        *   *Latency:* $N_{context} \times N_{out} = 2,000 \times 300 = 600,000$ operations.
        *   *Time:* $600,000 \text{ ops} / (2,000 \text{ tokens/s}) = 300 \text{ ms}$.

**Analysis:**
Even though the GPU is doing 600,000 operations per second (high compute), the **latency** is dominated by the prefill phase if the prompt is large. However, in this specific setup, the **Decode** phase dominates because the *per-token* latency is high ($300\text{ms}$) due to attending to a large context, not because the compute is slow.

*Correction for the example above:* To show Decode latency dominance clearly, we must reduce the prompt size so the prefill finishes quickly.

**Revised Numerical Example:**
*   **Prompt Tokens ($N_{prompt}$):** 50
*   **Output Tokens ($N_{out}$):** 300
*   **Context:** 2,000 tokens (fits in VRAM).

1.  **Prefill Time:** $50 \times 300 \text{ tokens} / (\text{Compute Rate})$. Let's say Compute Rate = 250 tokens/s. Time = 600ms.
2.  **Decode Time:**
    *   *Per-Token Latency:* $2,000 \text{ tokens} \times 300 \text{ tokens} / 250 \text{ tokens/s} = 2,400 \text{ ms}$.
    *   *Total Generation Time:* 300 tokens $\times$ 2,400 ms = 720 seconds (12 minutes).

**Conclusion:**
In this scenario, the **Decode phase** dominates the total time. The system is not slow because it cannot compute the next token quickly; it is slow because it has to attend to the entire 2,000-token context for every single output token. The "excellent prompt processing throughput" is a false positive; the system is I/O bound during decoding.
