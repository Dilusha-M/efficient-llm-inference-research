# Llama.cpp Benchmark Runner Design Proposal

## 1. Requirements and Invariants

**Inputs:**
*   `config.yaml`: Specifies model path, backend (CPU/GPU/Vulkan), context size (default 4096), generation limit (default 256), temperature, and optional overrides for workload-specific contexts.
*   `prompts`: A fixed list of text strings corresponding to the six workload types (`chat`, `batch`, `coding`, `summarization`, `agentic`, `world_knowledge`).
*   `hardware_metadata`: Hardware specs (CPU model, GPU model, driver version).
*   `model_info`: Model file hash, build version, and backend type.

**Artifacts:**
*   `benchmark/run_<timestamp>.txt`: The raw response text generated by the model.
*   `benchmark/metrics_<timestamp>.json`: JSON blob containing resource usage (GPU tensor cores, VRAM, CPU cycles) and timing data.
*   `benchmark/metadata_<run_id>.json`: Human-readable summary including the specific prompt used, hardware details, and high-level performance metrics.
*   `benchmark/raw_output_<run_id>.txt`: A raw dump of stdout/stderr from the process launch to allow manual audit.

**Success/Failure States:**
*   **Success:** Complete execution of all workloads, generation of valid metrics, and successful creation of all three artifact files.
*   **Failure (Run Specific):** Execution of the specific workload(s) fails, but no `metrics` or `metadata` files are generated for that run, and the raw output file contains a truncated or corrupted response.
*   **Failure (Pipeline):** The runner fails to initialize due to missing model, missing backend, or invalid config syntax, resulting in no output files being created.

**Experimental Identity Tuple:**
The unique identifier for a specific run is constructed from the hash of the model file path, the backend type, the hardware label, the context size, the generation limit, the prompt hash, and the temperature. This tuple ensures strict isolation: changing *any* component of this tuple results in a completely different run identity, regardless of the output content.

**Ambiguity Resolution:**
The primary ambiguity is the definition of "partial output." Does a process that generates tokens but fails to exit (e.g., hangs or crashes mid-generation) constitute a "failed run" (resulting in no artifacts) or a "failed model run" (resulting in an artifact but no metrics)?
*   **Resolution:** Per the specification, a "failed model run" implies the process was created and is in a state where metrics cannot be gathered. Therefore, if the process exits prematurely (OOM, timeout, crash), the run is still considered successful in terms of artifact creation (since files exist), but the `metrics` file is empty or indicates a "no_metrics" state. However, the spec implies that if the process *fails to complete* (e.g., crashes), the run should be marked as a failure state to prevent misleading comparisons.
*   **Refined Resolution:** We treat a "failed model run" specifically as a state where the process exits with a non-zero status code or crashes, resulting in no `metrics` file being written. If the process hangs (timeout) without crashing, it is treated as a "partial run" where the `metadata` file is generated but `metrics` is empty, explicitly labeled as `partial_metrics`. This distinction prevents conflating a hanging process (which blocks the main thread) with a crashed process (which terminates cleanly).

## 2. State Machine Workflow

The lifecycle is managed by a `BenchmarkRunner` class that follows a strict state progression:

1.  **Validation State:**
    *   Input: `config.yaml` and `prompts`.
    *   Action: Parse config, validate prompt strings against known workloads, verify required hardware features are present.
    *   Exit: Fail if config is invalid or missing required fields.

2.  **Launch State:**
    *   Input: Validated config, selected model path.
    *   Action:
        *   If `backend` is CUDA: Verify CUDA driver is installed and available.
        *   If `backend` is Vulkan: Verify Vulkan libraries are linked.
        *   If `backend` is CPU: Launch `llama.cpp` with `--backend=cpu` and specified `--n_threads`.
        *   If `backend` is GPU: Launch `llama.cpp` with `--backend=cuda` and specify `--n_gpu_layers`.
    *   Exit: Fail if backend is unsupported, environment not found, or if the process fails to start (exit code != 0).

3.  **Monitor Activation State:**
    *   Input: Runtime environment (e.g., `nvidia-smi` is available).
    *   Action:
        *   If `metrics` is enabled: Start collecting data on every token generation.
        *   If `metrics` is disabled: Collect no data.
    *   Exit: Transition to Monitoring State immediately upon activation.

4.  **Monitoring State (Active):**
    *   Input: In-flight generation.
    *   Action:
        *   Every N tokens: Sample data (e.g., every 100 tokens).
        *   On process exit: Flush pending data and write `metrics.json`.
    *   Exit: Transition to Finalization State upon successful write or timeout.

5.  **Finalization State:**
    *   Input: Process has exited.
    *   Action:
        *   If `metrics` was collected: Write `metrics_<timestamp>.json`.
        *   If `metrics` was not collected (e.g., partial run or timeout): Write `partial_metrics_<timestamp>.json` containing a `state` field set to `partial`.
        *   Write `metadata_<run_id>.json`.
        *   Write `raw_output_<run_id>.txt` (redirecting the process' stdout/stderr).
    *   Exit: Success state.

**Critical Error Handling:**
*   **OOM (Out of Memory):** If the model process exceeds available VRAM, it will crash. The state machine treats this as a **Failure State** where no artifact files are created for that specific run.
*   **Timeout:** If the process takes too long (e.g., stuck in a loop), the state machine sets `partial_metrics` state to indicate "no_metrics" to prevent misleading throughput calculations.
*   **Malformed Output:** If the process returns a non-zero exit code, the state machine terminates immediately, writing the raw output file, and does *not* write the `metrics` file.

## 3. Auditable Design

To ensure engineering teams can verify the design, we define strict boundaries for components and data preservation:

**Component Boundaries:**
*   **Validation Layer:** Pure Python `yaml`/`json` parsers. No external tools.
*   **Launch Layer:** The `llama.cpp` binary execution. This is the "black box." We cannot inspect its internals.
*   **Monitoring Layer:** A wrapper that calls `nvidia-smi` or `nvidia-cli` (if available) and aggregates the output into a JSON structure.
*   **Logging Layer:** A custom `logging` module that captures all stdout/stderr from the `llama.cpp` process before redirecting them.

**Metadata Schema:**
The `benchmark/metadata_<run_id>.json` file must contain:
```json
{
  "run_id": "uuid-v1-...",
  "model_file": "/path/to/model.gguf",
  "backend": "cuda|cpu|vulkan",
  "hardware_label": "nvidia-xxx",
  "context_size": 4096,
  "generation_limit": 256,
  "temperature": 0.7,
  "n_threads": 1,
  "prompt": "Input string",
  "prompt_hash": "sha256-of-input",
  "hardware_metadata": { "cpu_model": "Intel...", "gpu_model": "RTX...", "driver_version": "535.x.x" },
  "model_info": { "build": "v1.0.0", "backend_type": "cuda" },
  "status": "success|partial|failure",
  "error_message": "string|null"
}
```

**Atomic-Write / Partial-File Conventions:**
*   **Raw Output:** The `raw_output` file is a simple `>` redirection of the process' stdout to itself. It is appended to every single line of the original process output. This preserves the exact prompt, tokenization boundaries, and any debug prints.
*   **Metrics/Metadata:** These are written to JSON files using atomic operations (`touch` then `printf` or `echo`) to ensure the file exists before the process exits, preventing "missing file" errors in the audit trail.
*   **No Mixed Outputs:** The runner never attempts to write a `metrics` file if the process failed to exit cleanly or if the process crashed (OOM/Timeout). It strictly adheres to the rule: *No metrics file = Failed run.*

**Prompt Preservation:**
The prompt is appended to the very beginning of the raw output file (before the first newline of the response). This ensures that if the model logs a debug message or truncates the response, the prompt is still present for manual reconstruction of the generation.

## 4. Analysis Integrity

**Preventing Misleading Throughput:**
A common pitfall is calculating throughput based on raw tokens generated, ignoring the cost of model inference. To prevent this:
1.  **Exclude OOM/Timeout Runs:** Any run where the model process crashes or hangs is excluded from throughput calculations. If a run is "partial" (timed out but didn't crash), the throughput is set to 0.
2.  **Include Error Messages:** The `metadata` file includes an `error_message` field. If the model fails to generate a response (e.g., permission denied), this field describes the cause, allowing engineers to diagnose why the throughput metric is low rather than just assuming it is.
3.  **Hardware-Aware Scaling:** The runner must account for the fact that a GPU with 16GB VRAM cannot run a model requiring 24GB VRAM, even if the model is the same. The metrics file must include a `nvidia_vram_used_gb` field, allowing users to normalize throughput by VRAM capacity.

**Parsing Unknown Formats:**
The parser must be designed to be robust against llama.cpp's output variability.
*   **Fallback Strategy:** If the parser encounters a line that does not start with `response` or `generated_text`, it should attempt to parse it as a custom format (e.g., JSON lines, or plain text).
*   **Graceful Degradation:** If parsing fails, the parser should log a warning but still attempt to extract the token count (e.g., counting lines or extracting a specific marker) to populate the `generated_tokens` field.
*   **No Hard Fail:** The runner should not crash the entire benchmark suite if a single model output format differs from the expected canonical format. The integrity of the *aggregate* results should remain valid, even if individual run summaries are slightly off.

Once the process exits (successfully), it writes the `metrics` file (indicating no data was collected) and the `metadata` file. The `raw_output` file is generated, but it will be empty or contain only the prompt if the model returned nothing.

3.  **Prompt Containing Spaces/Newlines:**
    *   *Scenario:* The `prompts` file contains a line with spaces or newlines.
    *   *Action:* Run the runner with a "world_knowledge" prompt.

It writes a `metadata` file with `status: "success"` (since the file was created) but `metrics: "no_metrics"` and `partial_metrics: "no_metrics"` (or similar indicator). ## 6. Pre-Merge Review

### 3 Highest-Risk Design Flaws and Fixes

**Flaw 1: Ambiguity in "Partial Output" Classification**
*   **Risk:** If a model hangs or crashes mid-generation, should it be treated as a failed run (no artifacts) or a partial run (artifacts present)?
*   **Fix:** Explicitly define that a "failed model run" results in *no* artifact files. If the process exits with a non-zero status, the run is a failure. If the process times out or hangs without a crash, the `metadata` file is generated but explicitly labeled as `partial_metrics` to distinguish it from a clean success. This prevents conflating a hanging process (which blocks the runner) with a crashed process (which the runner can clean up).

**Flaw 2: Metrics File Existence Assumption**
*   **Risk:** Assuming `metrics.json` will always be written. If the runner crashes or the process exits with an error, the file might be missing, causing downstream tools to fail.
*   **Fix:** Implement atomic writes for all output files (`metrics`, `metadata`, `raw_output`). Ensure a "touch" command is used to guarantee the file exists on disk before the process exits, regardless of the process's exit code. This ensures the "no metrics" state is always readable.

**Flaw 3: Noisy Baseline in Throughput Calculation**
*   **Risk:** The raw token count from a failed or partial run could be interpreted as high throughput if the error message is not included in the analysis, or low throughput if the model fails silently.
*   **Fix:** The parser must strip out non-data tokens (e.g., tokenizer start/end tokens, debug logs, or garbage at the end of a partial response) *before* calculating throughput. Only tokens that are part of the final, coherent response should be counted. Additionally, the `error_message` field in the metadata must be populated so users know *why* the throughput is low, rather than guessing.
