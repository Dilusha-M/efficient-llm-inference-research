### Task 3 — robust aggregation

**Pseudocode: Median Calculation with Failure Handling**

```python
def robust_aggregate_decode_speeds(speeds, last_run_warning=True):
    """
    Validates records, handles failures, computes median.
    
    Args:
        speeds (list): List of decode speeds (tok/s).
        last_run_warning (bool): If True, the last run is considered failed.
    
    Returns:
        float: The median of successful runs.
        bool: True if fewer than two successful runs exist.
    """
    
    # 1. Validate records: Check for NaN, infinity, and negative values
    valid_speeds = [s for s in speeds if not (s is None or s == float('inf') or s == float('-inf')) and s >= 0]
    
    # 2. Handle the "out-of-memory" run
    if last_run_warning:
        # Treat the last run as failed
        valid_speeds.remove(last_run_warning)
        
    # 3. Compute median using a robust method (e.g., sorting or selection)
    sorted_speeds = sorted(valid_speeds, reverse=True)
    
    if len(sorted_speeds) < 2:
        return float('nan'), False
    
    n = len(sorted_speeds)
    mid = n // 2
    
    # Method A: If odd number, take the middle element
    if n % 2 == 1:
        median = sorted_speeds[mid]
    # Method B: If even, average the two middle elements
    else:
        median = (sorted_speeds[mid - 1] + sorted_speeds[mid]) / 2.0
    
    return median, n % 2 == 1
```

**Reporting Result if Fewer Than Two Runs Succeed:**
If `len(valid_speeds) < 2`, the function returns `float('nan')`. This signals a critical error state to the user, indicating that the dataset is insufficient for a statistical median. The median is undefined in this case, and no valid average can be computed.

### Task 4 — validity audit

**Four Threats to Validity**
1.  **Threat: Shared Memory Contamination (Cross-Process/Process-to-Process)**
    *   *Description:* If the CPU and CUDA kernels share a memory pool (or if the user reuses the same GPU memory for different tasks), the CPU layer might read/write data that was modified by the CUDA layer, or vice versa, leading to incorrect results.
    *   *Control:* Enforce exclusive memory ownership per backend. Ensure the CPU backend uses a separate, isolated memory pool or a distinct virtual address space not accessed by the CUDA backend.
2.  **Threat: Inconsistent Parallelization Strategy (Non-Architectural)**
    *   *Description:* If the CPU backend uses a different threading model (e.g., OpenMP) than the CUDA backend (e.g., CUDA streams), the way threads interact with the GPU can be inconsistent, leading to race conditions or incorrect results.
    *   *Control:* Use a single, consistent parallelization strategy (e.g., CUDA streams for both, or MPI for both) to ensure the communication pattern matches the hardware.
3.  **Threat: Workload/Output Comparability (Task-Specific)**
    *   *Description:* The CPU backend might be optimized for different types of operations (e.g., dense matrix multiplication vs. sparse operations) or different data types (float vs. int) than the CUDA backend, causing the outputs to be fundamentally different even if the "speed" matches.
    *   *Control:* Use a standard, well-defined benchmark suite (e.g., BENCHMARK) that explicitly specifies the task, data types, and output format for both backends. The results are only comparable if they address the exact same mathematical problem.
4.  **Threat: Runtime Environment Variability**
    *   *Description:* Differences in CPU architectures (e.g., Apple Silicon vs. AMD Zen) or CUDA driver versions between runs can lead to subtle performance differences unrelated to the model or workload.
    *   *Control:* Run the benchmark on a fixed set of hardware configurations and keep the compiler and runtime versions strictly pinned to specific versions for all runs.

### Task 5 — user-visible latency

**Definitions and Equation**
*   **Time to First Token (TTFT):** The time elapsed from the start of the prompt processing until the very first token is generated.
*   **Prompt-Evaluation Throughput:** The rate at which the LLM consumes the prompt tokens (tokens per second). This is a measure of *how quickly the model can read the input*, not how fast it generates output.
*   **Decode Throughput:** The rate at which the model generates output tokens (tokens per second). This is the actual latency experienced by the user.
*   **Total Wall-Clock Time:** The sum of TTFT, prompt evaluation time, decode time, and any overhead.

**Symbolic Equation:**
$$ T_{\text{total}} = T_{\text{TTFT}} + T_{\text{prompt\_eval}} + T_{\text{decode}} + T_{\text{overhead}} $$

**Example where optimizing prompt processing barely changes user experience:**
Suppose a model has a TTFT of 0.01 seconds. The user processes the prompt in 0.005 seconds. The model generates 200 tokens in 1.5 seconds.
*   **Scenario A (Prompt Processing Optimized):** Prompt takes 0.001s. $T_{\text{total}} \approx 0.01 + 0.001 + 1.5 = 1.511$ s.
*   **Scenario B (Prompt Processing Unoptimized):** Prompt takes 0.015s. $T_{\text{total}} \approx 0.01 + 0.015 + 1.5 = 1.525$ s.
*   **User Experience:** The user sees the first token appear 0.015s after the prompt was started instead of 0.01s. While the *total* time increased by 15ms, the **per-token latency** (TTFT) remained effectively constant (0.01s). To the user, the delay in generating the first token is negligible compared to the 200 tokens generated in 1.5 seconds. Therefore, optimizing the prompt processor has a near-zero impact on the perceived latency of the generation phase.
