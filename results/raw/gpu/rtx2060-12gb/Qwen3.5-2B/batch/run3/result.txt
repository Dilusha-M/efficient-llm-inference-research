### Task 3 — Robust aggregation

**Pseudocode for Median Calculation with Failure Handling**

```python
def robust_aggregate_decoding_speeds(speeds, has_failure=True):
    """
    speeds: list of float (decode speeds in tok/s)
    has_failure: boolean indicating if any run failed
    Returns: median of successful runs, or None if no success
    """
    
    # 1. Validate records: Ensure all speeds are valid floats
    valid_records = [speed for speed in speeds if isinstance(speed, (int, float)) and speed >= 0]
    
    if len(valid_records) == 0:
        return None # No data to process
    
    # 2. Keep failed run visible: Filter out invalid or failed runs from the list
    successful_runs = [speed for speed in valid_records if speed > 0] # Filter out 0s if desired
    
    # 3. Compute median for successful runs
    if len(successful_runs) == 0:
        return None # Fewer than two runs succeed
    
    # Sort the successful speeds
    successful_runs.sort()
    
    # Compute median
    mid = len(successful_runs) // 2
    if len(successful_runs) % 2 == 1:
        median = successful_runs[mid]
    else:
        median = (successful_runs[mid-1] + successful_runs[mid]) / 2.0
    
    # 4. Report if fewer than two succeed
    if len(successful_runs) < 2:
        return f"Median not computable: Only {len(successful_runs)} successful run(s) found."
    
    return median
```

### Task 4 — Validity Audit

**Four Threats to Validity (CPU vs. CUDA vs. Vulkan)**

1.  **Threat 1: GPU Memory Layout and Coalescing (Hardware/Software)**
    *   *Description:* CUDA uses shared memory and has specific memory coalescing rules that differ fundamentally from CPU register-level parallelism. A kernel launched on the GPU might not exhibit the same level of vectorization or caching efficiency as a CPU version, leading to different throughput metrics.
    *   *Control:* Run the same benchmark code on a **CPU-only** baseline. If the CUDA speed is significantly higher than the CPU baseline (even with full offloading), it indicates a hardware-specific acceleration (likely NVLink or specific tensor cores) rather than just the quantization method. Conversely, if the difference is negligible, it suggests the offloading is working correctly.
2.  **Threat 2: Thread Coalescing Efficiency (Workload/Output Comparability)**
    *   *Description:* CPU threads are often executed in a single context (one CPU core), whereas GPU threads may be pipelined across multiple GPUs or cores. The "2,000-token" prompt might be generated across multiple GPU streams or cores, while the CPU run is serialized.
    *   *Control:* Compare the **total throughput (tokens/sec)** and **time per token** across multiple GPU configurations (e.g., using 1, 2, 4, 8 GPUs) to isolate the effect of parallelism. If the difference between CPU and GPU is not present when scaling GPUs, the hardware acceleration (CUDA) is likely masking the true performance difference.
    *   *Specific Control:* Ensure the **workload** (prompt length, token count) is identical across all runs, including the CPU run, to ensure the output is comparable before comparing raw metrics.
3.  **Threat 3: Kernel Optimization and Pruning Differences**
    *   *Description:* Quantization often introduces sparsity (e.g., Q4_K_M) or changes the precision, affecting how the compiler optimizes kernels. A CPU version might use different optimization flags than the GPU version.
    *   *Control:* Run both CPU and GPU versions on the **same model** using the **exact same quantization parameters** (e.g., Q4_K_M) and **identical compilation flags** (e.g., `--opt level` or specific pruning configurations).
4.  **Threat 4: Latency vs. Throughput Distortion**
    *   *Description:* The time-to-first-token (TTFT) might be dominated by CPU synchronization overhead (host-gpu sync), while decode throughput is dominated by GPU compute. This creates a false impression of "speed" if TTFT is high but throughput is low.
    *   *Control:* Measure **TTFT**, **throughput**, and **total latency** separately for each backend. Report both metrics rather than conflating them into a single "latency" number.

### Task 5 — User-visible latency

**Definitions and Distinctions**

1.  **Time to First Token (TTFT):** The duration from when the user sends the prompt until the first generated token appears. This is the most critical metric for perceived "latency."
2.  **Prompt-Evaluation Throughput:** The number of tokens generated per second during the prompt processing phase (before the first token). This is the inverse of the inverse of TTFT.
3.  **Decode Throughput:** The number of tokens generated per second during the actual generation phase (after the first token).
4.  **Total Wall-Clock Time:** The sum of TTFT, processing time, and decode time.

**Symbolic Equation for Total Time:**
$$ T_{total} = TTFT + T_{processing} + T_{decode} $$
Where:
*   $T_{total}$ is the total user-visible time.
*   $TTFT$ is Time to First Token.
*   $T_{processing}$ is the time spent evaluating the prompt and generating the first token.
*   $T_{decode}$ is the time spent generating subsequent tokens (decode throughput).

**Example where optimizing prompt processing barely changes user experience:**
If the system is highly optimized (e.g., efficient quantization, good hardware offloading), the **TTFT** is very short (e.g., < 0.5 seconds). Even if you optimize the prompt processing phase (e.g., by reducing the number of tokens in the prompt or optimizing the quantization), the impact on $T_{total}$ is negligible because $TTFT$ dominates the total time.
*   *Scenario:* User experience is driven by TTFT.
*   *Optimization:* You reduce prompt processing time by 50%.
*   *Result:* $T_{total}$ decreases slightly (e.g., from 1.2s to 1.15s), but the user perceives the response as instant. The **TTFT** remains the dominant factor determining the *perceived* latency, while the **decode throughput** (tokens generated/sec) might still be high, meaning the server is actually processing tokens very quickly.
