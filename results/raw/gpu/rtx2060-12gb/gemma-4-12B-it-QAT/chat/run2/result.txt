### Analysis

**1. KV Cache Lifecycle & Recomputation**
*   **Prompt Processing (Prefill):** The system computes the Key and Value tensors for all $N=2,000$ input tokens simultaneously. Because these are computed in a single forward pass, the operation is **compute-bound**. The resulting KV cache is stored to avoid recomputing the attention scores for every subsequent token.
*   **Token-by-Token Decoding:** For each of the 300 generated tokens, the model fetches the entire historical KV cache from memory to compute the attention mechanism. Only the new token's K and V are appended. This is a **memory-bandwidth-bound** operation because the arithmetic intensity (FLOPs per byte) is low.

**2. Resource Stress & Throughput vs. Latency**
*   **Prefill** maximizes GPU utilization by saturating the Tensor Cores (high throughput). A high prompt tok/s indicates efficient parallel processing but does not reflect interactive feel.
*   **Decoding** is limited by the speed at which KV tensors can be moved from memory to the compute units. If the KV cache exceeds GPU VRAM, the system must swap data over the PCIe bus to system RAM. This introduces **PCIe overhead and high-latency memory access**, causing the "slowdown" as the cache grows, even if the GPU compute units remain idle.

**3. Scaling to 8,000 Tokens**
*   **Prefill:** Will remain compute-bound but will eventually hit a VRAM limit. If the 8,000-token KV cache exceeds 6GB, the prefill phase will trigger paging/swapping, causing a massive spike in initial latency.
*   **Decode:** The memory footprint of the KV cache scales linearly with context length ($O(N)$). At 8,000 tokens, the "memory pressure" increases significantly. Since decoding is bandwidth-bound, the time to fetch the 8,000-token cache for every single new token will likely exceed the time to actually compute the token.

**4. General Truths vs. Implementation Dependencies**
*   *General Truth:* Decoding is fundamentally more bandwidth-constrained than prefill.
*   *Implementation Dependent:* The exact bottleneck (e.g., PCIe saturation vs. CPU memory latency) depends on the **KV-cache quantization** (FP16 vs. INT8), the use of **FlashAttention** (which minimizes memory reads during prefill), and whether the system uses **PagedAttention** (which optimizes non-contiguous memory access).

**5. Proposed Measurements**
1.  **Bandwidth Profiling:** Measure `Tokens/sec` vs. `Context Length` for decoding. A linear drop in throughput as context increases suggests a **Memory Bandwidth** bottleneck.
2.  **Transfer Overhead Test:** Compare latency of a 2,000-token decode on GPU-only vs. GPU+System RAM offloading. The delta isolates **PCIe/Host-to-Device** overhead.
3.  **Arithmetic Intensity Check:** Measure `TFLOPS` during prefill vs. decoding. If prefill is near peak TFLOPS and decoding is <10% of peak, the system is confirmed to be **bandwidth-bound** during inference.

### Numerical Example
*Assumptions: 7B model, FP16 precision. Weight size $\approx 14$ GB. KV Cache $\approx 1$ GB per 1k tokens (variable by heads/dim).*

**Scenario A: Small Context (2k tokens)**
*   **Prefill:** 2,000 tokens $\times$ 10ms/token (parallel) $\approx$ **200ms**
*   **Decode:** 300 tokens $\times$ 50ms/token (bandwidth limited) $\approx$ **15,000ms**
*   *Observation:* Total time is dominated by decoding latency.

*   **Prefill:** 8,000 tokens $\times$ 10ms/token (parallel) $\approx$ **800ms**
*   **Decode:** 300 tokens $\times$ 200ms/token (PCIe/RAM bottleneck) $\approx$ **60,000ms**
*   *Observation:* The "slowdown" is exponential as the KV cache forces constant swapping over the slow PCIe bus.
