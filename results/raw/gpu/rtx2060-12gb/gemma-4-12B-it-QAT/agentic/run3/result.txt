### Requirements and Invariants

**Inputs:**
*   **Config File:** Model aliases (mapping names to paths), default parameters (context=4096, gen_limit=256, temp=0.7, threads=1), and hardware labels.
*   **Workload Definitions:** Fixed prompts for `chat`, `batch`, `coding`, `summarization`, `agentic`, and `world_knowledge`.
*   **Environment:** Hardware metadata (GPU model, Driver version, CUDA version), backend selection (CPU, CUDA, Vulkan), and `llama.cpp` build flags.

**Artifacts:**
*   **Raw Output:** Exact `stdout`/`stderr` from the `llama.cpp` process.
*   **Metrics File:** JSON/YAML per run containing parsed performance data.
*   **Metadata File:** JSON/YAML per run containing the experimental identity and environment.
*   **Response File:** The final text output of the model.

**Experimental Identity Tuple:**
A run is only comparable to another if all elements in this tuple are identical:
`(model_path, backend, hardware_label, context_size, gen_limit, prompt_hash, temperature, gpu_layers, build_id, driver_env)`

**Success/Failure States:**
*   **Success:** Process exits with code 0; `response.txt` is non-empty; metrics are parseable.
*   **Failure:** Process non-zero exit, OOM (Out of Memory), timeout, or `response.txt` is empty/malformed.
*   **Partial/Degraded:** Process succeeds but monitoring data is missing or sparse.

**Ambiguity to Resolve:**
*   *Prompt Hashing:* Does the prompt hash include the system prompt (if applicable) or only the user-provided workload string? **Resolution:** The hash must be calculated on the final concatenated string sent to the model to ensure exact reproducibility.

### State Machine

1.  **Validation:** Load config $\rightarrow$ Resolve alias $\rightarrow$ Validate model path exists $\rightarrow$ Check hardware availability $\rightarrow$ Generate Unique Run ID.
2.  **Initialization:** Create directory for Run ID $\rightarrow$ Write `metadata.json` (pre-filled with identity) $\rightarrow$ Prepare shell command.
3.  **Launch:** Spawn `llama.cpp` as a subprocess $\rightarrow$ Redirect `stdout` to `raw.log` and `stderr` to `error.log`.
4.  **Monitoring:** Start background thread to sample hardware metrics (e.g., `nvidia-smi` or `vulkaninfo`).
5.  **Execution & Observation:**
    *   *Timeout:* If process exceeds limit, SIGTERM and mark "Failed: Timeout".
    *   *OOM:* Capture stderr for "Out of Memory" strings; mark "Failed: OOM".
    *   *Monitor Failure:* If monitor process dies, continue run but flag `monitor_status: partial`.
6.  **Process Exit:** Capture exit code $\rightarrow$ Read `raw.log` $\rightarrow$ Parse performance metrics.
7.  **Finalization:**
    *   *Malformed Metrics:* If `llama.cpp` output is unrecognizable, write "Parser Error" to `metadata.json`.
    *   *Write:* Atomic write of `metrics.json` and `response.txt`.

---

### Auditable Design

**Component Boundaries:**
*   **Runner (Python):** Orchestrator. Handles config, loop logic, and subprocess management.
*   **Monitor (Python/Shell):** Independent sidecar process. Periodically writes to a shared buffer or pipe.
*   **Parser (Python):** Regex-based extractor for `llama.cpp` logs (e.g., `eval time`, `tokens/s`).

**Metadata Schema (JSON):**
```json
{
  "run_id": "uuid",
  "identity": { "model": "...", "backend": "...", "prompt_hash": "...", ... },
  "hardware": { "gpu": "...", "driver": "..." },
  "metrics": { "tokens_per_sec": 0.0, "eval_time": 0.0, "total_tokens": 0 },
  "status": "success | failed | partial_monitor",
  "exit_code": 0
}
```

**Atomic-Write & Preservation:**
*   **Raw Logs:** Use `subprocess.Popen` with `stdout=subprocess.PIPE`. Write to `raw.log` immediately to prevent buffer loss.
*   **Finalization:** Write `metrics.json` to a `.tmp` file and `os.replace()` to ensure the file is never partially written.
*   **Prompt Preservation:** The exact prompt used (including any overrides) must be stored in `metadata.json` alongside the hash.

### Analysis Integrity

**Handling Failure vs. Throughput:**
*   To prevent a failed run (e.g., 0 tokens produced) from skewing averages, the parser must check if `total_tokens > 0`. If 0, the run is excluded from "Throughput" calculations but remains in the "Failure" report.
*   **Variable Token Counts:** If a run produces fewer tokens than `gen_limit` due to an early `eos` token, the throughput must be calculated as `tokens_produced / time_spent`, not `gen_limit / time_spent`.

**Unknown Formats:**
*   The parser will use a "Best Effort" approach. If a new `llama.cpp` version changes the output format, the parser will log a `parsing_warning` and store the raw string. The UI/Analysis tool must treat any run with a `parsing_warning` as "Incomparable."

### Test Plan

1.  **Backend Failure:** Simulate a CUDA error by pointing to a non-existent GPU device; verify "Failed: OOM/Runtime Error" state.
2.  **Missing Monitor:** Kill the monitoring sidecar process 1 second after launch; verify run completes with `monitor_status: partial`.
3.  **Complex Prompt:** Input a prompt with `\n`, `\t`, and `"`; verify `prompt_hash` and `metadata.json` preserve exact characters.
4.  **Partial Output:** Simulate a process crash (SIGKILL) mid-generation; verify `response.txt` contains partial text and `status` is `failed`.
5.  **Changed Prompt Hash:** Run the same model twice with one character difference in the prompt; verify they receive different `run_id` and `prompt_hash`.
6.  **Context Override:** Pass a workload that explicitly overrides `context=8192`; verify `metadata.json` reflects 8192, not the default 4096.

### Pre-merge Review

**Risk 1: Race Condition on Monitor Data.**
*   *Problem:* The monitor might write to a file while the runner is trying to read it during finalization.
*   *Fix:* Use a named pipe (FIFO) or a thread-safe queue for monitor data, ensuring the runner "drains" the queue at the moment of exit.

**Risk 2: Log Buffer Overflow.**
*   *Problem:* Large model outputs might fill the OS pipe buffer if not read continuously.
*   *Fix:* Use `subprocess.Popen` with a dedicated thread to stream `stdout` directly to the `raw.log` file in real-time.

**Risk 3: Identity Drift.**
*   *Problem:* A user changes a system environment variable (e.g., `CUDA_VISIBLE_DEVICES`) between runs, but the runner doesn't capture it.
*   *Fix:* The runner must snapshot all relevant environment variables (CUDA_HOME, LD_LIBRARY_PATH, etc.) into the `driver_env` section of the metadata at the moment of launch.
