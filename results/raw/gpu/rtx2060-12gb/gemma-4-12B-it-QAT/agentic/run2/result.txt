### State Machine

1.  **Validation State:**
    *   Validate config file syntax.
    *   Verify model file existence.
    *   Verify `llama.cpp` binary is executable.
    *   *Transition:* If any fail, log error and exit.
2.  **Initialization State:**
    *   Resolve aliases to paths.
    *   Construct the command-line argument string.
    *   Generate a unique `Run_ID` (UUID or timestamp-based).
    *   *Transition:* Proceed to Launch.
3.  **Launch State:**
    *   Spawn `llama.cpp` as a subprocess.
    *   Redirect `stdout` to `raw_log.txt` and `stderr` to `raw_log.txt`.
    *   Start resource monitoring thread/process.
    *   *Transition:* Move to Monitoring.
4.  **Monitoring State:**
    *   Poll for process completion or timeout.
    *   Capture resource metrics (CPU/GPU/Mem) at defined intervals.
    *   *On Timeout:* Kill process, mark state as `TIMEOUT`.
    *   *On OOM/Crash:* Capture exit code, mark state as `CRASH`.
    *   *On Success:* Move to Finalization.
5.  **Finalization State:**
    *   Parse `raw_log.txt` for performance metrics (tokens/sec).
    *   Aggregate metrics and resource logs into `metadata.json`.
    *   Write `response.txt` from `stdout`.
    *   *Transition:* Exit.

### Auditable Design

**Component Boundaries:**
*   **`Runner_Core` (Python):** Orchestrates the state machine, handles subprocess lifecycle, and manages file I/O.
*   **`Monitor_Agent` (Python/Shell):** Independent process/thread that samples system stats (e.g., `nvidia-smi`, `top`) to ensure monitor failure doesn't block the runner.
*   **`Parser_Module`:** Extracts metrics from `llama.cpp` output using regex.

**Metadata Schema (JSON):**
```json
{
  "run_id": "uuid",
  "identity_tuple": { "model": "...", "backend": "...", "hw_label": "...", "ctx": 4096, "gen": 256, "prompt": "...", "temp": 0.7, "layers": 32, "build": "v1.0", "driver": "535.xx" },
  "performance": { "tokens_per_sec": 0.0, "time_to_first_token": 0.0 },

  "exit_code": 0
}
```

**File Conventions:**
*   **Atomic Writes:** `metadata.json` will be written to a `.tmp` file and renamed to `metadata.json` to prevent partial writes.
*   **Prompt Preservation:** The exact prompt used (including escaped newlines) will be stored in the `identity_tuple` to ensure the hash remains valid for audit.

### Analysis Integrity

**Failure Handling:**
*   **Failed Runs:** If `exit_code != 0`, `tokens_per_sec` in `metadata.json` must be set to `null`. The downstream analysis tool must filter out `null` values to prevent "zero-throughput" bias.
*   **Partial Output:** If `response.txt` is detected as truncated (e.g., ends mid-sentence or fails to reach `gen_limit`), a `truncated: true` flag is added to the metadata.
*   **Variable Token Count:** To prevent misleading comparisons, throughput must be calculated as `(Total_Tokens_Generated / Total_Time_Spent)`. If `Total_Tokens_Generated` is 0, the entry is invalidated.

**Parser Robustness:**
*   The `Parser_Module` will use a "Best Effort" approach. If `llama.cpp` changes its output format, the parser will log a `warning: unknown_format` in the metadata and return `null` for metrics rather than crashing the runner.
