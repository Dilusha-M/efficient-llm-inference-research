### State Machine
1.  **Validation State:** 
    *   Verify config file existence and model paths.
    *   Verify `llama.cpp` binary exists and is executable.
    *   Check if hardware labels map to available backends.
2.  **Preparation State:**
    *   Generate unique `run_id` based on the Identity Tuple.
    *   Capture environment variables and hardware metadata (e.g., `nvidia-smi` or `vulkaninfo`).
    *   Create empty files for `raw_response.txt` and `response.txt`.
3.  **Launch State:**
    *   Spawn `llama.cpp` as a subprocess.
    *   Redirect `stdout/stderr` to `raw_response.txt`.
4.  **Monitoring State:**
    *   Poll resource monitors (e.g., `nvml`, `top`).
    *   Handle **Timeout**: If process exceeds max time, send `SIGTERM`.
    *   Handle **Monitor Failure**: If monitor fails, flag `monitor_available: false` in metadata but continue run.
5.  **Process Exit State:**
    *   Capture exit code.
    *   If `exit_code != 0` or `raw_response.txt` is empty, mark as **FAILED**.
    *   If `raw_response.txt` contains "Out of Memory" or "Segmentation Fault," log specific error type.
6.  **Finalization State:**
    *   Parse `raw_response.txt` for performance metrics.
    *   If metrics are missing but process succeeded, mark as **METRIC_MISSING**.
    *   Write `run_metadata.json` containing all data + success/failure status.
    *   Atomic rename of metadata file to prevent partial writes.

### Auditable Design
**Component Boundaries:**
*   **Runner (Python):** Orchestrates the lifecycle, manages subprocesses, and handles the state machine.
*   **Parser (Python):** A dedicated module to regex-extract `tokens/sec` and `time_to_first_token` from raw strings.
*   **Collector (Shell/Python):** Handles hardware-specific calls (e.g., `nvidia-smi`) to ensure low-overhead data gathering.

**Metadata Schema (`run_metadata.json`):**
```json
{
  "run_id": "uuid",
  "identity_tuple": {"model_hash": "...", "backend": "...", ...},
  "status": "SUCCESS | FAILED | METRIC_MISSING",
  "error_message": "Optional string",
  "metrics": {"tokens_per_sec": 0.0, "latency": 0.0},
  "hardware_snapshot": {"gpu_temp": 0, "vram_used": 0, "driver": "..."},
  "monitor_status": "OK | UNAVAILABLE"
}
```

**Atomic-Write Convention:**
Write metadata to a `.tmp` file first, then move to `run_id.json`. This prevents a crash during finalization from leaving a corrupted JSON file.

**Preservation Strategy:**
The Runner will open `raw_response.txt` in append mode. The exact CLI command string used to invoke `llama.cpp` will be stored in the metadata to allow 1:1 reproduction.

### Analysis Integrity
*   **Failed Run Handling:** Any run marked `FAILED` or `METRIC_MISSING` must be excluded from mean/median calculations. They will be flagged in the final report but not contribute to the denominator of throughput.
*   **Variable Token Count:** To prevent "short" runs from skewing results, the runner will record `actual_tokens_generated`. If a run is truncated (e.g., by a safety filter or OOM), the `tokens_per_sec` will be calculated but the metadata will flag `is_truncated: true`.
*   **Unknown Formats:** If the Parser fails to find known metrics (e.g., `eval_time`), it will not guess. It will store the raw string in a `raw_metrics_block` field in the JSON and mark `metrics_parsed: false`.

### Pre-merge Review
1.  **Risk:** *Race conditions during multi-threaded execution of the runner.*
    *   **Fix:** Use a `threading.Lock` or a dedicated `Queue` for the Finalization State to ensure no two threads write to the same `run_id` or shared logs.
2.  **Risk:** *Subprocess buffer overflow.* (If `llama.cpp` outputs massive text, the pipe buffer might clog).
    *   **Fix:** Use `subprocess.Popen` with `stdout=subprocess.PIPE` and a dedicated thread to read and write to `raw_response.txt` concurrently.
3.  **Risk:** *Inconsistent Identity Tuple.* (e.g., a model file is updated on disk but the hash remains the same).
