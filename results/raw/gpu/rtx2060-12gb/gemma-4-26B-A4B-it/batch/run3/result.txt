### Task 1 — Quantization Tradeoff

**Memory Pressure Analysis**
*   **Q8_0 (8.0 GB):** Creates extreme memory pressure. Since the file size (8.0 GB) exceeds the available GPU VRAM (5.2 GB), the system must use system RAM via PCIe bus. This results in "split-offloading," significantly increasing latency due to memory bandwidth bottlenecks between CPU and GPU.
*   **Q4_K_M (4.8 GB):** Creates moderate memory pressure. The file size fits within the 5.2 GB free VRAM, allowing the model to reside entirely on the GPU. This maximizes throughput by utilizing high-bandwidth VRAM.

**Why File Size $\neq$ Runtime Memory Estimate**
File size only accounts for the static model weights. A complete runtime estimate must include:
1.  **KV Cache:** Memory required to store the context (activations) during inference, which scales with context length and batch size.
2.  **Activation Buffers:** Temporary memory required for intermediate calculations during the forward pass.
3.  **Overhead:** CUDA context/driver overhead and workspace memory required by the specific kernels being used.

**Required Measurements**
To declare a format "better," one must measure:
1.  **Perplexity (Quality):** A measure of how much information is lost due to quantization; higher perplexity indicates lower intelligence/accuracy.
2.  **Tokens per Second (Performance):** The actual inference speed (decode throughput) under the specific hardware constraints.

### Task 2 — Conservative Launch Decision

**Assumptions**
*   The 5.0 GB weight figure is strictly weights and excludes the KV cache.
*   The "conservative" goal is to avoid system instability or OOM crashes.

**Procedure**
1.  **Baseline (Start Small):** Begin by offloading only a subset of layers to the GPU (e.g., 50%) with a minimal context window (e.g., 512 tokens).
2.  **Incremental Scaling:** 
    *   Increase the number of GPU layers (`--n-gpu-layers`) until VRAM usage reaches ~90% of available capacity.
    *   Increase the context window (`-c`) in increments (e.g., 1024, 2048, 4096) until the total VRAM (Weights + KV Cache + Buffers) approaches the 6 GB limit.
3.  **Telemetry to Record:**
    *   Peak VRAM usage (via `nvidia-smi` or similar).
    *   System RAM usage (to monitor swap/paging).
    *   Inference speed (tok/s) at each step.

**Unsafe/Misleading Success**
*   **Unsafe Success:** A run that completes but utilizes 99% of VRAM, leading to a "context switch" or "OOM" crash as soon as the generation length increases or a slightly larger prompt is provided.
*   **Misleading Success:** Achieving high speed by offloading only a few layers, but failing to test the performance/stability at the user's required 2,512 total token workload.

### Task 5 — User-Visible Latency

**Definitions**
*   **Time to First Token (TTFT):** The duration from sending the prompt to receiving the very first generated token.
*   **Prompt-Evaluation Throughput:** The speed at which the model processes the input tokens (Prefill phase).
*   **Decode Throughput:** The speed at which the model generates subsequent tokens one-by-one (Decoding phase).
*   **Total Wall-Clock Time:** The total elapsed time from request to completion of the final token.

**Symbolic Equation**
$$T_{total} = T_{prefill} + (N_{gen} \times T_{decode\_step})$$
*(Where $T_{prefill}$ is the time to process the prompt and $N_{gen}$ is the number of generated tokens.)*

**Example of Diminishing Returns**
If a user is generating a very long document (e.g., 2,000 tokens) and the prompt is relatively short (e.g., 10 tokens), optimizing the **prompt-evaluation throughput** will have a negligible effect on the total wall-clock time because the vast majority of the latency is dominated by the iterative decoding phase.
