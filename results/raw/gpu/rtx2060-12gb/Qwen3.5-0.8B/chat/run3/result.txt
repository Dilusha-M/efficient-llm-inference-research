### 1. Lifecycle of KV Cache Reuse vs. Recomputation
In a 7B-only model on a 6GB consumer GPU with 32GB RAM, the KV cache operates as a **reused cache** (shared across all tokens) rather than an **incremental cache** (recomputed on every token).

*   **Shared Buffer:** During prompt processing, the model maintains a global pointer to the same 32GB RAM. It fetches a snapshot of the KV table from this shared memory.
*   **Token-by-Token Fetching:** When a user requests the 300th token, the GPU simply loads the previously cached key-value pairs into the shared 32GB RAM. No new computation or data is generated; the cache acts as a static storage unit.
*   **The Exception:** The system *must* compute the KV pairs for the 300th token to generate the output. However, for the first 1,999 tokens, the GPU only retrieves the data already in the shared 32GB RAM. This creates the latency spike described: early tokens are fast (prefill), but the 300th token requires a costly, one-shot computation.

### 2. Resource Differentiation: Prompt vs. Decoding
Prompt processing is a **preemptive, sequential** operation driven by the input vector, which does not depend on GPU memory bandwidth.

*   **Prompt Processing:** The user sends a 2,000-token prompt. The GPU performs a linear scan of the input, passing it through the decoder. This is purely CPU-bound and memory-bound only if the input fits in cache.
*   **Token-by-Token Decoding:** The 300th token is a **combinatorial** operation. It involves selecting the next token from a hidden state vector and applying a probability distribution. This involves kernel execution, memory access, and potential offloading. It is inherently CPU-GPU-bound and memory-bound.

Consequently, a high **prompt token/s** number does **not** imply low latency. High prompt throughput is merely throughput; it is a separate metric from decoding latency. If the decoding kernel is the bottleneck, the prompt-to-token ratio will still be high, but the latency per token will be high.

### 3. Analysis of 2,000 → 8,000 Context
Increasing context from 2,000 to 8,000 tokens changes the memory footprint significantly while maintaining the same number of tokens to process:

*   **Prefill Behavior:**
    *   **2,000 Tokens:** The model can fit 2,000 tokens into the shared 32GB RAM (assuming typical cache line size of 64KB). The system processes this in one massive loop.
    *   **8,000 Tokens:** The model now requires 8,000 tokens. These are fetched from the **same 32GB RAM**.
    *   **Impact:** The system now faces a **memory pressure bottleneck**. The shared 32GB RAM fills up. The GPU cannot allocate new shared memory for the next batch of tokens. It must either allocate a new shared buffer (incurring kernel overhead) or rely on a paging system to hold tokens in RAM.
*   **Decode Behavior:**
    *   **Prefill:** The model ignores the new 8,000 tokens in the prompt and only processes the first 2,000 tokens.
    *   **Decode:** The 300 tokens generated after the 2,000th prompt must be computed *from scratch* on the GPU. This is a high-overhead operation that dominates the latency of the entire conversation.

### 4. Separation of Claims (General vs. Implementation)
| Claim | Verdict | Justification |
| :--- | :--- | :--- |
| **Total time is dominated by prompt processing** | **True (for 2,000 tokens)** | At 2k, the shared buffer is fully utilized; no paging is needed. The bottleneck is simply the time it takes to read the input vector. |
| **Decoding latency increases as context grows** | **True** | The 300th token is recomputed on the GPU. While the prompt-to-token ratio might be high, the *cost* of recomputing 300 tokens is often higher than reading 1,990 vectors. |
| **High prompt tok/s does not equal low latency** | **False (technically)** | Requires a separate measurement for decoding latency. High prompt throughput is a proxy for prompt latency, not decoding latency. |
| **Memory bandwidth is the primary issue** | **Depends** | 32GB RAM is typically fast enough for 2k tokens. The issue is **Cache Line Packing** and **Kernel Support**, not raw bandwidth. |

### 5. Three Measurements for Bottleneck Diagnosis
To isolate the true culprit, conduct controlled comparisons:

1.  **Kernel Execution Time vs. Cache Hit Rate:**
    *   *Measure:* Run a kernel that generates 10,000 tokens. Compare the **average time per token** (including the recomputed 300th token) to the **average cache line fill rate** (how often the GPU can access a line).
    *   *Logic:* If Kernel Time >> Cache Hit Rate, the GPU is the bottleneck regardless of prompt rate. If Cache Hit Rate >> Kernel Time, the prompt-to-token ratio is the bottleneck.

2.  **Prefill Latency vs. Decode Latency:**
    *   *Measure:* Capture the latency of the first 2,000 tokens (prefill) and the 300th token (decode). Calculate the ratio.
    *   *Logic:* If Prefill Latency is significantly higher than Decode Latency (e.g., >3x), the hardware is prioritizing prompt processing over decoding. If Decode Latency is higher, the hardware is prioritizing decoding over prompt processing.

3.  **Memory Bandwidth vs. Kernel Memory Bandwidth:**
    *   *Measure:* Use a hardware benchmark (e.g., `gloo-ops` or similar) to measure the memory bandwidth of the shared 32GB RAM and the kernel's memory bandwidth. Compare the bandwidth ratio ($RAM\_BW / Kernel\_BW$).
    *   *Logic:* If $RAM\_BW / Kernel\_BW$ is high, the system is bandwidth-limited by the RAM, not the GPU. If $RAM\_BW / Kernel\_BW$ is low, the system is bandwidth-limited by the kernel.
