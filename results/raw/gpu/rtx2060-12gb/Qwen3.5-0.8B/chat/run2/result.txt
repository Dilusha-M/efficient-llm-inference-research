### 1. Lifecycle of the KV Cache (Prefill vs. Decode)
The KV cache operates in a **two-phase lifecycle** distinct from the main decoder:
*   **Prefill (Prompt Processing):** During the first few tokens, the model generates a small batch of intermediate `KV` states (e.g., 4–8 tokens). These are cached locally on the GPU to minimize recomputation. They are **reused** until the model consumes the entire prompt.
*   **Decode (Token-by-Token):** For the remaining tokens (e.g., 300 out of 2,000), the model must **recompute** the full KV state for every token. These are **recomputed** (not cached) and sent to the GPU.
*   **Key Observation:** Because the prefill cache is small and transient, the transition from prefill to decode is highly intermittent. A user with a 2k prompt only processes ~4k KV states before needing to compute the rest, creating a massive "gap" in cache utilization.

### 2. Why Prompt Processing ≠ Low Latency
While high `prompt-tokens-per-second` (e.g., 300) indicates high *prompt-processing* throughput, it does **not** guarantee low *interactive latency*.
*   **Mechanism:** High prompt throughput often drives the system to fetch more context or switch to higher-precision kernels (e.g., `cuda::softmax` vs `cuda::add`) to fill the cache.
*   **Latency Cost:** Switching to a higher-precision kernel can introduce significant latency due to the memory bandwidth and instruction count required to transfer large matrices. This latency often outweighs the benefit of faster prompt generation, leading to overall slow responses as the conversation grows.

### 3. Analysis of Context Growth (2k → 8k)
Increasing context from 2,000 to 8,000 tokens significantly alters the memory footprint:
*   **Prefill:** The prefill cache becomes critical. As context grows, the ratio of *cached* states to *recomputed* states drops, increasing the risk of out-of-memory (OOM) errors if the cache size is static.
*   **Decode:** The number of recompute operations scales linearly with context.
*   **Memory Bandwidth:** A 2,000-token context often consumes a small amount of memory. A 8,000-token context doubles the memory bandwidth requirements. Since GPU bandwidth is often limited by the system RAM, a larger context increases the throughput of the **CPU–GPU transfer** path, potentially becoming the bottleneck.

### 4. Separating Claims (General vs. Implementation)
| Claim Type | Verdict | Justification |
| :--- | :--- | :--- |
| **"Cache size prevents OOM"** | **True** (General) | As long as the cache is static, OOM is a valid failure mode. |
| **"Higher precision kernel = faster latency"** | **False** (Depends on details) | Precision changes do not automatically lower latency; they introduce cache misses and memory bandwidth costs. |
| **"CPU offload is the main bottleneck"** | **Unproven** | Depends on specific kernel versions and memory alignment. |
| **"Page fault latency is negligible"** | **Unproven** | Depends on system page size and OS implementation. |

### 5. Three Measurements to Distinguish Bottlenecks
To isolate the true cause, perform the following comparisons:

1.  **Warm vs. Cold Kernel Execution:**
    *   **Control:** Inject a small batch of `cuda::softmax` kernels (low precision) into a test run.
    *   **Measure:** Compare warm vs. cold kernel execution time for the same context length.
    *   **Insight:** If warm kernels are significantly faster, the bottleneck is **CPU–GPU transfer**, not the kernel itself. If cold kernels are faster, the bottleneck is **GPU offload** or **kernel support** (e.g., `cuda::add` vs `softmax`).

2.  **Context Size Scaling:**
    *   **Control:** Increment context size from 2,000 to 8,000 tokens while keeping prompt length constant.
    *   **Measure:** Monitor the ratio of `Prefill-States` to `Decode-States` (or the ratio of `Prefill` to `Total` tokens).
    *   **Insight:** If the transition to decode slows down proportionally to context size, the **Cache Traffic** is the bottleneck. If the CPU–GPU transfer latency dominates regardless of context size, the **Hardware Transfer** is the bottleneck.

3.  **Precise vs. Approximate Memory Bandwidth:**
    *   **Control:** Use a precise 64-bit kernel (e.g., `cuda::softmax` with `precision=2`) versus a 32-bit kernel (e.g., `cuda::add` with `precision=1`).
    *   **Measure:** Run the full prompt with both kernels on the same GPU.
    *   **Insight:** If the 32-bit kernel is faster, the bottleneck is **CPU–GPU transfer**. If the precise kernel is faster, the bottleneck is **GPU offload** or the **kernel itself**.
