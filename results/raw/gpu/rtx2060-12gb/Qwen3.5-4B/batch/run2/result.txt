### Task 1 — quantization tradeoff

**Memory Pressure Analysis**
*   **Q8_0 (8.0 GB file):** Creates high absolute memory pressure. On a system with a 6 GB GPU and 5.2 GB free, attempting to load this file directly will likely cause an immediate out-of-memory (OOM) error unless the entire model fits (which it does not, as 8.0 > 6.0). It forces the use of aggressive offloading strategies (e.g., swapping layers to system RAM) or requires a smaller context size to reduce KV cache overhead.
*   **Q4_K_M (4.8 GB file):** Creates moderate memory pressure. It fits within the 6.0 GB GPU capacity, leaving 1.2 GB for the KV cache (assuming negligible overhead beyond weights). This leaves a significant margin for error compared to Q8_0, allowing for larger context windows or more layers to stay resident in VRAM.

**Why File Size is Not a Complete Runtime-Memory Estimate**
File size represents only the static weight storage. Runtime memory consumption is a dynamic equation:
$$ \text{Memory}_{\text{total}} = \text{Weight}_{\text{file}} + \text{KV\_Cache} + \text{Activation_{\text{temp}}} + \text{Graph_{\text{overhead}}} $$
Key factors missing from file size:
1.  **KV Cache:** Scales non-linearly with context length and sequence parallelism. A 4.8 GB model with a 2k context will consume significantly more than 4.8 GB total, whereas 8.0 GB with a short context might fit if activations are optimized, but Q8_0 usually suffers from higher activation memory due to less aggressive pruning.
2.  **Activation Memory:** Depends on batch size and layer depth. Some quantizations (like Q4) often result in smaller activation tensors because the effective precision allows for more efficient computation, whereas Q8_0 may require larger temporary buffers.
3.  **Offloading Overhead:** If the model exceeds VRAM capacity, the system must swap layers to system RAM, introducing latency and potentially consuming RAM that was previously "free."

**Required Quality/Performance Measurements**
Before declaring one format better, the following two metrics are necessary:
1.  **Time to First Token (TTFT) / Total Latency:** Measures the impact of offloading overhead and activation memory. A format with slightly higher weight usage might be faster if it avoids swapping layers or reduces activation memory per token.
2.  **Effective Context Length or Generation Speed at Fixed Context:** Measures the degradation in throughput ($tok/s$) or the maximum usable context size ($N_{\text{max}}$) before hitting an OOM threshold or hitting a performance floor.

### Task 3 — robust aggregation

**Data Validation & Logic**
*   **Assumption:** The "8.0 tok/s" run with an OOM warning is a data quality event (failure), not a valid measurement of decode speed. Treating it as zero would skew the median.
*   **Logic:** Filter out records with status flags indicating failure (OOM warning). If fewer than 2 valid records exist, the median cannot be computed statistically.

**Pseudocode**

```python
def validate_and_aggregate_decode_speeds(records):
    """
    records: List of dicts with keys: 'speed_tok_s', 'status' (e.g., 'ok', 'oom')
    """
    # 1. Filter successful runs
    valid_records = [r for r in records if r['status'] == 'ok']
    
    # 2. Handle edge case: Fewer than 2 valid runs
    if len(valid_records) < 2:
        raise ValueError(
            f"Insufficient valid data for median calculation. "
            f"Only {len(valid_records)} successful runs found out of {len(records)} total. "
            f"Failed runs must be preserved for analysis but cannot be averaged."
        )
    
    # 3. Extract speeds
    speeds = [r['speed_tok_s'] for r in valid_records]
    
    # 4. Sort and find median
    speeds.sort()
    n = len(speeds)
    if n % 2 == 0:
        median = (speeds[n//2 - 1] + speeds[n//2]) / 2
    else:
        median = speeds[n//2]
        
    return median, valid_records # Return median and keep failed records in 'records' list
```

**Reporting Strategy**
If fewer than two runs succeed:
*   **Do not** report a median speed.
*   **Explicitly state:** "Statistical median is undefined due to insufficient valid trials (< 2)."
*   **Report:** List the successful values (e.g., "Valid speeds: 42.0, 41.5 tok/s") and note that the third run (8.0 tok/s) was excluded due to the OOM warning but is retained in the dataset for further investigation.

### Task 4 — validity audit

**Threats to Validity**

1.  **Threat: Workload/Output Comparability (The "Hardware" Bias)**
    *   *Description:* The comparison assumes the model generates the exact same output for all backends, but slight differences in floating-point precision (even if the same quantization is used) can cause the model to diverge after a few tokens. If the prompt is long, the outputs will differ, making latency comparisons invalid.
    *   *Control/Disclosure:* Run the experiment with a **short, fixed-sequence generation** (e.g., 10 tokens) to ensure deterministic outputs, or use **golden-set validation** to compare outputs token-by-token up to a divergence point. Disclose in the report: "Outputs diverged at token X; latency measured only until divergence."

2.  **Threat: GPU Memory Fragmentation / Allocation Overhead**
    *   *Description:* CUDA/Vulkan allocators may behave differently regarding memory fragmentation. A "failure" in one backend might be due to allocator inefficiency rather than model capacity, while the other succeeds.
    *   *Control/Disclosure:* Perform **multiple allocation cycles** (warmup runs) before the measurement. Disclose the allocator version and memory pool size used.

3.  **Threat: Thread Scheduling & Context Switching (CPU vs. GPU)**
    *   *Description:* The CPU uses 8 threads, but the OS scheduler might not pin these threads to specific cores. If the CPU run suffers from context switches during the critical path, the result is an artifact of the OS, not the model inference logic.
    *   *Control/Disclosure:* Use hardware affinity (`pthread_setaffinity_np`) to pin CPU threads to specific cores and disable hyperthreading for the duration of the test.

4.  **Threat: Library Implementation Differences (The "Software" Bias)**
    *   *Description:* llama.cpp might optimize operations differently for CPU (NEON intrinsics) vs. CUDA vs. Vulkan (custom kernels). A "slower" CPU result might be due to missing SIMD optimizations, not actual slowness.
    *   *Control/Disclosure:* Ensure all backends use the **same optimization flags** (e.g., `-march=native` for CPU, specific CUDA flags) and compare against a **reference implementation** (e.g., PyTorch with autograd) to establish a baseline.

### Task 5 — user-visible latency

**Definitions**

1.  **Time to First Token (TTFT):** The wall-clock time elapsed from the start of the prompt submission until the first character of the response is displayed. This is dominated by **prompt evaluation** time (processing the input) and the initial compute step.
2.  **Prompt-Evaluation Throughput:** The rate at which the model processes the input tokens ($Tokens_{input} / Time_{input}$). This is usually very fast and occurs almost instantaneously for standard text.
3.  **Decode Throughput:** The rate at which the model generates new tokens ($Tokens_{output} / Time_{output}$). This is the dominant factor in long-generation latency.
4.  **Total Wall-Clock Time:** The sum of prompt evaluation time and generation time.

**Symbolic Equation**
Let $T_{prompt}$ be the time to evaluate the prompt, $T_{gen}$ be the time to generate $N_{gen}$ tokens at a rate $R$ (tok/s).
$$ T_{total} = T_{prompt} + \frac{N_{gen}}{R} $$
Where:
*   $T_{prompt} \approx \frac{N_{prompt}}{R_{prompt}}$
*   $R$ is the decode throughput (tok/s).

**Example of Minimal Impact Optimization**
Consider a 2,000-token prompt and 200 generated tokens.
*   If the model evaluates the 2,000-token prompt in **50 ms** and generates tokens at 50 tok/s ($T_{gen} = 4s$).
*   Optimization A reduces prompt evaluation to **40 ms**.
*   **Result:** Total time changes from 4.050s to 4.040s.
*   **User Experience:** The user waits 0.01 seconds less, which is imperceptible. The user still waits 4.0 seconds for the content to appear. Optimizing prompt evaluation (which is mathematically small compared to $N_{gen}/R$) barely changes the experience because the generation phase dominates the total time. To make a visible difference, one would need to optimize decode throughput (e.g., increasing to 55 tok/s), which would save $\approx 0.09s$, or significantly increase context efficiency.
