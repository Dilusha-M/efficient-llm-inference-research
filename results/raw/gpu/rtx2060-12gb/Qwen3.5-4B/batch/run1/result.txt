### Task 1 — quantization tradeoff

**Memory Pressure Analysis**
*   **Q8_0 (8.0 GB file):** The file size itself is not the memory footprint during inference. However, Q8_0 weights typically require roughly 2.5x the VRAM to be fully loaded compared to Q4_K_M (assuming FP16/BF16 base). If the base model requires ~3.2 GB for Q4, Q8_0 would likely require ~8.0 GB or more in VRAM. Given the **5.2 GB free** limit on a 6 GB GPU, loading Q8_0 is **impossible** without aggressive offloading to system RAM (CPU memory). This creates a "hard stop" failure mode where the kernel launch fails immediately due to lack of contiguous VRAM.
*   **Q4_K_M (4.8 GB file):** This format fits comfortably within the 5.2 GB free limit, allowing for a safe inference run with headroom for the KV cache and activation buffers.

**Why File Size is Not a Complete Runtime-Memory Estimate**
1.  **Activation Memory:** The file size represents only the static weights. Inference requires temporary storage for activations (intermediate calculations) and the KV cache (context storage). A model that fits in weights but requires massive activations (due to large context or large hidden dimensions) can still OOM.
2.  **Kernel Overhead & Alignment:** GPU kernels require specific memory alignment and buffer overhead (e.g., `torch.cuda.empty_cache()` overhead, kernel stack, and fragmentation).
3.  **Quantization Algorithm Variance:** The file size assumes a specific quantization scheme (e.g., DQN vs. MPASS). A larger file size does not linearly guarantee lower VRAM usage during the actual forward pass, as the *runtime* quantization or dequantization process can introduce temporary spikes.

**Required Quality/Performance Measurements**
To declare one format "better" without ambiguity, two specific metrics are needed:
1.  **Memory Utilization Headroom:** The ratio of `(Free VRAM - Estimated Activation/KV Cache) / Total Model Size`. This determines stability, not just speed.
2.  **Tokens Per Second (tok/s) at Stable Throughput:** Measured over a sustained period (e.g., 100 tokens) to distinguish between peak throughput (spiky) and sustained throughput. Q4 may be slower than Q8_0 in a micro-benchmark but superior in a long-context scenario due to lower activation overhead.

def validate_and_aggregate(run_results):
    # Filter successful runs (exclude those with OOM warnings or errors)
    successful_runs = [r for r in run_results if r['status'] == 'success' and r['oom_warning'] == False]
    
    # Extract speeds
    speeds = [r['speed_tok_s'] for r in successful_runs]
    
    # Validation Logic
    if len(successful_runs) < 2:
        return {
            'status': 'insufficient_data',
            'message': 'Fewer than two successful runs recorded. Cannot calculate robust median.',
            'valid_count': len(successful_runs),
            'failed_runs': [r for r in run_results if r['status'] != 'success']
        }
    
    # Calculate Median
    speeds.sort()
    n = len(speeds)
    if n % 2 == 0:
        median_speed = (speeds[n//2 - 1] + speeds[n//2]) / 2
    else:
        median_speed = speeds[n//2]
    
    return {
        'status': 'success',
        'median_speed': median_speed,
        'valid_count': n,
        'failed_runs': [r for r in run_results if r['status'] != 'success'] # Keep failure visible
    }

### Task 4 — validity audit

**Threats to Validity and Controls**

1.  **Threat: Workload/Output Comparability (The "Prompt" Variable)**
    *   *Description:* If the three backends are run on the *same* physical input string, minor differences in tokenizer version or caching might yield identical outputs, masking differences in parsing speed or tokenization latency. 2.  **Threat: Hardware Thermal Throttling (The "CPU" Variable)**
    *   *Description:* The CPU run (8 threads) may not be able to sustain peak power for 30 seconds due to thermal limits, whereas the GPU runs do not. This makes the CPU appear slower not due to algorithmic inefficiency but due to hardware limits.
    *   *Control:* Enforce a **thermal governor policy** (e.g., `powersave` or `performance` mode depending on the goal) or use a high-end server CPU with active cooling. Alternatively, run the CPU benchmark in very short bursts (e.g., 100 tokens) to avoid thermal drift.

### Task 5 — user-visible latency

**Definitions and Differences**

1.  **Time to First Token (TTFT):** The wall-clock time from the start of the prompt input until the first character of the generation is received. This is dominated by **prompt evaluation time** (processing the input) + **initial kernel launch overhead**.
2.  **Prompt-Evaluation Throughput:** The rate at which the model processes the *input* tokens. This is purely a function of the input sequence length and the compute intensity of the prompt processing kernels. It is usually measured in tok/s but is only visible as delay during the pre-generation phase.
3.  **Decode Throughput:** The rate at which the model generates *output* tokens (tokens per second). This is the most critical metric for user experience during the "typing" phase of an AI chat.
4.  **Total Wall-Clock Time:** The duration from start to finish of the entire request (Prompt Evaluation + Generation).

**Symbolic Equation for Total Time**
$$ T_{total} = \frac{N_{prompt} \cdot C_{eval}}{F_{prompt}} + \frac{N_{gen} \cdot C_{dec}}{F_{dec}} + T_{launch} $$
*Where:*
*   $N_{prompt}, N_{gen}$: Number of input and generated tokens.
*   $C_{eval}, C_{dec}$: Cycle count per token for evaluation and decoding (usually $C_{eval} \approx C_{dec}$).
*   $F_{prompt}, F_{dec}$: Throughput (tok/s) for evaluation and decoding.
*   $T_{launch}$: Kernel initialization overhead (often negligible for long prompts, significant for short ones).

**Example: Optimizing Prompt Processing Barely Changes Experience**
*   *Scenario:* A user sends a 2,000-token prompt.
*   *Current State:* Prompt evaluation takes 0.5 seconds (TTFT = 0.5s).
*   *Optimization:* The prompt evaluation code is optimized, reducing time to 0.4 seconds.
*   *User Experience:* The user waits 0.1 seconds less before seeing the first character. If the generation takes 30 seconds, the user perceives the total response time as 30.1s vs 30.0s. The impact is negligible (<0.3% of total time). The optimization is invisible to the user compared to the dominant decode latency.
