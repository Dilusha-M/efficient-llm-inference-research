A 7B decoder-only model is served on a 6 GB consumer GPU with 32 GB system RAM. The model weights fit on the GPU, but the key-value (KV) cache does not always fit there. ### 1. KV Cache Lifecycle: Prefill vs. Decode
The system operates in two distinct phases with different computational and memory profiles:

*   **Prefill (Prompt Processing):** Upon receiving the 2,000-token prompt, the model executes the attention mechanism for all $N=2,000$ tokens simultaneously. The KV cache is **recomputed** (and allocated) for every token in the prompt. This phase is compute-bound (FLOPs) but memory-bandwidth heavy due to reading weights and writing the initial cache. Once complete, the full cache for the prompt is resident.
*   **Decode (Token Generation):** For each of the 300 generated tokens, the model only attends to the previous $N_{ctx}$ tokens. Crucially, the KV values for the *previous* steps are **reused** from the cache; they are not recomputed. The system reads the existing KV cache, computes a single output token, and appends the new KV entry to the cache. This phase is strictly memory-bandwidth bound (reading the growing cache) and serial by nature (cannot parallelize across tokens).

### 2. Resource Stress and Latency Mismatch
Prompt processing and decoding stress different hardware resources because their computational bottlenecks differ:

*   **Prefill Stress:** Dominated by **GPU Compute (FP16/INT8 FLOPs)** and **Weight Read Bandwidth**. With 2,000 tokens, the GPU can saturate its tensor cores. Throughput ($N$ tokens/sec) appears "excellent" because the GPU is busy doing parallel math.
*   **Decode Stress:** Dominated by **Memory Bandwidth** (reading the KV cache) and **Serialization**. The GPU cannot parallelize token generation; it must wait for the entire cache to be fetched from VRAM before computing the next token.
*   **The Latency Paradox:** A high prompt tok/s indicates the GPU can process a large batch of data quickly. However, interactive latency depends on the time to generate *one* token. If the KV cache exceeds 6 GB, the GPU cannot read it entirely from VRAM. The system must page memory to system RAM (32 GB). Even with fast DDR5 RAM, the memory latency for random accesses or the overhead of CPU-GPU data movement (PCIe) creates a serialization bottleneck that kills per-token latency, regardless of how fast the GPU computes the math.

### 3. Impact of Increasing Context (2k $\to$ 8k Tokens)
Increasing context from 2,000 to 8,000 tokens drastically alters the behavior:

*   **Prefill Phase:** The prefill time scales roughly linearly with prompt length ($O(N)$). An 8k prompt will take ~4x longer to process than a 2k prompt, increasing initial response time (TTFT).
*   **Decode Phase:** The latency per token increases significantly. The KV cache size grows linearly with context ($N_{ctx} \times \text{dim} \times \text{heads} \times 2$).
    *   As $N_{ctx}$ increases, the volume of data to read from VRAM per step grows.
    *   If the cache exceeds VRAM capacity (6 GB), the fraction of time spent waiting for data from system RAM increases.
    *   **Memory Bandwidth Role:** The decode speed is limited by how fast the memory subsystem can supply the full context window to the compute units. Doubling the context window does not double the latency linearly if the memory subsystem is saturated; however, on a consumer GPU, crossing the VRAM limit shifts the bottleneck from compute to PCIe bandwidth or memory latency, causing sub-linear scaling of throughput (high latency per token).

### 4. General Truths vs. Implementation Details
*   **Generally True:**
    *   Decode latency is inversely proportional to memory bandwidth; compute utilization drops as memory bandwidth becomes the limiting factor.
    *   Offloading KV cache to system RAM increases latency due to higher access latency and PCIe transfer overhead, even if it prevents OOM errors.
    *   Prefill is parallelizable; decode is inherently serial.
*   **Implementation Dependent:**
    *   **Cache Precision:** Using `float16` vs. `int8` (quantized KV) changes the cache size (and thus whether it fits in 6 GB) but not the fundamental bandwidth bottleneck.
    *   **GPU Offload/Paging:** The mechanism of handling OOM (e.g., native paging, external memory pools like vLLM's PagedAttention, or CPU swap) varies in overhead. Some implementations may batch decode steps on CPU before sending to GPU, adding significant latency.
    *   **Kernel Support:** Whether the decoder kernel supports "partial cache reads" (reading only the visible window efficiently) or requires full memory fetch impacts bandwidth utilization.

### 5. Diagnostic Measurements
To distinguish the bottleneck, perform these three controlled comparisons:

1.  **Weight vs. KV Traffic Isolation:**
    *   *Method:* Measure latency with a minimal cache (e.g., 0 tokens generated, only prompt) vs. a large cache (8k context).
    *   *Logic:* If latency is low in step 1 but high in step 2, the bottleneck is **KV-cache traffic**, not weight loading (which happens entirely during prefill).
2.  **CPU-GPU Transfer vs. Memory Latency:**
    *   *Method:* Compare latency with the cache fully in VRAM (if possible by reducing batch size/context) vs. cache in RAM. Introduce a dummy PCIe transfer task to measure baseline PCIe throughput.
    *   *Logic:* If latency with cache-in-RAM matches the theoretical time for `(Cache_Size / PCIe_Bandwidth) + (Memory_Latency * Accesses)`, the bottleneck is **CPU-GPU transfer or Memory Bandwidth**.
3.  **Prefill vs. Decode Scaling:**
    *   *Method:* Plot total time vs. number of generated tokens for fixed prompt lengths.
    *   *Logic:* If the slope of Time vs. Tokens is steep and non-linear, it indicates **serialization/memory bound** decode behavior. If the slope is flat and the intercept is high, it indicates **prefill/compute bound**.

### Numerical Example
Assume the following parameters:
*   **GPU Compute Speed:** 100 tokens/sec (saturated during prefill).
*   **VRAM Read Bandwidth:** 900 GB/s.
*   **PCIe 4.0 Bandwidth:** 32 GB/s.
*   **Memory Access Latency:** 100 ns (negligible for large transfers).
*   **Scenario A (Cache fits in 6 GB):** Cache size = 4 GB.
    *   Decode Time per token $\approx \frac{4 \text{ GB}}{900 \text{ GB/s}} \approx 4.4 \text{ ms}$.
    *   Compute Time per token $\approx 10 \text{ ms}$.
    *   **Total Decode Time $\approx 14.4 \text{ ms}$ (Compute bound).**
*   **Scenario B (Cache spills to RAM):** Cache size = 8 GB. 4 GB must be read from PCIe.
    *   PCIe Transfer Time $\approx \frac{4 \text{ GB}}{32 \text{ GB/s}} = 125 \text{ ms}$.
    *   **Total Decode Time $\approx 125 \text{ ms}$ (PCIe bound).**

**Conclusion:** Increasing context from 2k to 8k pushes the system from a 14.4 ms latency (excellent interactive feel) to 125 ms (unusable), demonstrating that total time is dominated by the slowest resource (PCIe transfer) once the cache exceeds VRAM capacity.
