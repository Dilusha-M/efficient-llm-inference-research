**State 2: Pre-Execution Check**

## Auditable Design

**Component Boundaries:**
1. **Configuration Loader:** Reads and validates the model alias configuration.
2. **Runner Orchestrator (Main Logic):** Manages the state transitions, parameter setting, and execution flow.

4. **Monitor Agent:** Periodically polls or waits for signals from hardware/process monitoring hooks.
5. **Output Parser & Writer:** Reads raw output, parses metrics, and writes the final Run Metadata file.

2. **Atomic Write:** The final Run Metadata file is written only after all data (metrics, raw output path, status) is fully collected and validated. If the write fails, the partial data is discarded, ensuring no corrupted state is persisted.

## Analysis Integrity

**Preventing Misleading Throughput Comparison:**
Throughput comparison must rely on metrics derived *only* from the run itself, not external factors.
1. **Token Counting:** The `generated-token count` must be the primary metric for throughput calculation. This count must be explicitly parsed from the raw output or the structured performance output.
2. **Normalization:** If a run fails (e.g., OOM), the throughput calculation for that run is discarded or flagged as invalid. A comparison should only occur between runs marked `SUCCESS` or `SUCCESS_WITH_MONITOR_MISSING`.
3. **Failure Flag:** The `status` field in the metadata file must be the gatekeeper for comparison. If a run is `FAILURE`, it is excluded from performance benchmarking.

**Handling Unknown Output Formats:**
The parser must employ a strict, format-specific parsing strategy.
1. **Format Identification:** The parser must first attempt to identify the output format based on known patterns (e.g., presence of specific keywords, expected delimiters, or expected structure based on the specified `llama.cpp` output format).
2. **Fallback Strategy:** If parsing fails (i.e., the structure does not match any known format), the parser must reject the metric set associated with that run and flag the run for manual audit. It should **never** invent metrics. If the format is entirely unknown, the parser defaults to setting the performance metrics to NULL/Error and ensures the final run status is `FAILURE`.

## Pre-merge Review

**Risk 1: Data Integrity During Failure (High Risk)**
* **Flaw:** If the process fails midway (e.g., OOM) before the monitoring or output collection phase, the system might leave partial, unvalidated state, potentially leading to false positives or incorrect failure reporting if cleanup is not strictly atomic.
* **Fix:** Enforce that the Process Executor must use transactional file operations for all intermediate data. If any step fails, the entire operation must roll back to a known clean state, ensuring that only fully validated data (or explicit failure markers) is written to the final metadata file.

**Risk 2: Ambiguous Metric Parsing (Medium Risk)**
* **Flaw:** The reliance on parsing potentially complex, unstructured `llama.cpp` output to extract performance metrics risks misinterpreting token counts or time values, leading to misleading throughput comparisons.
* **Fix:** Mandate that the parser must rely on explicit, structured output fields provided by `llama.cpp` (if available) or implement a strict, defined fallback parser for known structures. If parsing fails, the result must default to `FAILURE`, preventing erroneous throughput calculations.

**Risk 3: State Mismatch Enforcement (Medium Risk)**
* **Flaw:** The requirement to prevent mixing results based on the full set of input parameters (model, context, prompt hash, etc.) is complex to enforce if the comparison logic is external to the run itself.
* **Fix:** Make the `identity_tuple` the primary, immutable key for any downstream comparison. Any comparison algorithm must first check for an exact match on the entire tuple. If a comparison is attempted without the full tuple, it must be rejected by the orchestrator, enforcing the invariant that results are only comparable if the experimental identity is identical.
