### 1. KV Cache Lifecycle: Reuse vs. Recompute

In a decoder-only Transformer, the KV cache stores the Key ($K$) and Value ($V$) projections for every token processed so far.

*   **Prompt Processing (Prefill):** The model processes the 2,000-token prompt in parallel. For each token $i$, the model computes $Q_i, K_i, V_i$. $K_i$ and $V_i$ are written to the KV cache. **Nothing is reused** from previous steps during prefill; every token’s attention weights are computed from scratch against all preceding tokens in the prompt. This phase is compute-bound (matrix multiplications dominate) and memory-bandwidth efficient because data is accessed sequentially in large chunks.
*   **Token-by-Token Decoding:** For each of the 300 generated tokens, the model computes $Q_{new}$ for the new token. It then computes attention against **all** previous tokens (2,000 prompt + $t$ generated). Crucially, **$K$ and $V$ for previous tokens are reused** from the cache; they are not recomputed. However, the cache must be **read** for every previous token and **written** to append the new $K_{new}, V_{new}$. This phase is memory-bandwidth bound, specifically dominated by the sequential read/write of the growing KV cache.

### 2. Why High Prefill Throughput ≠ Low Interactive Latency

*   **Prefill (Prompt Processing):** Parallelizable across all $N$ prompt tokens. The GPU utilizes high arithmetic intensity (FLOPs per byte), saturating compute units (SMs). Latency is $T_{prefill} \approx \frac{N}{\text{prefill\_tok/s}}$. High throughput here means the GPU is doing heavy matrix math efficiently.
*   **Decoding (Generation):** Strictly sequential. Each new token depends on the previous one. The operation is dominated by loading the KV cache from VRAM into registers, computing attention, and writing back the new cache entry. The arithmetic intensity is low. Latency is $T_{decode} = \sum_{t=1}^{M} \text{time\_per\_token}(t)$.
*   **The Disconnect:** A system can have excellent prefill throughput (high FLOPs) but poor decode latency if memory bandwidth is saturated or if the KV cache is too large to fit in fast VRAM. Interactive latency is determined by the **sum** of prefill and decode times. If decode is slow due to memory bottlenecks, the user perceives lag despite fast prefill.

### 3. Scaling Context from 2,000 to 8,000 Tokens

*   **Prefill:** Time increases linearly with context length ($4\times$). However, since prefill is compute-bound, the GPU may still handle this efficiently if VRAM bandwidth isn't the bottleneck.
*   **Decode:** The KV cache size grows linearly with context. For 8,000 tokens, the cache is $4\times$ larger than for 2,000 tokens.
    *   **Memory Bandwidth Pressure:** Each decode step requires reading the entire KV cache. If the cache exceeds VRAM capacity or even fits but is large, the memory bandwidth becomes the critical bottleneck. Per-token latency increases because more data must be moved per step.
    *   **Offloading Impact:** If the cache is offloaded to system RAM (via GPU offload/paging), the PCIe bandwidth bottleneck becomes severe. Reading 8,000 tokens of KV cache from system RAM is orders of magnitude slower than from VRAM, drastically increasing per-token latency.

### 4. General Truths vs. Implementation Details

| Claim | Status | Explanation |
| :--- | :--- | :--- |
| **Prefill is compute-bound; Decode is memory-bound.** | **Generally True** | Due to parallelism in prefill vs. sequential cache access in decode. |
| **KV cache grows linearly with context length.** | **Generally True** | Each token adds a fixed-size $K, V$ vector. |
| **Offloading KV cache to system RAM reduces latency.** | **False** | System RAM has lower bandwidth than VRAM, and PCIe transfer adds latency. It only prevents OOM. |
| **KV cache size depends only on model size.** | **Implementation-Dependent** | Depends on hidden dimension, number of heads, head size, and **precision** (FP16 vs. INT8 vs. FP8). Quantization can reduce cache size by 2x-4x. |
| **PagedAttention eliminates memory fragmentation.** | **Implementation-Dependent** | Only if the framework supports it (e.g., vLLM). Standard implementations may suffer from fragmentation. |
| **Per-token latency is constant during decoding.** | **Implementation-Dependent** | In fixed-cache systems, latency may increase as cache grows. In paged systems, it may vary based on page faults. |

### 5. Proposed Measurements to Identify Bottlenecks

1.  **Measure Prefill Throughput with Varying Batch Sizes:**
    *   Run inference with batch sizes 1, 4, 8, 16.
    *   **Interpretation:** If throughput scales linearly, the bottleneck is compute-bound (good for prefill). If it saturates early, memory bandwidth or kernel launch overhead is limiting. This isolates prefill performance.
2.  **Measure Per-Token Latency with Fixed Context, Varying Generation Length:**
    *   Fix prompt length at 2,000 tokens. Generate 10, 50, 100, 300 tokens. Record time per token.
    *   **Interpretation:** If per-token latency is constant, the KV cache fits in VRAM and is efficiently accessed. If latency increases with generation length, memory bandwidth is being saturated by the growing cache, or page faults are occurring.
3.  **Profile Memory Bandwidth Utilization (NVML/Nsight):**
    *   Use NVIDIA Nsight Systems or `nvml` to monitor GPU memory bandwidth utilization during prefill and decode phases.
    *   **Interpretation:**
        *   **High compute utilization, low memory bandwidth during prefill:** Compute-bound (expected).
        *   **High memory bandwidth utilization during decode:** Memory-bound (expected for large cache).
        *   **Low utilization of both during decode:** Likely bottleneck is CPU-GPU transfer (offloading) or kernel launch overhead. If PCIe transfer is high, the bottleneck is CPU-GPU bandwidth.

### Numerical Example

Assume:
*   Model: 7B parameters.
*   Prompt: 2,000 tokens.
*   Generation: 300 tokens.
*   GPU: 6 GB VRAM, sufficient for weights.
*   Prefill speed: 100 tok/s (compute-bound).
*   Decode speed: 20 tok/s (memory-bound, cache fits in VRAM).

**Case A: Cache Fits in VRAM**
*   $T_{prefill} = 2000 / 100 = 20$ seconds.
*   $T_{decode} = 300 / 20 = 15$ seconds.
*   **Total Time:** 35 seconds.
*   **Dominant Phase:** Prefill (57% of time). User waits 20s before seeing first token.

**Case B: Cache Offloaded to System RAM (Slow Decode)**
*   $T_{prefill} = 20$ seconds (unchanged).
*   Decode speed drops to 5 tok/s due to PCIe bottleneck.
*   $T_{decode} = 300 / 5 = 60$ seconds.
*   **Total Time:** 80 seconds.
*   **Dominant Phase:** Decode (75% of time). First token appears after 20s, but subsequent tokens are very slow.

**Conclusion:** In Case A, optimizing prefill reduces total time. In Case B, optimizing decode (e.g., via quantization to keep cache in VRAM) is critical. The numerical example shows how a small change in decode latency dominates total time when generation length is significant.
