### 1. KV Cache Lifecycle and Reuse

In a decoder-only transformer, the KV cache stores the Key ($K$) and Value ($V$) projections for every token processed so far.

*   **Prefill (Prompt Processing):** For a 2,000-token prompt, the model processes all tokens in parallel (batch size = 1, sequence length = 2,000). The KV cache is **allocated and filled** from scratch. No prior KV states exist.
*   **Decode (Token Generation):** For each of the 300 generated tokens, the model attends to all previous 2,000 + $t$ tokens. The KV entries for the original 2,000 tokens are **reused** (read-only). The KV entry for the newly generated token $t$ is **computed and appended** to the cache.
*   **Memory Pressure:** As generation proceeds, the KV cache grows linearly. If the GPU VRAM is exhausted, the system must either page out old KV entries to system RAM (slow) or fail.

### 2. Prompt Processing vs. Decoding: Resource Stress

*   **Prefill is Compute-Bound:** Processing 2,000 tokens in parallel maximizes GPU utilization (FLOPs). The matrix multiplications are large and efficient. High prompt tok/s reflects high computational throughput.
*   **Decode is Memory-Bound:** Generating one token requires reading the entire KV cache (which grows with sequence length) and the model weights. The computational work per token is small compared to the data movement required.
*   **Why High Prefill ≠ Low Latency:** Prefill throughput measures how fast the GPU can *compute* a large batch. Decode latency measures how fast the GPU can *fetch* data for a single token. A GPU can have high FLOPs but low memory bandwidth, resulting in fast prefill but slow interactive response.

### 3. Impact of Increasing Context (2k → 8k Tokens)

*   **Prefill Time:** Increases roughly 4x (linear with sequence length), but remains compute-bound.
*   **Decode Latency:** Increases significantly due to **memory bandwidth saturation**.
    *   Each decode step must read the entire KV cache. An 8k cache is 4x larger than a 2k cache.
    *   If memory bandwidth is the bottleneck, per-token latency increases ~4x.
    *   Total response time = Prefill Time + (Decode Latency × 300). The decode phase will dominate total latency.
*   **Memory Bandwidth Role:** The GPU must stream KV data from VRAM (or system RAM if offloaded) to the compute units. This traffic dwarfs the weight traffic because KV cache is accessed every step, while weights are cached in SRAM after the first few accesses.

### 4. General Truths vs. Implementation Details

| Claim | Status | Reason |
| :--- | :--- | :--- |
| Decode is memory-bound | **Generally True** | Attention mechanism requires reading all previous KV states. |
| Prefill is compute-bound | **Generally True** | Large parallel matmuls saturate FLOPs. |
| KV cache fits in VRAM | **Dependent** | Depends on model size, precision (FP16/INT8), and context length. 7B models often exceed 6GB VRAM with long contexts. |
| Offloading to RAM helps | **Dependent** | Only helps if OOM would otherwise crash the system. It *increases* latency due to PCIe bandwidth limits. |
| Paging improves latency | **False** | Paging adds overhead. It prevents crashes but does not improve speed. |
| Kernel optimization matters | **Dependent** | Efficient attention kernels (e.g., FlashAttention) reduce memory traffic, but cannot eliminate the fundamental bandwidth constraint. |

### 5. Diagnostic Measurements

To isolate the bottleneck, perform these three controlled tests:

1.  **Vary Batch Size in Prefill:**
    *   *Method:* Run prompt processing with batch sizes 1, 4, 8.
    *   *Interpretation:* If throughput scales linearly with batch size, the system is **compute-bound**. If it plateaus, it is **memory-bandwidth-bound** (weights/KV traffic limits).
2.  **Vary Context Length in Decode:**
    *   *Method:* Generate 1 token from prompts of 1k, 4k, 8k tokens. Measure per-token latency.
    *   *Interpretation:* If latency scales linearly with context length, the bottleneck is **KV cache memory bandwidth**. If latency is constant, the bottleneck is **compute** or **weight loading** (unlikely for decode).
3.  **Profile PCIe Transfer vs. GPU Kernel Time:**
    *   *Method:* Use `nsys` or `nvprof` to profile the decode loop. Compare time spent in `cudaMemcpy` (if offloading) vs. `attention` kernels.
    *   *Interpretation:* If `cudaMemcpy` dominates, the bottleneck is **CPU-GPU transfer** (RAM offload). If `attention` dominates, the bottleneck is **GPU memory bandwidth**.

### Numerical Example

**Assumptions:**
*   GPU: 6 GB VRAM, 300 GB/s memory bandwidth.
*   Model: 7B parameters, FP16 weights (14 GB total, but only active layers fit in cache/VRAM). Assume effective weight traffic per token is 2 GB.
*   KV Cache: FP16, 16KB per token.
*   Prompt: 2,000 tokens. Generate: 300 tokens.

**Scenario A: KV Cache in VRAM (Fast)**
*   **Prefill:** 2,000 tokens × 10 ms/token (compute-bound) = **20 seconds**.
*   **Decode:** Per-token latency = (KV Read + Weight Read) / Bandwidth.
    *   KV Read per token: 2,000 tokens × 16KB = 32 MB.
    *   Weight Read per token: ~2 GB (assuming weights not fully cached in SRAM).
    *   Total Data per token: ~2.032 GB.
    *   Latency per token: 2.032 GB / 300 GB/s ≈ **6.77 ms**.
    *   Total Decode: 300 × 6.77 ms = **2.03 seconds**.
*   **Total Time:** ~22 seconds. Prefill dominates.

**Scenario B: KV Cache Offloaded to RAM (Slow)**
*   **Prefill:** Same, **20 seconds**.
*   **Decode:** Now, KV data must be fetched from system RAM via PCIe (assume 20 GB/s effective).
    *   KV Read per token: 32 MB from RAM.
    *   Time for KV fetch: 32 MB / 20 GB/s = **1.6 ms**.
    *   Weight Read: Still from VRAM/SRAM, ~6.77 ms (as above).
    *   *Wait, this is not the worst case.* The worst case is if the *entire* KV cache for the *current step* must be streamed from RAM because it doesn't fit in VRAM.
    *   Let's assume the KV cache for the *current step* (all previous tokens) is paged in.
    *   Data to fetch: 2,000 tokens × 16KB = 32 MB per step.
    *   Latency per token: 32 MB / 20 GB/s (PCIe) = **1.6 ms**.
    *   *Correction:* The bottleneck is usually that the GPU cannot process faster than the data arrives. If the KV cache is large, the GPU stalls waiting for data.
    *   Let's assume the effective bandwidth for KV access drops to 50 GB/s due to paging overhead.
    *   Latency per token: 2.032 GB / 50 GB/s ≈ **40.6 ms**.
    *   Total Decode: 300 × 40.6 ms = **12.2 seconds**.
*   **Total Time:** ~32.2 seconds. Decode latency is now significant.

**Scenario C: Long Context (8k tokens) with Offload**
*   **Prefill:** 8,000 × 10 ms = **80 seconds**.
*   **Decode:** KV per token = 8,000 × 16KB = 128 MB.
    *   Latency per token: 128 MB / 20 GB/s (PCIe) = **6.4 ms** (just KV fetch).
    *   Plus weight fetch: ~6.77 ms.
    *   Total per token: ~13.17 ms.
    *   Total Decode: 300 × 13.17 ms = **3.95 seconds**.
*   **Total Time:** ~84 seconds. Prefill still dominates, but decode latency has increased 2x from Scenario B.

**Conclusion:** In short-context scenarios, prefill dominates. In long-context scenarios with memory offloading, decode latency becomes non-negligible and scales linearly with context length.
