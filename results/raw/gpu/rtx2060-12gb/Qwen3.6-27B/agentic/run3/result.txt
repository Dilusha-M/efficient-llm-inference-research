Requirements and Invariants

**Inputs**
1.  **Configuration File (`config.yaml`):** Contains model aliases mapping logical names to file paths, backend definitions (CPU, CUDA, Vulkan), and default parameters (context=4096, n_predict=256, temp=0.7, n_threads=1).
2.  **Workload Definition:** A list of workloads (`chat`, `batch`, `coding`, `summarization`, `agentic`, `world_knowledge`). Each workload maps to a specific prompt template or fixed prompt string.
3.  **Run Matrix:** A Cartesian product of Models $\times$ Backends $\times$ Workloads, potentially with explicit overrides for context or GPU layers.

**Artifacts (Per Run)**
1.  `run_id.json`: Metadata file containing the experimental identity tuple, timestamp, hardware info, and exit status.
2.  `response.txt`: The raw textual output generated by the model.
3.  `stdout.log` / `stderr.log`: Raw capture of the `llama-cli` or `llama-bench` process I/O.
4.  `metrics.json`: Parsed performance metrics (tokens/sec, time per token, total time) extracted from stdout.

**Experimental Identity Tuple**
A run is uniquely identified by the hash of the following tuple. Any change invalidates the comparability of results:
`(model_path_hash, backend_type, hardware_label, context_size, n_predict, prompt_hash, temperature, n_gpu_layers, build_commit_hash, driver_version)`

**Success/Failure States**
1.  **Success:** Process exits with code 0, `response.txt` is complete (matches expected token count or EOF), and `metrics.json` is parseable.
2.  **Model Failure:** Process crashes (OOM, segfault), exits with non-zero code, or times out. `response.txt` may be partial.
3.  **Monitor Failure:** The model run succeeds, but hardware monitoring data (e.g., GPU VRAM usage via `nvtop` or CPU temp) is missing or sparse. This is *not* a run failure, but a data quality flag.

**Invariants**
1.  **Isolation:** No results are mixed. If the identity tuple changes, a new run directory is created.
2.  **Reproducibility:** The exact prompt string (including whitespace/newlines) is stored and hashed.
3.  **Atomicity:** Metadata files are written atomically to prevent corruption during crashes.
4.  **Raw Preservation:** Raw stdout/stderr are never truncated or modified, even if parsing fails.

**Ambiguity to Resolve**
*   **Prompt Interpolation:** The spec mentions "fixed workload prompts" but also "model aliases." It is ambiguous whether the prompt is static per workload or if it requires variable substitution (e.g., inserting the model name). *Resolution:* Assume prompts are static strings defined in the config, with no dynamic substitution, to ensure the `prompt_hash` remains stable across different models for the same workload.

State Machine

The runner operates as a state machine for each individual run instance.

1.  **INIT:**
    *   Load config.
    *   Resolve model alias to absolute path.
    *   Construct the `llama-cli` command line arguments.
    *   Validate model file existence.
    *   *Transition:* If validation fails $\rightarrow$ **FAIL (Config Error)**. Else $\rightarrow$ **VALIDATED**.

2.  **VALIDATED:**
    *   Generate unique `run_id`.
    *   Create run directory.
    *   Write initial `run_id.json` with status `STARTED`.
    *   Capture hardware metadata (CPU model, GPU device, driver version) via system commands.
    *   *Transition:* If hardware capture fails $\rightarrow$ **WARN** (log error, proceed with empty hardware fields). Else $\rightarrow$ **LAUNCH**.

3.  **LAUNCH:**
    *   Fork `llama-cli` process.
    *   Redirect stdout/stderr to temporary files.
    *   Start optional background monitors (if configured and available).
    *   *Transition:* If process fails to start $\rightarrow$ **FAIL (Launch Error)**. Else $\rightarrow$ **RUNNING**.

4.  **RUNNING:**
    *   Monitor process liveness.
    *   Check for timeout (e.g., 10 minutes for 256 tokens).
    *   *Transition:* If timeout $\rightarrow$ **FAIL (Timeout)**. If process exits $\rightarrow$ **EXITED**.

5.  **EXITED:**
    *   Stop monitors.
    *   Read exit code.
    *   Attempt to parse `stdout.log` for performance metrics using regex.
    *   Copy raw `response.txt` (if generated) to final artifact.
    *   *Transition:*
        *   If parse fails $\rightarrow$ **FAIL (Parse Error)** (metrics missing, but raw data preserved).
        *   If parse succeeds $\rightarrow$ **FINALIZE**.

6.  **FINALIZE:**
    *   Compute `prompt_hash` and `model_hash`.
    *   Write final `run_id.json` with status `SUCCESS` or `PARTIAL`.
    *   Write `metrics.json`.
    *   *Transition:* **DONE**.

**Error Handling Specifics:**
*   **OOM:** Detected via non-zero exit code or OOM killer message in stderr. State transitions to **FAIL (OOM)**.
*   **Malformed Output:** If regex fails to extract tokens/sec, `metrics.json` is marked invalid, but the run is not retried automatically (to prevent infinite loops). Raw logs are preserved for manual audit.
*   **Monitor Failure:** If a monitor process crashes or returns no data, the main run continues. `run_id.json` includes a `monitor_status: "unavailable"` flag.

Auditable Design

**Component Boundaries**
1.  **Orchestrator (Python):** Handles config loading, state machine logic, process spawning, and file management. It does *not* parse LLM output directly; it delegates parsing.
2.  **Executor (Shell/Bash):** A thin wrapper script invoked by Python. It runs `llama-cli` with exact arguments, redirects I/O to temp files, and returns the exit code. This ensures the command line is exactly as intended and avoids Python subprocess quoting issues.
3.  **Parser (Python):** A separate module that reads `stdout.log` and extracts metrics. It must be resilient to `llama.cpp` version changes.

**Metadata Schema (`run_id.json`)**
```json
{
  "run_id": "uuid-v4",
  "timestamp_start": "ISO-8601",
  "timestamp_end": "ISO-8601",
  "status": "SUCCESS|FAIL|PARTIAL",
  "identity": {
    "model_path": "/absolute/path/to/model.gguf",
    "model_hash_sha256": "abc123...",
    "backend": "cuda",
    "hardware_label": "RTX_3090",
    "context_size": 4096,
    "n_predict": 256,
    "prompt_hash_sha256": "def456...",
    "temperature": 0.7,
    "n_gpu_layers": 20,
    "llama_build_hash": "commit-xyz"
  },
  "metrics": {
    "tokens_per_second": 45.2,

    "prompt_eval_time_sec": 0.5,

  "error_message": "null or string"
```

**Atomic Write Conventions**
*   All JSON files are written to a `.tmp` file first, then `os.rename()` (atomic on POSIX) to the final name.
*   `response.txt` is written by `llama-cli` directly. If the process crashes, the file may be partial. The runner does *not* truncate it; it preserves the partial output for audit.

**Preserving stdout/stderr and Prompts**
*   **Prompts:** The exact prompt string is written to a hidden file `.prompt_raw.txt` in the run directory and hashed. This allows verification that the prompt sent to `llama.cpp` matches the workload definition.
*   **I/O:** `stdout.log` and `stderr.log` are appended to, not overwritten, in case of multiple retries (though retries are discouraged in this design, the structure supports it).

Analysis Integrity

**Preventing Misleading Throughput Comparisons**
1.  **Variable Token Count:** Throughput (tokens/sec) is only valid if the number of generated tokens is consistent. The runner enforces `n_predict=256` by default. If the model stops early (e.g., due to EOS token), the actual token count is less than 256.
    *   *Mitigation:* The parser extracts `actual_tokens_generated`. Throughput comparisons must be normalized or flagged if `actual_tokens < n_predict`. The analysis script should reject runs where `actual_tokens` deviates from the expected count unless the deviation is due to early stopping (which should be logged).
2.  **Failed Runs:** A failed run produces no metrics. The analysis script must filter out `status != SUCCESS` before computing averages. Partial runs (`status: PARTIAL`) are excluded from throughput calculations but included in failure rate analysis.
3.  **Warm-up Bias:** The first run on a backend may be slower due to caching. The design repeats each condition three times. The analysis should discard the first run (warm-up) or use the median of the three.

**Parser Resilience**
*   **Unknown Formats:** The parser uses a hierarchy of regex patterns. If the primary pattern (e.g., `llama_print_timings`) fails, it attempts fallback patterns. If all fail, it logs a warning and marks metrics as `null`. It never crashes the runner.
*   **Version Drift:** The parser should not assume exact spacing or label text (e.g., "t/s" vs "tokens/s"). It should use flexible regexes like `\d+\.\d+\s*t/s`.

Pre-merge Review

**Risk 1: Non-Atomic Metadata Corruption**
*   *Flaw:* If the runner crashes between writing `run_id.json` and `metrics.json`, the state is inconsistent. A subsequent analysis script might read a partial JSON file.
*   *Fix:* Implement strict atomic writes using `.tmp` files and `os.rename()`. Ensure that `run_id.json` is written *after* all artifacts are secured, or use a transactional approach where a `completed.flag` file is written last.

**Risk 2: Prompt Injection/Whitespace Sensitivity**
*   *Flaw:* Shell quoting issues in the executor script could alter the prompt (e.g., stripping newlines or collapsing spaces), leading to a `prompt_hash` mismatch between the config and what was actually sent to the model.
*   *Fix:* Pass the prompt via a temporary file rather than command-line arguments. The Python orchestrator writes the prompt to `.prompt_raw.txt`, and the shell script reads from this file using `--file` or stdin, avoiding shell interpretation of special characters.

**Risk 3: False Positives in Metric Parsing**
*   *Flaw:* The regex parser might match unrelated numbers in the stderr log (e.g., error codes, memory addresses) as throughput metrics, leading to garbage data in `metrics.json`.
*   *Fix:* Restrict parsing to `stdout.log` only, as `llama.cpp` writes timing info to stdout. Use anchored regexes that require the specific keyword prefix (e.g., `llama_print_timings:`) before extracting numbers. Add a validation step to ensure extracted tokens/sec is within a reasonable range (e.g., 0.1 to 10000).
