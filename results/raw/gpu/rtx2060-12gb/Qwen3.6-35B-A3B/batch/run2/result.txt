### Task 1 — Quantization Tradeoff

**Memory Pressure Analysis**
*   **Q8_0 (8.0 GB file):** The file size (8.0 GB) exceeds the available GPU memory (5.2 GB). Even with zero overhead for KV cache, batch size, or runtime buffers, this model **cannot fit entirely on the GPU**. It will require significant offloading to system RAM (CPU). This creates high "memory pressure" in the sense of bandwidth contention: the system must shuttle data between RAM and GPU, likely causing severe latency spikes and reduced throughput compared to an in-GPU run.
*   **Q4_K_M (4.8 GB file):** The file size (4.8 GB) fits within the 5.2 GB free GPU memory. This allows the model weights to reside entirely on the GPU. This reduces memory pressure by eliminating the need for frequent CPU-GPU data transfer for weights. However, it leaves only ~0.4 GB for KV cache and runtime overhead, which may limit context length or batch size.

**Why File Size ≠ Runtime Memory**
File size is a static measure of compressed weights on disk. It does not account for:
1.  **Runtime Overhead:** Frameworks (e.g., llama.cpp, vLLM) require additional memory for KV cache, activation buffers, and internal data structures.
2.  **Quantization/Dequantization:** Some formats require temporary dequantized buffers during inference.
3.  **Batch Size & Context Length:** These scale linearly or quadratically with memory usage depending on the architecture, independent of weight file size.
4.  **GPU Memory Fragmentation:** Even if total size < free memory, fragmentation can prevent allocation.

**Two Quality/Performance Measurements Needed**
Before declaring one format "better," you must measure:
1.  **Perplexity (PPL) or Semantic Accuracy:** To quantify the quality degradation from Q8_0 to Q4_K_M. A small drop in PPL may be acceptable for Q4, but a large drop indicates unacceptable loss of model capability.
2.  **Tokens Per Second (tok/s) at Target Context Length:** To measure actual inference speed under realistic load. Q4 may be faster due to less memory bandwidth usage, but only if the KV cache fits in GPU memory. If Q8_0 offloads heavily to CPU, it may be significantly slower. Speed must be measured at the *same* input/output token counts.

*Note: Q4 is not always faster. If the KV cache for Q4 exceeds GPU memory, causing swapping, it may be slower than a well-offloaded Q8 run with sufficient RAM bandwidth.*

### Task 2 — Conservative Launch Decision

**Assumptions**
*   Total RAM: 16 GB.
*   GPU VRAM: 6 GB.
*   Free GPU VRAM before load: 5.2 GB (as per Task 1, but we re-evaluate based on the 5.0 GB weight claim).
*   Model weights: 5.0 GB (excludes KV cache).
*   Prompt: 2,000 tokens.
*   Generation: 512 tokens.

**Conservative Procedure**

1.  **Initial Assessment (CPU-Only Baseline):**
    *   Load the model entirely into system RAM (16 GB).
    *   Calculate the estimated KV cache size for 2,000 + 512 tokens at full precision (FP16/BF16). For an 8B model, KV cache per token per layer is small, but with many layers, it can be significant. Estimate: `KV_size ≈ 2 * num_layers * hidden_size * num_heads * head_dim * seq_len * 2 bytes`.

2.  **GPU Offload Strategy (llama.cpp specific):**
    *   **Step 1: Try Maximum GPU Offload.** Set `n_gpu_layers` to load all layers that fit in 5.2 GB free VRAM. Since weights are 5.0 GB, try loading all layers (`-ngl -1` or `-ngl 999`).

    *   **Step 3: Reduce Offload.** Calculate the maximum number of layers (`L_max`) such that `Weight(L_max) + KV_Cache(2000 tokens) ≤ 5.2 GB`.
        *   Estimate KV cache size for 2,000 tokens. If it exceeds ~100 MB, you cannot fit all weights.
        *   Iteratively reduce `n_gpu_layers` until `Weight(n_gpu_layers) + KV_Cache(2000 tokens) ≤ 5.2 GB`.
    *   **Step 4: Validate with Small Test.** Run a 10-token generation with the calculated `n_gpu_layers` and prompt.

3.  **Telemetry to Record:**
    *   `n_gpu_layers` used.

    *   System RAM usage.
    *   Prompt evaluation time (ms).
    *   Decode throughput (tok/s).
    *   Any OOM errors or CPU fallback events.

4.  **Unsafe/Misleading Success:**

    *   **Unsafe:** The model loads but crashes during generation due to VRAM fragmentation or underestimation of KV cache size. This indicates the conservative estimate was wrong.
    *   **Misleading Speed:** Reporting high tok/s without noting that the prompt evaluation took 30 seconds due to CPU offload.

### Task 3 — Robust Aggregation

**Pseudocode**

```python
function compute_robust_median(runs):
    # runs: list of dictionaries, each with 'speed' (float) and 'status' (str)
    
    successful_runs = []
    failed_runs = []
    
    for run in runs:
        # Validate record
        if not isinstance(run['speed'], (int, float)) or run['speed'] < 0:
            # Invalid data point, skip or flag
            continue
            
        if run['status'] == 'success':
            successful_runs.append(run['speed'])
        elif run['status'] == 'failed' or 'oom' in run.get('warning', '').lower():
            failed_runs.append(run['speed']) # Keep visible but exclude from median
        else:
            # Unknown status, treat as invalid or exclude
            continue
            
    # Report result
    if len(successful_runs) < 2:
        return {
            "median": None,
            "message": "Insufficient successful runs (need >= 2). Failed runs: " + str(failed_runs),
            "failed_speeds": failed_runs
        }
    
    # Compute median of successful runs
    sorted_speeds = sorted(successful_runs)
    n = len(sorted_speeds)
    if n % 2 == 1:
        median = sorted_speeds[n // 2]
    else:
        median = (sorted_speeds[n // 2 - 1] + sorted_speeds[n // 2]) / 2.0
        
    return {
        "median": median,
        "successful_count": len(successful_runs),
        "failed_count": len(failed_runs),
        "failed_speeds": failed_runs
    }
```

**Explanation**
*   **Validation:** Checks for valid numeric speed values.
*   **Visibility:** Failed runs are stored in `failed_runs` and included in the output, preventing silent loss of data.
*   **Median Calculation:** Uses standard median logic on `successful_runs` only.
*   **Fewer than 2 Succeeds:** Returns `None` for median and explicitly lists failed speeds, ensuring the user is aware of the failure.

### Task 4 — Validity Audit

**Threats to Validity and Controls**

1.  **Threat: Inconsistent Workload/Output Comparability**
    *   *Description:* If the three backends (CPU, CUDA, Vulkan) are not run with identical prompts, seeds, and generation parameters, differences in output (e.g., sampling randomness) could be mistaken for performance differences.
    *   *Control/Disclosure:* Use a fixed random seed (`--seed 42`) for all runs. Use the exact same input prompt file. Verify that the generated text is identical (or within token-level equivalence) across backends for the same prompt.

2.  **Threat: Thermal Throttling (Hardware State)**
    *   *Description:* The order of runs matters. If the CPU run is first, the CPU may be cool. If the CUDA run is last, the GPU may be throttled due to heat, skewing results.
    *   *Control/Disclosure:* Randomize the order of backend runs. Allow sufficient cooldown time between runs (e.g., 5 minutes) or monitor GPU/CPU temperature and discard runs where throttling occurred. Disclose the ambient temperature and thermal limits.

3.  **Threat: Background System Load (Noise)**
    *   *Description:* Other processes (OS updates, browser tabs, other benchmarks) may consume CPU or RAM, affecting the CPU run or even GPU memory allocation.
    *   *Control/Disclosure:* Run benchmarks in a controlled environment with minimal background processes. Record system load average (`top`/`htop`) during each run. Exclude runs where system load exceeds a threshold (e.g., 0.5 per core).

4.  **Threat: Driver/Software Version Instability**
    *   *Description:* If the CUDA or Vulkan drivers are updated between runs, or if the llama.cpp binary is recompiled with different flags (e.g., different BLAS libraries for CPU), results are not comparable.
    *   *Control/Disclosure:* Document the exact version of the backend (CUDA toolkit, Vulkan driver, llama.cpp commit hash). Ensure the same binary/executable is used for all runs. Do not reboot or update drivers between runs.

### Task 5 — User-Visible Latency

**Definitions**
*   **Time to First Token (TTFT):** The latency from sending the prompt to receiving the first generated token. This is dominated by **prompt-evaluation throughput**.
*   **Prompt-Evaluation Throughput:** The speed at which the model processes the input prompt (tokens/sec). High throughput means low TTFT.
*   **Decode Throughput:** The speed at which the model generates subsequent tokens (tokens/sec). High throughput means low inter-token latency.
*   **Total Wall-Clock Time:** The total time from sending the prompt to receiving the last generated token.

**Symbolic Equation**
Let:
*   $N_p$ = Number of prompt tokens (2,000)
*   $N_g$ = Number of generated tokens (200)
*   $T_{eval}$ = Time to evaluate one prompt token
*   $T_{decode}$ = Time to decode one generated token

Then:
$$ \text{Total Time} = (N_p \times T_{eval}) + (N_g \times T_{decode}) $$

Or in terms of throughput ($R_{eval} = 1/T_{eval}$, $R_{decode} = 1/T_{decode}$):
$$ \text{Total Time} = \frac{N_p}{R_{eval}} + \frac{N_g}{R_{decode}} $$

**Example: Optimizing Prompt Processing Barely Changes Experience**
If $R_{eval} = 100$ tok/s and $R_{decode} = 50$ tok/s:
*   Prompt Time: $2000 / 100 = 20$ seconds.
*   Decode Time: $200 / 50 = 4$ seconds.
*   Total: 24 seconds.

If we optimize prompt processing to $R_{eval} = 200$ tok/s:
*   Prompt Time: $2000 / 200 = 10$ seconds.
*   Decode Time: $200 / 50 = 4$ seconds.
*   Total: 14 seconds.

While the total time decreased by 10 seconds, the **user experience** (TTFT) improved from 20s to 10s, which is significant. However, if $R_{decode}$ was much slower, e.g., $R_{decode} = 5$ tok/s:
*   Original Decode Time: $200 / 5 = 40$ seconds.
*   Original Total: $20 + 40 = 60$ seconds.
*   Optimized Total: $10 + 40 = 50$ seconds.

In this case, optimizing prompt processing saved 10 seconds out of 60, but the **inter-token latency** (1/5 = 0.2s) remained the same. The user still waits 40 seconds for the text to stream. If the user perceives latency as "how long until I see text," the TTFT improved. If they perceive it as "how long until the whole response is ready," it improved less. If the decode was extremely slow (e.g., 1 tok/s), the prompt optimization would be negligible in total time.

**Key Distinction:** Tok/s is not a single metric. "Prompt tok/s" affects TTFT. "Decode tok/s" affects streaming latency. Optimizing one does not help the other phase.
