### Task 1 — Quantization Tradeoff

**Memory Pressure Analysis**
The model’s base weight size in Q8_0 is 8.0 GB. The available GPU memory is 6.0 GB, with 5.2 GB free after system overhead.
*   **Q8_0 (8.0 GB file):** This format exceeds the available 5.2 GB free VRAM. Loading this entirely on the GPU is impossible without offloading layers to CPU RAM or using a swap mechanism, which drastically increases latency due to PCIe bandwidth limits. If forced onto the GPU, it will cause an immediate Out-Of-Memory (OOM) error.
*   **Q4_K_M (4.8 GB file):** This fits within the 5.2 GB free VRAM, leaving approximately 0.4 GB (400 MB) for the KV cache (context storage) and temporary buffers. This allows the entire model to reside on the GPU, enabling full GPU acceleration for both prompt processing and decoding, provided the context window is kept small.

**Why File Size ≠ Runtime Memory**
File size represents compressed weights on disk. Runtime memory usage includes:
1.  **Uncompressed Weights:** During loading, weights are often decompressed into larger structures (e.g., float16 or float32) before being cast to the target quantization format for inference, temporarily spiking memory usage.
2.  **KV Cache:** Context tokens require memory proportional to the sequence length, number of layers, and hidden dimensions. This is not reflected in the static weight file size.
3.  **Activation Buffers:** Intermediate tensors generated during forward passes require additional memory.
4.  **Overhead:** Frameworks (like llama.cpp) allocate memory for thread synchronization, scratch buffers, and memory alignment.

**Required Quality/Performance Measurements**
To declare one format "better," the following two measurements are necessary:
1.  **Perplexity (PPL) or Task-Specific Accuracy:** Quantization introduces approximation error. Q4_K_M may degrade semantic coherence or factual accuracy compared to Q8_0. A benchmark on the target task (e.g., MMLU, GSM8K, or a custom evaluation set) is required to quantify this loss.
2.  **Effective Throughput (tokens/sec) at Target Context Length:** While Q4 fits on the GPU, the remaining 0.4 GB limits the context window. One must measure decode speed at the *actual* expected context length. If Q4 forces truncation of the prompt or early stopping due to KV cache exhaustion, its effective utility may be lower than a CPU-offloaded Q8_0 with a larger context capacity, despite lower raw GPU speed.

*Note: Q4 is not always faster. If the context length is large, Q4 may overflow VRAM, forcing fallback to CPU, which is slower than a carefully offloaded Q8_0.*

### Task 2 — Conservative Launch Decision

**Assumptions**
*   Weight size = 5.0 GB (does not include KV cache or runtime buffers).
*   Total GPU VRAM = 6.0 GB.
*   RAM = 16 GB.
*   Prompt = 2,000 tokens; Generation = 512 tokens.
*   KV cache memory usage is proportional to: `2 * num_layers * hidden_size * num_heads * head_dim * context_length * sizeof(float16)` (simplified; exact formula depends on model architecture).

**Conservative Procedure**

1.  **Estimate KV Cache Requirement:**
    *   Calculate the maximum KV cache size needed for a context of 2,000 + 512 = 2,512 tokens.
    *   Formula: `KV_Size ≈ 2 * N_layers * D_model * N_heads * (Context_Length) * 2 bytes` (assuming fp16).
    *   Let `E_KV` be the estimated KV cache size in GB.

2.  **Determine Maximum Usable GPU Memory:**
    *   `Available_for_KV = Total_GPU_RAM - Weight_Size - Safety_Margin`
    *   `Safety_Margin` should be at least 0.5–1.0 GB to account for temporary buffers, CUDA context, and fragmentation.
    *   Example: `Available_for_KV = 6.0 - 5.0 - 0.5 = 0.5 GB`.

3.  **Iterative Layer Offload Strategy:**
    *   **Step 1: Try Full GPU Offload (n_gpu_layers = all).**
        *   Check if `E_KV <= Available_for_KV`.
        *   If yes, attempt launch.
        *   If no, proceed to Step 2.
    *   **Step 2: Reduce Context Size.**
        *   Reduce `context_size` until `E_KV(context_size) <= Available_for_KV`.
        *   If even 1 token fits, set this as the maximum context.
    *   **Step 3: Reduce GPU Layers.**
        *   If context reduction is insufficient, decrease `n_gpu_layers` from `all` downward.
        *   For each reduction, recalculate `Available_for_KV = 6.0 - (Weight_Size - Size_of_Layers_Moved_To_CPU) - Safety_Margin`.
        *   Find the largest `n_gpu_layers` such that `E_KV <= Available_for_KV`.

4.  **Telemetry to Record:**
    *   Final `n_gpu_layers` setting.
    *   Final `context_size` setting.
    *   Actual GPU memory usage at launch (via `nvidia-smi` or CUDA API).
    *   Whether any layers were offloaded to CPU.
    *   Time to first token (TTFT) and decode speed (tok/s).

5.  **Unsafe/Misleading Success Criteria:**
    *   **Unsafe:** The program launches but triggers a CPU fallback during inference (e.g., CUDA error 11), causing severe latency spikes or hangs.
    *   **Misleading:** The benchmark completes successfully but with a truncated context (e.g., only 500 tokens of the 2,000-token prompt processed), leading to an artificially high token throughput that does not reflect real-world performance with full prompts.

### Task 3 — Robust Aggregation

**Pseudocode**

```python
function compute_robust_median(speed_records):
    # speed_records is a list of objects/dicts: { 'id': str, 'speed': float, 'status': str }
    # status can be 'success', 'failure', 'timeout', etc.

    successful_runs = []
    failed_runs = []

    for record in speed_records:
        # Validate record structure
        if record is None or 'speed' not in record or 'status' not in record:
            continue
        
        # Keep failed runs visible in a separate list
        if record['status'] != 'success':
            failed_runs.append(record)
            continue
        
        # Validate speed is a positive finite number
        if is_finite(record['speed']) and record['speed'] > 0:
            successful_runs.append(record['speed'])
        else:
            failed_runs.append(record) # Treat invalid data as failure

    # If fewer than two successful runs, cannot compute a meaningful median
    if len(successful_runs) < 2:
        return {
            'status': 'insufficient_data',
            'message': f'Only {len(successful_runs)} valid runs. Cannot compute median.',
            'failed_runs': failed_runs,
            'successful_runs_count': len(successful_runs)
        }

    # Compute median of successful runs
    sorted_speeds = sort(successful_runs)
    n = len(sorted_speeds)
    if n % 2 == 1:
        median_speed = sorted_speeds[n // 2]
    else:
        median_speed = (sorted_speeds[n // 2 - 1] + sorted_speeds[n // 2]) / 2.0

    return {
        'status': 'success',
        'median_speed': median_speed,
        'num_successful_runs': n,
        'failed_runs': failed_runs, # Include details of failures for transparency
        'all_runs': speed_records   # Full log for audit
    }
```

**Reporting if Fewer Than Two Runs Succeed:**
The result should be reported as **"Insufficient Data for Median."** The report must explicitly list the number of successful runs (0 or 1), the speeds of any single successful run (if applicable), and the reasons/statuses of all failed runs. It should not substitute the failed run's speed with zero or exclude it from the failure log.

### Task 4 — Validity Audit

**Threats to Validity and Controls**

1.  **Threat: Unequal Prompt/Context Lengths Across Backends**
    *   *Description:* If the CPU, CUDA, and Vulkan runs process different numbers of tokens (e.g., due to different context window limits or truncation policies), the workload is not comparable.
    *   *Control:* Enforce an identical context length (e.g., exactly 2,000 tokens) and identical generation length (e.g., 200 tokens) for all three runs. Log the exact token count processed by each backend.

2.  **Threat: Output Non-Determinism Due to Different Precision or Library Implementations**
    *   *Description:* CUDA and Vulkan may use different FP16/FP32 rounding modes or optimized kernels that produce slightly different outputs. This affects metrics like perplexity if the "ground truth" is compared against a reference.
    *   *Control:* Fix the random seed for all runs. Use the same model weights and quantization format across all backends. Compare outputs token-by-token to identify divergence. Report the percentage of identical tokens.

3.  **Threat: Thermal Throttling Affecting CPU vs. GPU Performance**
    *   *Description:* The CPU run uses 8 threads. If the CPU thermally throttles during the run, throughput drops. The GPU may also throttle. Without thermal monitoring, performance differences may be attributed to backend efficiency rather than thermal limits.
    *   *Control:* Monitor CPU and GPU temperatures and clock speeds during each run. Discard or flag runs where thermal throttling occurs (e.g., temperature > 85°C). Report average clock speeds.

4.  **Threat: Inconsistent System Load (Noise from Other Processes)**
    *   *Description:* Background processes (updates, scans) may consume CPU or I/O bandwidth, affecting the CPU run more than the GPU run (which is more isolated).
    *   *Control:* Run all three backends in a controlled environment with minimal background processes. Alternatively, run each backend multiple times and interleave the runs (e.g., CUDA, CPU, Vulkan, CUDA, CPU, Vulkan) to average out temporal noise. Report the standard deviation of the runs.

### Task 5 — User-Visible Latency

**Definitions**
*   **Time to First Token (TTFT):** The wall-clock time from sending the prompt to receiving the first generated token. This is dominated by **prompt-evaluation throughput** (processing the 2,000-token prompt).
*   **Prompt-Evaluation Throughput:** The rate at which the model processes the input prompt tokens (tokens/sec). Higher throughput means lower TTFT.
*   **Decode Throughput:** The rate at which new tokens are generated after the prompt is processed (tokens/sec). This determines the speed of subsequent token generation.
*   **Total Wall-Clock Time:** The total time from sending the prompt to receiving the final token.

**Symbolic Equation for Total Time**
Let:
*   $P$ = number of prompt tokens (2,000)
*   $G$ = number of generated tokens (200)
*   $T_{TTFT}$ = Time to First Token
*   $R_{decode}$ = Decode throughput (tokens/sec)

$$ \text{Total Time} = T_{TTFT} + \frac{G}{R_{decode}} $$

Note: $T_{TTFT}$ is inversely proportional to prompt-evaluation throughput ($R_{prompt}$): $T_{TTFT} \approx \frac{P}{R_{prompt}} + \text{overhead}$.

**Example: Optimizing Prompt Processing Barely Changes Experience**
If the decode throughput is very slow (e.g., $R_{decode} = 2$ tok/s), the time to generate 200 tokens is:
$$ \frac{200}{2} = 100 \text{ seconds} $$

If the prompt evaluation is extremely fast (e.g., $T_{TTFT} = 1$ second), the total time is **101 seconds**.
If we optimize the prompt processing to reduce $T_{TTFT}$ to **0.1 seconds**, the total time becomes **100.1 seconds**.

The user experiences a difference of **0.9 seconds** in a 101-second interaction, which is negligible (<1%). The user's primary perception of speed is dominated by the slow decode phase, not the prompt processing. Thus, optimizing prompt throughput yields minimal user-visible benefit in this scenario.
