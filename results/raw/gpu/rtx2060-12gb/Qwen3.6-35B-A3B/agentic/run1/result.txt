3.  **Performance Metrics:** Extracted metrics (tokens/sec, latency, etc.) stored in the metadata file.

**Success/Failure States:**
*   **Success:** `llama.cpp` exits with code 0, performance metrics are parseable, and the run is logged.
*   **Model Failure:** `llama.cpp` exits non-zero, crashes, or OOMs. The run is logged as failed with the exit code and raw output preserved.
*   **Monitor Failure:** Missing or sparse data. The run is **not** failed; the monitor data field is marked as `null` or `partial`, but the performance metrics from `llama.cpp` are still valid and recorded.

**Experimental Identity Tuple:**
To ensure results are not mixed, every run is uniquely identified by the tuple:
`(model_path, backend, hardware_label, context_size, gen_limit, prompt_hash, temp, gpu_layers, llama_cpp_build_hash, driver_version)`

**Ambiguity to Resolve:**
*   *Ambiguity:* "Fixed workload prompts" are defined as templates. How are variables (like system prompts or user inputs) injected?
*   *Resolution:* The specification must define that "fixed workload" means the *template structure* is fixed, but the content may be deterministic based on the workload type (e.g., `coding` always uses a specific Python snippet). If external input is allowed, the `prompt_hash` in the identity tuple must change, ensuring isolation. For this design, we assume the prompts are fully deterministic strings defined in the config, keyed by workload name.

State Machine;
1.  **Validation:**
    *   Parse CLI args and config.
    *   Resolve model alias to file path. Verify file exists.
    *   Validate backend compatibility (e.g., Vulkan requires GPU).

    *   Check for existing runs with identical identity tuple (idempotency check). If exists, skip or abort based on policy.

    *   Initialize metadata schema with `status: "pending"`.

**Atomic Writes & Partial Files:**
*   Metadata is written to a temporary file (`.tmp`) and then renamed to the final `.json` file. This ensures no partial JSON is read by other tools.
*   Raw output is appended to in real-time. If the process crashes, the raw file is complete up to the crash point.

**Preserving Prompt:**
*   The exact prompt string used is stored in the metadata file under `prompt_used`. The `prompt_hash` ensures no two runs with different prompts (even if similar) are mixed.

Analysis Integrity;
**Preventing Misleading Throughput:**
*   **Failed Runs:** If `llama.cpp` fails (non-zero exit), `metrics` is set to `null`. Downstream analysis must explicitly filter out runs with `status != "completed"` or `metrics is null`.
*   **Variable Token Counts:** The identity tuple includes `gen_limit`. If a run terminates early due to OOM or timeout, the `total_tokens` in metrics (if available) will be lower than `gen_limit`. The analysis tool must check `metrics.total_tokens < identity.gen_limit` as a warning flag, even if status is "completed".
*   **Partial Output:** If the parser fails to extract metrics (e.g., `llama.cpp` output format changed), `metrics` is `null`. This is distinct from a zero throughput value.

**Handling Unknown Output Formats:**
*   The parser should use a whitelist of known regex patterns.
*   If no pattern matches, it logs a warning: "Unknown llama.cpp output format, metrics unavailable."
*   It does *not* crash; it returns `metrics: null`.
*   The raw output file is preserved for manual inspection.

Pre-merge Review;
**Highest-Risk Design Flaws:**

1.  **Flaw:** **Race Condition in Metadata Writing.**
    *   *Risk:* If two runs finish simultaneously, they might try to rename the same `.tmp` file or write to the same metadata file if the naming scheme is not unique.
    *   *Fix:* Use UUIDs for run IDs. Ensure the temporary file name includes the UUID. Use `os.rename` which is atomic on POSIX systems. Add a file lock or directory check to prevent collisions if the OS does not guarantee atomic rename across different filesystems (unlikely but safe to assume).

2.  **Flaw:** **Implicit Assumption of `llama.cpp` Output Format.**
    *   *Risk:* `llama.cpp` updates frequently. A new version might change the log format, causing the parser to fail silently (returning `null` metrics) and breaking analysis pipelines that expect valid numbers.
    *   *Fix:* Implement a "version detection" step that parses the first few lines of `llama.cpp` output to identify the version/build hash. Store this in the identity tuple. If the format is unknown, raise a hard error or require explicit user acknowledgment, rather than silently returning `null`. Alternatively, use `llama.cpp`'s JSON logging mode if available.

3.  **Flaw:** **Monitor Data Integrity vs. Run Status.**
    *   *Risk:* If a monitor crashes but `llama.cpp` succeeds, the run is marked `completed`. However, downstream analysis might assume monitor data is always present for `completed` runs, leading to `NoneType` errors.
    *   *Fix:* Explicitly define the schema for `monitor_data` to include an `available` boolean. Enforce this in the parser: if `monitor_data` is present, it must have `available: true`. If `available: false`, the field should be `null` to simplify downstream checks. Document that `status: completed` does not imply `monitor_data` is valid.
