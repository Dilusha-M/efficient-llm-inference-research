### Task 1 — quantization tradeoff

**Memory Pressure Analysis**
*   **Q8_0:** Requires **8.0 GB** of VRAM. Since the GPU has only 5.2 GB free, this format creates a "hard stop" pressure; the model will fail to launch immediately unless the system aggressively swaps to CPU RAM (if supported) or fails completely.
*   **Q4_K_M:** Requires **4.8 GB** of VRAM. This leaves **0.4 GB** of free VRAM ($5.2 - 4.8$). This creates moderate pressure but allows for a small KV cache buffer before hitting the hard limit, making it viable for immediate inference on this hardware.

**Why File Size $\neq$ Runtime Memory Estimate**
File size (weights only) is not a complete runtime-memory estimate because inference memory consumption is dynamic and includes:
1.  **KV Cache Overhead:** As the context length increases, the memory required to store the Key and Value tensors grows linearly (or super-linearly due to fragmentation). A 4.8 GB model might fit with zero context, but require 6.0+ GB with a long context.
2.  **Activation Memory:** Intermediate calculations during the forward pass generate temporary tensors (activations) that are not part of the static weight file but consume significant VRAM.
3.  **Fragmentation:** The actual available contiguous memory block might be smaller than the reported "free" space if the OS or driver cannot merge small chunks.

**Required Quality/Performance Measurements**
Before declaring one format better, the following must be measured:
1.  **Context Length Stability:** The maximum context length achievable before the GPU runs out of memory (OOM). Q4 might support 128k tokens while Q8_0 crashes at 64k.
2.  **Inference Throughput (tok/s):** The actual tokens per second generated *with the intended context size*. A format that crashes early is functionally useless regardless of its theoretical speed on short contexts.

*Hypothesis:* Q4_K_M is likely better for this specific hardware due to the remaining 0.4 GB buffer, but this is contingent on the context length being kept low.

### Task 3 — robust aggregation

**Data Validation & Logic**
The data provided contains a failure case (8.0 tok/s with an OOM warning). Treating this as "0 tok/s" or excluding it silently is invalid because the OOM event indicates a resource exhaustion failure, not just a slow run. The median should be calculated only on successful, non-failing runs.

**Pseudocode**

```python
def compute_robust_median(records):
    # Filter records: Only include those that did not log an OOM warning
    successful_records = [
        r for r in records 
        if not r.has_oom_warning()
    ]
    
    # Check if we have at least two valid runs for a median
    if len(successful_records) < 2:
        raise ValueError("Insufficient valid runs to compute a meaningful median.")
    
    # Sort and calculate median
    sorted_speeds = sorted([r.speed for r in successful_records])
    n = len(sorted_speeds)
    
    if n % 2 == 0:
        median = (sorted_speeds[n//2 - 1] + sorted_speeds[n//2]) / 2
    else:
        median = sorted_speeds[n//2]
        
    return median

# Application to Task 3 data
records = [
    {"speed": 42.0, "oom": False},
    {"speed": 41.5, "oom": False},
    {"speed": 8.0, "oom": True}  # Failed run
]

result = compute_robust_median(records)
# Result will be 41.75. The 8.0 run is preserved in the list but excluded from the median calc.
```

### Task 5 — user-visible latency

**Definitions**
*   **Time to First Token (TTFT):** The elapsed wall-clock time from the start of the prompt submission until the very first generated token is returned to the user. This is dominated by **prompt evaluation time** (processing the input).
*   **Prompt-Evaluation Throughput:** The rate (tok/s) at which the model processes the input tokens. This is usually fast and constant for a static prompt.
*   **Decode Throughput:** The rate (tok/s) at which the model generates new tokens based on the previous context. This is the speed of the "chat" phase.
*   **Total Wall-Clock Time:** The sum of TTFT + (Generation Count / Decode Throughput).

**Symbolic Equation**
Let $T_{prompt}$ be the time to process the input.
Let $N_{gen}$ be the number of generated tokens (200).
Let $R_{dec}$ be the decode throughput (tok/s).

$$T_{total} = T_{prompt} + \frac{N_{gen}}{R_{dec}}$$

**Example of Minimal Impact Optimization**
*   *Scenario:* A user sends a 2,000-token prompt.
*   *Optimization:* Reducing the prompt evaluation time from 2.0 seconds to 1.8 seconds (a 10% improvement).
*   *User Experience:* The user waits 2.0s for the first token vs 1.8s. The difference is negligible (0.2s) compared to the time it takes to generate 200 tokens (which might be 40s at 5 tok/s). The user perceives the response as still taking ~40 seconds regardless of that 0.2s optimization.
*   *Contrast:* Optimizing the **decode throughput** from 5 tok/s to 8 tok/s reduces the second term from 40s to 25s, saving 15 seconds of visible waiting time. This has a massive impact on user experience.
