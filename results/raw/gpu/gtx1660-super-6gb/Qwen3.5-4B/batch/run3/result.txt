### Task 1 — quantization tradeoff

**Memory Pressure Analysis**
*   **Q8_0 (8.0 GB):** This format consumes the majority of the available system RAM (8.0 GB) on a 6 GB GPU system, implying immediate offloading to CPU RAM or system memory. The memory pressure is high regarding total footprint, but the GPU's VRAM (6 GB) is largely unused (0.8 GB free), allowing for a standard context size without triggering offload layers.
*   **Q4_K_M (4.8 GB):** This format consumes significantly less RAM, leaving 1.2 GB free on the 6 GB GPU. This reduces the likelihood of offloading to CPU RAM and allows for a larger context window within the GPU's VRAM, potentially improving cache locality for the kernel execution.
*   **Assumption:** The model architecture (e.g., layer count, matrix dimensions) remains identical between the two quantized versions; the only variable is the bit-depth of the weights and activations.

**Why File Size is Not a Complete Runtime-Memory Estimate**
File size represents the static footprint of the weights only. It does not account for:
1.  **Activation Memory:** During inference, intermediate activation tensors must be stored. While Q4/K-M quantizes weights, the quantization of activations (if using Q4_K_M) and the overhead of the quantization scheme itself (e.g., scaling factors, zero-points) affect runtime memory usage differently from raw weight size.
2.  **Context (KV Cache):** The memory required to store the Key-Value cache grows linearly with the sequence length. A small file size model running a very long context may exceed GPU memory, whereas a larger file size model with a smaller context may fit comfortably.
3.  **Overhead:** Different implementations (e.g., GGUF vs. ONNX) have different memory management overheads that are not reflected in the binary file size.

**Required Quality/Performance Measurements**
Before declaring one format better, the following two metrics must be measured:
1.  **Peak Memory Usage (GB):** The maximum memory footprint reached during a benchmark run with a fixed, representative context length. This determines feasibility on the target hardware.
2.  **Tokens Per Second (tok/s) or Inference Latency (ms):** Throughput under a sustained load. High memory pressure can cause context switching between CPU/GPU or cache misses, leading to lower tok/s even if the file size is smaller.

*Note: It is a hypothesis that Q4 is faster due to reduced memory bandwidth requirements, but this cannot be claimed without empirical data.*

### Task 3 — robust aggregation

**Data Validation Logic**
The dataset contains: `[42.0, 41.5, 8.0]`. The third run logged an OOM warning, indicating a failure state. Treating this as `0` or ignoring it silently would be statistically invalid. The correct approach is to separate valid measurements from invalid ones.

**Pseudocode (Language-Agnostic)**

```python
def compute_robust_median(records):
    # Input: list of dicts with 'speed' (float) and 'status' (str: 'success'/'fail')
    # Output: (median_speed, success_count, failure_count, median_confidence)
    
    valid_records = []
    for record in records:
        speed = record.get('speed', None)
        status = record.get('status', 'unknown')
        
        # Validation: Speed must be positive and status must indicate success
        if speed is not None and speed > 0.0 and status == 'success':
            valid_records.append(speed)
        else:
            # Record failure for visibility but exclude from calculation
            continue
            
    # Case: Fewer than two successful runs
    if len(valid_records) < 2:
        return {
            'median': None, 
            'success_count': len(valid_records),
            'failure_count': len(records) - len(valid_records),
            'message': 'Insufficient successful runs to compute a reliable median.'
        }
    
    # Calculate Median
    valid_records.sort()
    n = len(valid_records)
    mid = n // 2
    
    if n % 2 == 0:
        median = (valid_records[mid - 1] + valid_records[mid]) / 2.0
    else:
        median = valid_records[mid]
    
    return {
        'median': median,
        'success_count': n,
        'failure_count': len(records) - n,
        'message': f'Median of {n} successful runs: {median:.2f} tok/s.'
    }

# Execution Example
data = [
    {'speed': 42.0, 'status': 'success'},
    {'speed': 41.5, 'status': 'success'},
    {'speed': 8.0, 'status': 'fail'} # OOM warning
]
result = compute_robust_median(data)
# Result: Median = 41.75, Failure count = 1
```

**Reporting Strategy**
If fewer than two runs succeed, the median cannot be calculated statistically (as a single data point is not a distribution). The result should be reported as **"Insufficient Data"** with a count of successful runs (e.g., "1 out of 3 runs succeeded"). The single valid run's speed could be reported as a "best case" metric with a high uncertainty flag, but it should not be labeled as the aggregate median.

### Task 4 — validity audit

**Four Threats to Validity**

1.  **Threat: Workload/Output Comparability**
    *   *Description:* The CPU implementation might use a different tokenizer (e.g., legacy vs. new version) or a different prompt normalization strategy compared to CUDA/Vulkan, leading to different output tokens despite identical inputs.
    *   *Control:* Use a strict, version-controlled "gold standard" prompt and tokenizer across all backends. Ensure the seed is reset for stochastic models (though LLMs are deterministic, internal RNGs may vary).
    *   *Disclosure:* Explicitly state the tokenizer version (e.g., `tokenizer.ggml`) and the specific prompt string used in the benchmark report.

2.  **Threat: Hardware Microarchitecture Differences**
    *   *Description:* The CPU uses 8 threads, but the core frequency, cache size, and instruction set of these specific threads differ from the CUDA cores on the GPU or the Vulkan compute units. A workload optimized for CPU AVX-512 may not map 1:1 to GPU tensor cores.
    *   *Control:* Normalize the benchmark by measuring "operations per second" normalized to the hardware's theoretical peak (e.g., GFLOPS) rather than raw tok/s, or ensure the CPU run uses a thread count that matches the effective parallelism of the GPU.
    *   *Disclosure:* Provide the specific CPU model, thread affinity settings, and the exact CUDA/Vulkan compute capabilities.

3.  **Threat: Non-Determinism / Stochastic Noise**
    *   *Description:* If the model includes any stochastic elements (e.g., dropout during inference, temperature sampling randomness), running it three times on the same seed may still yield slightly different logits or token sequences due to floating-point precision differences between CPU, CUDA, and Vulkan.
    *   *Control:* Run the benchmark 30 times per backend and report the mean and standard deviation, not just the average of three runs.
    *   *Disclosure:* Report the variance (std dev) alongside the mean to indicate the stability of the results.

4.  **Threat: Implementation-Specific Latency**
    *   *Description:* Vulkan and CUDA often have different overheads for context switching, synchronization, and memory management compared to a unified CPU thread pool. A "3 runs" average might hide a specific backend's poor latency profile for long sequences.
    *   *Control:* Measure both "time to first token" (TTFT) and "tokens per second" (TPS) separately, as latency behaves differently for the first token vs. sustained generation.
    *   *Disclosure:* Clearly distinguish between TTFT and TPS in the results table, and note the synchronization points measured.

### Task 5 — user-visible latency

**Definitions and Differences**

1.  **Time to First Token (TTFT):** The wall-clock time from the start of the prompt processing to the appearance of the first generated character. This includes prompt evaluation time, model inference time for the first step, and network/IO latency if applicable. It is the most critical metric for user "feel" regarding responsiveness.
2.  **Prompt-Evaluation Throughput:** The speed at which the input tokens are processed and passed to the model. This is usually very fast (milliseconds) compared to decode time but contributes significantly to TTFT for long prompts.
3.  **Decode Throughput:** The rate at which generated tokens are produced (tok/s). This determines how long it takes to generate the remaining 199 tokens.
4.  **Total Wall-Clock Time:** The sum of TTFT + (Decode Throughput $\times$ Generated Tokens). This is the total time the user must wait for the response to finish.

**Symbolic Equation**
Let $T_{prompt}$ be the time to evaluate the prompt, $T_{decode\_total}$ be the total time for generation, and $N$ be the number of generated tokens.
$$ T_{wall\_clock} = T_{TTFT} + (N \times \text{Latency}_{token}) $$
Where $T_{TTFT} \approx T_{prompt} + \text{Inference}_{first\_token}$.
And $\text{Latency}_{token} = \frac{1}{\text{tok/s}_{decode}}$.

**Example of Minimal Impact Optimization**
Consider a user sending a 2,000-token prompt.
*   **Scenario A:** Prompt evaluation takes 100ms. Decode starts immediately.
*   **Scenario B:** Prompt evaluation is optimized to 90ms.
*   **Impact:** The difference in TTFT is 10ms. Even if the user waits 5 minutes for the full response, a 10ms difference in TTFT is imperceptible. The user's experience is dominated by the *total time* (e.g., 300 seconds) rather than the initial burst. Optimizing prompt processing here yields negligible user-visible benefit compared to optimizing decode throughput (e.g., reducing latency per token from 10ms to 8ms would save 300ms total, which is more noticeable).

*Note: Equating `tok/s` to latency requires specifying that `tok/s` represents the sustained generation rate, not the instantaneous TTFT.*
