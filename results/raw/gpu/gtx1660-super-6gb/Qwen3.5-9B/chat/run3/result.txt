### Executive Summary
The system exhibits a classic **prefill-decode imbalance** exacerbated by **GPU memory capacity constraints**. The high prompt throughput indicates efficient parallel processing (prefill), while the degradation during long conversations is caused by **KV cache eviction pressure** and the resulting **CPU-GPU offloading latency**. Moving the cache to RAM mitigates OOM errors but introduces significant PCIe transfer overhead, increasing per-token latency.

---

### 1. KV Cache Lifecycle and Computation Reuse
The inference loop consists of two distinct phases with different memory access patterns:

*   **Prompt Processing (Prefill):**
    *   **Action:** The model processes the entire 2,000-token input in parallel.
    *   **KV Cache Status:** The KV cache is **populated** (written) token-by-token. No cache is reused during this phase because no prior tokens exist.
    *   **Resource:** Dominated by **weight bandwidth** (reading parameters) and **memory bandwidth** (writing new KV entries to VRAM).
*   **Token-by-Token Decoding:**
    *   **Action:** The model generates one token at a time.
    *   **KV Cache Status:** The system **reads** the entire accumulated KV cache (2,000 input + $N$ generated tokens) to compute the next token's logits. Only the newly generated token's KV entry is **written**.
    *   **Reuse:** The massive pre-computed KV cache is reused for every single autoregressive step. Recomputation of past states is zero; latency is purely driven by retrieving the cache.

### 2. Hardware Stress: Prefill vs. Decode Latency
High prompt tok/s does not imply low interactive latency because these metrics optimize for different bottlenecks:

*   **Prefill Stress:** Maximizes **parallel compute utilization** and **weight bandwidth**. Since the 7B model weights fit in the 6 GB VRAM, the GPU can saturate its compute units efficiently, yielding high throughput (tok/s).
*   **Decode Stress (Interactive Latency):** Becomes **memory-bound** and **sequential**.
    *   **The Constraint:** The 6 GB VRAM is insufficient to hold the full KV cache for a growing context. Once the cache exceeds ~4.5–5 GB (leaving <1.5 GB for weights + activations), the system must either evict entries (causing errors) or offload to system RAM.
    *   **Latency Spike:** When offloading to RAM (as observed in your experiment), the per-token latency is dominated by the **PCIe round-trip time** (CPU read/write) rather than GPU compute. A single token generation may involve reading ~10–20 MB of cache data from system RAM to the GPU, which takes milliseconds, dwarfing the microseconds required for the matrix multiplication.

### 3. Impact of Increasing Context (2k $\to$ 8k Tokens)
Increasing context size linearly increases the KV cache volume ($V_{cache} \propto \text{Context Length} \times \text{Batch Size} \times \text{Hidden Dim} \times 2$).

*   **Prefill Behavior:** Prefill time increases linearly with input length. However, since weights fit on GPU, the bottleneck remains weight bandwidth, which is typically faster than the decode bottleneck.
*   **Decode Behavior:**
    *   **VRAM Pressure:** The required cache size grows. At 8k tokens, the cache will almost certainly exceed the remaining free VRAM, forcing aggressive offloading.
    *   **Memory Bandwidth:** The decode phase requires reading the *entire* history. At 8k tokens, the GPU must fetch significantly more data per step from system RAM compared to 2k tokens.
    *   **Result:** Per-token latency will increase super-linearly relative to the 2k case due to the larger PCIe data transfer volume and potential DRAM bandwidth saturation on the CPU side.

### 4. General Principles vs. Implementation Details
*   **Generally True:**
    *   Autoregressive decoding is inherently memory-bandwidth bound (reading previous states).
    *   Offloading KV cache to system RAM introduces PCIe latency that scales with context length.
    *   Prefill is compute/weight-bandwidth bound; Decode is KV-cache-bandwidth bound.
*   **Implementation Dependent:**
    *   **Cache Precision:** Using FP8 or quantized KV cache reduces VRAM footprint, potentially keeping the cache on GPU, but requires kernel support.
    *   **Paging/Offload Policies:** The specific eviction strategy (e.g., LRU vs. PagedAttention) dictates how OOM errors are handled and the exact overhead of swapping cache pages.
    *   **Kernel Fusion:** Some implementations fuse the attention kernel with weight loading; others separate them, affecting how efficiently small batches or offloaded data are processed.

### 5. Investigation Plan: Three Controlled Measurements
To identify the specific bottleneck, perform these controlled experiments:

1.  **Isolate CPU-GPU Transfer (PCIe Bottleneck):**
    *   *Method:* Enable full offloading (cache in RAM). Measure the time delta between the moment the previous token finishes generating and the start of the next token's computation.
    *   *Diagnostic:* If latency is dominated by the PCIe round-trip, the per-token time will scale linearly with the amount of data transferred (context length).
2.  **Isolate Weight Bandwidth (GPU Bottleneck):**
    *   *Method:* Run a synthetic prefill test with varying input lengths but *zero* output tokens (or minimal). Alternatively, run a decode test where you artificially zero-out the KV cache to force re-computation of all past states (if hardware supports it) or measure the time difference between "warm" (cache in VRAM) and "cold" (cache in RAM) states.
    *   *Diagnostic:* If latency is dominated by weight bandwidth, increasing context length (prefill) will increase total time, but per-token decode latency should remain stable if the cache fits.
3.  **Bisect the Cache Residency:**
    *   *Method:* Gradually reduce the system RAM speed (e.g., throttle CPU memory controller) or use a slower storage backend to simulate RAM latency.
    *   *Diagnostic:* If latency increases proportionally to the simulated RAM slowdown, the bottleneck is the CPU-side memory access (DRAM bandwidth) or the PCIe transfer, not the GPU compute.

### Numerical Example: Time Dominance Analysis

**Assumptions:**
*   **Model Weights:** 4.5 GB (fits in 6 GB VRAM).
*   **KV Cache Size (2k context):** 1.5 GB.
*   **Scenario A (Cache in VRAM):**
    *   Prefill Time: 50 ms.
    *   Decode Time per token: 2 ms (Compute + Small Memory Access).
*   **Scenario B (Cache Offloaded to RAM):**
    *   Prefill Time: 50 ms (Weights read from VRAM, Cache written to RAM).
    *   Decode Time per token: 15 ms (2 ms Compute + 13 ms PCIe Transfer for 1.5 GB data).

**Total Time Calculation for a 300-token request:**

| Scenario | Prefill | Decode ($300 \times T_{token}$) | **Total Time** | Dominant Factor |
| :--- | :--- | :--- | :--- | :--- |
| **A: Cache in VRAM** | 50 ms | $300 \times 2 = 600$ ms | **650 ms** | **Decoding** (Memory Bandwidth) |
| **B: Cache in RAM** | 50 ms | $300 \times 15 = 4,500$ ms | **4,550 ms** | **Decoding** (PCIe Transfer) |

**Analysis:**
In both cases, decoding dominates the total time. However, moving the cache to RAM increases the decode time by **7.5x**. While the prefll (50 ms) is negligible compared to decoding, the *rate* at which decoding happens is strictly limited by the memory subsystem available for the KV cache. If the context grows to 8k tokens, the cache size might triple to ~4.5 GB, doubling the PCIe transfer time and further degrading latency, confirming that **decode latency is the primary constraint**, not the initial prompt processing speed.
