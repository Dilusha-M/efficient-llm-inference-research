### 1. KV Cache Lifecycle and Recomputation vs. Reuse
The inference workflow divides into two distinct phases with different memory access patterns:

*   **Prefill (Prompt Processing):** The model processes all 2,000 input tokens in parallel.
    *   **KV Cache Action:** For every layer, the attention mechanism computes $K$ and $V$ vectors for the entire input sequence. Since the input is new, **all** KV entries are freshly computed and written to the cache.
    *   **Reuse:** None. Every token generates new cache entries.
    *   **Hardware Stress:** Dominated by **weight bandwidth** (reading weights $N$ times) and **input token bandwidth**. Computation is memory-bound due to massive parallelism.

*   **Decode (Token-by-Token Generation):** The model generates one token at a time (steps 2001 to 2300).
    *   **KV Cache Action:** Only the *new* $K$ and $V$ for the current generated token are computed. The **entire existing cache** (2,000 previous tokens + previous outputs) is read in full for the attention calculation.
    *   **Reuse:** The full historical cache is reused. As the context grows, the volume of data read from HBM (High Bandwidth Memory) increases linearly.
    *   **Hardware Stress:** Dominated by **KV-cache bandwidth** (reading the growing cache) and **compute** (the transformer block operations are smaller in parallelism than prefill).

### 2. Decoupling Throughput and Latency
*   **Prompt Processing (High Throughput):** Prefill utilizes thousands of CUDA cores simultaneously. The GPU can saturate its memory bandwidth quickly, hiding latency. The "excellent tok/s" metric reflects this massive parallel throughput, not the time-to-first-token.
*   **Decoding (High Latency):** Decode is inherently serial. Each step must wait for the previous to finish before reading the updated cache and generating the next token.
*   **The Mismatch:** A system can have high prompt throughput (efficient batch processing) but high interactive latency because the **decode path is the critical path** for user-perceived speed. The "slowing down" as the conversation grows is a direct result of the **linear increase in memory reads** required for the attention mechanism as the cache expands.

### 3. Impact of Increasing Context (2k $\to$ 8k Tokens)
Moving from 2,000 to 8,000 tokens significantly degrades performance due to memory bandwidth saturation:

*   **Prefill:** Scales linearly with prompt length. Time $\propto 8k/2k = 4\times$ longer.
*   **Decode:** The bottleneck shifts dramatically. Attention complexity is $O(N)$ regarding memory bandwidth (where $N$ is context length).
    *   **Prefill Time:** Increases by factor of 4.
    *   **Decode Time per Token:** Increases by factor of 4 (reading 4$\times$ more cache data).
*   **Bandwidth Saturation:** On a 6 GB consumer GPU (likely 192-bit or 256-bit bus), the decode path will likely hit the memory wall much sooner than the prefill path. The latency will increase super-linearly if the system switches from a compute-bound to a memory-bound regime, or simply scales linearly with a steep constant.

### 5. Investigative Measurements and Comparisons
To distinguish the bottleneck, perform these three controlled experiments:

1.  **Isolate Weight Bandwidth (Prefill Bottleneck):**
    *   *Method:* Run a massive prefill task (e.g., 100k tokens) on the GPU with a tiny generation request (1 token).
    *   *Reasoning:* If the system is weight-bandwidth bound, this will be slow. If it is fast, but interactive latency is high, the issue is decode/KV-cache.
2.  **Isolate KV-Cache Traffic (Decode Bottleneck):**
    *   *Method:* Run a fixed prompt (2k) with varying generation lengths (1, 10, 100 tokens) and measure time-per-token. Plot Time vs. Context Length.
    *   *Reasoning:* A linear increase confirms memory bandwidth bound (reading cache). A super-linear spike suggests the GPU is trying to read too much data and falling back to slower mechanisms or swapping.
3.  **Isolate CPU-GPU Transfer (Offload Bottleneck):**
    *   *Method:* Compare latency of: (A) Full cache on GPU (OOM), (B) Full cache on RAM (current slow state), vs. (C) Using a library like `llama.cpp` with `--n-gpu-layers -1` (full offload) or `vLLM` with swap enabled to see if optimized paging improves latency over naive copying.
    *   *Reasoning:* If (C) is significantly faster than (B), the bottleneck is the inefficiency of the current offloading mechanism (naive memcpy) rather than the raw PCIe bandwidth.

### Numerical Example: Dominant Factors
*Assumptions:* 2,000 token prompt, 300 generated tokens.
*   **Prefill Work:** Reading weights for 2,000 tokens + writing 2,000 KV entries. Let's assume this takes **40 ms** due to high parallelism.
*   **Decode Work (300 steps):** Each step reads the full KV cache.
    *   At 2k context: Reading ~2k vectors. Assume 10 ms total for 300 steps ($\approx 33\mu s$/step).
    *   At 8k context: Reading ~8k vectors. Assume 40 ms total for 300 steps ($\approx 133\mu s$/step).

**Scenario A (Small Context):**
*   Total Time = 40 ms (Prefill) + 10 ms (Decode) = **50 ms**.
*   *Dominant Factor:* Prefill (80% of time).

**Scenario B (Large Context):**
*   Total Time = 40 ms (Prefill) + 40 ms (Decode) = **80 ms**.
*   *Dominant Factor:* Equal split. If context grows further to 32k, Decode becomes **160 ms**, making total time **200 ms**.
*   *Conclusion:* The "slow down" is purely the Decode component scaling with context size, eventually dominating the total latency despite the prefill remaining constant in cost (once the prompt is loaded).
