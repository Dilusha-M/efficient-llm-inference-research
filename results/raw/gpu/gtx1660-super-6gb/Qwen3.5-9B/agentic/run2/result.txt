# Requirements and Invariants

*   `model_path`: Path to the GGUF model file (required).
*   `backend`: Target execution backend (`cpu`, `cuda`, `vulkan`).
*   `config_file`: Path to JSON/YAML file defining model aliases and workload parameters.

*   `system_prompt`: The initial system instruction string.
*   `user_prompt`: The user input string.
*   `context_size`: Override for default 4096 (optional).
*   `max_tokens`: Override for default 256 (optional).
*   `temperature`: Override for default 0.7 (optional).
*   `cpu_threads`: Override for default 1 (optional).
*   `monitoring_flags`: Boolean flags enabling resource monitoring (optional).

**Artifacts**
*   `response.txt`: Raw text output generated by the model (required for audit).
*   `metadata.json`: Structured run information including inputs, hardware detection, and build info.
*   `metrics.json`: Performance data (tokens/sec, total time, memory usage) if available.
*   `raw_stdout.log`: Verbatim copy of `stdout` from the llama.cpp process.
*   `raw_stderr.log`: Verbatim copy of `stderr` from the llama.cpp process.
*   `prompt_hash.txt`: SHA-256 hash of the exact prompt string used.

**Success/Failure States**
*   **Success**: `response.txt` is non-empty, `metadata.json` is created, and the process exited with code 0.
*   **Model Failure**: `response.txt` exists but is empty or truncated; `metrics.json` may be missing or indicate an error; `raw_stderr.log` contains crash/abort messages.
*   **Monitor Failure**: `response.txt` and `metadata.json` exist; `metrics.json` is missing or contains null values for resource counters; no model crash occurred.
*   **Validation Failure**: Process exits immediately with code 1; no `response.txt` or `metadata.json` created.

**Experimental Identity Tuple**
A unique run is identified by the tuple: `(model_path, backend, hardware_label, context_size, max_tokens, prompt_hash, temperature, build_id, driver_version)`. Results must not be mixed if any element of this tuple differs.

**Ambiguity to Resolve**
*   **Partial Output Definition**: The specification states a model may fail after creating partial output. It is ambiguous whether a run containing 1 token of output followed by a crash counts as a "Success" state for throughput calculation or a "Failure." *Resolution required*: Define a minimum token threshold (e.g., 10 tokens) below which any run is treated as a failure for statistical analysis, regardless of exit code 0.

# State Machine

**Lifecycle Stages**
1.  **Validation**:
    *   Verify `model_path` exists and is a valid GGUF file.
    *   Parse `config_file` and resolve model aliases.
    *   Calculate `prompt_hash`.
    *   Detect hardware (CUDA version, Vulkan driver, CPU threads) and build info (llama.cpp version).
    *   *Action*: If validation fails, exit immediately, write `metadata.json` with `status: "validation_failed"` and error message, stop.
2.  **Launch**:
    *   Spawn the llama.cpp binary with specific arguments.
    *   Redirect `stdout` and `stderr` to temporary files in a unique temp directory.
    *   Apply timeout (e.g., 300s) to prevent hanging.
    *   *Action*: If spawn fails, transition to Finalization with `status: "launch_failed"`.
3.  **Monitoring**:
    *   If monitoring flags are set, poll OS-level resources (RSS memory, CPU usage) or query backend-specific tools (nvidia-smi, etc.).
    *   *Action*: If monitoring tools are missing or commands fail, log warning, do not crash, continue to Process Exit.
4.  **Process Exit**:
    *   Wait for the child process to terminate.
    *   Check exit code and signal.
    *   *Action*: If timeout or OOM signal received, transition to Finalization with `status: "timeout"` or `status: "oom"`.
5.  **Finalization**:
    *   Move temporary `stdout`/`stderr` to `raw_stdout.log`/`raw_stderr.log`.
    *   Read `response.txt`.
    *   Parse performance metrics from output; if parsing fails or data is incomplete, mark `metrics.json` as incomplete.
    *   Write `metadata.json` and `metrics.json` atomically.
    *   Determine final status:
        *   If `response.txt` has significant content and no crash: `status: "success"`.
        *   If `response.txt` is empty/truncated or exit code != 0: `status: "model_failure"`.
        *   If monitoring data is missing but run completed: `status: "success_partial_monitor"`.
    *   *Action*: Clean up temp directory (except kept logs).

**Error Handling Specifics**
*   **Timeout**: Terminate process forcibly. Mark as timeout failure. Do not attempt to parse partial stdout.
*   **OOM**: Catch SIGSEGV/SIGKILL. Mark as OOM failure.
*   **Malformed Performance Output**: If the expected metric line (e.g., `speed: X tokens/s`) is missing or unparseable, set metric fields to `null` and flag `metrics_valid: false` in metadata. Do not abort the run.
*   **Monitor Failure**: If an optional monitor command (e.g., `nvml`) fails, log the error to `stderr`, set corresponding metric fields to `null`, and proceed. Distinguish this from model failure.

# Auditable Design

**Component Boundaries (Shell Wrapper)**
*   **Entry Point**: `run_benchmark.sh`
    *   Parses CLI args.
    *   Calls Python validation script.
    *   Spawns the model process using `nohup`, `timeout`, and file redirection.
    *   Orchestrates the finalization logic.
*   **Validation Script**: `validate_run.py`
    *   Reads config, checks file existence, computes hashes, detects hardware/build info.
    *   Outputs a validated command string or exits with non-zero code.
*   **Metrics Parser**: `parse_metrics.py`
    *   Reads `response.txt` and `raw_stdout.log`.
    *   Uses regex to extract float values for speed, latency, etc.
    *   Handles unknown formats by logging a warning and returning `null` for unknown fields rather than crashing.
*   **Metadata Generator**: `generate_metadata.py`
    *   Aggregates inputs, hardware info, prompt hash, and parsed metrics.
    *   Writes JSON files.

**Metadata Schema (`metadata.json`)**
```json
{
  "run_id": "<uuid>",
  "timestamp": "<ISO8601>",
  "status": "<success|validation_failed|launch_failed|model_failure|timeout|oom>",
  "experimental_identity": {
    "model_path": "...",
    "backend": "...",
    "hardware_label": "...",
    "context": <int>,
    "generation_limit": <int>,
    "prompt_hash": "<sha256>",
    "temperature": <float>,
    "build_id": "...",
    "driver_env": "..."
  },
  "inputs": {
    "system_prompt": "...",
    "user_prompt": "..."
  },
  "monitoring": {
    "enabled": true/false,
    "available": true/false,
    "error": "<null or error message if unavailable>"
  },
  "artifacts": {
    "response_file": "response.txt",
    "raw_stdout": "raw_stdout.log",
    "raw_stderr": "raw_stderr.log"
  },
  "metrics_valid": true/false
}
```

**Atomic Write & Partial File Conventions**
*   **Atomic Writes**: All JSON outputs are written to a temporary file (`.tmp`) first. Only after a successful write is the filename updated via `os.replace()` (atomic rename). This prevents partial metadata files from being read if the runner crashes during write.
*   **Partial Output Preservation**: `response.txt` and logs are never truncated. Even if the process crashes mid-sentence, the file contains the exact bytes written before the crash.
*   **Prompt Preservation**: The exact prompt string passed to the model is stored in `metadata.json` under `inputs`. The `prompt_hash.txt` file contains the raw hash string.

**Preserving Stdout/Stderr**
*   The shell wrapper launches the process with `stdout` and `stderr` redirected to distinct files in a run-specific temp directory (e.g., `/tmp/bench_<run_id>/`).
*   These files are renamed to `raw_stdout.log` and `raw_stderr.log` during Finalization.
*   No filtering (e.g., `grep -v`) is applied to these files; they remain raw for manual audit.

# Analysis Integrity

**Preventing Misleading Throughput Comparisons**
*   **Filtering Criteria**: Before aggregating results, the analysis layer must verify `metrics_valid` is `true` in `metadata.json`.
*   **Token Count Validation**: Throughput is calculated as `tokens / seconds`. If the parser detects that the generated token count in `response.txt` is significantly lower than expected (e.g., due to a crash at token 5 vs expected 256), the run is flagged as `model_failure`.
*   **Zero-Duration Handling**: If a run completes in < 100ms (cold start overhead dominating), calculate throughput conservatively or exclude from average unless explicitly requested, noting the high variance.
*   **Partial Output Handling**: Runs where `response.txt` is truncated (detected by mismatch between `generation_limit` and actual output length) are excluded from throughput averages and marked as failures in the summary.

**Handling Unknown Output Formats**
*   **Parser Strategy**: The `parse_metrics.py` script should use a strict regex pattern matching llama.cpp's standard output format.
*   **Unknown Formats**: If the expected regex pattern is not found in `raw_stdout.log`, the parser must:
    1.  Log a warning to `stderr` indicating the format change.
    2.  Set metric fields to `null` or `0` as appropriate.
    3.  Set `metrics_valid` to `false` in `metadata.json`.
    4.  **Crucially**: Do not crash or throw an exception. The run is considered "success" regarding execution if `response.txt` exists, but "unknown metrics" regarding performance. This allows the run to be included in logs for manual inspection rather than being silently dropped.

# Pre-merge Review

**High-Risk Design Flaw 1: Conflating Monitor Failure with Model Failure**
*   **Risk**: If the monitoring subsystem fails (e.g., `nvidia-smi` missing), the current design might inadvertently mark the run as a failure if the status logic isn't strictly separated. This leads to false negatives in success rates.
*   **Fix**: Explicitly separate the `monitoring.available` flag in `metadata.json`. The `status` field must only be set to `model_failure` or `validation_failed` based on the model process exit code and output integrity, never based on the absence of optional monitoring data. Add a specific check in Finalization: if model exit code is 0 and `response.txt` is valid, status is "success" regardless of monitoring errors.

**High-Risk Design Flaw 2: Non-Atomic Metadata Writes**
*   **Risk**: If the runner crashes between parsing metrics and writing `metadata.json`, a subsequent read might see a partially written JSON file, causing the analysis pipeline to crash or interpret incomplete data as valid.
*   **Fix**: Enforce atomic writes using the "write-to-temp-then-rename" pattern for all JSON artifacts. Ensure the temp directory is created in a location where the OS guarantees atomicity of file renames (standard filesystems do). Do not write directly to the final filename.

**High-Risk Design Flaw 3: Ambiguous Handling of Unknown Output Formats**
*   **Risk**: If a new version of llama.cpp changes the output format (e.g., adds debug lines or removes the speed metric), the parser might fail to parse *any* metrics and potentially crash if exception handling is too eager. This could halt the entire benchmark suite.
*   **Fix**: Implement a "fail-open" strategy for the parser. If the expected metric lines are missing, set values to `null` and `metrics_valid` to `false` instead of raising an exception. Log a non-fatal warning to `stderr` so the run continues and the user can manually inspect `raw_stdout.log` to understand the format change.
