### Task 1 — quantization tradeoff

**Assumptions:**
*   The "8.0 GB" and "4.8 GB" file sizes represent the raw disk footprint of the quantized weights (Q8_0 and Q4_K_M respectively).
*   The GPU's "5.2 GB free" refers strictly to available VRAM at the start of inference.
*   The 8B model name implies a parameter count roughly consistent with current 8B architectures (approx. 7.5B parameters), but exact counts depend on the specific architecture.
*   VRAM usage includes model weights, KV cache, and framework overhead (activations, optimizer states if training, but here only inference).

**Analysis of Memory Pressure:**
*   **Q8_0 (8.0 GB file):** This format stores weights at 8-bit precision. While the *file* size is 8.0 GB, loading this onto a 6 GB GPU creates immediate **critical memory pressure**. Even if the raw weight loading fits (8.0 > 6.0 is false, but let's assume the file size includes metadata or the 8.0GB is a loose upper bound; strictly speaking, 8.0 GB weights cannot load into 5.2 GB free VRAM without offloading). If the 8.0 GB figure is the exact weight footprint, Q8_0 is **impossible** to load entirely on this GPU without offloading layers to system RAM. If offloading is enabled, the pressure shifts to the CPU-RAM bus bandwidth, creating a bottleneck where the GPU waits for weights.
*   **Q4_K_M (4.8 GB file):** This format stores weights at 4-bit precision. The 4.8 GB footprint fits comfortably within the 5.2 GB free VRAM (assuming a small margin for KV cache). This creates **low memory pressure** regarding weight loading, allowing the entire model to reside in high-bandwidth VRAM. However, it increases the risk of GPU OOM if the prompt is long enough to expand the KV cache beyond the remaining ~0.4 GB.

**Why File Size is Not a Complete Runtime Estimate:**
File size on disk ($S_{disk}$) is not equal to runtime memory usage ($S_{runtime}$) due to:
1.  **Framework Overhead:** Libraries like llama.cpp or PyTorch add buffers for activations, gradients (if mixed precision), and internal tensors that are not in the weight file.
2.  **KV Cache Growth:** During generation, the Key-Value cache grows linearly with context length. A 5.2 GB free slot might hold 4.8 GB of weights, leaving only 0.4 GB for a growing KV cache.
3.  **Page Table & Metadata:** OS and driver overhead consume a fraction of VRAM.
4.  **Quantization Scheme Variance:** Some quantization formats include extra metadata per block that slightly inflates the effective size compared to the raw file size.

**Required Quality/Performance Measurements:**
Before declaring one format better, these two measurements are necessary:
1.  **Per-Token Latency (Decode Speed):** Measured in tokens per second (tok/s). This determines responsiveness. Q4_K_M will likely show higher tok/s due to faster memory access, but Q8_0 might be comparable if the bottleneck is compute-bound rather than memory-bound.
2.  **Perplexity (PPL) or Semantic Similarity Score:** Measured on a held-out test set (e.g., PPL on WikiText-2 or BLEU/ROUGE on a generation task). This quantifies the accuracy loss due to quantization. Q4_K_M usually has a slight PPL penalty compared to Q8_0.

*Conclusion:* You cannot claim Q4 is always faster because if the GPU is compute-bound (e.g., H100), the reduced precision might not improve speed, and the memory savings only help if the model is memory-bound (e.g., older GPUs or very large contexts).

### Task 2 — conservative launch decision

**Assumptions:**
*   Total RAM = 16 GB.
*   Total GPU RAM = 6 GB.
*   Model Weights ($W$) = 5.0 GB.
*   Prompt tokens = 2,000; Generation tokens = 512.
*   The 5.0 GB weight figure is exclusive of KV cache.
*   System RAM is available for offloaded layers.

**Conservative Procedure for llama.cpp:**

1.  **Step 1: Determine Maximum Safe Context ($N_{max}$):**
    *   Estimate KV cache size per token. For an 8B model, a rough estimate is ~1.5–2.0 MB per token (depending on embedding dim and batch size). Let's assume a conservative 2.0 MB/token.
    *   Calculate required KV cache: $2,000 + 512 = 2,512$ tokens.
    *   Estimated KV Cache Size: $2,512 \times 2.0 \text{ MB} \approx 5.02 \text{ GB}$.
    *   *Critical Observation:* 5.02 GB (KV) + 5.0 GB (Weights) = 10.02 GB. This exceeds the 6 GB GPU.
    *   *Decision:* You **must** offload layers to system RAM.

2.  **Step 2: Configure `llama.cpp` Arguments:**
    *   **`-ngl 0` (or `-ngl 999` with specific flags):** Start with `-ngl 0` to offload *zero* layers to the GPU, forcing the entire 5.0 GB model into system RAM (16 GB available, which is sufficient).
    *   **Context Size (`-n`):** Do not launch with the full 2,512 tokens immediately. Start with a reduced context (e.g., `-n 512`) to fit the KV cache on GPU if desired, or keep it offloaded.
    *   **`-m 0` (Memory Mapping):** Ensure memory mapping is active if using large files.
    *   **`-b 1` (Batch Size):** Keep batch size small (1) to minimize fragmentation and overhead.

3.  **Step 3: Telemetry to Record:**
    *   **VRAM Usage:** Monitor peak VRAM usage during the first prompt evaluation.
    *   **Swap/Page Faults:** Monitor system RAM usage; if it approaches 16 GB, check for swapping activity (high latency indicator).
    *   **Decode Latency:** Measure tokens/sec. If offloading all layers (`-ngl 0`), latency will be dominated by the PCIe bus speed.
    *   **Error Logs:** Specifically look for `llama_memory_get_used` exceeding limits or CUDA errors.

4.  **What Constitutes an Unsafe/Misleading Success:**
    *   **Unsafe:** Launching with `-ngl 999` (all layers on GPU) without verifying that the KV cache fits, resulting in an immediate OOM crash or silent degradation (garbage values) if the system silently swaps VRAM to system RAM (which can cause massive latency spikes).
    *   **Misleading Success:** Reporting a speed of "X tok/s" based on a tiny 32-token prompt while the intended workload is 2,500 tokens. The cache size dynamics change drastically between these two; a test on 32 tokens will vastly overestimate performance for the full 2,500-token context.
    *   **Unsafe:** Ignoring the fact that 5.0 GB weights + 5.0 GB KV cache > 6 GB VRAM and attempting to force the model onto the GPU without layer offloading.

**Procedure Summary:** Start with `-ngl 0` (all layers on CPU) to guarantee the 5.0 GB weights fit in the 16 GB system RAM. Gradually increase `-ngl` only if telemetry shows CPU memory pressure or acceptable latency. Always validate with the full context length (2,512 tokens), not a short test prompt.

### Task 3 — robust aggregation

**Logic:**
1.  Validate each record: Check for error flags (e.g., "out-of-memory").
2.  Keep the failed run's data visible (do not drop it or set speed to 0).
3.  Calculate statistics (median) only on the subset of successful runs.
4.  Handle the edge case where fewer than 2 runs succeed.

**Pseudocode:**

```python
def aggregate_decode_speeds(records):
    """
    records: list of dicts with keys 'speed_tok_s' and 'status' (e.g., 'success', 'oom')
    """
    
    # 1. Validate and classify records
    successful_runs = []
    failed_runs = []
    
    for record in records:
        if record['status'] == 'success':
            successful_runs.append(record['speed_tok_s'])
        else:
            # Keep failed run visible
            failed_runs.append({
                'speed': record['speed_tok_s'], # Keep the raw number or NaN
                'error': record['error_msg']
            })
            
    # 2. Compute Median for Successful Runs
    if len(successful_runs) < 2:
        # Edge case: Cannot compute a robust median
        return {
            'status': 'INSUFFICIENT_DATA',
            'message': f"Only {len(successful_runs)} successful run(s). Median undefined.",
            'successful_runs': successful_runs,
            'failed_runs': failed_runs
        }
    
    successful_runs.sort()
    n = len(successful_runs)
    # Median calculation
    if n % 2 == 1:
        median_speed = successful_runs[n // 2]
    else:
        median_speed = (successful_runs[n // 2 - 1] + successful_runs[n // 2]) / 2
        
    return {
        'median_speed': median_speed,
        'successful_runs_count': n,
        'failed_runs': failed_runs # Explicitly listing failures
    }

# Example Usage
input_data = [
    {'speed_tok_s': 42.0, 'status': 'success'},
    {'speed_tok_s': 41.5, 'status': 'success'},
    {'speed_tok_s': 8.0, 'status': 'oom', 'error_msg': 'out-of-memory'}
]

result = aggregate_decode_speeds(input_data)
print(f"Median: {result['median_speed']}")
print(f"Failed runs preserved: {result['failed_runs']}")
```

**Reporting Strategy if Fewer Than Two Runs Succeed:**
Do not report a single number or an average. Report the dataset as **statistically invalid for median calculation**. State explicitly: "Median cannot be computed due to insufficient successful samples (N < 2). The single successful run reported is {X} tok/s, but this is subject to high variance and may not represent the system's stable performance." Include the failed run details to explain the instability (e.g., "Run 3 failed due to OOM").

### Task 4 — validity audit

**Context:** CPU (8 threads) vs. CUDA (full offload) vs. Vulkan (full offload). Each run 3 times.

**Threat 1: Thermal Throttling / Frequency Drift**
*   **Threat:** Running three consecutive heavy inference tasks in quick succession causes GPU or CPU temperatures to rise, leading to frequency scaling (throttling). The 3rd run will be slower than the 1st, introducing noise unrelated to backend efficiency.
*   **Control/Disclosure:** Insert a cooling interval or monitor temperature metrics. Disclose if the 3rd run was performed on a thermally degraded device. Report only the first run or average after thermal equilibrium is reached.

**Threat 2: PCIe Bus Contention / Memory Bandwidth Saturation**
*   **Threat:** CUDA and Vulkan offloading all layers to the GPU means they rely heavily on PCIe bandwidth. If the CPU (8 threads) is used for preprocessing or if the system has only one PCIe slot, the "CPU" baseline might be artificially fast if it doesn't saturate the PCIe bus, or conversely, the GPU baselines might be slower due to PCIe saturation rather than compute limits. The 8-thread CPU limit might also starve the PCIe transfer if other processes are running.
*   **Control/Disclosure:** Ensure the PCIe bus is dedicated or measure throughput with a memory-bound benchmark. Disclose the PCIe lane width (e.g., x16 vs x8) and whether the CPU is the bottleneck for data movement.

**Threat 3: Workload/Output Comparability (Precision/FP16 vs FP32)**
*   **Threat:** Different backends might default to different floating-point precisions or handle quantization differently (e.g., CUDA might use INT8 kernels while CPU uses FP32). If the comparison is based on raw token counts without checking the *actual output quality*, a backend might appear faster because it outputs garbage faster or skips certain normalization steps.
*   **Control/Disclosure:** Force all backends to use identical precision settings (e.g., FP16 or BF16) and verify that the generated text is semantically identical across backends. Disclose if one backend uses a different kernel implementation that bypasses a specific normalization step.

**Threat 4: Scheduling and Context Switching Artifacts**
*   **Threat:** The CPU backend (8 threads) might benefit from hyper-threading or different scheduling policies compared to the GPU backends, which run asynchronously. The "3 runs" might include varying amounts of OS scheduling noise, making the CPU runs appear faster or slower depending on thread affinity.
*   **Control/Disclosure:** Pin CPU threads to specific cores for the CPU backend and disable hyper-threading during the test. Disclose the OS scheduler type (e.g., CFS vs. RT) and whether GPU drivers introduced latency spikes during context switching.

### Task 5 — user-visible latency

**Explanation of Terms:**
*   **Time to First Token (TTFT):** The time elapsed from pressing "Generate" until the first character appears. This depends heavily on how quickly the model processes the prompt and computes the first hidden state.
*   **Prompt-Evaluation Throughput:** The rate (tok/s) at which the model processes the input prompt (2,000 tokens) to generate the initial logits. This is often the bottleneck for long prompts.
*   **Decode Throughput:** The rate (tok/s) at which the model generates new tokens once the first token is produced. This is usually memory-bandwidth bound and consistent per token.
*   **Total Wall-Clock Time:** The sum of time spent processing the prompt plus the time spent generating the response.

**Symbolic Equation:**
Let $T_{prompt}$ be the time to process the prompt and $N_{prompt}$ be the number of prompt tokens.
Let $T_{decode}$ be the time to generate each new token and $N_{gen}$ be the number of generated tokens.
Let $TTFT$ be the time to first token (which includes the time to process the prompt up to the generation of the 1st token).

$$ T_{total} = T_{TTFT} + (N_{gen} - 1) \times \frac{1}{\text{Decode Throughput}} $$

*Note: $T_{TTFT}$ implicitly contains the processing of the prompt. The term $(N_{gen} - 1)$ accounts for the fact that the first token is already included in $T_{TTFT}$.*

**Example of Minimal Impact Optimization:**
Consider a scenario where the model is **compute-bound** or the prompt is extremely short relative to the generation limit, but more importantly, consider a scenario where **prompt processing is already optimized** or the bottleneck is strictly the **decode phase**.

*   **Scenario:** A user asks a question with a 2,000-token context. The model takes 10 seconds to process the prompt ($T_{prompt}$) and outputs the first token. The decode speed is 50 tok/s. The user needs 200 tokens.
*   **Calculation:**
    *   $T_{TTFT} \approx 10 \text{ s}$ (assuming prompt processing dominates the wait).
    *   Remaining tokens to generate: 199.
    *   Decode time: $199 / 50 = 4.0 \text{ s}$.
    *   $T_{total} = 10 + 4 = 14 \text{ s}$.
*   **Optimization:** Suppose we optimize the prompt processing algorithm by 20% (reducing $T_{prompt}$ from 10s to 8s).
    *   New $T_{TTFT} = 8 \text{ s}$.
    *   New $T_{total} = 8 + 4 = 12 \text{ s}$.
*   **User Experience:** The user sees the first character at 8s instead of 10s. However, if the user is reading the *content*, they are reading 200 tokens. The total time saved is 2 seconds.
*   **Barely Changes Experience Case:** If the user's perception of "latency" is dominated by the **total duration** of the answer appearing (e.g., reading a long summary), saving 2 seconds on a 12-second response is a 16% improvement. BUT, if the user cares about **instant feedback** (chatbot feel), the 2-second drop is significant.
*   **Counter-Example (Barely Changes):** If the prompt was only 10 tokens, $T_{TTFT}$ might be 0.5s. Optimizing prompt processing to reduce it to 0.4s saves 0.1s. In a 14s total response, 0.1s is imperceptible. The user experience changes negligibly because the **decode phase** (generating the 200 tokens) dominates the total time, and optimizing the prompt processing (which is a tiny fraction of the total work) barely changes the user's experience of waiting for the full response.

**Clarification on tok/s:**
Do not equate "high tok/s" with "low latency" without specifying the phase. A model can have 100 tok/s decode speed (fast generation) but terrible TTFT (slow prompt processing), resulting in a high total latency for long prompts. Conversely, a slow decoder (10 tok/s) with instant TTFT feels "responsive" initially but drags on for long answers.
