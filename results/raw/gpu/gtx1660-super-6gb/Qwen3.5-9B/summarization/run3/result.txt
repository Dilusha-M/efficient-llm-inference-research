Technical document:

Large language model inference on consumer hardware is constrained by a combination of memory capacity, memory bandwidth, compute throughput, software backend maturity, and workload shape. Unlike training, inference is often dominated by repeated matrix-vector operations during autoregressive decoding. During prompt processing, the model can evaluate many tokens in parallel, using matrix-matrix operations that may achieve higher hardware utilization. During decoding, one token is generated at a time, and the model repeatedly reads large quantities of weights and key-value cache data. This shift means that prompt evaluation throughput and decode throughput should be measured separately.

The key-value cache is central to decoder-only transformer inference. For each generated or processed token, attention layers store key and value tensors so that later tokens can attend to previous context without recomputing all prior activations. This improves computational efficiency but increases memory usage roughly with context length, number of layers, hidden size, and cache precision. On resource-constrained systems, the cache can become a major memory consumer. If the cache spills into system memory or causes paging, latency can become unstable. Consumer GPUs with limited VRAM may perform well at short context lengths but degrade when the model weights and cache no longer fit comfortably.

Model quantization changes the tradeoff between quality, memory footprint, and throughput. Higher precision formats such as Q8_0 generally require more memory but may preserve model quality better. Lower precision formats such as Q4 variants reduce memory requirements and may allow larger models to run on smaller devices. However, throughput does not always improve linearly with smaller quantization because kernels, backend support, memory alignment, and dequantization overhead matter. A benchmark should record the exact GGUF filename and quantization type because two files with the same parameter count may have different practical performance characteristics.

Backend selection also changes the result. A CPU backend depends heavily on core count, clock speed, vector instruction support, cache hierarchy, and memory bandwidth. CUDA performance depends on NVIDIA GPU architecture, VRAM capacity, driver version, power limits, and the number of model layers offloaded to the GPU. Vulkan can provide broader GPU support but may have different kernel maturity, scheduling behavior, and memory management characteristics. Comparing CPU, CUDA, and Vulkan backends requires careful documentation of binary versions, build options, driver versions, and runtime parameters.

Hardware labels should be stable and human-readable. A label such as cpu/ryzen5600 identifies a CPU-only test context, while gpu/rtx2060-12gb identifies a GPU test context. Multi-GPU labels should explicitly identify the device combination. Labels are not substitutes for system metadata; each run should still capture CPU model, RAM capacity, GPU model, VRAM capacity, driver version, operating system, and relevant environment information. The label is a path and grouping convention, while metadata is the evidence needed for reproducibility.

Workloads should represent different inference patterns. A chat workload can test general explanatory response generation. A coding workload can test structured reasoning and code production. A summarization workload should include a long prompt, stressing prompt processing and context handling. A batch workload can include several unrelated tasks in one prompt, representing users who submit grouped questions. An agentic workload can simulate a coding agent planning and reviewing a solution without using external tools. Fixed prompts are important because small changes in prompt length and content can affect tokenization, prompt processing time, and generation behavior.

Repeated runs are necessary because performance on consumer systems can vary. Thermal throttling, background processes, power management, GPU boost behavior, and memory pressure can all alter throughput. A minimum of three runs per condition helps reveal instability, though more runs may be needed for statistical confidence. Runs should be stored separately rather than only aggregated. Raw outputs allow later re-parsing when extraction logic improves, and per-run metadata makes it possible to diagnose anomalies.

The benchmark runner should capture llama.cpp performance output using the built-in performance reporting flag. The important values include prompt evaluation time, number of prompt tokens, prompt evaluation tokens per second, decode evaluation time, generated tokens, and decode tokens per second. The runner should preserve the full stdout and stderr stream in a result file because llama.cpp output formatting can change between versions. A parser can extract known metrics while leaving the raw file available for manual inspection.

Resource monitoring should be sampled during the run. NVIDIA GPU monitoring can use nvidia-smi to capture timestamp, power draw, temperature, memory usage, and utilization. CPU and RAM monitoring can use standard Linux interfaces such as /proc/stat, /proc/meminfo, uptime, and sensors when available. Not all metrics will be available on every machine. Missing values should be recorded as blank or null rather than causing the benchmark to fail. The framework should distinguish between a failed model run and missing auxiliary monitoring data.

Time to first token is useful but may not always be available from llama.cpp output. If the runner cannot measure it reliably without changing the inference process, it should record a null value instead of inventing a number. Total generation time can be measured externally around the command invocation, while prompt and decode times should be extracted from llama.cpp performance output. Researchers should be clear about which timings come from the model runtime and which come from the wrapper script.

Failure handling is part of the experiment. A benchmark may fail because the model file is missing, the backend binary is unavailable, the context length is too large, VRAM is insufficient, GPU drivers are misconfigured, or the model cannot be loaded. These failures are meaningful data points when studying resource-constrained hardware. Each run should write metadata indicating success or failure, an error message when available, and enough context to reproduce the attempt.

Processed CSV output is useful for analysis, but it should not replace raw artifacts. The CSV should include experiment identifier, date, hardware label, backend, model, workload, context length, prompt tokens, generated tokens, prompt evaluation throughput, decode throughput, time to first token, total time, RAM usage, VRAM usage, GPU power, GPU temperature, and status. Additional columns may be useful later, but a stable baseline schema supports notebooks, plots, and tables.

Reproducibility depends on controlling and recording configuration. The benchmark should store the model alias, resolved model path, backend, binary path, prompt file, context length, generation length, temperature, GPU layer count, run index, and timestamp. It should also store hardware metadata and resource monitor samples. If a researcher changes a prompt, model file, build, or runtime parameter, the resulting experiment should be considered a different condition.

There are several threats to validity. First, generated token count can vary when sampling is enabled, so benchmarks may prefer deterministic settings or fixed generation limits. Second, model quality is not measured by throughput alone, and lower precision quantization may change output quality. Third, comparing different backends may compare both hardware and software maturity rather than hardware alone. Fourth, consumer systems are affected by thermal and power behavior. Fifth, a single prompt may not represent broad real-world use. A careful study should acknowledge these limits and avoid overgeneralizing from a small set of devices and workloads.

In summary, a useful consumer-hardware LLM inference benchmark should separate prompt processing from decoding, preserve raw outputs, record hardware and model metadata, monitor resources, repeat runs, and use fixed workloads. The framework should be simple, inspectable, and robust to missing optional metrics. Its purpose is not to hide variability but to expose it in a form that can be analyzed and reported transparently.

Additional methodology details:

A benchmark condition should be treated as a tuple containing model file, backend, hardware label, context length, generation limit, prompt file, temperature, GPU layer count, llama.cpp build, and driver environment. If any element of that tuple changes, the result should not be mixed with earlier results without a clear explanation. This matters because a single throughput number can hide multiple causes. For example, raising the context length may reduce decode throughput because the attention cache grows, while changing quantization may reduce memory pressure but alter kernel behavior. Similarly, a newer backend build may improve performance independently of the hardware.

Researchers should decide whether they are measuring maximum achievable throughput or realistic interactive performance. A maximum-throughput experiment might close background applications, lock power settings, warm up the model, and run under controlled thermal conditions. A realistic consumer-hardware experiment might intentionally use ordinary desktop settings but record system load and power behavior. Both approaches can be valid, but they answer different questions. The experiment documentation should state which interpretation is intended.

Prompt token counts should be taken from the inference runtime when possible because tokenization depends on the model vocabulary and chat template. Estimating prompt length from words or characters is not sufficient for analysis. A summarization workload with several thousand tokens stresses the prompt processing path and key-value cache allocation. A short chat prompt stresses decoding more heavily. A coding prompt may produce longer structured outputs, which can make sampling variability more visible. Batch prompts combine several independent tasks and can reveal whether the model maintains instruction separation across a longer input.

The runner should preserve failed attempts because failure is an empirical observation. If a model cannot load on a 4 GB GPU with a given offload setting, that result is relevant to resource-constrained inference. The metadata should record failure status and the final error output rather than silently skipping the condition. Later analysis can classify failures separately from successful throughput measurements. This avoids survivorship bias where only successful runs are plotted and smaller devices appear more capable than they were in practice.

Monitoring samples should be interpreted carefully. GPU utilization from nvidia-smi is a sampled device-level metric, not a direct measurement of kernel efficiency. Power draw and temperature can lag behind instantaneous workload changes. CPU utilization can be difficult to interpret on systems with simultaneous multithreading or heterogeneous cores. RAM usage from the operating system includes caches and other processes. These limitations do not make the metrics useless, but they mean the analysis should report them as contextual indicators rather than exact causal explanations.

For CPU-only tests, the number of threads can strongly influence performance. If the runner relies on llama.cpp defaults, that choice should be recorded. If thread counts are fixed, they should be part of the experimental tuple. Memory speed and channel configuration may matter as much as core count for quantized models. Older desktop processors and laptop CPUs may have very different sustained power behavior even when their short-run benchmark scores look similar. A careful hardware table should include CPU model, core count, thread count, RAM capacity, and any known memory configuration.

For GPU tests, layer offload is a major independent variable. Offloading all layers may be fastest when the model and cache fit in VRAM, but partial offload can be necessary on smaller cards. Too much offload can cause allocation failure or severe slowdown if memory is oversubscribed. Multi-GPU configurations introduce additional complexity because layer placement, interconnect bandwidth, and driver scheduling can affect results. A label such as rtx2060+gtx1660super is useful for grouping, but the metadata should still capture each visible GPU and its memory capacity.

The processed CSV should be regarded as a derived artifact. It is convenient for notebooks, plots, and statistical summaries, but it should be regenerated from raw run directories whenever parser logic changes. Raw result files are the primary source because they contain the exact llama.cpp output. Metadata files are the second source because they record configuration and status. Monitor CSV files are supporting evidence. This separation makes the framework auditable: another researcher can inspect a raw run, compare it with the parsed row, and decide whether the extraction was correct.

Statistical reporting should avoid overclaiming from three repetitions. Three runs can expose obvious instability and provide a rough median, but they are not enough to characterize all variance sources. A thesis or paper should report the number of repetitions, aggregation method, and whether failed runs were included in denominator counts. Median throughput is often more robust than mean throughput when one run is affected by background activity, while maximum throughput may be useful for showing best-case capability. Confidence intervals require more careful experimental design.

The framework should keep prompts deterministic and versioned. If prompts are edited during the project, old results should remain associated with the old prompt content. A simple approach is to store the prompt file path and keep prompt files under version control. A stronger approach is to store a prompt hash in metadata. That makes it possible to detect accidental prompt edits. The same principle applies to model files: recording the alias is convenient, but recording the resolved filename and path is necessary for reproducibility.

Temperature and sampling settings can affect generation length, content, and sometimes throughput. A fixed maximum token count limits the upper bound, but models may stop early depending on end-of-sequence behavior. Deterministic decoding can reduce content variability, while sampled decoding may better reflect interactive usage. The selected policy should be consistent across compared conditions unless the experiment explicitly studies decoding settings. When outputs differ in length, decode tokens per second is usually more comparable than total wall-clock time, but total time remains important for user experience.

Finally, benchmark automation should stay simple enough to inspect. Shell scripts are appropriate for invoking binaries, arranging directories, and starting monitors. Python standard-library code is appropriate for parsing structured files and producing CSV output. Adding large orchestration frameworks too early can make the experiment harder to reproduce on older machines. The main goal is to ensure that every result can be traced back to a model, prompt, command line, hardware snapshot, raw output, and parser rule.
