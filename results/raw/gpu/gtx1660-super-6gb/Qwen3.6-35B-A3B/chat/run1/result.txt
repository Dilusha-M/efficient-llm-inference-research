Scenario:
A 7B decoder-only model is served on a 6 GB consumer GPU with 32 GB system RAM. The model weights fit on the GPU, but the key-value (KV) cache does not always fit there. A user sends a 2,000-token prompt and requests 300 generated tokens. The system reports excellent prompt-processing throughput but becomes much slow ... (truncated)
### 1. KV Cache Lifecycle and Reuse
*   **Prefill (Prompt Processing):** The 2,000 tokens are processed in parallel. The model computes the attention scores for all positions. The resulting $N \times d_{model}$ Key-Value pairs are written to the KV cache. This phase is **Compute-Bound** (high arithmetic intensity) and utilizes the GPU’s high-throughput tensor cores.
*   **Decode (Token Generation):** For each subsequent token, the model computes the attention for the *current* token only. It must read the entire existing KV cache (all previous $k$ tokens) to attend to them. The new KV pair is appended to the cache. This phase is **Memory-Bound**.
*   **Reuse vs. Recomputation:** The KV cache is **reused** to avoid recomputing attention for past tokens. Without the cache, decoding would require $O(k^2)$ recomputation per step; with the cache, it is $O(k)$ memory reads.

### 2. Why High Prompt Tok/s ≠ Low Interactive Latency
*   **Parallelism vs. Serialism:** Prefill processes 2,000 tokens simultaneously. Decode processes 1 token at a time, serially dependent on the previous step.
*   **Resource Stress:**
    *   **Prefill:** Limited by FLOPs (floating-point operations). A 6 GB GPU can saturate its compute units quickly.
    *   **Decode:** Limited by **Memory Bandwidth**. Each token generation requires reading the entire KV cache (which grows linearly with context) and the model weights. The ratio of arithmetic operations to memory bytes accessed (arithmetic intensity) drops drastically in decode, making it bandwidth-bound.
*   **Conclusion:** A high prompt throughput indicates good compute utilization, but decode latency is dictated by how fast data can be moved from memory to the compute units, not how fast the compute units can process them.

### 3. Impact of Increasing Context from 2,000 to 8,000 Tokens
*   **KV Cache Size:** Scales linearly. For a 7B model with `bf16` KV heads and 32 layers, cache size $\approx 2 \times \text{layers} \times \text{hidden\_dim} \times \text{tokens} \times 2 \text{ bytes}$. Increasing context 4x increases KV cache size 4x.
*   **Decode Latency:** Increases linearly with context length. Each decode step must read a larger KV cache. If the KV cache exceeds GPU memory (6 GB), it spills to system RAM (32 GB).
*   **Memory Bandwidth Bottleneck:**
    *   On-GPU RAM bandwidth: ~500–1,000 GB/s.
    *   PCIe Bandwidth (CPU-GPU): ~15–32 GB/s (Gen3/Gen4).
    *   **Spill Effect:** If KV cache spills to RAM, the effective bandwidth drops by 10–50x, causing per-token latency to spike dramatically. Even on-GPU, larger context means more data to fetch per token, saturating memory bandwidth faster.

### 4. True Claims vs. Implementation-Dependent Claims
| Claim | Status | Reasoning |
| :--- | :--- | :--- |
| Decode latency scales linearly with context length. | **Generally True** | Attention mechanism requires reading all previous KV pairs. |
| Prefill is compute-bound; decode is memory-bound. | **Generally True** | For decoder-only models, arithmetic intensity drops sharply in decode. |
| Spilling KV cache to RAM always causes significant latency. | **Implementation-Dependent** | Depends on PCIe speed, kernel optimization (e.g., paged attention), and whether the system uses zero-copy memory. |
| KV cache precision (FP16 vs. INT8) halves memory traffic. | **Implementation-Dependent** | Only if the kernel supports quantized KV caching and attention computation. |
| GPU offload (part of model on CPU) helps decode. | **False** | Offloading model weights to CPU during decode usually *worsens* latency due to PCIe bandwidth limits, unless batch size is huge and memory is severely constrained. |

### 5. Three Measurements to Identify Bottleneck

1.  **Isolate KV Cache Traffic:**
    *   **Test:** Fix context length at a small value (e.g., 100 tokens) where KV cache fits entirely in GPU L2/VRAM. Measure decode latency. Then, increase context until KV cache spills to system RAM.
    *   **Interpretation:** If latency jumps significantly at the spill point, **PCIe bandwidth** is the bottleneck. If latency increases linearly but smoothly, **GPU memory bandwidth** is the bottleneck.

2.  **Isolate Weight Traffic:**
    *   **Test:** Use a very short context (e.g., 10 tokens) but vary the batch size (number of concurrent sequences). Or, compare latency with and without weight quantization (if supported).
    *   **Interpretation:** If latency scales linearly with batch size or drops significantly with quantization, **weight memory bandwidth** is the bottleneck. Note: For a single sequence, weight traffic is constant per step; KV cache traffic grows.

3.  **Isolate Compute Bound:**
    *   **Test:** Measure the ratio of GPU utilization (SM active cycles) vs. memory controller activity. Use profiling tools (Nsight Systems).
    *   **Interpretation:** If SM utilization is high but memory throughput is low, the bottleneck is **compute** (unlikely in decode for large models). If memory throughput is saturated and SM utilization is low, it is **memory-bound**. If CPU-GPU transfer rates are near PCIe max, the bottleneck is **host-device transfer**.

### Numerical Example: Dominance of Decode vs. Prefill

**Assumptions:**
*   Model: 7B params, `bf16` weights (14 GB), `bf16` KV cache.
*   GPU: 6 GB VRAM, 500 GB/s bandwidth.
*   Context: 2,000 tokens prompt, 300 tokens generation.
*   KV Cache Size for 2,000 tokens: ~2 GB (fits in GPU).
*   KV Cache Size for 300 tokens: ~0.3 GB.
*   Total KV Cache during decode: ~2.3 GB.
*   Memory Bandwidth: 500 GB/s.
*   Compute Power: 100 TFLOPS (saturated in prefill).

**Prefill Time (Compute-Bound):**
*   Operations: ~$2 \times 7 \times 10^9 \times 2000 \approx 28 \times 10^{12}$ FLOPS.
*   Time: $28 \times 10^{12} / 100 \times 10^{12} = 0.28$ seconds.
*   *(Note: This is an estimate; actual time depends on kernel efficiency.)*

**Decode Time (Memory-Bound):**
*   For each of the 300 tokens:
    *   Read KV Cache: ~2.3 GB (grows from 2.0 to 2.3 GB).
    *   Read Weights: 14 GB (fully loaded for each token in naive implementation, but often optimized). Let's assume weight caching in L2 reduces this. Dominant cost is KV cache read.
    *   Memory Traffic per token: ~2.3 GB (KV) + ~0.1 GB (other) = ~2.4 GB.
    *   Time per token: $2.4 \text{ GB} / 500 \text{ GB/s} = 0.0048$ seconds = 4.8 ms.
*   Total Decode Time: $300 \times 0.0048 = 1.44$ seconds.

**Comparison:**
*   Prefill: 0.28 s
*   Decode: 1.44 s
*   **Total:** 1.72 s
*   **Conclusion:** In this scenario, decode latency dominates (~84% of total time). If context increases to 8,000 tokens, KV cache size becomes ~8 GB (spills to RAM). Assuming PCIe bandwidth of 20 GB/s:
    *   Memory Traffic per token: ~8.3 GB.
    *   Time per token: $8.3 / 20 = 0.415$ seconds.
    *   Total Decode Time: $300 \times 0.415 = 124.5$ seconds.
    *   **Result:** Decode time becomes 124.5 s vs. Prefill 0.28 s. **Decode is overwhelmingly dominant.**
