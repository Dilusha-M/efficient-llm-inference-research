### Task 1 — Quantization Tradeoff

**Memory Pressure Analysis**
*   **Q8_0 (8.0 GB file):** The file size (8.0 GB) significantly exceeds the available GPU memory (5.2 GB free). Therefore, **100% of the model weights must be offloaded to system RAM (CPU)**. The GPU will only hold the active KV cache and compute buffers. This creates high CPU-to-GPU bandwidth pressure and high CPU RAM usage, likely resulting in slow inference due to PCIe transfer bottlenecks if layers are swapped, or simply heavy CPU load if all weights reside in RAM.
*   **Q4_K_M (4.8 GB file):** The file size (4.8 GB) fits within the free GPU memory (5.2 GB). Therefore, **all model weights can reside on the GPU**. This minimizes data transfer overhead during inference (assuming the KV cache also fits). The primary memory pressure comes from the **KV cache**, which grows with context length.

**Why File Size $\neq$ Runtime Memory**
File size represents the *static* storage footprint of the model weights. It does not account for:
1.  **KV Cache:** Dynamic memory required to store key-value pairs for the context window. This can consume gigabytes depending on context length and batch size.
2.  **Activation Buffers:** Temporary memory for intermediate tensor computations.
3.  **Overhead:** Memory allocators, thread stacks, and library overheads.
4.  **Fragmentation:** Available contiguous memory blocks may be less than total free memory.

**Two Quality/Performance Measurements Needed**
Before declaring Q4_K_M better (despite its likely speed advantage from GPU residency), you must measure:
1.  **Perplexity (PPL) or Task-Specific Accuracy:** Quantization introduces approximation errors. Q4_K_M may degrade performance on complex reasoning or precise factual recall tasks compared to Q8_0. You need empirical evidence that the accuracy loss is acceptable for your use case.
2.  **Tokens per Second (tok/s) or Latency per Token:** While Q4 on GPU is *typically* faster, you must measure actual throughput. However, note that if the KV cache is large, the GPU might run out of memory even if weights fit, causing fallback to CPU or swapping, which negates the speed benefit. Thus, measuring stable tok/s under the *actual* target context length is critical.

**Note:** Q4 is not *always* faster. If the context is very long, the KV cache might exceed the remaining 0.4 GB on the GPU (5.2 GB free - 4.8 GB weights), forcing the KV cache onto the CPU, which could make Q4 slower than Q8 if Q8’s CPU-based inference is better optimized for that specific hardware or if the Q8 model’s higher precision allows for fewer retries in speculative decoding (if used).

### Task 2 — Conservative Launch Decision

**Assumptions**
*   The 5.0 GB weight size is *only* for model parameters.
*   KV cache memory is *not* included in the 5.0 GB.
*   System RAM (16 GB) is available for CPU offloading and KV cache if needed.
*   GPU VRAM (6 GB) is the primary constraint for speed.

**Conservative Procedure**

1.  **Estimate KV Cache Size:**
    *   Calculate the approximate memory required for the KV cache for 2,000 input tokens + 512 output tokens = 2,512 tokens.
    *   Formula: $Memory_{KV} \approx 2 \times \text{num\_layers} \times \text{head\_dim} \times \text{num\_heads} \times \text{context\_len} \times \text{datatype\_size}$.
    *   Assume a typical 7B–8B model uses ~4–8 GB VRAM for KV cache at 2k context. This is a *large* fraction of the 6 GB GPU.

2.  **Initial Strategy (Max GPU Offload with Safety Margin):**
    *   Allocate **4.0 GB** of the 5.0 GB weight budget to the GPU. Leave **1.0 GB** of weights on CPU RAM.
    *   *Why?* This reserves ~1.6 GB (5.2 GB free - 4.0 GB weights) of GPU memory for the KV cache and activation buffers. This is still tight but safer than loading all weights.

3.  **Execution & Telemetry:**
    *   Set `--n-gpu-layers` to offload as many layers as possible within the 4.0 GB weight limit.
    *   Set `--ctx-size` to 2,048 (power of 2, close to 2,000).

### Task 3 — Robust Aggregation

**Pseudocode**

```python
function compute_robust_median(runs):
    # runs: list of dictionaries, each with 'speed' (float) and 'status' (str)
    
    successful_runs = []
    failed_runs = []
    
    # 1. Validate and Separate
    for run in runs:
        if not run.has_key('speed') or not run.has_key('status'):
            continue # Skip malformed records
        
        speed = run['speed']
        status = run['status']
        
        # Check for OOM or explicit failure
        if status == 'FAILED' or status == 'OOM' or speed <= 0:
            failed_runs.append(run)
        else:
            successful_runs.append(speed)
            
    # 2. Report if insufficient data
    if len(successful_runs) < 2:
        return {
            'median': None,
            'error': 'Insufficient successful runs to compute median. Found: ' + str(len(successful_runs)),
            'failed_runs': failed_runs,
            'successful_runs_count': len(successful_runs)
        }
    
    # 3. Compute Median of Successful Runs
    successful_runs.sort()
    n = len(successful_runs)
    if n % 2 == 1:
        median = successful_runs[n // 2]
    else:
        median = (successful_runs[n // 2 - 1] + successful_runs[n // 2]) / 2.0
        
    # 4. Return Result with Visibility of Failures
    return {
        'median': median,
        'failed_runs': failed_runs, # Keep visible
        'successful_runs': successful_runs
    }
```

**Reporting if Fewer Than Two Runs Succeed:**
The result should be reported as **`NaN` (Not a Number)** or **`undefined`** for the median, with a clear error message stating the number of successful runs (0 or 1). The failed runs must be included in the output for debugging. Do not average in failed runs (which might be 0) as this would skew the median toward zero, hiding the performance issue.

### Task 4 — Validity Audit

**Threat 1: Output Comparability (Workload)**
*   **Threat:** The CPU, CUDA, and Vulkan backends may not produce identical outputs due to differences in floating-point precision, reduction order, or kernel implementations. This makes it impossible to determine if performance differences are due to speed or correctness.
*   **Control/Disclosure:** Run a **determinism test**: Generate the same prompt on all three backends and compare the output token IDs and logits for the first 100 tokens. Disclose the maximum absolute difference in logits or the number of divergent tokens. If outputs diverge, the comparison is invalid for accuracy-sensitive tasks.

**Threat 2: Hardware State Contamination**
*   **Threat:** The three backends are run sequentially (implied by "each backend is run three times"). Thermal throttling, power limits, or background OS processes may change between runs, affecting CPU threads vs. GPU utilization differently.
*   **Control/Disclosure:** Interleave the runs: Run Backend A (run 1), Backend B (run 1), Backend C (run 1), then repeat. Disclose ambient temperature and GPU/CPU clock speeds during each run. Use a thermal pad or active cooling to minimize throttling.

**Threat 3: CPU Thread Contention**
*   **Threat:** The CPU uses 8 threads. If the GPU offloading tasks (CUDA/Vulkan) still spawn CPU threads for data preparation or kernel launch overhead, the 8-thread limit may not be sufficient, leading to contention. The CPU run might be artificially slowed because it’s competing with the GPU host code.
*   **Control/Disclosure:** Measure and disclose **CPU utilization percentage** and **thread count** for each backend run. For CUDA/Vulkan runs, isolate the CPU load by monitoring if the 8 threads are fully utilized or if they are idle waiting for GPU completion. Consider using `taskset` to pin the CPU backend to specific cores and monitor interference.

**Threat 4: Warm-up and Initialization Bias**
*   **Threat:** The first run of each backend includes JIT compilation (CUDA), Vulkan shader compilation, and CPU cache cold-start penalties. If the "three times" are not averaged correctly or if the first run is discarded inconsistently, the results will be skewed.
*   **Control/Disclosure:** Disclose exactly which runs are included in the average (e.g., "Runs 2–3 averaged, Run 1 discarded as warm-up"). Ensure the same warm-up procedure is applied to all backends (e.g., one dummy inference before timing). Report the standard deviation of the three runs to show stability.

### Task 5 — User-Visible Latency

**Definitions**
*   **Time to First Token (TTFT):** The wall-clock time from sending the prompt to receiving the *first* generated token. This dominates user perception of "responsiveness."
*   **Prompt-Evaluation Throughput:** Tokens per second during the *prefill* phase (processing the 2,000-token prompt). High throughput here reduces TTFT.
*   **Decode Throughput:** Tokens per second during the *generation* phase (producing the 200 tokens). High throughput reduces the time to complete the response.
*   **Total Wall-Clock Time:** The total time from sending the prompt to receiving the *last* token.

**Symbolic Equation**
Let:
*   $T_{prefill}$ = Time to process the 2,000-token prompt.
*   $T_{decode}$ = Time to generate 200 tokens.
*   $T_{overhead}$ = Network latency, serialization, and other fixed costs.

$$ T_{total} = T_{overhead} + T_{prefill} + T_{decode} $$

Where:
*   $T_{prefill} = \frac{2000}{\text{Prompt Throughput (tok/s)}}$
*   $T_{decode} = \frac{200}{\text{Decode Throughput (tok/s)}}$

**Example: Optimizing Prompt Processing Barely Changes Experience**
If the **Decode Throughput** is very slow (e.g., 2 tok/s on a CPU), then:
*   $T_{decode} = \frac{200}{2} = 100$ seconds.
*   Suppose optimizing the prompt evaluation reduces $T_{prefill}$ from 10 seconds to 1 second (a 9-second improvement).
*   **User Experience:** The user waits 1 second for TTFT (good), but then waits 100 seconds for the rest. The total time changes from 111 seconds to 102 seconds. While a 9-second improvement is measurable, the user still experiences a *long* wait. The bottleneck is decode, not prefill. Thus, optimizing prompt processing has a minimal *perceived* impact on the overall experience compared to optimizing decode speed.
