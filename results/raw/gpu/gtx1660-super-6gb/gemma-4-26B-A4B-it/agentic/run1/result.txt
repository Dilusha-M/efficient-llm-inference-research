**Success/Failure States:**
* **Success:** Process exits with code 0, `response.txt` is non-empty, and metrics are successfully parsed.
* **Model Failure:** Process exits with non-zero code or crashes (OOM), or `response.txt` is empty/incomplete.
* **Monitor Failure:** Process exits with code 0, but resource logs are missing or truncated. This is *not* a model failure.

**Experimental Identity Tuple (The Uniqueness Constraint):**
A run is unique if and only if the following tuple remains constant:
`{model_path, backend, hardware_label, context_length, gen_limit, prompt_hash, temperature, gpu_layers, llama_cpp_build_version, driver_version}`.

### State Machine

1.  **VALIDATION:** 
    *   Verify model path exists via alias. 
    *   Compute `prompt_hash`. 
    *   Check if the Identity Tuple has been run before to prevent result mixing. 
    *   *Transition:* To **LAUNCH** if valid, else **ABORT**.
2.  **LAUNCH:**
    *   Spawn `llama.cpp` process.
    *   Spawn sidecar monitoring processes (CPU/GPU/RAM).
    *   *Transition:* To **MONITORING** if successful, else **FAILURE**.
3.  **MONITORING:**
    *   Stream `stdout`/`stderr` to buffers.
    *   Sample monitors at defined intervals.
    *   *Events:* 
        *   **Timeout/OOM:** Terminate process, mark state as **MODEL_FAILURE**.
        *   **Process Exit:** Transition to **PARSING**.
4.  **PARSING:**
    *   Attempt to extract metrics from `stdout`.
    *   If metrics are missing/malformed: Mark as **MALFORMED_METRICS**.
    *   If monitors failed: Mark as **PARTIAL_DATA** (but keep model status as Success/Failure).
    *   *Transition:* To **FINALIZATION**.
5.  **FINALIZATION:**
    *   Atomic write of `metadata.json` and `response.txt`.
    *   Cleanup of temporary buffers.
    *   *Transition:* **COMPLETE**.

### Auditable Design

**Component Boundaries:**
* **Orchestrator (Python):** Manages the lifecycle, identity tuple validation, and metadata assembly.
* **Runner (Shell/Subprocess):** Executes the `llama.cpp` binary.
* **Monitors (Python/System Tools):** Independent processes that log to temporary files.

**Metadata Schema (JSON):**
```json
{
  "identity": { "model": "...", "backend": "cuda", "context": 4096, "prompt_hash": "sha256:..." },
  "environment": { "driver": "535.129", "build": "v1.5.4" },
  "results": { "status": "success|model_failure|malformed_metrics", "tokens_generated": 150 },
  "metrics": { "tps": 45.2, "latency_ms": 3300 },
  "monitoring_available": true
}
```

**Atomic-Write & Preservation:**
* **Stdout/Stderr:** Redirected to `run_{timestamp}_raw.log`.
* **Prompt Preservation:** The exact prompt used must be written to `prompt.txt` to ensure the `prompt_hash` can be manually verified.
* **Atomicity:** Write all files to a `.tmp/` directory first. On successful exit and parsing, `mv` the directory to the final `results/` folder to prevent partial artifacts from being treated as valid runs.

### Analysis Integrity

**Preventing Misleading Throughput:**
* **Normalization:** Throughput (tokens/sec) must be calculated as `total_tokens_generated / total_generation_time`. 
* **The "Partial Run" Trap:** If a model is killed by an OOM or timeout, the parser must flag `tokens_generated` as 0 or `null`. The orchestrator must refuse to include any run with `status != success` in aggregate averages.
* **Variable Lengths:** Since generation length varies, comparison must rely on `tokens_per_second` and `time_per_token` rather than total wall-clock time.

**Parser Robustness:**
* The parser must use regex to find specific patterns (e.g., `eval time = ...`). 
* If the `llama.cpp` output format changes (unknown format), the parser must throw a `FormatMismatchError`, marking the run as `malformed_metrics` rather than guessing values or defaulting to zero.

### Pre-merge Review

**High-Risk Design Flaws:**

1.  **Risk: Race conditions in monitoring.** If the monitor process outlives the model process, it might attribute the model's "shutdown" resource spike to the next run.
    *   *Fix:* Use process groups (PGID) to ensure the Orchestrator kills both the model and all sidecar monitors simultaneously.
2.  **Risk: Identity Tuple Collision via Hash.** Using a simple hash of the prompt might ignore subtle whitespace differences that affect LLM performance.
    *   *Fix:* Use a SHA-256 hash of the *entire* raw prompt string, including all trailing newlines and whitespace.
3.  **Risk: Silent Data Corruption.** If the disk fills up during the `mv` of the `.tmp/` directory, the metadata might be truncated.
    *   *Fix:* Implement a checksum (e.g., MD5) of the `metadata.json` and store it as a separate `.checksum` file; the post-run audit tool must validate this.
