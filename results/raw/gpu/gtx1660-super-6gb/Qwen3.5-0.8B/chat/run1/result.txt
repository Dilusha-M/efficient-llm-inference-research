### 1. Lifecycle of the KV Cache
The KV cache operates as a stateful memory pool with a strict lifecycle:
*   **Prefill (Reused):** As the model processes the prompt, the model's parameters are loaded into the GPU's shared memory. The model itself updates these parameters during inference, leaving the shared memory state unchanged. The model's **internal** state (parameters) is not cached; only the **KV cache** (key-value pairs) is cached.
*   **Decoding (Computed):** When the model generates a new token, the kernel must compute the specific values required for the next token (e.g., `qkv_cache[0][1]`). This computation is done in the kernel and written back to the GPU's shared memory.
*   **The Bottleneck:** The memory bandwidth required to write these computed values to the GPU shared memory is the primary constraint. If the KV cache grows beyond 32 GB (the system RAM limit), the kernel must spill data to system RAM before it can be written back, causing latency spikes.

### 2. Resource Separation and Latency
Prompt processing and decoding stress distinct hardware resources because they utilize different memory types and architectures:
*   **Prompt Processing:** Utilizes **Shared Memory**. It is highly parallel and GPU-centric, driven by kernel launch overhead and memory access patterns.
*   **Decoding:** Utilizes **GPU Shared Memory** (the same location as the KV cache) but involves the **Kernel**. The kernel launch overhead and memory bandwidth constraints are significantly higher for decoding.
*   **Latency Distinction:** A high prompt rate does not imply low interactive latency. Decoding requires the kernel to compute values, which often involves more complex memory operations than the simple parameter updates of prompt processing. Therefore, the latency curve is dominated by the decoding kernel launch overhead, not the prompt processing latency.

### 3. Context Scaling Effects
Increasing context from 2,000 to 8,000 tokens fundamentally shifts the workload:
*   **Prefill:** The model remains in the same state, so the KV cache is reused. However, the prompt length increases, increasing the total number of tokens the system must process (Prompt + Tokens).
*   **Decode:** The number of computed KV values doubles. If the 32 GB RAM is insufficient to hold all 8,000 tokens, the kernel must spill to system RAM during every decoding batch. This increases the frequency of memory writes, raising per-token latency.
*   **Bandwidth:** The critical factor is memory bandwidth. With 8,000 tokens, the total memory bandwidth required to write data to the GPU increases linearly (or more aggressively if the cache is full), pushing the bottleneck toward the GPU's memory bandwidth capacity rather than the CPU's.

### 4. Separation of Claims (General vs. Implementation Details)
*   **Generally True:**
    *   The model parameters are not cached; the KV cache *is* the cache.
    *   Spilling to system RAM increases latency.
    *   More context = more total tokens to process.
    *   Latency increases when the cache fills, not just when it is empty.
*   **Implementation Details (Dependence):**
    *   **Cache Precision:** A 8-bit precision cache will not store the full 8,000 tokens (requires 64-bit precision or 16-bit per token).
    *   **GPU Offload:** If the KV cache is offloaded to the CPU, the latency is dominated by CPU kernel launch, not the GPU cache bandwidth.
    *   **Paging:** The specific way the kernel handles the GPU shared memory (paging vs. direct mapping) determines if the bottleneck is the cache or the memory subsystem.
    *   **Kernel Support:** The ability to efficiently compute the KV cache depends on the specific kernel implementation (e.g., whether it uses vectorization, unrolling, or specialized hardware instructions).

### 5. Proposed Measurements for Binning
To isolate the bottleneck, implement the following comparisons:

1.  **Total Latency by Context:** Measure the total latency from the start of the conversation (Prompt + Prefill) to the end of the conversation (Prompt + Tokens). Plot this against context size. The slope should be shallow for small contexts and steep for large ones (indicating decoding overhead).
2.  **Throughput vs. Latency Ratio:** Calculate the number of tokens processed per second (Prompt Rate) and the latency per token (Latency). If the Latency per token is dominated by decoding, the throughput should remain stable even as context grows.
3.  **System RAM Usage:** Monitor the percentage of the 32 GB system RAM being in use during the experiment. If this percentage stays constant across contexts, the bottleneck is the **GPU Shared Memory bandwidth**. If it spikes dramatically, the bottleneck is **System RAM**.

*   **Scenario A (Prefill + Decode):** The system processes 2,300 tokens.
