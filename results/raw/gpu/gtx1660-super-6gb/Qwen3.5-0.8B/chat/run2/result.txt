**Executive Summary**
The observed slowdown is not caused by a hardware limit of the 6 GB GPU but by **non-uniform memory access (NUMA) topology** and **preference-based caching** between the GPU and RAM. Because the 2,000-token prompt is fully loaded into GPU registers/VRAM, adding context to the prompt increases the volume of data that must be moved to RAM. This forces the GPU to perform more expensive cache misses, while the system RAM is a low-bandwidth, high-latency target for the 300 tokens. The "excellent throughput" was misleading because it measured high-frequency requests, not the actual latency of the growing conversation.

### 1. Lifecycle of KV Cache: Reused vs. Recomputed
The lifecycle of the Key-Value (KV) cache is strictly partitioned based on the model's architecture and the nature of the prompt.

*   **Reused (Pre-Context):** Tokens $t=0 \dots n_{reused}$ are loaded into the GPU's internal **KV cache** and **register cache**. These are accessed sequentially and are **never recomputed** during the decoding phase.
*   **Recomputed (Post-Context):** Tokens $t=n_{reused}+1 \dots n_{total}$ are **never loaded into the GPU cache**. Instead, the model must **recompute** the KV pairs for these tokens using the "prompt" values it already has in register cache. The system effectively treats the entire prompt as a "new" prompt for the subsequent tokens, forcing the CPU to fetch the prompt from RAM to the GPU.

**Critical Distinction:** If the model supports **dynamic eager decoding** (loading KV into GPU on every token), the bottleneck is purely the GPU cache capacity. If the model supports **lazy eager decoding** (loading only when needed), the bottleneck is the RAM-to-GPU bandwidth transfer. The prompt size is irrelevant to the number of recomputed tokens; it is only relevant to the **total number of times** the prompt is reloaded to the GPU.

### 2. Stress Differentiation: Prompt vs. Decoding
Prompt processing and decoding utilize distinct hardware pathways that are often misaligned by the system.

*   **Prompt Processing (Input):** This is a **CPU-bound** operation. It involves parsing the prompt, generating the initial KV cache, and potentially fetching the prompt from the system RAM to the GPU. This latency is determined by the **prompt-to-GPU bandwidth** and the CPU's ability to manage the data stream.
*   **Decoding (Output):** This is a **GPU-bound** operation. It involves the massive kernel that performs the full matrix-vector multiplication and attention mechanism. Because this kernel runs entirely on the GPU, the latency is dominated by **GPU memory bandwidth** and the number of **cache misses** incurred during the kernel launch.

**Why High Prompt $N_{tok} \neq$ Low Latency:**
A high token count does not imply low interactive latency because the latency for the *entire conversation* is dominated by the **prompt-to-GPU bandwidth bottleneck**, not the GPU throughput. The system is not trying to generate more tokens; it is trying to generate *more context*. The GPU is simply acting as a bridge between the CPU's high-frequency requests and the GPU's massive bandwidth.

### 3. Analysis of 2,000 vs. 8,000 Token Context
The shift from 2,000 to 8,000 tokens fundamentally changes the workload on the system:

*   **Prefill Behavior:**
    *   **2,000 tokens:** The prompt is fully loaded into GPU VRAM. The prompt is **never reloaded** to the CPU to the GPU. The CPU does not need to fetch the prompt.
    *   **8,000 tokens:** The prompt is still loaded into GPU VRAM. However, **1,800 new tokens** are requested. The system must **reload the prompt from System RAM to the GPU**. This introduces a significant latency spike because the prompt is a large, complex data set that the GPU is not optimized to process efficiently.
*   **Decode Behavior:**
    *   **2,000 tokens:** The 1,800 new tokens are likely recomputed from the stored prompt.
    *   **8,000 tokens:** The 1,800 new tokens are recomputed from the **newly reloaded prompt**. The GPU has to pay for the cost of loading a larger prompt, increasing the frequency of the "reload-to-GPU" step.
*   **Memory Bandwidth:**
    *   The bottleneck shifts from the GPU's internal cache to the **System RAM-to-GPU bandwidth**. The CPU is now acting as a memory bus. The latency is now dominated by the system's ability to move the massive 8,000-token prompt (and its recomputed data) to the GPU.

### 5. Recommended Measurements to Distinguish Bottlenecks
To isolate the true bottleneck, perform these three comparisons:

1.  **Memory Bandwidth (MBW) vs. Prompt Bandwidth (PBW):**
    *   **Metric:** Measure the total bandwidth consumed during the initial prompt load to the GPU (CPU->GPU) vs. the total bandwidth consumed during the prompt re-load (GPU->CPU).
    *   **Goal:** If **Prompt Bandwidth > Memory Bandwidth**, the bottleneck is the prompt-to-GPU transfer. If **Memory Bandwidth > Prompt Bandwidth**, the bottleneck is the GPU cache.

2.  **Cache Hit Rate vs. Re-computation Count:**
    *   **Metric:** Log the number of times the prompt is reloaded to the GPU per second, and the number of recomputed tokens.
    *   **Goal:** If **Re-computation > Prompt Load**, the bottleneck is the GPU's inability to compute attention for new tokens. If **Prompt Load > Re-computation**, the bottleneck is the latency of fetching the prompt.

3.  **Latency (ms) vs. Throughput (tokens/sec):**
    *   **Metric:** Measure the latency of the first 500 tokens vs. the 800th token.
    *   **Goal:** If the 800th token is significantly slower than the first 500, the latency is dominated by the prompt-to-GPU transfer (high latency). If latency is dominated by the kernel (e.g., 20ms per token), the bottleneck is the GPU's computational capability.

**Numerical Example:**
Assume the prompt is 2,000 tokens and the prompt-to-GPU bandwidth is 8 GB/s.
*   **2,000 tokens:** 2,000 requests. Latency = 20ms per request. Total Time = 400ms.
*   **8,000 tokens:** 1,800 reloads. Latency per reload = 10ms.
    *   **Total Time:** $1,800 \times 10ms + 20ms \times 2,000 \approx 20,000ms$.
    *   **Result:** The system becomes 100x slower because the prompt-to-GPU transfer time dominates, not the GPU's ability to compute.
