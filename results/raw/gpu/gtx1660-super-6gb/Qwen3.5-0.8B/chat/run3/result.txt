### 1. Lifecycle of the KV Cache
The lifecycle of the KV cache in a 7B model on a 6GB GPU is distinct from standard LLM architecture due to the lack of a dedicated key-value store. The cache exists only for **prompt processing**, not token generation.

*   **Prompt Processing:** The system maintains a global buffer holding the sequence of past tokens. The 7B model only needs to look this up once per input token.
*   **Computation:** The model performs the actual token-by-token decoding using the global prompt buffer.
*   **Reuse:** As the conversation progresses, the same prompt buffer is consumed. If the prompt exceeds the GPU's available VRAM, the cache is overwritten.
*   **Recomputed:** When a new token arrives (or the prompt is truncated), the model must **recompute** its attention mechanism from scratch using the new prompt buffer. This is computationally expensive.

### 2. Why Prompt & Decoding Stress Differ Resources
Prompt processing is a memory-bound operation; decoding is a computation-bound operation.

*   **Prompt Processing:** The system acts as a massive on-demand memory pool. Latency is dominated by fetching tokens from the GPU's VRAM to the kernel's global memory.
*   **Decoding Stress:** When the prompt grows, the model must recompute attention weights for new tokens. This involves significant kernel launches and attention pass cycles.
*   **High Token/Rate vs. Latency:** A high `prompt tok/s` implies the GPU can sustain a high memory bandwidth load. However, it does not guarantee low latency because the system must manage the overhead of re-computing attention. If the recompute phase takes longer than the fetch phase, overall latency spikes.

### 3. Effects of Context Increase (2k → 8k)
Increasing context increases the footprint of the global prompt buffer.

*   **Prefill Behavior:** The system must re-verify the prompt buffer against the GPU's VRAM capacity. If 8k tokens require more memory than 6GB, the cache will be overwritten.
*   **Decode Behavior:** As the prompt buffer grows, the model spends more time re-computing attention for the new tokens.
*   **Bandwidth:** The transition from 2k to 8k often involves a data transfer (e.g., copying the full buffer to RAM). This introduces memory bandwidth bottlenecks. If the transfer is slower than the concurrent decode workload, the total system time increases, even if the model itself is efficient.

### 4. Separating General Claims from Implementation Details
| Claim | Verdict | Justification |
| :--- | :--- | :--- |
| **Cache precision matters** | **False** | GPU kernels are high-precision (usually 32-bit). Precision errors do not degrade correctness, only throughput. |
| **GPU offload is the primary bottleneck** | **False** | While offloading is critical, it does not inherently prevent cache overflow. A GPU can be fully offloaded if the prompt fits entirely within its VRAM. |
| **Kernel support is the limiting factor** | **False** | Kernel support is a resource constraint, not a memory constraint. A kernel can support 10k tokens indefinitely as long as RAM is available. |

### 5. Three Measurements to Distinguish Bottlenecks
To isolate the cause, measure the following three resources concurrently:

1.  **GPU VRAM Memory Bandwidth (MB/s):** Measure the raw throughput of the GPU's VRAM when the prompt buffer exceeds capacity.
    *   *Formula:* Total VRAM Bandwidth / Number of Tokens in Buffer.
2.  **Total Latency (ms):** Measure the time elapsed from prompt generation to token generation.
3.  **CPU–GPU Memory Transfer Latency (ms):** Measure the time for the full prompt buffer to move from GPU VRAM to system RAM.
    *   *Control:* Ensure the GPU is fully offloaded and the system RAM is fully loaded (e.g., 80% full).

### Numerical Example
Consider a scenario where the prompt buffer fills the GPU VRAM.

*   **Scenario A (Prefill Dominated):**
    *   **Prompt:** 2,000 tokens.
    *   **GPU VRAM:** 6 GB.
    *   **Result:** The cache is full immediately. The model must recompute attention for the first 2,000 tokens.
    *   **Time:** ~2,000 tokens $\times$ 20ms (recompute) + 500ms (prefill overhead) = **~2.5 seconds**.
    *   **Output:** The conversation ends after 2.5s.

*   **Scenario B (Decode Dominated):**
    *   **Prompt:** 2,000 tokens.
    *   **System RAM:** 32 GB.
    *   **Result:** Prefill succeeds. The model computes attention for 2,000 tokens and generates 300 tokens in parallel.
    *   **Time:** ~2.0 seconds (recompute) + 300 tokens $\times$ 10ms (decode) = **~2.5 seconds**.
    *   **Observation:** Since the prompt size is identical, the system behaves identically. The difference lies in the **cache capacity**, not the model's logic. If the prompt were larger (e.g., 8,000 tokens), Scenario B would fail immediately, and the 2.5s latency would remain unchanged, proving the bottleneck was the **cache overflow**, not the compute.
