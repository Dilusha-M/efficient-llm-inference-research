### Task 1 — quantization tradeoff:
**Memory Pressure Analysis:**
*   **Q8_0 (8B model, 8.0 GB file):** This format allocates the full 8.0 GB of memory to the model and its constant-time buffers. In Q4_K_M, the file size is smaller (4.8 GB), meaning the GPU must discard roughly 3.2 GB of memory to save space. This creates **high memory pressure** on the GPU, especially for larger models or higher quantization scales (e.g., Q4_0), where the discard cost is significant.
*   **Q4_K_M (4.8 GB file):** This format allocates less memory to the model, allowing the GPU to keep more of its resident set size (RMS) free. This creates **lower memory pressure**, reducing peak GPU memory utilization and potentially lowering latency.

**Why File Size is Not a Complete Runtime-Memory Estimate:**
*   **The Gap:** The file size represents the *compressed* memory footprint (RAM + Disk Space). It does not accurately reflect the *actual* physical memory consumed by the running process.
*   **Hidden Costs:** Q8_0 often has higher constant-time buffer overheads (for dynamic buffers in Q4_K_M) compared to Q4_K_M. Additionally, the Q4_K_M file might include the Q8_0 file's data if not explicitly removed, inflating the "space" figure. Furthermore, the Q4_K_M file might contain unnecessary overhead for the quantization pack, while the Q8_0 file might be cleaner.
*   **Inference Timing:** Memory pressure occurs at inference time. The file size might be small, but if the model's constant-time buffers (like Q4_K_M's) are large or if there is a large constant-time buffer in Q8_0 that isn't released before inference, the GPU will hold onto that memory until inference completes, even if the file size looks smaller than the Q8_0 file.

**Qualities/Performance Measurements Needed:**
Before declaring one format better, you must verify the following:
1.  **Latency/Throughput:** Compare the **decode throughput** (tokens per second, typically measured over a batch of 1000-5000 tokens) for both formats. Q4_K_M should generally outperform Q8_0 for inference speed.
2.  **Memory Utilization and Peak Memory:** Measure the **peak memory usage** and the **minimum peak memory** (to ensure the quantization pack is not blocking the GPU). Verify that the Q4_K_M file is not significantly larger than the Q8_0 file due to hidden overheads.
3.  **Quantization Scale:** Ensure the Q4_K_M file is not artificially compressed to the Q8_0 file's size (e.g., by removing the quantization pack itself) to avoid overestimating the file size.

### Task 3 — robust aggregation:
**Pseudocode:**
```python
def validate_runs(run_results):
    successful_runs = [r for r in run_results if r.get('status') == 'success']
    failed_runs = [r for r in run_results if r.get('status') == 'failure']

    if len(successful_runs) < 2:
        return {
            'median': 0.0,
            'fail_count': len(failed_runs),
            'failed_run_ids': [r.get('id') for r in failed_runs],
            'message': 'Insufficient data: fewer than 2 successful runs.'
        }

    # Sort by speed (lowest first)
    sorted_runs = sorted(successful_runs, key=lambda x: x['speed'])

    # Compute Median
    if len(sorted_runs) % 2 == 0:
        median = (sorted_runs[len(sorted_runs)//2 - 1]['speed'] + 
                 sorted_runs[len(sorted_runs)//2]['speed']) / 2.0
    else:
        median = sorted_runs[len(sorted_runs)//2]['speed']

    return {
        'median': round(median, 2),
        'successful': len(sorted_runs),
        'failed': len(sorted_runs) - len(sorted_runs),
        'failed_ids': [r.get('id') for r in failed_runs],
        'median_run_id': sorted_runs[len(sorted_runs)//2 - 1]['id']
    }
```
**Handling Failing Runs:**
*   The failed run is preserved in the list of failures but excluded from the median calculation.
*   If fewer than two runs succeed (e.g., only 1 run is successful), the function returns `{'median': 0.0, 'fail_count': 1, 'message': 'Insufficient data: fewer than 2 successful runs.'}`. The failed run is visible in the result but not included in the statistics.

### Task 5 — user-visible latency:
**Time to First Token (TTFT):**
*   This is the time a user perceives a token is "generated." It is primarily determined by the **prompt processing time** (the time the input is read and analyzed) and the **model's inference latency**.
*   If the prompt processing time is the dominant factor, TTFT is roughly the same regardless of quantization.

**Prompt-Evaluation Throughput (PET):**
*   This is the **average tokens processed per second** over a specific window (e.g., 100 tokens). It is calculated by dividing the total tokens processed by the total time elapsed.
*   It does **not** represent the time to the first token, but rather the throughput during a specific window.

**Decode Throughput (DT):**
*   This is the **tokens per second** during the actual decoding phase. It is the rate at which the model generates new tokens as the user provides new tokens.
*   It is distinct from prompt-evaluation throughput.

**Total Wall-Clock Time (TWT):**
*   The sum of the individual phases:
    $$ \text{TWT} = \text{TTFT} + \text{PROMPT\_PROCESSING} + \text{INFER\_LATENCY} + \text{DT} $$
*   Symbolically: $T_{total} = T_{prompt} + T_{inference} + T_{DT}$.

**Example where optimizing prompt processing barely changes experience:**
*   Scenario: A user types a very long prompt (e.g., 5,000 tokens) and immediately receives a response.
*   Explanation: If the **prompt processing time** is less than **10% of the total user wait time** (the time to send a token and the time to receive the response), optimizing the prompt processing (e.g., using an optimized prompt format or a faster model) will not significantly change the user's perceived latency. The user waits primarily for the model's inference, which is likely the bottleneck. Optimizing the prompt might only reduce the time by 0.5%, which is negligible to the user experience.
