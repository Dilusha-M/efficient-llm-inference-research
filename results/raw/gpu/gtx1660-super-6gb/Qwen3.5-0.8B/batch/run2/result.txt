### Task 2 — Conservative Launch Decision
**Assumptions:**
1.  The 5.0 GB weight figure represents the *model weights* only. It does not include the `llama.cpp` KV cache, attention masks, or the `.pt` metadata file.
2.  The 2,000-token prompt is fixed.

**Conservative Procedure:**
To choose the optimal context size and GPU layer offload conservatively, one should not just pick the smallest possible size, but rather the smallest size that still allows the model to complete the task within the generation limit.

**1. What to Try First:**
*   **Context Size:** Start with the smallest context size (e.g., 64 tokens) that the model can handle without exceeding the 512-token generation limit.
*   **Layer Offload:** Immediately attempt to offload the largest possible layers. This often yields the most significant speedup because layers that are not currently in use are skipped entirely.

**2. Telemetry to Record:**
*   **Generation Latency:** Record the time it takes to generate the full prompt and the full generation.
*   **Completion Status:** Record whether the generation completed successfully or if the model crashed/rolled back due to the generation limit.
*   **Context Size Impact:** Record the latency if the context size is increased by a fixed token amount (e.g., 2 tokens) to measure if adding context improves performance.

**3. Unsafe or Misleading Success:**
*   **False Premise:** Claiming that "larger context size = faster inference" without validating against the generation limit is misleading.
*   **Unnecessary Offload:** Claiming that "offloading all layers" is the *only* way to speed up an inference pipeline, when a smaller context size with partial offloading might actually be faster.
*   **Ignoring the Limit:** Claiming the task is complete simply because the generation limit was reached, without verifying that the *actual* generation time is under the limit, which is often the bottleneck.

def robust_aggregation(run_results):
    # 1. Identify "Successful" runs (those that completed within the generation limit)

    #    If fewer than two, we cannot report a median.

        median_success = successful_runs[0]['decode_speed']

        median_success = successful_runs[0]['decode_speed']

    else:

        sorted_runs = sorted(successful_runs, key=lambda x: x['decode_speed'])
        # Compute median
        sorted_runs = sorted_runs[0::2] + sorted_runs[1::2]
        if len(sorted_runs) % 2 == 1:
            median_success = sorted_runs[len(sorted_runs) // 2]['decode_speed']
        else:

            median_success = (sorted_runs[len(sorted_runs) // 2 - 1]['decode_speed'] +

    return {

### Task 4 — Validity Audit
**Assumptions:**
1.  The CPU is running on a single thread.
2.  CUDA is running on a single thread.
3.  Vulkan is running on a single thread.
4.  The workload is identical across all backends (CPU, CUDA, Vulkan).

**Threats to Validity:**

1.  **Hardware vs. Software (Hardware vs. CUDA):**
    *   **Concrete Control/Disclosure:** The CPU does not have the same memory bandwidth or rendering capabilities as the GPU. The CPU's throughput is strictly limited by the CPU core count and cache size, whereas the GPU's is limited by the GPU's memory bandwidth and rendering pipeline. A comparison might falsely suggest the CPU is faster, when in reality, it is slower due to fundamental hardware constraints.
2.  **Output Comparability (Output vs. Hardware):**
    *   **Concrete Control/Disclosure:** The CPU's output is discrete bits (bytes/bytes). The GPU's output is continuous (pixel data). While both are images, the CPU cannot output pixels directly; it outputs a 2D array of pixels. The GPU's output is a stream of 3D vectors. Comparing the number of bytes produced by the CPU to the number of pixels the GPU produces is fundamentally invalid because the data types and dimensions differ.
3.  **Workload vs. Output (Latency vs. Output):**
    *   **Concrete Control/Disclosure:** The CPU's latency is measured in cycles. The GPU's latency is measured in frames or pixels. While they are both time measurements, the units and the nature of the metric (cycle vs. pixel) make a direct comparison of "latency" misleading. One might be "better" (fewer cycles), but the other might be "better" (more pixels).
4.  **Hardware vs. Software (Software vs. CPU):**
    *   **Concrete Control/Disclosure:** The CPU is a hardware device with a fixed core count and memory architecture. Software (or the CUDA driver) can only utilize a subset of these cores. Claiming the CPU is the fastest or most resource-efficient is false because the CUDA driver manages a different set of resources, and the GPU's performance is tied to its own hardware.

### Task 5 — User-Visible Latency
**Assumptions:**

3.  "Time to first token" is the time until the first character is output.
4.  "Prompt-evaluation throughput" is the time it takes to process a full prompt (prompt + generation).
5.  "Decode throughput" is the time it takes to process a single token.
6.  "Total wall-clock time" is the sum of these components.

**Explanation of Differences:**
*   **Time to First Token:** This is the latency to generate the very first character. It is the most critical metric for the user's initial experience.
*   **Prompt-evaluation throughput:** This is the average tokens processed per second (TPS) for the entire 2,000-token prompt. It does not include the generation latency for the 200 tokens; it includes the entire processing time of the prompt itself.
*   **Decode throughput:** This is the average tokens processed per second (TPS) for a single token. It does not include the generation latency for the 200 tokens; it includes the processing time of that single token.
*   **Total wall-clock time:** This is the sum of the Time to First Token, Prompt-evaluation throughput, and Decode throughput.

**Symbolic Equation:**
Let $T_{first}$ be the time to first token (seconds).
Let $T_{prompt}$ be the time to process the entire 2,000-token prompt (seconds).
Let $T_{token}$ be the time to process a single token (seconds).
Let $T_{gen}$ be the time to generate the 200 generated tokens (seconds).

The symbolic equation for total wall-clock time is:
$$ \text{Total Time} = T_{first} + T_{prompt} + T_{token} + T_{gen} $$

**Example where optimizing prompt processing barely changes the user's experience:**
*   **Context Size vs. Prompt Length:** Consider a scenario where the user has 2000 tokens in their prompt but the model can only handle 200 tokens of context. In this case, the *prompt evaluation* throughput is determined by the context size. If you increase the context size to 2000 tokens, the prompt evaluation throughput increases significantly. *   **More concise example:** If the user's prompt is exactly 2000 tokens, and the model can process 1000 tokens of context, then the *prompt-evaluation throughput* is low (e.g., 20 tokens/s). If the context size is increased to 2000 tokens, the *prompt-evaluation throughput* increases. Optimizing prompt processing (e.g., by reducing context size) would **not** change the user's experience because the bottleneck is the prompt evaluation itself, not the generation of 200 tokens. The *Time to First Token* might increase if the model is slow at decoding long context, but the *prompt-evaluation throughput* remains the primary constraint.
*   **Better example:** If the user's prompt is 2000 tokens, the model is currently 20 tokens/s (prompt + generation). If the context size is increased to 500 tokens, the prompt evaluation throughput drops to 2 tokens/s. In this case, optimizing prompt processing (reducing context size) would change the user's experience significantly.
