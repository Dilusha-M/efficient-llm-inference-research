### Task 1 — Quantization Tradeoff

**Memory Pressure Analysis:**
*   **Q8_0 (8.0 GB):** This format exceeds the available 5.2 GB VRAM. It will trigger "memory swapping" (system RAM offloading), creating high memory pressure. This typically results in a significant performance drop as the system moves weights between the GPU and CPU over the PCIe bus.
*   **Q4_K_M (4.8 GB):** This format fits within the 5.2 GB free VRAM. It creates low memory pressure, allowing the entire model to reside on the GPU for inference.

**Why File Size $\neq$ Runtime Memory:**
File size represents the compressed weights on disk. Runtime memory is higher because of:
1.  **KV Cache:** Memory allocated to store the "keys" and "values" of the current conversation context.
2.  **Activation Buffers:** Temporary memory used during the forward pass.
3.  **Overhead:** CUDA kernels, context managers, and library overhead (e.g., bitsandbytes or llama.cpp overhead) consume additional VRAM.

**Required Measurements for Comparison:**
1.  **Perplexity (PPL) or MMLU Score:** To measure the "Quality" loss incurred by moving from 8-bit to 4-bit precision.
2.  **Tokens per Second (tok/s):** To measure the "Performance" gain of the Q4_K_M format's faster memory bandwidth utilization versus the Q8_0 format's higher precision.

### Task 2 — Conservative Launch Decision

**Procedure:**
1.  **Initial Attempt:** Start with `n_gpu_layers` set to the maximum possible that leaves at least 1.5 GB of VRAM free for the KV cache (e.g., if the model is 32 layers, try offloading 30 layers first).
2.  **Telemetry to Record:**
    *   `VRAM_Used` (Peak during prompt processing).
    *   `VRAM_Used` (Peak during generation).
    *   `Tokens_Per_Second` (Prompt vs. Generation).
    *   `Context_Size` (Number of tokens successfully processed before crash).
3.  **Iterative Adjustment:** If a "CUDA Out of Memory" error occurs, reduce `n_gpu_layers` by 2. If the KV cache exceeds memory, reduce `n_ctx` (context size).

**Unsafe or Misleading Success:**
*   **Success:** A run that completes but uses >98% of VRAM. This is "unsafe" because it provides no headroom for KV cache growth, leading to crashes on longer prompts.
*   **Misleading Success:** A run that finishes quickly because `n_ctx` was set so low that the model "forgot" the 2,000-token prompt.

### Task 4 — Validity Audit

1.  **Hardware Heterogeneity:** The CPU, CUDA, and Vulkan backends use different memory architectures (Shared vs. Dedicated).
    *   *Control:* Use the same physical machine for all three tests to isolate software overhead from hardware disparity.
2.  **Thread Contention:** 8 threads on CPU might be saturated by OS tasks, while CUDA/Vulkan might have different driver-level scheduling.
    *   *Control:* Use `taskset` or `nice` to isolate CPU cores and ensure the CPU test has exclusive access to the assigned cores.
3.  **Driver/Library Versioning:** Different versions of CUDA or Vulkan drivers can significantly alter performance.
    *   *Control:* Log and disclose the exact version of the drivers and the library versions (e.g., `torch`, `llama.cpp`) used for each backend.
4.  **Workload/Output Comparability (The "Logic" Threat):** If the CPU and GPU versions use different kernels (e.g., different attention implementations), they may produce slightly different outputs or use different arithmetic paths.
    *   *Control:* Perform a "Bitwise Parity Check" on the first 10 tokens of a fixed prompt across all three backends; if outputs differ, the comparison is invalid as they are not running the same logic.

### Task 5 — User-Visible Latency

**Definitions:**
*   **Time to First Token (TTFT):** The duration from the user hitting "Enter" to the first character appearing.
*   **Prompt-Evaluation Throughput:** The speed (tok/s) at which the model processes the 2,000-token input.
*   **Decode Throughput:** The speed (tok/s) at which the model generates the 200 new tokens.
*   **Total Wall-Clock Time:** The sum of the time taken to process the prompt and the time taken to generate all output tokens.

**Symbolic Equation:**
$T_{total} = \frac{Tokens_{prompt}}{Throughput_{prompt}} + \frac{Tokens_{gen}}{Throughput_{gen}}$

**Example of Negligible Impact:**
If a user is generating a very long response (e.g., 2,000 tokens), optimizing the prompt-evaluation throughput (the 2,000-token input) might save 1 second of time, but the total generation time might take 100 seconds. In this case, the user's perception of the "speed" of the model is dominated by the decode throughput, making the prompt optimization nearly imperceptible in the context of the total experience.
