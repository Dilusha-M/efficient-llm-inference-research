## Requirements and Invariants

**Success/Failure States:**
* **Success:** A complete, verifiable run with all required metrics and raw output is generated, and the run is distinguishable from failure states.
* **Failure:** Occurs if a required component fails, if monitoring data is missing, or if a critical process fails (e.g., OOM, process termination).
* **Distinguished Failure:** A failure state must be clearly differentiated from missing optional monitoring data.

**Experimental Identity Tuple:**
The unique identifier for a single benchmark run must be determinable and reproducible. This tuple must include: (Model Alias, Backend, Hardware Label, Context, Generation Limit, Temperature, CPU Threads, Workload, Prompt Hash, Run Timestamp).

**Ambiguity to be Resolved:**
The specification states that the runner must distinguish a failed model run from missing optional monitoring data. It does not explicitly define the threshold or mechanism for distinguishing these.
* **Resolution Needed:** Define the exact condition under which a run is considered "failed" (e.g., non-zero exit code, failure to produce output, or inability to read required metrics) versus a run where optional monitoring data is simply absent or sparse.

## State Machine

**Initial State:** Configuration loading and validation.

**Phase 1: Validation & Setup**
1. **Load Configuration:** Load model aliases and runtime defaults.
2. **Validate Inputs:** Check for existence of prompts, model files, and required hardware context.
3. **Determine Identity:** Construct the Experimental Identity Tuple.
4. **Initialize Run State:** Create the run-specific metadata file structure.

**Phase 2: Execution**
1. **Pre-Execution Check:** Verify all required inputs for the chosen backend (CPU/CUDA/Vulkan).
2. **Launch Model:** Execute the `llama.cpp` process with specified parameters (context, limit, temperature, workload, prompt).
3. **Monitor:** Start concurrent monitoring of the process execution and system resources (memory, CPU).

**Phase 3: Post-Execution & Finalization**
1. **Wait for Exit:** Wait for the model process to terminate.
2. **Process Result Check:** Check the exit code.
    * **If Exit Code indicates Failure (e.g., non-zero):** Mark run as FAILED. Record error details.
    * **If Process Failed (OOM, Signal):** Mark run as FAILED. Record failure reason.
3. **Artifact Collection:**
    * Capture raw output (`response.txt`).
    * Capture performance metrics.
    * Capture hardware metadata snapshot.
4. **Integrity Check:** Verify that all required data points (including required monitoring data) are present.
    * **If Required Data Missing (but no process failure):** Mark run as WARNING/PARTIAL (missing optional monitoring).
    * **If All Data Present:** Mark run as SUCCESS.
5. **Finalization:** Write the complete, audited run metadata file.

**Timeout/Error Handling:**
* **Timeout:** If the process exceeds a defined timeout, terminate it, mark as FAILED, and record timeout event in metadata.
* **OOM:** If the process triggers an Out-Of-Memory error, terminate it, mark as FAILED, and record OOM event.
* **Malformed Output:** If the parser for `response.txt` fails during post-processing, mark as FAILED, retaining the raw output for manual audit.
* **Monitor Failure:** If a monitoring thread fails to report data, the run status is marked based on the presence of *required* data. Missing optional data results in a warning, not a hard failure, unless the missing data was critical for the final success criteria.

4. **Monitor Agent:** Responsible for polling or receiving data from system/process monitoring tools to gather performance metrics.

**Atomic-Write/Partial-File Conventions:**
1. **Raw Output Preservation:** `response.txt` (or equivalent) must be written immediately to a unique, temporary location. Only upon successful completion of all post-processing should it be finalized into the metadata structure.

3. **Partial Data:** If monitoring fails, the system must explicitly record the missing data (e.g., `monitor_data_available: false`) rather than omitting the key, ensuring the distinction between missing optional data and hard failure is explicit.

## Analysis Integrity

**Preventing Misleading Throughput Comparison:**
Throughput must be calculated using only data confirmed to be generated by the model execution, excluding any data derived from failed monitoring or parsing steps.
1. **Source of Truth:** Throughput calculation must rely solely on the timing data captured *during* the execution phase (Phase 2/3) and the token counts derived from the raw output parsing.
2. **Failure Gate:** If the final status is `FAILED`, the calculated throughput is marked as invalid or set to a sentinel value (e.g., -1) in the metadata. The comparison logic must filter out any runs marked `FAILED`.

**Handling Unknown Llama.cpp Output Formats:**
The parser must adopt a defensive, strict parsing strategy:
1. **Schema Validation:** The parser must attempt to match the raw output against an expected structure (if one exists) or a known format.
2. **Fallback Strategy:** If parsing fails (e.g., output is corrupted or in an unexpected format), the parser must *not* attempt to guess the result. Instead, it must treat the entire raw output as an unparseable artifact.
3. **Error Reporting:** If parsing fails, the resulting state must be marked as `FAILED` (or `PARTIAL_WARNING` if output was present but unreadable) and the raw output must be preserved for manual audit, ensuring that an erroneous metric calculation does not mask the input error.

## Pre-merge Review

**Highest-Risk Design Flaw 1: Ambiguity in Failure vs. Missing Data Classification**
* **Flaw:** The distinction between a hard failure (process crash, OOM) and missing optional monitoring data is not rigidly defined, risking misclassification and inaccurate reporting of operational health.
* **Fix:** Enforce a strict hierarchy in the State Machine: A run is **FAILED** only if the model process exited with an error code or crashed. A run is **PARTIAL\_WARNING** only if the process succeeded but optional monitoring data is absent. The `metrics.monitor_data_available` flag must explicitly capture the absence of optional data, regardless of success status.

**Highest-Risk Design Flaw 2: Integrity of Raw Output vs. Metrics**
* **Flaw:** If the output parser fails (leading to a `FAILED` state), the system might incorrectly discard performance metrics or fail to retain the raw output, violating the requirement that "Raw output must remain available for manual audit."
* **Fix:** Implement the Artifact Writer to prioritize the preservation of the raw output file and its checksum. The failure status must be determined *after* artifact collection. If the parsing fails, the status is `FAILED`, but the raw output and its checksum are still stored, fulfilling the audit requirement.

**Highest-Risk Design Flaw 3: Determinism of Environment Variables vs. Runtime Overrides**
* **Flaw:** The runner relies on a complex interplay of fixed defaults, configuration file aliases, and runtime overrides (e.g., workload overrides context). This complexity increases the risk of non-deterministic identity generation, violating the requirement that the identity tuple must be perfectly reproducible.
* **Fix:** The Runner Orchestrator must establish a strict, sequential application order for all configuration parameters. All inputs (aliases, defaults, runtime overrides) must be explicitly mapped into the `experimental_identity` tuple *before* execution begins, ensuring that the resulting tuple is a direct, unambiguous reflection of the exact environment used for the benchmark.
