**Ambiguity to Resolve:**
The specification states: "Raw output must remain available for manual audit." ## State Machine

**States:**
1. **Configuration Load & Validation (CLV):** Load configuration, validate all required inputs (workload, limits, hardware selection).
2. **Artifact Preparation (AP):** Generate the unique run ID, calculate prompt hash, and prepare the execution environment based on configuration.
3. **Llama.cpp Execution (LE):** Launch the specific llama.cpp variant with the specified workload and prompts.
4. **Monitoring & Capture (MC):** Continuously monitor the execution process and capture raw output, performance metrics, and hardware telemetry.
5. **Post-Processing & Validation (PPV):** Parse raw output, validate all captured metrics against invariants, and check for failure conditions.
6. **Finalization & Archival (FA):** Write the final, validated result set (including raw output) to disk, ensuring the failure status is explicitly recorded.

**Transitions & Error Handling:**

* **CLV $\rightarrow$ AP:** Success if all configuration parameters are valid. Failure if any required parameter is missing or invalid.
* **AP $\rightarrow$ LE:** Success if the correct executable path and arguments are constructed. Failure if the chosen model alias or backend is invalid.
* **LE $\rightarrow$ MC:**
    * **Timeout/OOM:** If process terminates abnormally (timeout, OOM), transition to **MC (Failure Mode)**, marking the run as failed due to process error.
    * **Normal Exit:** If process exits normally, transition to **MC**.
* **MC $\rightarrow$ PPV:**
    * **Monitor Failure:** If required monitoring data is missing (e.g., performance metrics file absent), transition to **PPV (Missing Data Failure)**.
    * **Malformed Output:** If parsing fails, transition to **PPV (Parsing Failure)**.
    * **Success:** If all data is present and consistent, transition to **FA**.
* **PPV $\rightarrow$ FA:** If validation passes, archive the data. If validation fails, archive the data explicitly marked as failed.

## Auditable Design

**Component Boundaries:**
1. **Configuration Manager:** Reads and validates configuration file, determines the Experimental Identity Tuple.
2. **Execution Orchestrator (Main Runner):** Manages the flow between steps, handles process spawning, and manages error states.
3. **Llama.cpp Wrapper:** Responsible for constructing and executing the specific llama.cpp command based on runtime parameters.
4. **Monitor Agent:** Hooks into the execution environment to capture real-time performance and hardware data.
5. **Output Processor:** Handles raw data serialization, parsing, and validation against invariants.

**Metadata Schema (Per Run):**
The metadata file ($\text{run\_id}.\text{json}$) must contain:
* `run_id`: Unique identifier.
* `status`: (SUCCESS, FAILED_EXECUTION, FAILED_MONITORING, FAILED_PARSE).
* `experimental_identity`: (As defined above).
* `configuration_snapshot`: Exact input parameters used (Context, Temp, Workload, etc.).
* `hardware_metadata`: Snapshot of hardware used.
* `performance_metrics`: Generated token counts, latency, etc. (or null/error indicator if missing).
* `raw_output`: The complete, unaltered stdout/stderr stream from the execution.
* `error_details`: Detailed description of the failure, if applicable.

**Atomic-Write/Partial-File Conventions:**
* **Atomic Writes:** The final metadata file ($\text{run\_id}.\text{json}$) must be written atomically (e.g., write to a temporary file, then rename).
* **Raw Output Preservation:** The entire raw output ($\text{raw\_output}$) must be written to a separate, uniquely named file (e.g., $\text{run\_id}.\text{raw}$) to ensure full auditability, regardless of parsing success.
* **Failure Distinction:** The `status` field in the JSON metadata must explicitly distinguish between execution failure (LE failure) and data quality failure (MC/PPV failure).

**Stdout/Stderr/Prompt Preservation:**
The Execution Orchestrator must pipe the stdout/stderr streams directly into the respective run-specific raw files ($\text{run\_id}.\text{raw}$). The exact prompt used must be explicitly written into the metadata file (`configuration_snapshot`).

## Analysis Integrity

**Preventing Misleading Throughput:**
Throughput comparison must only occur between runs where the *exact* set of variables defining the experiment is identical. The Experimental Identity Tuple serves as the strict key. If a run fails to generate required metrics (e.g., missing $\text{generated\_tokens}$), the comparison must explicitly treat the result as invalid or exclude it from throughput calculations, rather than imputing a value.

**Handling Unknown Output Formats:**
The Output Processor must implement a strict, layered parsing strategy:
1. **Format Identification:** Attempt to identify the Llama.cpp output format based on structural markers or known patterns.
2. **Schema Validation:** Attempt to map the identified structure against the expected schema derived from the configuration.
3. **Fallback:** If mapping fails (unknown format), the parser must *not* attempt to generate metrics. Instead, it must flag the result as $\text{FAILED\_PARSE}$ and rely solely on the $\text{raw\_output}$ for manual audit, ensuring that no fabricated or guessed metrics enter the comparison pipeline.

## Test Plan

1. **Standard Success Test:** Run with default settings, ensure all metrics are present and valid.
2. **Simulated Backend Failure Test:** Configure the runner to invoke llama.cpp with an invalid or corrupted model path/argument, verifying the State Machine transitions to $\text{FAILED\_EXECUTION}$.
3. **Missing Monitor Test:** Configure the environment such that the Monitor Agent fails to write performance data (simulating monitor failure), verifying the result transitions to $\text{FAILED\_MONITORING}$ and that the output is archived correctly.
4. **Prompt Complexity Test:** Use a prompt containing embedded spaces and newlines, ensuring the raw output capture correctly preserves the exact input and the parsing logic handles multi-line context correctly.
5. **Partial Output Test:** Simulate a scenario where the model process exits prematurely, leaving only partial output in the raw stream, verifying that the system correctly flags this as a failure state and does not attempt to parse incomplete data as a success.
6. **Prompt Hash Invariance Test:** Run two identical experiments differing only by a single, non-content parameter (e.g., slightly adjusting the generation limit or temperature, while keeping all other variables identical), ensuring that the resulting Experimental Identity Tuple is unique and the comparison logic correctly rejects cross-comparison.

## Pre-merge Review

**Highest Risk Design Flaw 1: Invariant Enforcement on Failure Modes**
* **Flaw:** The distinction between $\text{FAILED\_EXECUTION}$ (process error) and $\text{FAILED\_MONITORING}$ (data error) is critical, but if the monitoring agent fails *while* the process is still running, the system must decide if the process failure supersedes the monitoring failure.
* **Fix:** Enforce that $\text{FAILED\_EXECUTION}$ is the highest priority failure state. If the process exits abnormally, the result is $\text{FAILED\_EXECUTION}$, regardless of whether monitoring data was partially collected.

**Highest Risk Design Flaw 2: Raw Output vs. Metric Dependency**
* **Flaw:** Relying on parsing metrics to validate success, while simultaneously requiring the raw output for audit, creates a dependency risk. If parsing fails, the system must not invent metrics.
* **Fix:** Mandate that the $\text{status}$ field in the metadata *must* be $\text{FAILED\_PARSE}$ if the output cannot be mapped to the expected format, and this state must be prioritized over any metric-based success check.

**Highest Risk Design Flaw 3: Experimental Identity Collision**
* **Flaw:** If the system relies solely on runtime parameters for the identity, subtle environmental factors (e.g., system time, internal process IDs, or timing drift) could lead to two logically identical runs producing different identifiers, breaking the requirement that results must not be mixed based on *all* environmental changes.
* **Fix:** The Experimental Identity Tuple must incorporate a deterministic hash of the entire execution environment snapshot (including system/hardware identifiers captured at launch) *in addition* to the explicit configuration parameters.
