Scenario:
A 7B decoder-only model is served on a 6 GB consumer GPU with 32 GB system RAM. The model weights fit on the GPU, but the key-value (KV) cache does not always fit there. A user sends a 2,000-token prompt and requests 300 generated tokens. The system reports excellent prompt-processing throughput but becomes much slow ... (truncated)
This situation describes a classic bottleneck transition in autoregressive LLM inference, shifting from compute-bound prefill to memory-bound decoding.

---

### 1. Lifecycle of the KV Cache

The KV cache stores the intermediate attention states necessary for the model to attend to previously processed tokens.

*   **Prompt Processing (Prefill Phase):** The entire 2,000-token prompt is processed in a single, parallel matrix multiplication operation across all tokens. **All** KV cache entries for these 2,000 tokens are computed and stored. This phase is highly compute-bound, leveraging the massive parallelism of the GPU.
*   **Token-by-Token Decoding (Decoding Phase):** As subsequent tokens are generated (one by one), the new token's key and value vectors are computed, and the *entire* existing KV cache (for the prompt + all previously generated tokens) must be re-read and re-used for the attention calculation with the new token. **No** new weight computation occurs; only the memory access and attention score computation over the existing cache are performed. This phase is memory-bound due to the size of the cache.

**Reused vs. Recomputed:**
*   **Reused:** The weights ($\mathbf{W}$) and the previously computed KV cache entries are reused for every subsequent decoding step.
*   **Recomputed:** The attention scores and the new KV cache entries for the newly generated token are computed in each decoding step.

### 2. Resource Stress and Latency

**Prompt Processing vs. Decoding Stress:**
*   **Prompt Processing (Prefill):** This phase is **compute-bound**. It involves large, dense matrix multiplications across all input tokens simultaneously. High throughput (tokens/s) is achievable because the GPU's massive floating-point units (FP32/FP16 cores) are saturated.
*   **Decoding (Autoregressive):** This phase is increasingly **memory-bound**. While the arithmetic intensity remains high, the latency is dominated by the time required to fetch the necessary KV cache entries from memory (either GPU VRAM or System RAM) and perform the subsequent attention calculations.

**Why High Prompt Tok/s $\neq$ Low Interactive Latency:**
A high prompt throughput only indicates fast *batch processing* of the initial prompt. Interactive latency (time-to-first-token, or time-per-token) is dominated by the sequential nature of the decoding phase, which is gated by the memory bandwidth required to feed the KV cache during the token generation loop.

### 3. Effect of Increasing Context (2k $\to$ 8k Tokens)

Increasing context size significantly amplifies the memory bottleneck, especially in the decoding phase.

*   **Prefill Behavior:** The initial prompt processing time will increase **quadratically** (or near-linearly, depending on specific attention implementation details) with the context length, as the number of required attention computations scales with $L^2$ or $L$ times the sequence length $L$.
*   **Decoding Behavior:** The KV cache size scales linearly with context length ($L$). Since the KV cache must reside in slower system RAM (as the GPU VRAM is constrained), the time spent fetching these larger structures dominates the per-token latency. The memory bandwidth constraint becomes the primary limiter, as the GPU must wait for data transfer between system RAM and VRAM.

**Memory Bandwidth Role:** Larger context means a larger cache that must be constantly streamed during decoding. If the cache exceeds GPU VRAM, the system relies on slower PCIe/interconnect transfers to system RAM, drastically increasing the latency per token.

### 4. Distinguishing True vs. Implementation Claims

| Claim | Classification | Rationale |
| :--- | :--- | :--- |
| Weight bandwidth | True (Fundamental constraint) | Determined by $\text{Model Size} \times \text{Activation Size}$. |
| KV-cache traffic | True (Runtime constraint) | Directly proportional to context length and batch size. |
| CPU–GPU transfer | Implementation-dependent | Depends on memory hierarchy (HBM vs. DDR) and data placement strategy. |
| Paging | Implementation-dependent | Relates to OS/driver behavior when VRAM is exhausted. |
| Kernel support | Implementation-dependent | Relates to efficient implementation of attention kernels. |

### 5. Proposed Measurements

To isolate the bottleneck, we must measure the time spent in each major component:

1.  **Weight Bandwidth Bottleneck:** Measure the time taken for a single, large matrix multiplication ($\text{Prefill}$) while keeping the KV cache size constant (e.g., $L=2000$). Compare this against the theoretical peak FLOPs of the GPU.
2.  **KV-Cache Traffic Bottleneck:** Measure the total time spent on **memory read/write operations** during the decoding phase. This requires profiling the memory access patterns (GPU memory controller utilization) during token generation, separating the time spent on arithmetic vs. data transfer.
3.  **CPU–GPU Transfer Bottleneck:** Measure the time taken specifically for the data transfer phase (e.g., loading the KV cache from System RAM to GPU VRAM, or moving intermediate results) across the entire sequence generation, focusing on PCIe/interconnect latency metrics.

**Numerical Example:**
Assume:
*   Prompt Processing (Prefill, $L=2000$): $T_{\text{prefill}} = 0.5$ seconds.
*   Decoding (Generating 300 tokens): $T_{\text{decode}} = 10.0$ seconds.
*   Total Time: $T_{\text{total}} = 10.5$ seconds.

If the system was purely compute-bound during prefill, the time per token during decoding would be $10.0 \text{ s} / 300 \approx 33.3 \text{ ms}$. If the system is memory-bound during decoding, this time might inflate to $50 \text{ ms}$ or more, depending on the latency of the system RAM access.
