### 1. Lifecycle Trace: Prefill vs. Decode

The degradation in latency is driven by the divergence in memory access patterns between the **prefill** phase (generation of the prompt response) and the **decode** phase (generating the actual output tokens).

**Prefill Phase (Prompt-to-Response):**
During the initial prompt processing, the 7B model generates the entire response (e.g., 300 tokens) from scratch.
*   **Action:** The KV-cache is computed for all $N_{total}$ tokens in the conversation history (prompt + history).
*   **Traffic:** High. All weights (W, KV, O) are accessed simultaneously or in tight, sequential windows to compute the output logits.
*   **Reusability:** The KV-cache is discarded after this pass; no subsequent tokens depend on this specific KV state.

**Decode Phase (Token-by-Token):**
As the conversation progresses, the system processes each new token individually.
*   **Action:** The model re-computes the KV-cache for the *single* new token being generated. The old KV state (from the previous token) is **reused** and moved to the next slot.
*   **Traffic:** Low per-token. The model only needs to access the weights required for the current token, plus the reused KV state and the newly generated weights.
*   **Reusability:** High. The KV state persists across the entire generation pass.

**Why Latency Degrades:**
The "excellent prompt-processing throughput" is misleading because it masks the high peak memory bandwidth required during the initial **prefill**. While the *rate* of prompt completion might be high, the *time* required to compute that initial cache and perform the heavy initial weight access dominates the total generation time. Once the prompt is generated, the system relies on the **reused** KV-cache. If this reused state cannot fit in L3 cache (or even L2), it must be loaded from system RAM, causing a significant bottleneck that scales linearly with the total conversation length.

---

### 2. Hardware Stress Dissection & Latency Mismatch

**Why Prompt Processing $\neq$ Interactive Latency:**
*   **Prefill Stress:** Prefill involves massive, parallel weight access across the entire context window to generate the response. The system's primary stress here is **memory bandwidth**. If the GPU lacks sufficient L3 cache and the model cannot fit in L2, the prefill time is dictated by how fast the data can be streamed from System RAM to the GPU.
*   **Decode Stress:** Decode involves sequential weight access (one token at a time) and the reuse of the KV-cache. The primary stress is **memory bandwidth again**, but specifically for the *reused* KV state and the *new* KV state for the current token.
*   **The Paradox:** A high prompt-to-token ratio (e.g., 300/2000 = 0.15) suggests the system is very fast at the start. However, if the total generation time is $T_{total} = T_{prefill} + N_{dec} \times T_{decode}$, and $T_{prefill}$ is huge due to initial bandwidth saturation, the *per-token* latency ($T_{dec}$) remains constant or increases slightly due to the growing total context size, regardless of the initial ratio. The user experiences constant latency, not "improving" latency per token.

**Why High Prompt-to-Token Doesn't imply Low Latency:**
The metric "prompt-processing throughput" typically measures **tokens generated per second** (tokens/s). This is a **rate**, not a **latency** metric.
*   Example: Generating 300 tokens in 1 second yields 300 tokens/s.
*   However, if the first 100 tokens take 5ms to generate (due to memory pressure), the next 200 tokens take 5ms each. The *average* speed is 200 tokens/s, but the *average* latency is 5ms. The system appears slow because the initial burst is delayed.

### 3. Scaling Effects: 2k to 8k Tokens

Increasing context from 2,000 to 8,000 tokens introduces two distinct bottlenecks:

1.  **Prefill Growth:** The initial generation (prefill) now covers 8,000 tokens instead of 2,000. Since the model weights fit but the KV cache (KV weights) do not, the *prefill time* scales linearly with context size. The system spends significantly more time computing the initial KV states.
2.  **Decode Bottleneck (The Real Culprit):** The **decode phase** scales linearly with context size. As the conversation grows, the frequency of **reused KV states** increases.
    *   In a 2,000-token conversation, the system generates ~200 new KV states and reuses ~1,800 old ones.
    *   In an 8,000-token conversation, the system generates ~800 new KV states and reuses ~7,200 old ones.
    *   **Memory Bandwidth Impact:** As the number of reused KV states grows, the total KV cache traffic (KV+O) hitting the memory hierarchy scales up. If the system RAM (SRAM) cannot handle the growing stream of reused KV states, the effective bandwidth available for decoding drops, causing latency to increase non-linearly or linearly depending on the hierarchy hit rates.

**Role of Memory Bandwidth:**
The bottleneck is almost certainly **System Memory Bandwidth (SRAM)**, not the GPU's compute capability or L3 cache size (assuming L3 is not the limiting factor for the 2k case). The system must stream data from DDR memory to the GPU's SRAM during decoding. If the rate of new KV generation outpaces the rate of memory transfer for the reused states, decoding becomes the new bottleneck.

### 4. Separating Claims: True vs. Implementation-Dependent

| Claim | Verdict | Reasoning |
| :--- | :--- | :--- |
| **"KV Cache does not fit in L3, causing latency."** | **True** (High probability) | Standard practice for 7B models on consumer GPUs (e.g., A100/V100). L3 is often too small for full context or large KV states. |
| **"Moving KV to SRAM increases per-token latency."** | **True** (If not optimally utilized) | If the system relies on L2 cache for the reused KV states, moving them to SRAM forces a L2-to-SRAM transfer, which is significantly slower than L2-to-SRAM (reduced latency) or L3-to-SRAM (worse latency). |
| **"High prompt-to-token ratio guarantees high throughput."** | **Depends on Implementation** | Throughput (tokens/s) is a rate metric. It does not correlate with per-token latency. A high ratio can mask a high initial memory load. |
| **"Prefill latency dominates total generation time."** | **Depends on Implementation** | True if the initial memory bandwidth saturation is severe. False if the system is optimized for sequential decode traffic (e.g., using specific prefetching or mixing strategies). |
| **"Kernel support (e.g., `torch.compile`, `flash-attn`) is irrelevant to latency."** | **False** | These features explicitly optimize the memory access patterns (e.g., `flash-attn` moves KV/O access to SRAM, `flash` operations reduce compute). They directly reduce latency. |

### 5. Diagnostic Measurements

To distinguish between the three potential bottlenecks, perform the following controlled comparisons:

1.  **Measure L2 Cache Hit Rates (Prefill vs. Decode):**
    *   *Method:* Compare the time required to generate the first 100 tokens vs. the next 100 tokens (or a 20k token context test).
    *   *Expected Result:* If L2 cache hit rates drop significantly between the first 100 tokens and the rest, the **L2 cache** is the bottleneck. If L2 hit rates stay high but latency still increases, **SRAM bandwidth** is the bottleneck.

2.  **Measure VRAM Utilization / Kernel Overhead:**
    *   *Method:* Run the same experiment with and without `torch.compile` or `flash-attn` enabled.
    *   *Expected Result:* If latency drops drastically without `flash-attn` (which moves KV/O to SRAM), then the **kernel overhead** or **data movement** to/from SRAM is the bottleneck. If latency remains high even with `flash-attn`, the bottleneck is likely **memory bandwidth** (SRAM) or **compute** (if the model is heavily unoptimized).

3.  **Measure SRAM Bandwidth vs. Compute:**
    *   *Method:* Run the experiment on a GPU with a fixed amount of L3 cache (e.g., by using a smaller model or simulating a smaller context) while keeping the same context size.
    *   *Expected Result:* If latency increases when L3 is artificially reduced (by swapping a smaller model or simulating smaller L3), the bottleneck is **L3 size**. If latency increases on the *same* hardware but the *same* model size, the bottleneck is **System Memory Bandwidth (SRAM)**.

### Small Numerical Example

Assume a 7B model with 2,000 tokens context.
*   **Prefill:** Takes 2.0s.
*   **Decode:** Takes 20.0s (approximate, assuming 20 tokens/sec decode speed is typical for this memory configuration).
*   **Total Time:** $2.0s + (200 \text{ tokens} \times 20.0s/\text{token}) = 4,020s \approx 67$ minutes.

If the conversation grows to 8,000 tokens:
*   **Prefill:** Takes 4.0s (scaling linearly).
*   **Decode:** Takes 40.0s (scaling linearly, assuming constant per-token latency).
*   **Total Time:** $4.0s + (800 \text{ tokens} \times 40.0s/\text{token}) = 32,044s \approx 89$ minutes.

**Conclusion:**
The total time increases significantly (from ~67 to ~89 mins), but the *per-token* latency remains constant (20s). This confirms that the system is experiencing **constant interactive latency** due to the scaling of the **reused KV-cache**, rather than a degradation in prompt processing speed. The bottleneck is the inability to sustain the memory bandwidth required to stream the growing stream of reused KV states, not the initial prompt generation speed.
