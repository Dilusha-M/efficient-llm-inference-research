### Task 4 — Validity Audit
**Threats to Validity (CPU/CUDA/Vulkan Comparison):**

1.  **Threat: Workload/Output Comparability (Irrelevant vs. Hardware)**
    *   **Description:** The two backends (CPU and CUDA) are performing the exact same task (LLM generation) on the exact same model architecture and prompt. However, the "workload" (the sequence of operations) differs significantly between CPU and GPU.
    *   **Disclosure:** To ensure comparability, one must use a **same-shot evaluation**. This means running the exact same prompt and model configuration on *both* backends simultaneously, or using a benchmark suite that normalizes the operations. Simply comparing raw speed is misleading because the CPU might be doing fewer operations per second than CUDA due to the different algorithms, even if the output quality is identical.
    *   **Control:** Use a **Same-Shot Benchmark**. Run the same prompt length and model configuration on both backends concurrently to isolate the hardware effect, or use a framework that maps operations to a common logical unit.

2.  **Threat: Non-Determinism / Variability**
    *   **Description:** The model runs three times. Hardware (CPU/GPU) and software (runtime environment) are not perfectly deterministic.
    *   **Disclosure:** Variance in results (e.g., one run generates 100 tokens, the next 102) makes it impossible to claim a definitive superiority of one backend over the other based solely on these three runs.
    *   **Control:** **Replication Count.** Run the benchmark many more times (e.g., 50 runs per backend) to establish a standard deviation. A 3-run test is insufficient to claim validity.

3.  **Threat: Memory Contention / Interference**
    *   **Description:** In a CPU comparison, the CPU is single-core (or limited threads). In a CUDA comparison, all layers are offloaded.
    *   **Disclosure:** If the CPU is sharing resources (like shared system RAM for OS) with the GPU (which is offloading layers), there could be contention. If the CPU is single-threaded and the GPU is multi-threaded, the GPU might suffer from "stuttering" (latency spikes) due to the CPU acting as a bottleneck for shared memory or system calls.
    *   **Control:** Isolate the hardware. Run the CPU comparison on a dedicated single-core machine, and run the CUDA comparison on a dedicated multi-core GPU with sufficient VRAM and power supply headroom.

4.  **Threat: Latency vs. Throughput Confounding**
    *   **Description:** A CPU might have high *throughput* (tokens/sec) because it's doing fewer operations per second, but high *latency* (ms/tok) because it's doing many operations per second. A GPU might have high *throughput* but also high *latency*.
    *   **Disclosure:** The user experience depends on the **Total Wall-Clock Time** (Latency), not just the raw speed metric (Throughput). Optimizing for throughput might make a CPU look faster than a GPU, but if the GPU is slower per token, the user experience is worse.
    *   **Control:** Measure **Latency (Time per Token)**, not just speed. Compare the 95th percentile latency of the CPU vs. the GPU.

### Task 5 — User-visible latency
**Definitions:**
*   **Prompt-evaluation throughput:** How fast the LLM processes the user's input prompt and generates the first response token (Token 1).
*   **Decode throughput:** How fast the LLM processes subsequent tokens (Tokens 2 through N) after the first token has been generated.
*   **Total wall-clock time:** The sum of the time spent in all three phases: Prompt Processing -> Model Generation -> Response Formatting.

**Symbolic Equation:**
$$T_{total} = T_{prompt\_processing} + T_{first\_token} + T_{decode\_throughput}$$

*Where:*
*   $T_{prompt\_processing}$ = Time to evaluate the 2,000-token prompt.
*   $T_{first\_token}$ = Time to generate the first token.
*   $T_{decode\_throughput}$ = Time to generate the remaining 199 tokens.

**Example of optimizing prompt processing barely changing user experience:**
*   **Scenario:** A user types a 500-word document to generate a summary.
*   **Action:** You optimize the prompt processing to load the 2,000-token context (if it wasn't already loaded) or optimize the prompt engineering to make the prompt more concise.
*   **Result:** The time to first token ($T_{first\_token}$) remains exactly the same because the model has already seen the prompt. However, the **total wall-clock time ($T_{total}$)** might decrease slightly because the system avoids a redundant prompt evaluation cycle.
*   **User Experience:** The user sees the text appear instantly. The *subjective* experience of waiting for the first token is unchanged (or improved if the previous slow path was waiting for a prompt evaluation that was stuck), but the *objective* time to generate the response is reduced by the optimization of the prompt processing phase.

**Crucial Note:** Do not equate "tok/s" with "latency" without specifying the phase. "tok/s" describes *throughput* (rate), while "latency" describes *delay* (time). A model can have high tok/s but high latency (slow per token), or high tok/s and low latency (fast per token).
