### Task 1 — quantization tradeoff

**Assumptions & Constraints:**
*   **Model Size:** 8 Billion parameters (8B).
*   **Memory Profiles:** 8.0 GB Q8_0, 4.8 GB Q4_K_M.
*   **Hardware:** 6 GB GPU with 5.2 GB free memory.
*   **Runtime:** Inference execution.
*   **Assumption:** The 8.0 GB file size represents the *static* model weight storage (pre-inference). Q8_0 is 2-bit per precision, while Q4_K_M is 4-bit with K-vocab scaling (16-bit effective weight storage due to scaling).

**Memory Pressure Analysis:**
*   **Q8_0:** The static model (8.0 GB) exceeds the available GPU memory (5.2 GB). Even if the model is not loaded entirely, the quantized file alone consumes 8.0 GB. This creates an immediate **OOM (Out Of Memory)** condition upon loading the model into GPU memory, regardless of context size.
*   **Q4_K_M:** The static model (4.8 GB) is within the available 5.2 GB. However, Q4_K_M introduces "K-vocab scaling" (scaling the KV cache to match the output vocabulary size), which significantly increases the *dynamic* runtime memory footprint beyond just the static 4.8 GB. It is possible that the KV cache grows to 6 GB or more during inference, pushing the system over the 5.2 GB free limit.

**Why File Size is Not a Complete Runtime Estimate:**
File size is a static metric representing the compressed weights. It fails to account for:
1.  **KV Cache Expansion:** As noted above, Q4_K_M expands the memory footprint dynamically based on context length.
2.  **Activation/Attention Memory:** Modern LLMs often keep activations in HBM (Host Global Memory) or GPU HBM1 during attention layers, adding to the static model size.
3.  **Runtime Buffer:** Inference engines (like llama.cpp) often maintain buffers for gradients, optimizer states, or intermediate activations that are not part of the quantized file.

**Two Required Quality/Performance Measurements:**
To declare a format better, one must run a controlled inference benchmark under identical conditions (same prompt, same context length) and measure:
1.  **Token Generation Time per Second (Token Rate):** Measures raw throughput.
2.  **Stability / Memory Stability:** Measures how often the system crashes or stalls due to memory pressure during inference.

**Conclusion on "Is Q4 always faster?"**
No. While Q4_K_M offers better compression and often allows for a larger context window (reducing the ratio of KV cache to model size), it increases the per-token computational cost (due to K-vocab scaling and larger batch sizes required for stability) and memory overhead. In specific cases where the hardware cannot handle the K-vocab scaling overhead, Q8_0 (though likely OOM) or Q4_A50 (if available) might be slower due to reduced parallelism efficiency. Therefore, Q4 is not inherently faster; it is a trade-off between compression efficiency and computational intensity.

### Task 3 — Robust aggregation

**Pseudocode Implementation:**

```python
def calculate_average_throughput(run_data):
    # run_data is a list of dictionaries containing 'tokens_per_second'
    
    # 1. Validate records: Check if 'tokens_per_second' is a number and >= 0
    valid_records = []
    for run in run_data:
        if isinstance(run.get('tokens_per_second'), (int, float)):
            if run['tokens_per_second'] >= 0:
                valid_records.append(run['tokens_per_second'])
            else:
                record = {
                    "run_id": run.get('run_id'),
                    "status": "FAILED",
                    "message": "Negative or non-numeric tokens_per_second"
                }
                # Store failed record explicitly for visibility, do not filter it out
        else:
            record = {
                "run_id": run.get('run_id'),
                "status": "FAILED",
                "message": "Invalid tokens_per_second value"
            }
            valid_records.append(record)

    # 2. Compute median for successful runs
    if valid_records:
        sorted_records = sorted(valid_records, reverse=True)
        median = sorted_records[len(sorted_records) // 2]
    else:
        median = None

    return median, valid_records
```

**Handling Fewer Than Two Successful Runs:**
If fewer than two runs succeed (i.e., `len(sorted_records) < 2`), the function returns `None` for the median. In this case, reporting the result requires a fallback mechanism:
1.  **Display the count:** "Only N runs succeeded."
2.  **Report the minimum:** "The median speed of the N successful runs was X tok/s."
3.  **Report the maximum:** "The median speed of the N successful runs was X tok/s."
4.  **Provide a warning:** "Data is insufficient for a meaningful median calculation due to low sample size."

This approach ensures the user understands that while a median *can* be calculated from a single run, it is not statistically robust for a distribution, and the system does not silently discard the failure but rather reports the specific constraint.

### Task 4 — Validity Audit

**Threats to Validity (CPU/CUDA/Vulkan Comparison):**
1.  **Threat 1: Workload/Output Comparability (Hardware vs. Software Simulation)**
    *   **Threat:** The CPU running on a physical architecture (e.g., x86) vs. CUDA on NVIDIA GPUs, and Vulkan on different architectures (e.g., Apple Silicon vs. x86) are fundamentally simulating different instruction sets and memory access patterns.
    *   **Control/Disclosure:** Use **same-architecture** runs. Run the Vulkan backend on a physical CPU or on a GPU that matches the target architecture of the CPU backend (if virtualization is used, ensure the hypervisor emulation mode is consistent). Alternatively, run the CPU backend on a GPU using the exact same hardware configuration (same VRAM, same GPU generation) as the Vulkan backend.
2.  **Threat 2: Hardware Variance (GPU Differences)**
    *   **Threat:** The 8-thread CPU might be a high-end server CPU with a specific memory latency profile, while the CUDA GPU is a consumer card with different memory bandwidth and coherence issues.
    *   **Control/Disclosure:** Use **single-core** runs or runs where the GPU is the only active accelerator. Ensure the GPU is the same model generation (e.g., all RTX 3090s) with the same driver version.
3.  **Threat 3: Driver/Compiler Version (Software Heterogeneity)**
    *   **Threat:** Differences in CUDA SDK versions or Vulkan driver versions between runs can cause subtle differences in optimization levels, threading models, or memory management algorithms.
    *   **Control/Disclosure:** Record the exact CUDA/DirectX version strings used and force them to be identical across all runs.
4.  **Threat 4: Workload/Output Comparability (Latency vs. Throughput)**
    *   **Threat:** Comparing raw throughput (tokens/sec) vs. latency (time per token) is ambiguous. A GPU might be 2x faster in throughput but 2x slower in latency due to higher internal clock speeds or different overhead structures.
    *   **Control/Disclosure:** Use **same-architecture** runs where possible, or explicitly report both metrics and normalize them. For a true validity check, ensure the *user-visible* latency (time to first token, time to last token) is comparable across backends, not just the raw rate.

**Specific Note on Threat 4:** The prompt asks for a threat concerning "workload/output comparability, not just hardware or software." The most direct threat here is **Latency vs. Throughput Anomalousness**. If CPU and GPU show a 2:1 ratio (e.g., 200ms latency vs 400ms latency) but the GPU is 2x faster in raw tokens, the latency metric is misleading for the user. The control is to report **Latency** as the primary metric, not just `tokens_per_second`, and normalize by the number of threads used or ensure the hardware configuration is identical.

### Task 5 — User-visible latency

**Definitions and Distinctions:**
*   **Time to First Token (TTFT):** The wall-clock time from the start of the prompt to the generation of the first token. This reflects the latency of the prompt processing phase.
*   **Prompt-Evaluation Throughput:** The number of tokens processed per second (e.g., tokens per second spent on parsing the user input). This is a rate, not a wall-clock time.
*   **Decode Throughput:** The number of tokens generated per second (tokens per second). This is a rate, not a wall-clock time.
*   **Total Wall-Clock Time:** The sum of all processing phases (TTFT + Prompt Eval + Decode + Post-processing).

**Symbolic Equation for Total Time:**
$$ \text{Total\_Time} = \text{TTFT} + \text{Prompt\_Eval\_Latency} + \text{Decode\_Latency} + \text{Post\_Processing\_Latency} $$

*Where:*
*   $\text{TTFT}$ is the latency to the first token.
*   $\text{Prompt\_Eval\_Latency} = \frac{\text{Total\_Prompt\_Tokens}}{\text{Prompt\_Eval\_Throughput}}$
*   $\text{Decode\_Latency} = \frac{\text{Total\_Generated\_Tokens}}{\text{Decode\_Throughput}}$
*   $\text{Post\_Processing\_Latency}$ accounts for UI updates or API overheads.

**Example where optimizing prompt processing barely changes user experience:**
Consider a scenario where the user prompt is extremely verbose (e.g., 10,000 tokens) but the model is heavily optimized for the specific vocabulary of that prompt (few-shot learning).
*   **Scenario:** The model's attention mechanism finds that 9,000 tokens are redundant or repetitive based on previous context.
*   **Effect:** The **Prompt-Evaluation Throughput** is high (many tokens processed quickly), but the **TTFT** is negligible because the model ignores most of the tokens instantly.
*   **Result:** Optimizing the prompt processing (reducing the number of tokens sent to the model) yields a small reduction in the *rate* of tokens processed, but the *wall-clock time* remains largely unchanged because the bottleneck is the model's inference speed, not the parsing speed. The user perceives the response time as constant, even if the internal computational load on the CPU/GPU is higher than necessary.
