### Task 3 — robust aggregation

**Pseudocode:**

```python
def robust_aggregate(speeds, is_last_run_warning_out_of_memory):
    # Initialize a list to store successful runs
    successful_records = []
    
    # Validate records
    valid_records = []
    for i, speed in enumerate(speeds):
        # Check if this is the last run and if it reported OOM
        if i == len(speeds) - 1 and is_last_run_warning_out_of_memory:
            # Log failure explicitly
            print(f"Run {i+1} ({speed:.1f} tok/s) failed due to OOM.")
            valid_records.append(None) # Mark as invalid
        else:
            # Validate numeric range (optional, but robust)
            if speed >= 0:
                valid_records.append(speed)
    
    # Check if fewer than two runs succeed (i.e., 0 successful runs)
    successful_count = len(valid_records)
    
    if successful_count < 2:
        # Report the result: Median of successful runs (or 0 if none)
        median_speed = 0.0
        if successful_count > 0:
            median_speed = median_of_list(valid_records)
        
        report_result(f"Median decode speed: {median_speed:.1f} tok/s (based on {successful_count} successful runs).")
    else:
        median_speed = median_of_list(valid_records)
        report_result(f"Median decode speed: {median_speed:.1f} tok/s.")

# Helper function
def median_of_list(lst):
    if not lst:
        return 0.0
    mid = len(lst) // 2
    sorted_lst = sorted(lst)
    return sorted_lst[mid]
```

**Handling Fewer Than Two Successful Runs:**
If the script reports fewer than two successful runs, the logic dictates reporting the **median of the successful runs only**. The code explicitly avoids treating the failure as zero by storing `None` in the list and calculating the median strictly over the valid numbers provided.

### Task 4 — validity audit

**Threats to Validity:**
1.  **Threat 1: Hardware / Software Heterogeneity.**
    *   **Threat:** The comparison assumes all backends (CPU/CUDA/Vulkan) are running on the *same* machine, but the user might be running them on different machines or configurations (e.g., a specific NVIDIA RTX vs. a generic CPU).
    *   **Control:** Run the same benchmark suite on a controlled, isolated environment (e.g., a single Docker container with identical OS, drivers, and kernel versions).
2.  **Threat 2: Workload / Output Comparability.**
    *   **Threat:** The user might be comparing the raw throughput of the CPU vs. CUDA vs. Vulkan using different generation strategies (e.g., using different quantization levels, different batch sizes, or different prompt engineering). This makes the raw numbers incomparable.
    *   **Control:** Use a **canonicalized workload**: Fixed quantization (e.g., Q4_K_M), fixed batch size, fixed context size, and a standardized prompt.
3.  **Threat 3: Kernel / Driver Bug.**
    *   **Threat:** A bug in the Vulkan driver or the specific Vulkan implementation of a particular GPU layer could cause false positives (e.g., reporting Vulkan as 1000ms/s when it's actually 1ms/s due to a race condition).
    *   **Control:** Run the benchmark with and without the specific driver/kernel versions in question. Run multiple times with different random seeds to detect reproducibility issues.
4.  **Threat 4: Data Leakage / State Persistence.**
    *   **Threat:** If the benchmark is run across multiple sessions, the model state or random seeds might persist, leading to non-deterministic results where the second run is "faster" just because the system was "warmed up."
    *   **Control:** Run the benchmark in a strictly isolated session with no prior runs. Ensure random seeds are reset for every run.

### Task 5 — user-visible latency

**Explanation of Metrics:**

1.  **Time to First Token (TTFT):**
    *   **Definition:** The time elapsed from the moment the user sends the prompt until the very first token is returned to the user.
    *   **Impact:** This is the critical metric for UX. It determines how long the user has to wait before reading any content.

2.  **Prompt-Evaluation Throughput:**
    *   **Definition:** The number of tokens processed per unit of time (e.g., tokens per second) during the prompt processing phase (before decoding).
    *   **Impact:** This measures how efficiently the model handles the input. High throughput means the prompt is processed quickly, potentially reducing TTFT.

3.  **Decode Throughput:**
    *   **Definition:** The number of tokens generated per unit of time (e.g., tokens per second) during the decoding phase (after the prompt is evaluated).
    *   **Impact:** This measures the speed of generation. High decode throughput means the user receives tokens rapidly once the prompt is ready.

4.  **Total Wall-Clock Time:**
    *   **Definition:** The sum of all time phases (TTFT + Prompt-Processing Time + Decode Time) measured from prompt input to final output completion.
    *   **Impact:** The user-visible latency.

**Symbolic Equation:**
$$ T_{\text{total}} = T_{\text{TTFT}} + T_{\text{prompt\_eval}} + T_{\text{decode}} $$

**Example where optimizing prompt processing barely changes experience:**
*   **Scenario:** The user has a very fast CPU and a slow GPU (e.g., a 6 GB GPU with low compute units).
*   **Optimization:** Optimizing the prompt processing (e.g., by rewriting the prompt to be more concise or using a more efficient quantization for the weights).
*   **Result:** The optimization might reduce the **Prompt-Evaluation Throughput** by 10%, but the **Total Wall-Clock Time** remains roughly unchanged because the **Decode Throughput** (determined by GPU speed) is the bottleneck. The user's experience (waiting for the first token or reading the first few tokens) does not improve significantly, as the system is waiting for the GPU to process the output rather than the CPU to process the input. The bottleneck shifts from the prompt to the model decoding.
