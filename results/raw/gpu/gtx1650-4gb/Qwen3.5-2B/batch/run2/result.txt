# Task 1 — quantization tradeoff

**Assumptions and Data Constraints**
*   **Model Size:** 8B parameters (approx. 7.68B float32).
*   **File Sizes:** $8.0\text{ GB}$ (Q8_0), $4.8\text{ GB}$ (Q4_K_M).
*   **Hardware:** 6 GB GPU with **5.2 GB free memory**.
*   **Runtime Estimate:** The 8.0 GB file is a static file size; it does not account for the dynamic memory required for activations, gradients, or KV cache during inference. A 4.8 GB file is even smaller.

### Memory Pressure Analysis
The **Q8_0** format creates **severe memory pressure**.
*   **Static vs. Dynamic:** The 8.0 GB file represents the static weight storage. However, runtime inference requires significantly more memory to hold activations (hidden state) and gradients. Unless the model has been pre-quantized (statically quantized to Q8), the *dynamic* memory usage for an 8B model on an 8B Q8 model often exceeds 10 GB, easily exhausting the 6 GB GPU's 5.2 GB free budget.
*   **Q4 Advantage:** The 4.8 GB file is smaller, suggesting better static memory efficiency. However, even if the file size were identical to Q8_0, Q4_K_M offers a quantization factor of 4, meaning the same *model size* requires roughly $1/4$ the memory of Q8 for weights. Therefore, if the 8B Q8 file is 8.0 GB, the equivalent Q4 model would likely fit much better in memory, potentially leaving headroom for activations.
*   **Critical Limitation:** Without knowing the specific quantization factor (e.g., is the 8.0 GB model 8B Q4 or 8B Q8?), we cannot mathematically prove the 4.8 GB file is lighter *in terms of memory footprint*. A 4.8 GB Q4 file could theoretically contain 16B weights if the model is not Q4_K_M.

**Conclusion on Memory Pressure:** The Q8_0 file creates a definite risk of OOM (Out of Memory) because the static file size alone does not cover the dynamic runtime requirements. The Q4_K_M file is a better candidate for low-memory inference, but its advantage in memory is only clear if the model size is actually 16B (implied by the factor of 4). If the model is 8B, the 4.8 GB file is still lighter in static memory, but the dynamic overhead of Q4 activations is not eliminated.

### Why File Size is Not a Complete Runtime Estimate
1.  **Activation Memory:** During inference, the hidden state and gradients must reside in GPU memory. For a 6GB GPU, the *dynamic* memory usage of an 8B model is often closer to the file size than the *static* file size, especially in quantized formats where activations are not pre-quantized.
2.  **KV Cache:** Large context lengths (not specified here, but common for 8B models) require significant KV cache memory, which is not stored in the model file.
3.  **Gradient Memory:** During training, gradients are large; during inference, they are small, but still required.

### Two Quality/Performance Measurements Needed
Before declaring one format "better," you must measure:
1.  **Quantization Factor:** Confirm the actual reduction in parameter count (e.g., 4.8 GB / 8.0 GB $\approx$ 0.6, implying a factor of ~4.1, or explicitly check the Q4_K_M factor). If the factor is not 4, the memory savings are misleading.
2.  **Throughput/Inference Speed:** Run a benchmark (e.g., LM Studio, vLLM) to compare `tokens/sec` or `tokens/s` for both formats. A 4.8 GB file might be faster in static memory but slower in throughput due to lower precision and higher memory bandwidth contention.

### Conclusion
Do not claim Q4 is always faster. Q4 is generally preferred for **memory efficiency** (fewer parameters = less activation memory), but it is not always preferred for **throughput** (often requires more precision to maintain speed). The Q8_0 file is likely too large for a 6GB GPU due to dynamic activation requirements, whereas the Q4_K_M file is the safer bet for running the model.

### Conservative Procedure for Context Size and Offload
1.  **Step 1: Attempt with minimal context and offload.**
    *   *Action:* Launch the model with the smallest supported context size (likely 128 or 256 tokens) and enable GPU layer offloading.
    *   *Goal:* Verify that the model fits in VRAM and that the offload mechanism (e.g., `offload_layers` in llama.cpp) is functioning correctly.
2.  **Step 2: Measure VRAM usage and offload ratio.**
    *   *Action:* Run the minimal context launch and record the GPU memory usage (VRAM) and the ratio of VRAM used to total model size (or the offload ratio).
    *   *Goal:* Determine the optimal context size that fits within the 16 GB system RAM while ensuring the GPU offload ratio stays below 80-90% (to prevent OOM on the GPU).
3.  **Step 3: Increment context size.**
    *   *Action:* Increase the context size by 128 tokens (or 256 tokens if supported) while keeping the offload setting.
    *   *Goal:* Check if the VRAM usage increases significantly enough that the model would fail to launch on the 6GB GPU even with the offload.
4.  **Step 4: Finalize configuration.**
    *   *Action:* Once the context size is found where the 6GB GPU can run the full 512-token prompt without OOM, set the context size to that specific value.
    *   *Constraint:* Do not increase context size beyond the point where the 6GB GPU is exhausted.

### Telemetry to Record
To make the decision robust, record the following metrics:
*   **VRAM Usage (MB):** The exact GPU memory consumed during the launch.
*   **Offload Ratio:** `(VRAM Used by Offloaded Layers / Total Model Size in VRAM)`.
*   **System RAM Used (MB):** Total RAM consumed by the process.
*   **Decoding Throughput (tok/s):** Performance at the chosen context size.

An unsafe or misleading success occurs if:
*   **Context Size is increased:** If the model launches successfully at the chosen context size but VRAM usage is dangerously close to 100% (e.g., 95%), increasing the context size will almost certainly cause OOM.

*   **Decoding Throughput is artificially high:** If the throughput metric looks good but the VRAM usage is high, it indicates poor efficiency or potential memory leaks, not necessarily better inference quality.

# Task 3 — robust aggregation

### Pseudocode for Robust Aggregation

```python
def robust_aggregate_speeds(decode_speeds):
    # decode_speeds: List[float] from the runs
    # Returns: float, the median of successful runs; -1.0 if fewer than 2 succeed
    
    successful_runs = []
    
    for speed in decode_speeds:
        # Validate record: Check if speed is a valid number
        if not isinstance(speed, (int, float)):
            print(f"Warning: Invalid speed {speed}, skipping.")
            continue
            
        # Check for non-negative speed
        if speed < 0:
            print(f"Warning: Negative speed {speed}, skipping.")
            continue
            
        # Keep the failed run visible (add to a separate list for reporting)
        if speed < 0:
            failed_runs.append(speed)
            continue
            
        successful_runs.append(speed)
    
    # Compute median
    if len(successful_runs) == 0:
        raise ValueError("No successful runs found.")
    
    median_speed = median(successful_runs)
    
    return median_speed

def median(values):
    sorted_vals = sorted(values)
    n = len(sorted_vals)
    mid = n // 2
    if n % 2 == 1:
        return sorted_vals[mid]
    else:
        return (sorted_vals[mid - 1] + sorted_vals[mid]) / 2

def report_result(meaningless_runs, successful_runs, failed_runs, median_speed):
    # Determine if fewer than two runs succeeded
    if len(successful_runs) < 2:
        print(f"WARNING: Only {len(successful_runs)} runs succeeded. Result cannot be statistically significant or robust.")
        print(f"Median speed: {median_speed} tok/s.")
        print(f"Failed runs (visible): {sorted(failed_runs)}")
    else:
        print(f"Median speed: {median_speed} tok/s.")
```

**How to report the result if fewer than two runs succeed:**
Instead of treating the failure as zero, the output must explicitly state the number of successful runs and the median of those runs. The function above prints a warning message detailing the specific speed of the failed run and lists the failed runs. This allows the user to see exactly what went wrong (e.g., "Only 1 run succeeded. Median: 41.5 tok/s.") rather than receiving a single, meaningless aggregate number.

# Task 4 — Validity Audit

**Four Threats to Validity**

1.  **Threat: Inconsistent Workload/Output Comparability**
    *   **Description:** If the CPU and CUDA backends run *different* portions of the same model (e.g., CPU runs the last 100 layers while CUDA runs the first 100 layers), the outputs will not be directly comparable.
    *   **Control/Disclosure:** Ensure the exact same set of layers is loaded into both backends. Alternatively, run the exact same layer sequence on both backends and compare the outputs of those specific layers directly.

2.  **Threat: Non-Random Workload / Bias**
    *   **Description:** The "three times" repetition might not be random. If the same sequence of prompts is used for all three runs, the results are biased. If the system is optimized for the specific inputs used (e.g., all 200 tokens are prompts), the "generation" phase is not being tested.
    *   **Control/Disclosure:** Use a large, diverse, and random batch of prompts (e.g., 10,000 unique prompts) to ensure the model is not overfitted to the test set.

3.  **Threat: GPU Utilization / Power Efficiency**
    *   **Description:** The CPU might be running at high utilization while the GPU is idle or underutilized, leading to a misleading perception of performance.
    *   **Control/Disclosure:** Monitor the utilization percentages of both the CPU and GPU during the benchmark run. If the GPU is not near 100% utilization, the "speed" reported is likely an artifact of the CPU's performance rather than the model's capability.

4.  **Threat: Hardware / Software Compatibility**
    *   **Description:** The comparison assumes the hardware (CPU/GPU architecture) and software stack (CUDA version, Vulkan API) are identical or that the differences are purely architectural.
    *   **Control/Disclosure:** Explicitly list the specific hardware models and driver versions used. If the hardware is significantly different (e.g., an old CPU vs. a new GPU), the results are invalid for generalization.

# Task 5 — User-visible latency

**Definitions and Distinctions**

1.  **Time to First Token (TTFT):** The wall-clock time from the moment a prompt is sent until the very first token of the response is generated. This is the most critical metric for user experience because it dictates how long the user waits to see *any* content.
2.  **Prompt-Evaluation Throughput:** The number of tokens processed *per unit of time* during the preparation of the response, independent of the number of tokens generated. This measures how fast the model can read the prompt and start generating.
3.  **Decode Throughput:** The number of tokens generated *per unit of time* during the generation phase. This measures the raw speed of the model's computation.
4.  **Total Wall-Clock Time:** The sum of all time components: TTFT + Prompt Processing Time + Decode Throughput Time.

### Symbolic Equation for Total Time
$$ \text{Total Time} = \text{TTFT} + \text{Prompt Time} + \frac{\text{Total Tokens}}{\text{Decode Throughput}} $$

Where:
*   $\text{TTFT}$ is the Time to First Token.
*   $\text{Prompt Time}$ is the time to process the input prompt.
*   $\text{Total Tokens}$ is the sum of prompt tokens + generation tokens.
*   $\text{Decode Throughput}$ is the tokens per second (tok/s).

### Example of Optimizing Prompt Processing
**Scenario:** A user has a 2,000-token prompt and 200 generated tokens. The user's experience depends heavily on how long it takes to *read* that prompt, not how fast the model generates the response.

**Example:**
*   **Optimization A (Optimize Prompt Processing):** You add a pre-processing step to the application that takes **0.1 seconds** to parse the 2,000 tokens (e.g., a specific regex parser that is slightly slower than a simple string check).
*   **Result:** The TTFT remains 0.01 seconds. The 200 generated tokens take 0.5 seconds (based on the decode throughput).
*   **User Experience:** The *perceived* latency remains unchanged. The user sees the first token almost instantly. However, your application is now **slower** overall because the pre-processing step adds overhead that was previously negligible.
*   **Conclusion:** Optimizing prompt processing barely changes the user's experience (TTFT) but significantly degrades the total wall-clock time.

*Note: "Tok/s" is a rate. Optimizing tok/s (generating 1000 tok/s) does not equate to optimizing TTFT. You can have a 1000 tok/s model that has a 2-second TTFT (slow start), while a 500 tok/s model might have a 0.1-second TTFT (fast start).*
