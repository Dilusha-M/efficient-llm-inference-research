# State Machine Workflow

The lifecycle of the `LlamaRunner` agent follows the state machine below. Transitions are handled via atomic operations or checkpointing.

1.  **Initialize:**
    *   **State:** `INITIAL`
    *   **Action:** Load `config.yaml`, parse `metadata.txt` (if present), and set hardware metadata.
    *   **Constraint:** Validate `context` (default 4096) and `generation_limit` (default 256). If overridden, apply new values.

2.  **Validation & Launch:**
    *   **State:** `VALIDATING`
    *   **Action:** Perform model instance validation (check `response.txt` or file existence). Attempt to launch the llama.cpp process with the specified backend (CUDA/Vulkan).
    *   **Constraint:** Do not mix results if model backend, hardware label, or driver environment changes.

3.  **Monitoring:**
    *   **State:** `MONITORING`
    *   **Action:** Wait for process completion.
    *   **Constraint:** Monitors may be unavailable or sampled sparsely. If a process fails to start or complete, the monitor is not written to.

4.  **Process Exit:**
    *   **State:** `EXITING`
    *   **Action:** Wait for process termination.
    *   **Constraint:** If `summary.json` is empty or invalid, exit immediately without generating `summary.json`.

5.  **Finalization:**
    *   **State:** `FINALIZED`
    *   **Action:** Write `summary.json`, `raw_output.txt` (if available), and `run_metadata.json`. Log `monitor.log` (if populated).
    *   **Constraint:** `raw_output.txt` is written unconditionally if it exists; otherwise, write an empty file.

6.  **Timeout / OOM / Malformed Output:**
    *   **State:** `FAILED`
    *   **Action:** Trigger a `process_failed` event.
    *   **Behavior:** Do not attempt to restart. Log a failure reason (e.g., "OOM", "Timeout", "Invalid Config"). Do not overwrite `summary.json`.

# Auditable Design

**Shell/Python Component Boundaries:**
*   **`config_loader.py`**: Handles YAML parsing, metadata file loading, and hardware metadata retrieval.
*   **`run_engine.py`**: Orchestrates the llama.cpp launcher, manages process lifecycle, handles timeout/oom checks, and writes the final artifacts.
*   **`process_manager.py`**: Manages the llama.cpp process, ensures it is not restarted, and monitors its exit status.
*   **`output_writer.py`**: Handles the writing of `summary.json`, `raw_output.txt`, and `run_metadata.json`.

**Metadata Schema:**
All metadata is stored in JSON files or direct string fields within the output.
*   `metadata.json`: `{ "env": "dev", "context": 4096, "gpu": { "type": "cuda", "version": "12.1", "layers": 4 }, "build": "nightly", "driver": "136.9" }`
*   `raw_output.txt`: Contains the raw prompt, response, and metrics (if available).

**Atomic-Write Convention:**
*   **Atomic Writes:** `summary.json`, `raw_output.txt`, and `run_metadata.json` are written atomically using `atomic_write` (Python standard library) to prevent race conditions where intermediate files are overwritten.
*   **Partial Writes:** `monitor.log` is written atomically if it exists. If a monitor fails, the log file remains empty.
*   **Error Handling:** If `atomic_write` fails (e.g., permission denied, binary mismatch), the exception propagates to `process_failed`.

**Preservation of Stdout/Stderr:**
*   The `run_engine` writes `raw_output.txt` *only* if it can retrieve the raw response. If retrieval fails, the output is not written, but the process failure is logged. This ensures the *process* fails, but the *audit trail* is preserved.

# Analysis Integrity

**Prevention of Misleading Throughput:**
*   **Variable Counting:** The `token_count` variable in `summary.json` must be derived from the exact number of characters in the `response.txt` (including newline characters) using regex or string length calculation.
*   **Tokenization:** The parser must tokenize the model response *before* calculating metrics. It should not use the model's internal tokenizer unless explicitly configured.
*   **Partial Output Handling:** If the model fails to complete (OOM or timeout), `token_count` must be set to `0` or `None` in `summary.json`, rather than accumulating partial tokens. This prevents a "throughput comparison" where a slow process looks like high throughput relative to a fast one, or vice versa.

**Handling Unknown llama.cpp Output Formats:**
*   **Parser Strategy:** The `response.txt` parser must be flexible. It should attempt to parse the response using a standard llama.cpp tokenizer (e.g., from the `llama.cpp` library). If the format is unknown (e.g., binary stream, custom encoding), the parser should:
    1.  Attempt standard tokenization.
    2.  If the generated `tokens` list is empty, return a `None` or an empty string.
    3.  If the parser fails to parse, write an empty `response.txt` file and log a warning, ensuring the process fails.
*   **Safety:** Never hardcode a specific output format string; always fall back to standard llama.cpp behavior.

# Pre-merge Review

**Highest-Risk Design Flaws:**

1.  **Ambiguity in "Missing Output" Handling:**
    *   *Flaw:* The specification requires raw output for audit but does not specify what happens if the system cannot access the file system or model instance.
    *   *Risk:* A user might expect a cryptic `File not found` error, whereas the design should ensure the audit trail (the file) is never lost, even if the process fails.
    *   *Fix:* Implement a fallback strategy where if `response.txt` cannot be retrieved, a placeholder file (`no_output_available.txt`) containing a generic empty response is generated. This ensures the "raw output" requirement is met even under network obsolescence.

2.  **Undefined Behavior for Unknown llama.cpp Formats:**
    *   *Flaw:* The parser is not explicitly defined to handle binary or custom llama.cpp output formats.
    *   *Risk:* If a model sends output in a binary format or a custom tokenizer, the runner might crash or generate incorrect metrics (e.g., counting bytes instead of tokens).
    *   *Fix:* The parser must attempt standard llama.cpp tokenization first. If the parser fails to parse the output, it must write an empty `response.txt` and log a failure reason, preventing the runner from crashing and allowing the failure to be logged rather than silently ignored.

3.  **Atomic-Write Overwrite Risk:**
    *   *Flaw:* Writing `summary.json` or `raw_output.txt` atomically without ensuring the file system allows binary or large data writes.
    *   *Risk:* If the process crashes during the write, the intermediate file might remain partially valid, or if the process restarts, the data might be corrupted.
    *   *Fix:* Use the standard Python `atomic_write` module (via `llama.cpp` or a wrapper) to ensure atomicity. Additionally, add a check in the runner to only write to files if the `atomic_write` succeeds and the file exists.
