## 2. State-Machine Workflow

The lifecycle of a benchmark run is defined by the following states:

### Init State
1.  **Validation:** Check model file exists and is valid llama.cpp. Check environment variables and config file.
2.  **Configuration:** Set defaults (context=4096, gen_limit=256, temp=0.7). If user overrides `context_override`, update defaults. If user sets `output_format`, accept it.
3.  **Hardware Setup:** Initialize CPU/CUDA/Vulkan resources. If hardware is missing, mark as "Hardware Missing".

### Process Execution State
4.  **Generate Model:**
    *   Check `output_format` for `raw` or `json`.
    *   If `raw`, print to `stdout` (or `stderr` if `stderr` is set).
    *   If `json`, write to `stdout` and `metrics.json`.
    *   If neither, print to `stdout` or `stderr` based on default.
5.  **Run Workload:** Execute the specified prompt (chat, batch, etc.).
6.  **Monitor & Process:**
    *   If `enable_monitoring` is true, start the llama.cpp process for monitoring.
    *   **Timeout Handling:** If `elapsed_seconds` exceeds 20 seconds, log timeout.
    *   **OOM Handling:** If `cuda` or `cpu` memory exceeds limits, log OOM error.
    *   **Monitor Failure:** If monitoring process terminates unexpectedly, check if `response.txt` is empty. If so, mark as "Monitor Failure" but allow `metrics.json` to be valid.
7.  **Process Exit:** Wait for process to finish.
8.  **Finalization:**
    *   Check `response.txt` for validity.
    *   If valid: Create `metrics.json`.
    *   If invalid: Create `audit_log.txt` with the exact prompt/response.
    *   Write `summary.txt`.
    *   Mark state as "Completed".

### Transitions on Events
*   **Timeout:** Transition to "Timeout Detected". Log `elapsed_seconds` > 20. Do not finish run.
*   **OOM:** Transition to "Memory Limit Exceeded". Log `cpu_usage_percent` > 100. Do not finish run.
*   **Monitor Failure:** If monitoring stops unexpectedly (e.g., crash, SIGKILL), check `response.txt` contents.
    *   If `response.txt` is empty: Transition to "Monitor Failure". Do not create `metrics.json`. Create `audit_log.txt` with prompt/response.
    *   If `response.txt` exists and is non-empty: Transition to "Success".
    *   Otherwise: Transition to "Unknown Failure".

## 3. Auditable Design

### Component Boundaries
*   **CLI Shell:** Handles argument parsing, config file reading, and process termination.
*   **Worker Process:** Handles llama.cpp execution, resource management, and I/O.
*   **Metadata Manager:** Manages schema validation, atomic writes, and log file generation.

### Atomic-Write Conventions
*   **`metrics.json`:** Use `atomic-write` atomic file operations (e.g., `atomic_write` in Python's `fcntl` module or `sync` in C++). This ensures `metrics.json` is written atomically, even if the llama.cpp process crashes or hangs during writing.
*   **`audit_log.txt`:** Write to a separate atomic file. Use `atomic_write` to ensure the log is persisted even if the main process fails.
*   **`summary.txt`:** Write to a separate atomic file. This allows users to verify the run summary after the main process has finished.

### Output Preservation
*   **`stdout`:** Pass a pipe to `llama.cpp`. If `stdout` is the default, it captures everything. If `stderr` is the default, it captures errors. The runner must explicitly set `stdout` or `stderr` in its config.
*   **`response.txt`:** Write the model's output to `response.txt`. This file is the primary source of truth for manual audit.
*   **`metrics.json`:** Write metrics to `metrics.json` *after* `response.txt` is generated.

### Prompt Handling
*   Use `llama.cpp`'s `prompt` argument (e.g., `--prompt`) or a dedicated `prompt` argument in the wrapper script.
*   Ensure the prompt is escaped properly (e.g., `\n` becomes `\n`).
*   Store the exact prompt in `metadata.json` alongside the model data.

## 4. Analysis Integrity

### Preventing Variable Generated-Token Count from Misleading Throughput
To ensure throughput is accurate, the generated token count (`generated_tokens`) must be the same as the input token count.
*   **Mechanism:** The `prompt` argument in `llama.cpp` is used to generate text. The number of tokens generated by a prompt is deterministic based on the prompt content.
*   **Risk:** If the prompt contains variable tokens (e.g., different words per sentence), the raw response will vary, breaking the throughput calculation.
*   **Fix:** The runner must ensure the prompt is static and the model's output length is consistent. Additionally, the `generated_tokens` counter should be incremented only when the model output is fully generated and verified as valid.

### Handling Unknown llama.cpp Output Formats
When processing `response.txt` for `metrics.json`, the parser must handle multiple formats without crashing.
*   **Strategy:** Use a JSON parser that supports multiple formats (e.g., `json`, `text`, `xml`) or a flexible regex parser.
*   **Action:** If a format is detected but unknown, skip the specific metric for that format but record the format name in the metadata.
*   **Validation:** The `generated_tokens` counter should only count tokens found in a valid `response.txt` or a valid `metrics.json` field. If the file is malformed, the `generated_tokens` should be 0, preventing a false high-throughput reading.

## 6. Pre-merge Review

### Highest-Risk Flaws
1.  **Ambiguity on `response.txt` Stream:**
    *   *Risk:* If the model prints to `stdout` but the runner reads `stdout` (default), partial output is retained, potentially skewing metrics. If the runner reads `stderr`, it misses partial outputs.
    *   *Fix:* The runner must explicitly specify `stdout` or `stderr` in its config. The `metadata.json` must record the chosen stream.

2.  **Variable Token Count Impact on Throughput:**
    *   *Risk:* If a prompt generates variable amounts of text, the "generated_tokens" counter will fluctuate, making throughput comparisons unreliable.
    *   *Fix:* Ensure the prompt is fixed and the model output length is consistent. Use a token counter that only increments on successful, verified generation.

3.  **Monitor Process Dependency:**
    *   *Risk:* If the monitoring process crashes before the model finishes, `response.txt` might be empty, but `metrics.json` might still exist. This leads to incomplete audit trails.
    *   *Fix:* Ensure the runner waits for the monitor process to finish *after* the model completes. If the monitor fails, `response.txt` must be checked explicitly before writing `metrics.json`.
