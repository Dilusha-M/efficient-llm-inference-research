### 1. Lifecycle of the KV Cache (Reused vs. Recomputed)
The lifecycle is defined by the **Reuse Ratio**. In a standard 256-bit cache, the KV cache (K/V) is typically reused 70–80% of the time, meaning only 20–30% of the computed tokens are recomputed.
*   **Reused:** The cache holds the "hot" tokens (those already seen by a model) and their associated key-value pairs (key + value), which are updated during inference.
*   **Recomputed:** The cache holds the "cold" tokens (newly generated tokens). These are only stored after the full decoding process is complete.
*   **Constraint:** In this scenario, the KV cache fits in 32 GB of system RAM, which is insufficient for the full context window of 8,000 tokens. The hardware must slice the 8,000 tokens into 32 GB blocks, leaving gaps (the "cold" tokens) for the GPU to decode on demand.

### 2. Hardware Resource Stress: Prompt vs. Decoding
Prompt processing (LLM decoding) and interactive token-by-token decoding are computationally distinct.
*   **Prompt Processing:** A high token count per second (e.g., 100k tokens/s) is driven by **Instruction-Normalized Inference (INO)**. This involves training/evaluating a small number of parameters (e.g., 10k–100k), not the full model. The GPU is essentially a specialized accelerator for training/evaluating this small subset.
*   **Decoding Stress:** Interactive decoding is the "full model inference" phase. It is computationally heavier due to the need to generate the full token sequence.
*   **Latency vs. Throughput:** A high prompt rate does not guarantee low latency. Latency is the time to process a *specific* token. If the prompt is 100k tokens/s, but the decoding phase takes 50ms per token, the latency spikes. The prompt rate is a ceiling; the decoding latency is the bottleneck.

### 3. Context Growth Effects (2000 → 8000)
Increasing context length increases the **Prefill** phase (filling the cache) and the **Decode** phase (generating new tokens).
*   **Prefill Cost:** The GPU must pay for the memory bandwidth to fill the 32 GB cache with 8,000 tokens. This is linear in token count ($T_{prefill} \propto T_{tokens}$).
*   **Decode Cost:** The GPU must pay for the memory bandwidth to generate the new tokens. This scales linearly with the number of new tokens generated ($T_{decode} \propto T_{new}$).
*   **Bandwidth Bottleneck:** As $T_{tokens}$ increases, the memory bandwidth of the GPU becomes the limiting factor, not the CPU. The CPU handles the prefetching; the GPU handles the decoding. If the GPU's memory bandwidth is saturated (due to 6 GB GPU + 32 GB RAM limit), latency increases linearly with context size.

### 4. Separation of Claims (General vs. Implementation)
| Claim | Validity | Root Cause |
| :--- | :--- | :--- |
| **"Prompt rate = 100k tokens/s."** | **General True.** High I/O throughput is a property of the prompt pipeline. | Hardware limitation: The GPU only supports 6 GB of RAM. This limits the total throughput, not the theoretical high-speed capability. |
| **"Latency increases with context."** | **Implementation Specific.** | Depends on **cache precision** (e.g., 256-bit vs. 512-bit), **GPU offload** (is it offloaded to CPU or kept on GPU?), and **paging** behavior. |
| **"Cache misses force CPU involvement."** | **Implementation Specific.** | Depends on **kernel support** (if the GPU kernel supports KV caching) and **page alignment**. Some GPUs do not cache KV efficiently. |

### 5. Measurement Strategy to Distinguish Bottlenecks
To isolate the bottleneck, perform the following controlled comparisons:

1.  **Prefill Bandwidth Ratio:** Measure the ratio of total Prefill Memory Bandwidth ($B_{prefill}$) to the total token count ($T_{tokens}$).
    *   *Expected Ratio:* Should be low ($<1.2$) if the GPU is the bottleneck. If $B_{prefill} \approx T_{tokens}$, the GPU is saturated.
2.  **Decode Memory Bandwidth Ratio:** Measure the ratio of total Decode Memory Bandwidth ($B_{decode}$) to the new token count ($T_{new}$).
    *   *Expected Ratio:* Should be high ($>1.5$) if the CPU is the bottleneck.
3.  **Memory Bandwidth Ratio (GPU vs. CPU):** Compare the GPU's memory bandwidth to the CPU's memory bandwidth.
    *   *Expected Ratio:* Should be $\approx 1.0$. If $B_{GPU} \approx 1.2 \times B_{CPU}$, the GPU is the limiting factor.

**Numerical Example:**
Assume the system has a 6 GB GPU and 32 GB RAM.
*   **Prefill:** The GPU fills 6 GB with 2,000 tokens. Time $\approx 0.1$ seconds.
*   **Decode:** The GPU fills 6 GB with 8,000 new tokens. Time $\approx 0.12$ seconds.
*   **Total Latency:** 0.12 seconds.
*   **Total Prompt Throughput:** 2,000 tokens / 0.1s = **20k tokens/s**. (This is the theoretical max, constrained by the 6 GB GPU).
*   **Decoding Latency:** 8,000 tokens / 0.12s = **66k tokens/s**.
*   **Conclusion:** The bottleneck is **Prompt Processing**. The 8,000 tokens required for decoding are simply consumed in the CPU's memory bandwidth to fetch the pre-filled 2,000 tokens. The GPU is only capable of 20k tokens/s because it is limited by the system RAM.
