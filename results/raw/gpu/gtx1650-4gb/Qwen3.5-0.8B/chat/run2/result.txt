### 1. Lifecycle of the KV Cache: Reused vs. Recomputed
The KV cache on a consumer GPU (e.g., NVIDIA H100) operates as a **shared, non-sequential** cache. Unlike the memory subsystem, the cache is not allocated per token but per model weight and is **reused** across the entire conversation.

*   **Reused:** The same set of 32 GB RAM slots holds the weights for all models. When a user sends a 2000-token prompt, the GPU loads the weights into the cache.
*   **Recomputed:** For each generated token, the model must look up a specific key-value pair (e.g., `q-32k` for position 32k) from the cache and compute the associated values. The cache is not pre-filled with the specific 8000 tokens requested; it is only populated once during initialization.
*   **The Bottleneck:** Because the cache is a global pool, the CPU/GPU cannot "wait" for the next token to be computed until the current one is successfully retrieved. This causes a massive spike in **recomputed (lookup) operations**, which dominate the latency curve compared to the few pre-computed lookups.

### 2. Stress Resources and Latency Paradox
Prompt processing and decoding stress distinct, limited hardware resources differently:

*   **Prompt Processing:** Requires **memory bandwidth** to transfer weights from CPU/GPU to the GPU. This is a **bandwidth-constrained** operation. It is often the limiting factor regardless of KV cache size.
*   **Decoding:** Requires **compute capability** to execute the model's attention mechanism. This is a **compute-bound** operation. The latency of decoding is primarily determined by the **model's attention window size** and the GPU's compute units, not the amount of KV traffic.

**Why High Prompt Tok/s $\neq$ Low Latency:**
A high prompt processing rate (e.g., 10k tokens/s) indicates the GPU can handle the memory bandwidth of the prompt. However, if the KV cache is full, the model must perform a lookup for every single token. This causes a **non-linear latency explosion** because the CPU has to fetch data sequentially rather than in parallel. The latency is dominated by the number of lookups, not the speed of the pre-processing.

### 3. Context Scaling Effects (2k $\to$ 8k)
*   **Prefill:** Increasing context from 2,000 to 8,000 tokens requires loading the remaining 6,000 tokens into the cache. This **increases the cache size** (assuming 32 GB is available). It does not increase latency; it just changes the cache footprint.
*   **Decode:** The bottleneck remains the same. The model now needs to compute values for all 8,000 tokens. The latency curve shifts from "lookup-heavy" to "lookup-heavy + more compute," but the CPU/GPU transfer bottleneck for the prompt is still the limiting factor.
*   **Memory Bandwidth:** The primary driver of latency in this scenario is **CPU-GPU transfer speed** (e.g., PCIe 4.0 vs. PCIe 5.0). If the transfer is the bottleneck, increasing context length does not improve throughput; it only increases the chance of hitting the transfer wall.

### 4. Separating General Claims from Implementation Details
| Claim | Status | Dependencies |
| :--- | :--- | :--- |
| **KV cache size affects latency** | **False (General)** | Only true if the cache is small and the bottleneck is *memory bandwidth* (e.g., CPU transferring data). |
| **Prefill latency is the bottleneck** | **False** | Only true if the bottleneck is *CPU transfer speed* (e.g., PCIe 4.0) or if the model is memory-mapped. |
| **High Prompt Rate = Low Latency** | **False** | True if the bottleneck is **lookup overhead**. If the bottleneck is transfer, latency is independent of prompt rate. |
| **32 GB RAM is sufficient** | **Depends on implementation** | Depends on whether the cache is shared and if the GPU can offload the heavy compute. |
| **Offloading GPU is required** | **False** | The prompt processing throughput is the bottleneck. Offloading is only needed if the prompt processing throughput drops below a threshold. |

### 5. Proposed Measurements
To distinguish the bottlenecks, run the following controlled comparisons:

1.  **Memory Bandwidth vs. Transfer Bandwidth:**
    *   **Metric:** Measure the time it takes to transfer 10k tokens from CPU to GPU.
    *   **Result:** If **Transfer Bandwidth** is the bottleneck (even with 32 GB RAM), the latency should be dominated by the transfer delay, not the KV cache. If Transfer bandwidth is not the bottleneck, the latency depends on the KV cache.

2.  **Compute Load (Load Balancing):**
    *   **Metric:** Calculate the load of the compute unit (e.g., using `nvidia-smi` and checking if it hits 100% utilization during the decode phase).
    *   **Result:** If the compute unit is saturated during the 8k context phase, the latency will increase due to compute throughput limits, not just KV cache size. If the compute unit is saturated during the prompt phase, latency is purely memory-related.

3.  **Per-Token Latency Profile (Lookup vs. Compute):**
    *   **Metric:** Split the latency curve at the prompt start (where KV cache is large) and at the prompt end (where cache is small).
    *   **Result:** The curve must show a **sharp spike in latency** immediately after the prompt start (indicating the large lookup pool) but **no spike** immediately before it (indicating no heavy compute). This confirms the latency is determined by the number of lookups, not the compute capacity.
