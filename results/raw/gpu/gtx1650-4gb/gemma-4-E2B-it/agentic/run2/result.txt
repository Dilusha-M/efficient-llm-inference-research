## State Machine

**State 1: Initialization and Validation**
1. Load configuration and set default runtime parameters (Context=4096, GenLimit=256, Temp=0.7, Threads=1).
2. Validate required inputs (Model, Workload).
3. Generate a unique Run ID.
4. Initialize the run-specific metadata file structure.

**State 2: Execution Setup**
1. Determine the specific command-line arguments based on the chosen backend (CPU/CUDA/Vulkan).
2. Construct the full prompt, incorporating the required workload and the specific user prompt.
3. Capture and record the exact prompt string and its hash for later invariant checking.

**State 3: Model Launch and Monitoring**
1. Launch the `llama.cpp` process with all parameters.
2. Start concurrent monitoring threads for process exit, resource usage (CPU/Memory), and potential performance output streams.
3. **Timeout Check:** If the process does not exit within a predefined time limit, transition to State 5 (Failure - Timeout).

**State 4: Process Exit and Data Capture**
1. Wait for the model process to terminate.
2. Capture the final raw output (`response.txt`).
3. Capture all collected monitoring data (hardware metrics, token counts, timing).
4. Validate the captured output against expected structure and check for missing optional monitoring data.

**State 5: Finalization and Auditing**
1. **Failure Branch:** If any validation fails (e.g., OOM, malformed output, missing monitor), mark the run as Failed, ensuring the failure reason is logged in the metadata file.
2. **Success Branch:** If all data is present and consistent, finalize the metadata file, ensuring the raw output is preserved alongside the metrics.
3. Ensure the run adheres to the invariant: No results are mixed if any parameter (model, backend, context, prompt, etc.) has changed since the baseline.

## Analysis Integrity

**Preventing Misleading Throughput:**
Throughput calculation ($\text{Tokens} / \text{Time}$) must be based *only* on tokens and time recorded directly from the `llama.cpp` execution metrics, not derived from the raw text output parsing. If the raw output parser fails, the system must rely on the explicit token counts reported by the execution environment (if available) or explicitly defined metrics. If the output format is unknown, the parser defaults to recording the explicit token counts and time reported by the monitoring subsystem, treating the raw text content as secondary audit data, not primary performance input.

**Handling Unknown Output Formats:**
The parser must employ a strict format-checking mechanism. If the expected performance metrics (token counts, time) cannot be successfully parsed from the raw output stream, the parser must treat the run as **partially failed** (State 5 Failure) if these metrics are mandatory for the success state. If the failure is merely in parsing the human-readable text, the system should log a specific "Parsing Error" in the metadata but still attempt to record the explicit token counts and time gathered from the monitoring system, ensuring the failure is distinguishable from a complete execution failure.

## Pre-merge Review

**Risk 1: Invariant Violation During Parallel Execution.**
* **Flaw:** If the monitoring or execution threads operate asynchronously, a parameter change (e.g., changing the temperature) might affect the performance metrics recorded by the Monitor Agent *after* the main process has already finalized its internal state, leading to a mismatch between the execution parameters and the recorded performance data.
* **Fix:** Implement a strict synchronization barrier. All performance metrics must be collected *only* when the process explicitly signals completion (State 4), and the configuration snapshot used for comparison must be locked against the collected metrics at that moment.

**Risk 2: Ambiguity in Output Parsing vs. Process Failure.**
* **Flaw:** Difficulty in distinguishing between a run that failed internally (OOM) and a run that simply produced unreadable text. If the parsing logic is too aggressive, it might incorrectly flag a valid run as failed due to malformed text, or conversely, ignore critical failure signals.
* **Fix:** Enforce a hierarchical failure mechanism. A process crash/OOM is a hard failure (State 5), whereas parsing errors are soft failures that result in a metadata flag (`status: FAILURE, reason: PARSING_ERROR`) but still allow the raw output and gathered metrics to be saved for audit.

**Risk 3: Atomicity of Raw Data Preservation.**
* **Flaw:** If the system attempts to write the metadata file before the raw output file is guaranteed to be fully written and immutable (especially across distributed systems or failure recovery), the auditability is compromised.
* **Fix:** Enforce the "Write-Then-Rename" pattern strictly. The raw output file must be fully written and closed *before* the metadata writer begins its atomic operation. The final successful state is only achieved when the metadata file and the raw output file are both present and validated.
