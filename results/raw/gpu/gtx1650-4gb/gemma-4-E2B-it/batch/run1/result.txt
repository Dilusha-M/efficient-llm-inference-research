## Task 1 — quantization tradeoff:

**Data Provided:**
*   8B Model: $8.0 \text{ GB}$ ($\text{Q8\_0}$)
*   8B Model: $4.8 \text{ GB}$ ($\text{Q4\_K\_M}$)
*   GPU Memory: $6.0 \text{ GB}$
*   Free GPU Memory before inference: $5.2 \text{ GB}$

**Explanation of Memory Pressure:**

1.  **$\text{Q8\_0}$ (8.0 GB):** This format requires $8.0 \text{ GB}$ just for loading the model weights. Since the GPU only has $5.2 \text{ GB}$ free, loading the $\text{Q8\_0}$ model alone would cause immediate memory pressure or require significant swapping/offloading, potentially failing the inference if the KV cache is also considered.
2.  **$\text{Q4\_K\_M}$ (4.8 GB):** This format requires $4.8 \text{ GB}$ for the weights. This leaves $6.0 \text{ GB} - 4.8 \text{ GB} = 1.2 \text{ GB}$ for the KV cache and activation memory, making it significantly more feasible to run inference on the $6 \text{ GB}$ GPU compared to the $\text{Q8\_0}$ format.

**Why File Size is Not a Complete Runtime-Memory Estimate:**
File size only estimates the storage requirement for the model weights ($\text{VRAM}$ footprint *if* loaded). It does not account for:
1.  **KV Cache:** The memory required to store the Key/Value states during autoregressive decoding, which scales with the sequence length and batch size.
2.  **Activations/Overhead:** Memory used by the forward pass computations, intermediate tensors, and the runtime overhead of the inference engine itself.
3.  **Quantization Overhead:** The specific memory layout and computational requirements introduced by the quantization scheme (e.g., $\text{Q4\_K\_M}$ requires specific decompression/reconstruction steps during computation).

**Two Quality/Performance Measurements Needed:**
To declare one format better, one must measure the actual runtime performance and output quality:
1.  **Inference Latency (Time per token):** Measures the speed of generation under real operational constraints.
2.  **Perplexity/Accuracy (Quality):** Measures the semantic correctness or predictive quality of the generated output relative to the ground truth or a baseline.

**Disclaimer:** I cannot claim that $\text{Q4\_K\_M}$ is always faster. Performance depends heavily on the specific hardware architecture, the specific inference kernel implementation, and the required quality threshold.

**Conservative Procedure for Choosing Context Size and GPU Layer Offload (llama.cpp):**

The goal is to maximize the use of the GPU while respecting the $16 \text{ GB}$ RAM limit and ensuring the system remains stable.

*   **Action:** Set GPU layer offload to the minimum possible value (e.g., $0$ or $1$ layer).

*   **Goal:** Determine the baseline memory pressure caused by the prompt processing (context loading) and the initial KV cache.

*   **Action:** Keep the layer offload minimal and increase the context size (e.g., try $2,000$ tokens, then $4,000$, etc.).

## Task 5 — user-visible latency:

**Context:** Prompt ($2,000$ tokens), Generation ($200$ tokens).

**Definitions:**

1.  **Time to First Token (TTFT):** The time elapsed from when the user sends the entire prompt to the model until the model begins generating the very first output token. (Primarily prompt processing time).
2.  **Prompt-Evaluation Throughput:** The rate at which the model processes the input prompt to prepare for generation (i.e., the time taken to process the $2,000$ tokens).
3.  **Decode Throughput:** The rate at which the model generates output tokens once decoding begins (measured in tokens per second, $\text{tok/s}$).
4.  **Total Wall-Clock Time:** The total elapsed time from the very beginning (sending the prompt) until the final generated token is produced.

**Symbolic Equation for Total Time:**

$$\text{Total Time} = \text{TTFT} + \text{Time}_{\text{Generation}}$$

Where:
$$\text{Time}_{\text{Generation}} = \frac{\text{Generated Tokens}}{\text{Decode Throughput}}$$

**Example where Optimizing Prompt Processing Barely Changes User Experience:**

**Scenario:** Optimizing prompt processing (e.g., prompt attention calculation) barely changes the user's experience.

*   **Context:** The prompt is $2,000$ tokens, and the generation is $200$ tokens.
*   **Optimization Focus:** Optimizing the time taken to process the $2,000$-token prompt ($\text{Time}_{\text{Prompt}}$).
*   **Justification:** Since the generation phase ($200$ tokens) is typically much longer and dominates the total time, the time required to process the initial $2,000$-token prompt ($\text{TTFT}$) is a small fraction of the total $\text{Time}_{\text{Generation}}$. If $\text{TTFT}$ is, for example, $50 \text{ ms}$ and $\text{Time}_{\text{Generation}}$ is $5$ seconds, optimizing the $50 \text{ ms}$ prompt phase might save $10 \text{ ms}$ in total time, which is imperceptible to the end-user.
