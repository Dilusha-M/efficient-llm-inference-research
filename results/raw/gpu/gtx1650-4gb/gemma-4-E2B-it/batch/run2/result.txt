## Task 1 — quantization tradeoff

**Assumptions:**
1. The provided file sizes (8.0 GB and 4.8 GB) are the total disk footprint for the model weights.
2. The GPU has 5.2 GB of free memory available for runtime operations.
3. The inference process requires memory for weights, activations, and the KV cache.

**Memory Pressure Explanation:**
* **Q8\_0 (8.0 GB):** This format requires significantly more memory for the model weights. Given the 5.2 GB free memory, loading the 8.0 GB model weights alone would cause immediate memory pressure or require swapping/offloading, making runtime memory estimation difficult without knowing activation overhead.
* **Q4\_K\_M (4.8 GB):** This format requires less memory for the weights, leaving more headroom in the 5.2 GB free memory for activations and the KV cache during inference.

**Why File Size is Not a Complete Runtime-Memory Estimate:**
File size (disk footprint) only estimates the memory required to load the **static model weights**. It does not account for:
1. **Activations:** The intermediate tensors generated during the forward pass, which consume significant memory.
2. **KV Cache:** The memory used to store the Key-Value pairs for previously generated tokens, which scales with the prompt and generation length.
3. **Inference Overhead:** Memory required for the operating system, CUDA context, and other runtime buffers.

**Two Quality/Performance Measurements Needed:**
To declare one format better, one must measure runtime performance metrics that incorporate the actual memory usage during execution:
1. **Peak Memory Usage (during inference):** Measure the maximum GPU memory consumed by the model and its associated KV cache during the full generation.
2. **Inference Latency (Time per token):** Measure the time taken to generate successive tokens, which reflects the actual computational bottleneck and memory bandwidth utilization.

**Note on Speed:** Do not claim that Q4 is always faster. Quantization affects both memory usage and computational intensity; the actual speed depends heavily on the specific hardware, the library implementation, and the specific operation being measured.

## Task 2 — conservative launch decision

**Goal:** Choose context size and GPU layer offload conservatively given 16 GB RAM, 6 GB GPU, 5.0 GB weights, 2000-token prompt, and 512-token generation limit.

**Conservative Procedure:**

1. **Establish Baseline (Smallest Viable Test):** Start by testing the absolute minimum required for the prompt and a minimal generation.
    * **Action:** Set the context size ($N$) to the smallest possible value that fits the prompt plus a small buffer (e.g., $N = 2000$).
    * **Telemetry Recorded:** Total VRAM usage for the weights and the KV cache for the prompt.
2. **Iterative Context Scaling:** Gradually increase the context size ($N$) up to the 2000-token limit, monitoring the memory footprint.
    * **Action:** Increment $N$ in small steps (e.g., 500 tokens) and record the peak memory usage.
    * **Telemetry Recorded:** Peak VRAM usage vs. $N$.
3. **Layer Offload Test (If Memory is Tight):** If the system is still constrained, test offloading layers.
    * **Action:** Attempt to offload the initial layers (e.g., the first 20 layers) to the CPU, keeping the rest on the GPU.
    * **Telemetry Recorded:** VRAM usage (GPU) vs. CPU RAM usage.
4. **Generation Test:** Run a full generation using the determined context size and layer configuration.
    * **Action:** Attempt to generate the full 512 tokens.
    * **Telemetry Recorded:** Total generation time and final memory state.

**Unsafe or Misleading Success:**
* **Unsafe Success:** Achieving a low generation time while using extreme memory pressure (e.g., 90%+ utilization) that risks system instability or forces heavy OS swapping.
* **Misleading Success:** Achieving a fast time while only testing a context size that is far below the potential, suggesting the configuration is optimal when it might only be optimal for a very short prompt.

## Task 3 — robust aggregation

**Input Data:** Decode speeds: $\{42.0, 41.5, 8.0 \text{ tok/s}\}$. Last run failed (OOM warning).

**Pseudocode for Validation and Median Calculation:**

```pseudocode
FUNCTION Aggregate_Decode_Speeds(Speeds_List)
    // Speeds_List = [42.0, 41.5, 8.0]
    Successful_Speeds = []
    Failed_Run_Logged = FALSE
    
    FOR EACH Speed IN Speeds_List:
        IF Speed is NOT ERROR_FLAG_OOM:
            ADD Speed TO Successful_Speeds
        ELSE:
            Failed_Run_Logged = TRUE // Mark that at least one run failed
            // Keep the failed run visible (e.g., log it separately)
            LOG_FAILURE(Speed, "OOM Warning") 
            
    IF LENGTH(Successful_Speeds) > 0:
        Median_Speed = CALCULATE_MEDIAN(Successful_Speeds)
        RETURN {
            "Successful_Median": Median_Speed,
            "Failed_Runs_Count": LENGTH(Speeds_List) - LENGTH(Successful_Speeds),
            "All_Results": Speeds_List // Keep all results visible
        }
    ELSE:
        // Case where fewer than two runs succeed (0 or 1 success)
        IF LENGTH(Successful_Speeds) == 0:
            RETURN {
                "Status": "No_Success",
                "Message": "All runs failed or no successful runs found.",
                "All_Results": Speeds_List
            }
        ELSE: // Exactly one success
            RETURN {
                "Status": "Single_Success",
                "Median_Speed": Successful_Speeds[0],
                "Message": "Only one run succeeded. Median is the single successful result."
            }
```

**Reporting Strategy for Fewer Than Two Successes:**

If fewer than two runs succeed (i.e., zero or one success), the median calculation is not robustly defined. The report should explicitly state the status:

1. **Zero Successes:** Report the individual results and state: "No successful runs were recorded. All runs resulted in failure."
2. **One Success:** Report the single successful speed as the result, explicitly stating: "Only one run succeeded. The reported speed is [X.X] tok/s." (This avoids implying a median exists when it is not.)

## Task 5 — user-visible latency

**Context:** 2,000-token prompt, 200 generated tokens.

**Definitions:**

1. **Time to First Token (TTFT):** The time elapsed from sending the entire prompt to receiving the very first token of the generated response. (Primarily prompt processing and initial kernel launch time.)
2. **Prompt-Evaluation Throughput:** The rate at which the model processes the initial 2,000-token prompt and prepares for generation. (Measured in tokens/second, reflecting the time spent processing the input context.)
3. **Decode Throughput:** The rate at which the model generates new tokens during the generation phase. (Measured in tokens/second, reflecting the sustained speed of the autoregressive loop.)
4. **Total Wall-Clock Time:** The total time elapsed from the moment the prompt is sent until the final token of the 200 generated tokens is received.

**Symbolic Equation for Total Time:**
$$\text{Total Time} = \text{TTFT} + \text{Time}_{\text{Generation}}$$
Where:
$$\text{Time}_{\text{Generation}} = \frac{\text{Generated Tokens}}{\text{Decode Throughput}}$$

**Example Where Optimizing Prompt Processing Barely Changes User Experience:**
If the **Prompt-Evaluation Throughput** is very high (e.g., the prompt is small relative to the model's capacity, or the prompt is processed almost instantly by the GPU), optimizing the prompt processing time might only shave off milliseconds. The user perceives the delay as negligible compared to the actual generation time ($\text{Time}_{\text{Generation}}$). In this case, optimizing the initial prompt processing has no discernible effect on the overall perceived latency.
