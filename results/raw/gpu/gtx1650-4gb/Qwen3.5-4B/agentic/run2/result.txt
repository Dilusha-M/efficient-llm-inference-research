### Requirements and Invariants

**Inputs:**
*   **Configuration File:** Defines model aliases, backend selection (CPU/CUDA/Vulkan), default parameters (`context=4096`, `max_tokens=256`, `temp=0.7`, `threads=1`), and workload definitions.
*   **Model File Path:** Absolute path to the `.gguf` or binary model file.
*   **Workload Definition:** Specifies prompt template, expected output structure, and specific parameter overrides.
*   **Benchmark Options:** Timeout duration, concurrency limits, and flag to enable/disable hardware monitors.

**Artifacts:**
*   **`run_metadata.json`**: Atomic-write file containing the experimental identity tuple, timestamps, and exact input configuration.
*   **`response.txt`**: Raw stdout/stderr concatenation from the llama.cpp process.
*   **`metrics.log`**: Structured performance data (if monitors are active).
*   **`summary_report.txt`**: Human-readable analysis of throughput, token count, and status.

**Success/Failure States:**
*   **Success:** The process exits with code 0, generates a non-empty `response.txt`, and produces a valid `run_metadata.json`.
*   **Partial Success:** The process exits with code 0 but generates empty or malformed output; or exits with non-zero code but generated partial output.
*   **Failure:** The process exits with non-zero code due to OOM, hardware error, or timeout; OR the process exits with code 0 but the output is empty.
*   **Monitor Failure:** Monitors fail to initialize or return sparse data. This does *not* constitute a benchmark failure unless the metric is explicitly required by the workload spec.

**Experimental Identity Tuple:**
`{model_hash}:{backend}:{gpu_label}:{context}:{max_tokens}:{temp}:{prompt_hash}:{build}:{driver_version}`
*Constraint:* Results are strictly isolated if any component of this tuple changes.

**Ambiguity to Resolve:**
The specification requires distinguishing a "failed model run" from "missing optional monitoring data." However, it does not explicitly define the **threshold for "partial output"**. Is a response containing 10 tokens a success if the limit is 256? The design must resolve this by defining a **Minimum Valid Generation Threshold** (e.g., `min_tokens >= 4` or `min_tokens >= 10%` of `max_tokens`). Without this, a process that crashes after 10 tokens cannot be distinguished from a process that crashed immediately (0 tokens), yet both might be treated as "failed" depending on the monitoring logic.

### State Machine

The lifecycle follows a strict linear flow with conditional branches for errors:

1.  **Validation Phase:**
    *   Check model file existence and format.
    *   Compute `model_hash` and `prompt_hash`.
    *   Resolve parameters from config (apply defaults first, then workload overrides).
    *   **If** validation fails $\rightarrow$ **Abort**, write `run_metadata.json` with `status: "invalid_input"`, exit.

2.  **Environment Setup:**
    *   Construct `llama.cpp` command line arguments based on resolved parameters.
    *   Initialize monitor threads (if enabled).
    *   **If** monitor initialization fails (but not mandatory) $\rightarrow$ Log warning, proceed without monitor data.
    *   **If** model loading fails (e.g., OOM during init) $\rightarrow$ **Abort**, write `run_metadata.json` with `status: "init_failure"`, capture logs, exit.

3.  **Execution Phase:**
    *   Spawn child process.
    *   **If** timeout occurs $\rightarrow$ **Terminate** process, write `run_metadata.json` with `status: "timeout"`, exit.
    *   **If** child exits with non-zero code $\rightarrow$ Capture `response.txt`, write `run_metadata.json` with `status: "process_error"`, exit.
    *   **If** child exits with code 0:
        *   Read `response.txt`.
        *   **If** `response.txt` is empty or contains only whitespace $\rightarrow$ **Abort**, write `run_metadata.json` with `status: "empty_output"`, exit.
        *   **If** `response.txt` tokens < `min_valid_threshold` $\rightarrow$ Treat as **Partial Success**, write `run_metadata.json` with `status: "partial_generation"`, exit.
        *   **If** `response.txt` tokens >= `min_valid_threshold` $\rightarrow$ Proceed to Finalization.

4.  **Finalization Phase:**
    *   Aggregate metrics if available.
    *   Parse `response.txt` to calculate actual `generated_tokens`.
    *   Compute `throughput` (tokens/second).
    *   Generate `summary_report.txt`.
    *   Write `run_metadata.json` with `status: "success"` (or `partial`).
    *   **Exit** with code 0.

**Handling Edge Cases:**
*   **Timeout:** The parent sends `SIGKILL` to the child after the deadline. The child's stderr is captured and appended to `response.txt`.
*   **OOM:** Detected via non-zero exit code or specific error strings in stderr. Handled as `process_error`.
*   **Malformed Metrics:** If `metrics.log` is present but contains unparseable lines, the parser skips invalid lines and logs a warning; if the entire file is garbage, the metric is treated as `null`.
*   **Monitor Failure:** If the monitor thread dies or hangs, the parent waits for a timeout (e.g., 5s) before declaring the monitor failure. The benchmark continues with missing metrics.

### Auditable Design

**Component Boundaries:**
*   **Shell Script (`benchmark_runner.sh`):** Handles process spawning, signal handling, file I/O, and orchestration. It acts as the "black box" wrapper.
*   **Python Module (`parser.py`):** Dedicated for parsing `llama.cpp` output formats (text and JSON metrics). It is isolated to ensure logic changes don't affect process management.
*   **Config Parser:** A lightweight JSON/YAML loader to resolve parameters.

**Atomic-Write Strategy:**
*   **Metadata File:** Instead of writing directly to `run_metadata.json`, the runner writes to a temporary file `run_metadata.json.tmp`, appends completion markers, and then performs an atomic rename (`mv` or `ftruncate` followed by `rename` on POSIX) to ensure the file is never in a half-written state.
*   **Response File:** Appends to `response.txt` in a buffer (e.g., 4KB chunks) to minimize I/O latency, then flushes atomically.

**Preservation of Artifacts:**
*   **Stdout/Stderr:** The shell script forks the child process and pipes both `STDOUT` and `STDERR` to a single file descriptor redirected to `response.txt`. This ensures raw logs, including `llama.cpp` internal debug prints and user-facing text, are concatenated without separation, preserving the exact order of events.
*   **Exact Prompt:** The prompt text is embedded directly into `run_metadata.json` as a base64-encoded string to prevent escape sequence interpretation issues, alongside the `prompt_hash` for integrity verification.

**Metadata Schema (`run_metadata.json`):**

  }

### Analysis Integrity

**Preventing Misleading Comparisons:**
*   **Token Count Normalization:** Throughput is calculated only if `generated_tokens >= min_valid_threshold`. If a run fails to generate a minimum threshold, it is excluded from aggregate statistical calculations (mean, variance) unless a "partial" flag is raised explicitly.
*   **Variable Generation Handling:** To prevent a run that generates 10 tokens (due to a crash) from skewing a mean throughput calculation against a run that generated 250 tokens, the analysis script uses **trimmed mean** statistics or **median** for throughput, ignoring the outlier runs below the threshold.
*   **Failed Run Isolation:** A failed run (non-zero exit) or empty output run is tagged in the metadata. The analysis script checks this tag and excludes the run from the "throughput" dataset, but may include it in a "latency to failure" dataset if relevant.

**Parser Robustness:**
*   **Unknown Output Formats:** The `parser.py` must attempt to detect the output format based on the first 50 characters of `response.txt`.
    *   If it matches the standard `llama.cpp` JSONL format, parse as JSON.
    *   If it matches the plain text format (common in older builds or specific backends), parse line-by-line.
    *   **If** the format is unrecognized, the parser returns a `ParseError` and logs the raw bytes, but does not crash the benchmark runner. The `status` is set to `partial` (due to data loss) rather than `failure`, allowing the user to see the raw text in `response.txt` for debugging.
*   **Metric Extraction:** If the metrics JSON is truncated or malformed, the parser defaults to `null` for that specific metric rather than throwing an exception that halts the entire run.

### Test Plan

1.  **Simulated Backend Failure (OOM/Exit Code):**
    *   *Setup:* Create a config pointing to a non-existent model file or inject a fake `llama-server` script that exits with code 1 immediately.
    *   *Expectation:* `response.txt` contains the error message. `run_metadata.json` status is `process_error`. `summary_report.txt` indicates failure. No partial output is generated.

2.  **Missing Monitor:**
    *   *Setup:* Disable the monitor flag in the config, then re-run with the monitor enabled on a machine with no GPU drivers.
    *   *Expectation:* The runner logs a warning "Monitor initialization failed". `run_metadata.json` shows `monitor_available: false`. Benchmark completes successfully if the model generates output. `throughput` is calculated based on wall time only.

3.  **Prompt Containing Spaces/Newlines:**
    *   *Setup:* Use a prompt string with embedded newlines and special characters, ensuring the hash computation handles them correctly.
    *   *Expectation:* `prompt_hash` matches the hash of the escaped/newline-containing string. `response.txt` contains the exact prompt followed by model output. No corruption occurs.

4.  **Partial Output (Crash during Generation):**
    *   *Setup:* Create a model file that loads but crashes the process after generating exactly 5 tokens. Set `min_valid_threshold` to 10.
    *   *Expectation:* `response.txt` has 5 tokens. `run_metadata.json` status is `partial_generation`. Throughput is recorded but flagged as unreliable. It is excluded from the main "success" throughput mean.

5.  **Changed Prompt Hash (Isolation):**
    *   *Setup:* Run the same model with Prompt A, then immediately with Prompt B (only 1 char difference).
    *   *Expectation:* `prompt_hash` differs. The system must not mix results. A subsequent analysis script must verify that the `identity` tuple for Run 1 is distinct from Run 2 and cannot be correlated with the other run's performance.

6.  **Malformed Performance Output:**
    *   *Setup:* Modify the `llama.cpp` binary or output stream to emit garbage JSON for the metrics file.
    *   *Expectation:* The parser detects the malformed JSON, logs a warning, skips the invalid line, and returns `null` for the metric. The runner does not crash. `run_metadata.json` reflects `monitor_data_quality: "sparse"`.

### Pre-merge Review

**Risk 1: Ambiguity in "Partial" Definition Leading to False Negatives**
*   *Flaw:* If `min_valid_threshold` is set too high (e.g., 90% of `max_tokens`), a process that generates 100 tokens before crashing (when limit is 1000) will be treated as a "partial failure" and excluded from throughput stats, masking the actual speedup of that configuration.
*   *Fix:* Lower the `min_valid_threshold` to a fixed absolute value (e.g., 10 tokens) regardless of `max_tokens`, or use a percentage based on the actual time taken (e.g., generated > 100ms). The spec must explicitly define this threshold as a constant `MIN_GEN_TOKENS = 10`.

**Risk 2: Atomic Write Race Conditions in High-Concurrency**
*   *Flaw:* If the benchmark runner spawns multiple processes simultaneously and they all write to `response.txt` before the parent processes exit, there is a risk of interleaved writes if the shell redirection is not robust. Additionally, if the parent exits before renaming the metadata file, a partial `run_metadata.json` could be left in the directory, causing confusion in audit logs.
*   *Fix:* Ensure the shell script uses `exec > response.txt` combined with `exec 2>&1` to fully redirect both streams to the file descriptor before forking. For metadata, use a strict `tempfile` library pattern or `mv` only after the child process confirms completion via a file descriptor close event.

**Risk 3: Hash Collision Leading to Result Mixing**
*   *Flaw:* Relying solely on `prompt_hash` for isolation is insufficient. If two different models or backends produce identical hashes (unlikely with SHA-256 but theoretically possible with weak hashing or identical inputs), or if the `model_hash` calculation is flawed (e.g., ignoring file headers), results could be mixed.
*   *Fix:* The `identity` tuple must include `model_path` (absolute path) and `backend` explicitly in addition to the hashes. The isolation check should verify that *all* components of the tuple match before aggregating data.
