### System Dynamics and Bottleneck Analysis

#### 1. KV Cache Lifecycle: Prefill vs. Decode
In a decoder-only architecture, the lifecycle of the Key-Value (KV) cache diverges sharply between the prefill phase and the decoding phase:

*   **Prefill (Prompt Processing):** The model processes the entire 2,000-token input in parallel. For every token $t$, the attention mechanism computes $Q_t$ against **all** previous keys $K_{1..t}$. This results in $O(N^2)$ memory accesses where $N$ is the context length. The KV cache is constructed atomically; subsequent tokens do not reuse this data during the prompt phase.
*   **Decode (Token-by-Token):** Once the prompt is fully processed, the system enters an iterative loop. For token $t$, $Q_t$ is computed against only the immediately preceding $K_{t-1}$. The previous $N-1$ keys are **reused** directly from memory (GPU VRAM or System RAM), eliminating the quadratic cost for that step. The cache is updated by appending the new $K_t, V_t$ and discarding the oldest entries (if context is capped) or sliding the window.

**Key Distinction:** Prompt processing is a **massive parallel memory load** (bandwidth-bound), while decoding is a **sequential memory reuse** (latency-bound if off-chip).

#### 2. Hardware Stress: Why High Tpk/s $\neq$ Low Latency
The divergence in stress arises from the architectural difference between the CUDA stream used for prefill and the stream used for decoding:

*   **Prefill Stress:** Dominated by **Memory Bandwidth**. The GPU must stream $O(N^2)$ float16/BF16 values from HBM2/HBM2e to the compute units. Since this is a bulk transfer, it saturates the GPU's memory bus but rarely stalls the compute pipeline if the bandwidth is sufficient.
*   **Decode Stress:** Dominated by **Memory Latency and Coalescing**. Even though only one key is accessed per token, the total traffic scales linearly with context length ($N \times \text{tokens}$).
    *   *GPU VRAM:* If the KV cache exceeds VRAM capacity, the system must evict to System RAM (System Memory). Accessing 32 GB DDR5 from System RAM to HBM2 involves a PCIe transfer (~100–500 ns round trip) plus DRAM latency (~100 ns), adding ~1.5–3.0 $\mu s$ per token.
    *   *GPU VRAM (Full):* Accesses are local (~50–100 ns), adding negligible latency.

**The Paradox:** A high prompt tok/s indicates the GPU can handle the massive **bandwidth** of loading the initial KV cache. It does **not** imply low decode latency because once the cache is resident (or offloaded), the bottleneck shifts to the **latency** of retrieving the single preceding key for each new token. If the cache spills to RAM, the latency penalty compounds linearly with every generated token, causing the "slow as conversation grows" symptom.

#### 3. Scaling from 2k to 8k Tokens
Increasing context from 2,000 to 8,000 tokens exacerbates both phases, but disproportionately impacts the decode phase via memory pressure:

*   **Prefill Cost:** Scales quadratically ($N^2$). At 8k tokens, prefill memory traffic increases by a factor of 16 compared to 2k. This will almost certainly cause out-of-memory (OOM) on the GPU even if weights fit, forcing an immediate fallback to System RAM for the KV cache.
*   **Decode Behavior:**
    *   *With NVLink/Shared Bus:* If the GPU has sufficient HBM (e.g., 24GB+ on modern A-series), the cache fits, and latency remains stable (~1–2 $\mu s$/token).
    *   *With 6GB VRAM:* At 8k tokens, the KV cache (approx. 8,000 $\times$ 2 $\times$ 128 bytes $\approx$ 2MB per layer; for 7B params $\approx$ 40 layers, total $\approx$ 80–100MB) might still fit, but the **working set for active attention** grows. More critically, if the user increases batch size or the model is larger, the 6GB limit is breached. The system will page the KV cache to the 32GB RAM.
*   **Memory Bandwidth Role:** As context grows, the prefill bandwidth requirement becomes the hard limit. However, during decode, the **PCIe bottleneck** becomes the primary constraint when the KV cache resides in System RAM. The GPU waits for the PCIe bus to fetch the previous key, creating a "latency wall" that linearly degrades throughput.

#### 4. General Truths vs. Implementation Details

| Claim Category | Status | Reasoning |
| :--- | :--- | :--- |
| **Prefill is $O(N^2)$** | **True** | Architectural definition of Self-Attention. |
| **Decode is $O(1)$ per token** | **True** | Only one previous key is accessed per iteration. |
| **RAM > VRAM for KV cache** | **Implementation Dependent** | Depends on HBM2e bandwidth vs. PCIe bandwidth. On consumer GPUs (Ampere), PCIe is often faster for small transfers, but latency kills performance. |
| **Prefill tok/s ignores RAM latency** | **Generally True** | Prefill is bandwidth-bound; RAM latency is negligible compared to the massive data volume. |
| **Decode tok/s suffers from RAM latency** | **Generally True** | If the cache is offloaded, the round-trip to CPU RAM dominates the kernel execution time. |
| **7B Model fits in 6GB VRAM** | **Generally True** | Weights $\approx$ 4.5–5GB (float16). Leaves margin for KV cache up to ~4k–6k tokens depending on precision and batch size. |

#### 5. Diagnostic Measurements

To isolate the bottleneck, perform these three controlled experiments:

1.  **Isolate Weight Bandwidth (Prefill Stress):**
    *   *Setup:* Run 2,000-token prefill only. Measure GPU utilization and memory bandwidth usage (via `nvprof` or `nvidia-smi`).
    *   *Target:* Confirm if the GPU hits its peak memory bandwidth (e.g., 1.0 TB/s). If not, prefill is not the bottleneck.

2.  **Isolate KV-Cache Traffic (Decode Stress):**
    *   *Setup:* Run 2,000-token prefill, then generate 100 tokens. Keep the KV cache **entirely on GPU** (ensure it fits in VRAM). Measure the time per token.
    *   *Target:* If latency is stable (~0.5–1.5 ms/t), the decode logic is efficient on-chip. If latency spikes immediately, the system is likely offloading to RAM or there is a kernel inefficiency.

3.  **Isolate CPU–GPU Transfer (Offload Stress):**
    *   *Setup:* Force KV cache offload to System RAM (configure `--tensor-parallel-size` or specific library flags to use CPU memory for KV). Measure the time per token.
    *   *Target:* Compare the per-token latency here against the "GPU-only" baseline. If the RAM latency is ~5x–10x slower, PCIe transfer is the confirmed bottleneck.

#### Numerical Example: Total Time Dominance

Assume a 1ms per-token decode cost when KV cache is on GPU.
Let $T_{prefill}$ be the time to process the prompt.
Let $T_{decode}$ be the time to generate $k$ tokens.

*   **Scenario A (2,000 tokens prompt, 100 tokens output):**
    *   $T_{prefill} \approx 4000 \text{ tokens} \times 400 \mu s \text{ (avg prefill cost)} \approx 1.6 \text{ s}$
    *   $T_{decode} \approx 100 \times 1 \text{ ms} = 0.1 \text{ s}$
    *   **Total:** 1.7s. **Dominant Factor:** Prefill.
    *   *Insight:* High prompt tok/s hides the fact that the first second is consumed by loading the KV cache.

*   **Scenario B (2,000 tokens prompt, 1000 tokens output, KV cache in RAM):**
    *   $T_{prefill} \approx 1.6 \text{ s}$ (Same)
    *   $T_{decode} \approx 1000 \times (1 \text{ ms} + 2 \text{ ms PCIe/DRAM}) = 3.0 \text{ s}$
    *   **Total:** 4.6s. **Dominant Factor:** Decode (due to offload penalty).
    *   *Insight:* As the conversation grows, the cumulative penalty of fetching keys from RAM dwarfs the initial prefill cost, causing the observed latency explosion.

**Recommendation:** For interactive use cases on 6GB VRAM, limit context to <4,000 tokens to keep KV cache on GPU. If 8k+ is required, accept the latency penalty or utilize a system with larger HBM or a specialized inference accelerator (e.g., NVIDIA HGX) to avoid PCIe bottlenecks.
