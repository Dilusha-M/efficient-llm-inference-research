Scenario:
A 7B decoder-only model is served on a 6 GB consumer GPU with 32 GB system RAM. The model weights fit on the GPU, but the key-value (KV) cache does not always fit there. A user sends a 2,000-token prompt and requests 300 generated tokens. The system reports excellent prompt-processing throughput but becomes much slow ... (truncated)
### 1. KV Cache Lifecycle: Prefill vs. Decode
The lifecycle diverges sharply at the boundary between the **prefill phase** (prompt processing) and the **decode phase** (token generation).

*   **Prefill (Prompt Processing):**
    *   **Action:** The model processes the 2,000-token input in parallel.
    *   **KV State:** For every token, the attention mechanism computes new Key (K) and Value (V) vectors. These are **not** reused because there is no prior sequence.
    *   **Hardware Stress:** Massive parallelism across all layers; high compute demand; memory bandwidth limited by the need to read the entire input matrix and write the full KV matrix.
    *   **Outcome:** A contiguous block of KV cache is allocated on the GPU (e.g., 2000 $\times$ hidden_dim $\times$ heads). If this exceeds 32GB total available (weights + KV + overhead), the system must spill or swap, but since weights fit, the *prompt* likely fits if the KV size is conservative.

*   **Decode (Token-by-Token Generation):**
    *   **Action:** For each generated token, only the **previous** token's KV state is needed to compute the current hidden states.
    *   **Reused vs. Recomputed:**
        *   **Reused:** The K and V matrices for the 2,000 prior tokens are **retrieved** (read) from memory.
        *   **Recomputed:** The K and V matrices for the newly generated token are **computed** (write) into memory.
    *   **Hardware Stress:** Sequential processing; low compute per token; **extreme memory bandwidth stress** as the GPU must read the massive existing KV cache (2,000 tokens) to attend to the new token, then write the updated KV for that single token.

### 2. Hardware Stress & Throughput vs. Latency
*   **Resource Divergence:**
    *   **Prefill** is **Compute-Bound**. It utilizes the GPU's full throughput (TFLOPS). High token/s (tok/s) indicates the GPU is saturated with arithmetic operations.
    *   **Decode** is **Memory-Bound**. The bottleneck is the bandwidth required to stream the KV cache back and forth. Even with 0% compute utilization, the GPU sits idle waiting for memory reads/writes.
*   **The Illusion of High Prefill Throughput:**
    A high prompt tok/s suggests the prompt size is small enough to fit entirely in VRAM and processed efficiently. However, it does **not** imply low interactive latency because:
    1.  **Latency is Decode-Dominated:** Interactive latency is determined by the time to generate *one* token, which depends on KV cache streaming, not prompt throughput.
    2.  **Context Expansion:** As context grows (e.g., 2,000 $\to$ 3,000 tokens), the KV cache size grows linearly. The prefill tok/s remains high (compute bound), but the decode latency increases linearly due to larger KV reads, even though the prefill phase finishes instantly.

### 3. Scaling to 8,000 Tokens: Prefill, Decode, and Bandwidth
*   **Prefill Behavior:** Scaling from 2k to 8k tokens increases prefill compute by 4x. Since the model is compute-bound, prefill time increases roughly 4x, but the *average* tok/s drops slightly due to longer total time, not a fundamental change in hardware behavior.
*   **Decode Behavior:**
    *   **KV Size:** Increases 4x (2k $\to$ 8k).
    *   **Bandwidth Demand:** To generate 1 token, the GPU must read 8k entries (or 4k if the cache is dynamic/evicted, assuming no eviction).
    *   **Memory Pressure:** With 32GB system RAM, the OS page allocator may begin paging if the combined GPU VRAM + System RAM allocation exceeds physical limits or if the GPU offload mechanism (e.g., `torch.compile` with `device='auto'` or CUDA graph limitations) fails to keep the hot KV cache resident in high-speed memory.
    *   **The Spill Effect:** If the KV cache spills to system RAM, the latency penalty is the PCIe/NVLink overhead plus the slower memory access speed of DRAM vs. HBM2e/HBM3.

### 4. General Truths vs. Implementation Dependencies

| Claim Type | Statement | Dependency |
| :--- | :--- | :--- |
| **General Truth** | **Decode latency scales linearly with context size** (in non-evicted scenarios). | None (Physics of Attention). |
| **General Truth** | **Prefill is compute-bound**; Decode is memory-bound. | Architecture class (Transformer). |
| **Impl. Dep.** | **KV Cache Spilling** behavior (error vs. slow). | OS memory management (swapping vs. pinned pages). |
| **Impl. Dep.** | **Performance loss** when moving KV to RAM. | GPU memory hierarchy (HBM speed) vs. System RAM speed; Kernel optimization for pinned memory. |
| **Impl. Dep.** | **Exact latency increase** factor. | Kernel fusion, CUDA Graphs, or Flash Attention implementation. |

*Note: Modern Flash Attention v2 can reduce prefill latency by tiling, but it does not eliminate the memory traffic during decode, nor does it help if the KV cache exceeds physical memory bounds.*

### 5. Diagnostic Measurements & Comparisons

To isolate the bottleneck, perform these three controlled experiments:

1.  **Measure Prefill vs. Decode Ratio:**
    *   Run a fixed 2k prompt with 100 generated tokens.
    *   Compare total time against the theoretical compute-bound time ($T_{compute} \approx \frac{\text{Total FLOPs}}{\text{Peak TFLOPS}}$).
    *   **Diagnosis:** If $T_{total} \gg T_{compute}$, the system is memory-bound (likely KV cache streaming).

2.  **Isolate KV Cache Size (The "Half-Context" Test):**
    *   Run identical decodes with 2k context vs. 4k context.
    *   Monitor **GPU Memory Usage** and **Memory Bandwidth Utilization** (via `nvidia-smi` or `nvprof`).
    *   **Diagnosis:** If latency scales linearly with context size while GPU compute utilization stays near 0% and memory bandwidth hits 80%+, the bottleneck is **KV cache bandwidth**, not weight loading.

3.  **CPU-GPU Transfer Test (Zero-KV-Prefill):**
    *   Generate a short sequence (e.g., 50 tokens) but **do not load weights or KV cache to GPU** (or use a minimal model).
    *   Force the decode loop to read the KV from **System RAM** (simulating the spill scenario) while keeping the GPU active.
    *   **Diagnosis:** If latency increases by 10-50x compared to GPU-resident KV, the bottleneck is **PCIe/System RAM latency**, confirming the need for pinned memory or GPU offload optimization.

### Numerical Example: Latency Dominance

Assume a 2B parameter model where 1 token of decode requires:
*   **Compute:** 0.5 ms (if fully saturated).
*   **KV Read (2k tokens):** 4.0 ms (memory bound).
*   **KV Write (1 token):** 0.1 ms.

**Scenario A: 2,000 Token Context (Fits in VRAM)**
*   Total per-token time = Compute + KV Read + KV Write
*   $T = 0.5 + 4.0 + 0.1 = 4.6 \text{ ms}$.
*   **Latency:** 4.6 ms.
*   **Throughput:** $\approx 218 \text{ tok/s}$.

**Scenario B: 8,000 Token Context (Spills or Overflows VRAM)**
*   Assume the system moves the KV cache to System RAM.
*   **Compute:** Still 0.5 ms (unchanged).
*   **KV Read:** Increases from 4.0 ms to 16.0 ms (4x size, assuming linear scaling and no eviction).
*   **KV Write:** Slight increase due to PCIe latency, say 1.0 ms.
*   $T = 0.5 + 16.0 + 1.0 = 17.5 \text{ ms}$.
*   **Latency:** 17.5 ms.
*   **Throughput:** $\approx 57 \text{ tok/s}$.

**Observation:** Even though the prompt processing (prefill) might still take only ~10ms (compute bound), the **decode latency jumps from 4.6ms to 17.5ms** solely due to the increased KV cache size and memory subsystem characteristics. The "high prompt tok/s" seen in Scenario A is irrelevant to the user experience in Scenario B.
