## Task 1 — quantization tradeoff:

**Given Data:**

**Analysis:**

**Memory Pressure Created by Each Format:**
*   **Q8\_0 (8.0 GB):** This format requires significantly more memory for loading the weights. Given the 5.2 GB free memory, loading the full Q8\_0 weights will consume most or all available memory, potentially leading to immediate Out-Of-Memory (OOM) errors during loading or context management, depending on the overhead of the runtime environment.
*   **Q4\_K\_M (4.8 GB):** This format requires less memory for weights, leaving more free memory (5.2 GB - 4.8 GB = 0.4 GB free). This format is less memory-intensive upfront, providing more headroom for the KV cache and activation memory during inference.

**Why File Size is Not a Complete Runtime-Memory Estimate:**
File size (e.g., 8.0 GB vs 4.8 GB) only measures the static storage requirement for the model weights. Runtime memory usage is significantly higher because:
1.  **KV Cache:** The Key-Value cache for the attention mechanism scales linearly with the sequence length (prompt + generated tokens) and the number of layers, and this cache must reside in GPU memory during inference.
2.  **Activations/Intermediate Buffers:** The intermediate activations generated during the forward pass must also be stored in memory.
3.  **Runtime Overhead:** The memory required for the inference engine itself (e.g., CUDA context, runtime buffers) is added to the weight loading.

**Two Quality/Performance Measurements Needed Before Declaring One Format Better:**
1.  **Inference Latency (Time per token):** Measures the actual speed of generation.
2.  **Peak Memory Footprint During Inference:** Measures the maximum memory required during the process, which is crucial for fitting within the 6 GB GPU constraint.

**Disclaimer:** I cannot declare one format definitively better without running the actual inference and memory profiling on the specific hardware and sequence length.

## Task 3 — robust aggregation:

**Given Data:**
*   Run 1: 42.0 tok/s (Success)
*   Run 2: 41.5 tok/s (Success)
*   Run 3: 8.0 tok/s (Failure, OOM warning)

**Pseudocode for Robust Aggregation:**

```pseudocode
FUNCTION Aggregate_Decodes(Results):
    // Results is a list of (speed, status) tuples
    Successful_Speeds = []
    Failed_Runs = []

    FOR EACH Run IN Results:
        Speed = Run.speed
        Status = Run.status // e.g., "SUCCESS" or "FAILED"

        IF Status == "SUCCESS":
            ADD Speed TO Successful_Speeds
        ELSE:
            ADD Run TO Failed_Runs

    // 1. Compute Median for Successful Runs
    IF SIZE(Successful_Speeds) >= 2:
        SORT Successful_Speeds ASCENDING
        // Calculate Median: If count is odd, take the middle element. If even, average the two middle elements.
        IF SIZE(Successful_Speeds) IS ODD:
            Median_Speed = Successful_Speeds[FLOOR(SIZE(Successful_Speeds) / 2)]
        ELSE:
            Mid1 = Successful_Speeds[SIZE(Successful_Speeds) / 2 - 1]
            Mid2 = Successful_Speeds[SIZE(Successful_Speeds) / 2]
            Median_Speed = (Mid1 + Mid2) / 2.0
        
        RETURN {
            "median_success_speed": Median_Speed,
            "successful_runs_count": SIZE(Successful_Speeds)
        }
    ELSE:
        // 2. Report Result if Fewer Than Two Runs Succeed
        IF SIZE(Successful_Speeds) == 0:
            RETURN {
                "error": "No successful runs found.",
                "failed_runs": Failed_Runs
            }
        ELSE IF SIZE(Successful_Speeds) == 1:
            RETURN {
                "warning": "Only one successful run found. Median is the single successful value.",
                "median_success_speed": Successful_Speeds[0],
                "failed_runs": Failed_Runs
            }
```

**Reporting Strategy if Fewer Than Two Runs Succeed:**
If fewer than two runs succeed, the system should **not** report a median, as a median requires at least two points for meaningful comparison. Instead, it should report the **best observed success** (the maximum speed among the successful runs, or the single successful result if only one exists) and explicitly list all failed runs, clearly indicating that the aggregate result is based on limited data.

## Task 5 — user-visible latency:

**Scenario:** Prompt (2,000 tokens), Generation (200 tokens).

**Definitions:**

1.  **Time to First Token (TTFT):** The time elapsed from sending the complete prompt to the model and receiving the very first generated token. This measures the latency of the initial prompt processing phase.
2.  **Prompt-Evaluation Throughput:** The rate at which the model processes the initial 2,000-token prompt and prepares the necessary context (e.g., attention mechanism setup). Measured in tokens processed per second ($\text{tok/s}$).
3.  **Decode Throughput:** The rate at which new tokens are generated sequentially after the first token is produced. Measured in tokens generated per second ($\text{tok/s}$).
4.  **Total Wall-Clock Time:** The total duration from the moment the prompt is sent until the final generated token is received.

**Symbolic Equation for Total Time:**
$$\text{Total Time} = \text{TTFT} + \text{Time}_{\text{Generation}}$$
Where $\text{Time}_{\text{Generation}}$ is calculated based on the generation rate and the number of tokens:
$$\text{Time}_{\text{Generation}} = \frac{\text{Generated Tokens}}{\text{Decode Throughput}}$$

**Example Where Optimizing Prompt Processing Barely Changes User Experience:**

**Scenario:** Optimizing prompt processing (e.g., using a more efficient prompt encoding or context management technique) barely changes the user experience if the **Time to First Token (TTFT)** is already significantly larger than the total generation time.

**Example:**
If the TTFT is 5.0 seconds, and the generation time (for 200 tokens at 50 tok/s) is $200 / 50 = 4.0$ seconds.
*   **Total Time** $\approx 9.0$ seconds.

In this case, optimizing the prompt processing might reduce the TTFT from 5.0s to 4.5s, resulting in a total time of 8.5s. The user perceives the experience as nearly identical, as the overall latency is dominated by the prompt processing overhead, not the subsequent, longer generation phase.
