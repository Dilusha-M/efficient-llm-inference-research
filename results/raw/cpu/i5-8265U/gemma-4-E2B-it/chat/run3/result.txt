Scenario:
A 7B decoder-only model is served on a 6 GB consumer GPU with 32 GB system RAM. The model weights fit on the GPU, but the key-value (KV) cache does not always fit there. A user sends a 2,000-token prompt and requests 300 generated tokens. The system reports excellent prompt-processing throughput but becomes much slow ... (truncated)
This scenario describes a classic trade-off between computational throughput and memory bandwidth/latency in large language model (LLM) inference.

### 1. KV Cache Lifecycle

The Key-Value (KV) cache stores the intermediate attention states computed during the self-attention mechanism, which must be recomputed for every new token generation.

*   **Prompt Processing (Prefill):** When processing the initial 2,000-token prompt, the entire sequence is processed in parallel. The entire KV cache for these 2,000 tokens is computed once. This phase is dominated by **matrix multiplications** over the entire context length.
*   **Token-by-Token Decoding (Generation):** For each subsequent generated token, the model only needs to compute the attention for the *new* token against the *existing* KV cache. The keys and values from the previous tokens are reused. The system must compute the attention for the new token and append the new key/value vectors to the cache. This phase is dominated by **sequential memory access/read/write** of the existing cache, plus the new computation.

**Reused vs. Recomputed:**
*   **Reused:** The weights ($\mathbf{W}$) and the cached Key ($\mathbf{K}$) and Value ($\mathbf{V}$) vectors from the preceding tokens are reused across subsequent decoding steps.
*   **Recomputed:** The attention mechanism must be recomputed for the new token, which involves computing new $\mathbf{K}$ and $\mathbf{V}$ vectors and the final output logits.

### 2. Resource Stress Differentiation

*   **Prompt Processing (Prefill):** This phase is **compute-bound**. It involves large, parallel matrix multiplications across the entire input sequence. If the model weights fit on the GPU, this phase benefits maximally from the high arithmetic intensity of the GPU cores. High prompt throughput ($\text{tok/s}$) suggests the GPU is efficiently saturated with floating-point operations (FLOPS).
*   **Decoding (Generation):** This phase is **memory-bound** (or latency-bound). While the computation per token is small, it requires frequent, sequential access to the KV cache. Moving the KV cache to system RAM (CPU memory) increases the latency of these memory accesses (due to PCIe transfer and memory access latency) rather than increasing the raw FLOPS capacity of the GPU. High prompt throughput does not imply low interactive latency because the bottleneck shifts from raw computation (prefill) to memory bandwidth and latency (decode).

### 3. Effect of Increasing Context Length (2k $\rightarrow$ 8k)

Increasing context length $L$ significantly impacts both phases:

*   **Prefill:** The time complexity scales roughly as $O(L^2 \cdot d)$ or $O(L \cdot d^2)$ depending on implementation (where $d$ is dimension). Increasing $L$ dramatically increases the size of the initial matrix multiplications, leading to a **significant increase in prefill time**.
*   **Decode:** The time complexity scales linearly with $L$ for the cache access and attention calculation per step, but the total cache size ($\text{Cache Size} \propto L \cdot \text{Tokens} \cdot d$) grows linearly. More importantly, the **memory bandwidth** required to read/write the larger KV cache becomes the dominant factor, especially when the cache spills to slower system RAM.

**Memory Bandwidth Role:** As $L$ increases, the total amount of data transferred for the KV cache during both prefill and decode phases increases. If the memory bus (e.g., PCIe bandwidth or HBM bandwidth) becomes saturated, the time spent waiting for data transfers (memory bound) will dominate the actual computation time (compute bound), leading to increased per-token latency.

### 4. Claim Separation

**Generally True (Implementation Independent):**
*   The cost of processing $L$ tokens scales with $L$ for the prompt and $L$ for the generation phase.
*   The KV cache size scales linearly with the number of tokens processed.

**Implementation Dependent (Hardware/Software Specific):**
*   The specific impact of moving the cache to system RAM depends entirely on the PCIe bandwidth and system memory latency.
*   The bottleneck shifts from compute to memory based on the ratio of $\text{Memory Bandwidth} / \text{Compute FLOPS}$.
*   The actual latency increase is determined by the specific memory access pattern and kernel launch overheads, which depend on the GPU architecture and driver implementation.

### 5. Proposed Measurements to Isolate Bottlenecks

To distinguish between weight bandwidth, KV-cache traffic, and CPU–GPU transfer as the bottleneck, we need controlled measurements:

1.  **Weight Bandwidth Test (Compute Dominance):**
    *   **Measurement:** Fix the KV cache size (e.g., 2,000 tokens) and measure the time taken to process a very long prompt (e.g., 10,000 tokens) using only the GPU.
    *   **Goal:** Determine if the time increase is linear with $L$ (indicating compute-bound processing) or if it plateaus (indicating a memory/bandwidth limit on the weights).

2.  **KV-Cache Traffic Test (Memory Bandwidth Dominance):**
    *   **Measurement:** Fix the prompt length (2,000 tokens) and measure the time taken for sequential decoding, systematically varying the KV cache size (e.g., test 100, 500, 1000, 2000 tokens).
    *   **Goal:** Observe how the time increase correlates with the increase in KV cache size. A sharp, non-linear increase strongly suggests memory bandwidth is the bottleneck.

3.  **CPU–GPU Transfer Test (Host-Device Bottleneck):**
    *   **Measurement:** Perform the decoding process where the KV cache is explicitly stored in system RAM (as in the experiment), and measure the time spent *only* on the data transfer (Host $\leftrightarrow$ Device) and the subsequent kernel execution time.
    *   **Goal:** Isolate the latency introduced by PCIe transfer and system memory access overhead versus the raw computation time. A large discrepancy points to the transfer mechanism being the bottleneck.
