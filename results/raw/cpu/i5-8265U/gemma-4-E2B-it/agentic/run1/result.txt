**Success/Failure States:**

* **Failure (Missing Data):** Optional monitoring data is unavailable or sampled sparsely, but the core run succeeded.

**Experimental Identity Tuple:**

## State Machine

**Initial State:** Configuration loaded, validation checks passed.

**Phase 1: Validation & Setup**
1. **Input Validation:** Verify all required inputs are present and consistent with the configuration.
2. **Environment Setup:** Determine the specific `llama.cpp` executable and necessary environment variables based on the selected backend (CPU/CUDA/Vulkan).
3. **Parameter Finalization:** Merge default parameters with explicit overrides (Context, Gen Limit, Temp, Threads, Workload).
4. **Prompt Hashing:** Calculate a hash of the final prompt.

**Phase 2: Execution**
1. **Process Launch:** Execute the `llama.cpp` process with the finalized parameters and prompt.
2. **Monitoring Start:** Initialize resource monitoring hooks for the process.
3. **Execution Loop:** Monitor the process execution.
    * **Timeout:** If execution exceeds the defined time limit, terminate the process and record timeout failure.
    * **OOM:** If the process signals Out-Of-Memory, terminate and record OOM failure.
    * **Process Exit:** Wait for the process to complete. Record exit code and raw output.

**Phase 3: Post-Execution & Finalization**
1. **Output Parsing:** Attempt to parse the raw output and performance metrics.
    * **Malformed Output:** If parsing fails, flag the result as a parsing failure, preserving the raw output.
2. **Data Integrity Check:** Compare the derived performance metrics against the expected invariants (e.g., ensuring generated tokens are accounted for).
3. **Metadata Generation:** Create the run-specific metadata file, including the full experimental identity tuple, raw output, and metrics.
4. **Failure Determination:** Determine the final state:
    * **Hard Failure:** Model process failed, OOM occurred, or critical data is missing.
    * **Soft Failure:** Run succeeded, but optional monitoring data was missing or sparse.
5. **Output Availability:** Ensure the raw output is available for manual audit regardless of success/failure status.

4. **Monitor Agent:** Hooks into the execution environment to track resource usage (CPU, Memory, GPU utilization).

## Analysis Integrity

**Preventing Misleading Throughput:**
Throughput must be calculated using the total generated tokens and the actual elapsed time from the raw output, rather than relying solely on the `llama.cpp` reported metrics, as the latter might be incomplete or misleading upon early exit.
* **Calculation:** $\text{Throughput} = \frac{\text{Total Generated Tokens}}{\text{Time Elapsed (from start to finish)}}$.
* If the run fails before completion, the time elapsed up to the failure point is recorded, and the throughput calculation reflects the partial run, which is explicitly flagged in the metadata status.

**Handling Unknown Output Formats:**
The parser must operate in a defensive, layered approach:
1. **Signature Check:** Check for known markers (e.g., specific delimiters, expected JSON structure) in the raw output.
2. **Fallback Parsing:** If signature check fails, attempt to parse based on the expected format derived from the run's configuration (e.g., if `workload` is `chat`, expect a specific conversational structure).
3. **Raw Preservation:** If all parsing attempts fail, the parser must record a `PARSE_ERROR` status in the metadata and store the entire raw output as a string/byte sequence in the metadata, ensuring the raw data is never lost or misrepresented, fulfilling the audit requirement.

## Pre-merge Review

**Highest-Risk Design Flaw 1: State Management and Invariant Enforcement**
* **Flaw:** The requirement to prevent mixing results based on environmental changes is complex. If the system relies solely on post-hoc comparison, subtle differences in how different backends report timing or resource usage could lead to false positives/negatives, especially when dealing with sparse monitoring data.
* **Fix:** Implement a strict, immutable **Run Signature Check** performed immediately after launch. This signature must include all environmental variables, runtime parameters, and the prompt hash. If the signature does not match the expected configuration for a direct comparison, the system must refuse to merge the results or flag the comparison as invalid, regardless of the reported success state.

**Highest-Risk Design Flaw 2: Raw Output vs. Metrics Discrepancy**
* **Flaw:** The requirement to preserve raw output while simultaneously deriving performance metrics risks decoupling the two critical artifacts. If the parser fails, the system must not accidentally discard the raw data, and vice versa.
* **Fix:** Enforce a strict **One-to-One Mapping** in the metadata schema. The `raw_output_path` must be the sole reference to the raw data. If parsing fails, the metadata entry must explicitly state the failure mode, and the raw output file must remain untouched, fulfilling the audit requirement directly.

**Highest-Risk Design Flaw 3: Handling of Asynchronous Failures (Monitoring vs. Process Exit)**
* **Flaw:** The concurrent nature of monitoring and process exit means a failure might occur before monitoring can fully register the state, leading to a corrupted final status (e.g., marking a successful process as a failure due to a late monitoring error).
* **Fix:** Implement a **Synchronous Barrier** in the State Machine. The finalization phase (Phase 3) must wait for definitive signals from *both* the Process Executor (exit code) and the Monitor Agent (final resource snapshot) before writing the final metadata. If a timeout or OOM occurs, the process exit signal takes precedence; if the process exits cleanly but monitoring is absent, the absence is flagged as a soft failure, not a hard failure.
