### Task 1 — quantization tradeoff

**Memory Pressure Analysis**
*   **Q8_0 (8.0 GB):** This format requires 8.0 GB of VRAM for weights alone. Given a 6 GB GPU with only 5.2 GB free, loading this model will immediately trigger an Out-of-Memory (OOM) error. The pressure is absolute; it exceeds the device's capacity by 1.8 GB.
*   **Q4_K_M (4.8 GB):** This format requires 4.8 GB of VRAM for weights. With 5.2 GB free, there is a buffer of 0.4 GB available after weight loading. However, this buffer is extremely thin because it must accommodate the Key-Value (KV) cache (which grows with context), the tokenizer, and the model's internal overhead. Any increase in context size or overhead could push the system over the limit.

**Why File Size is Not a Complete Runtime-Memory Estimate**
File size represents the static memory required to load weights. It does not account for:
1.  **Dynamic Overhead:** The KV cache required for the input context and future generation tokens.
2.  **Internal Buffers:** Memory allocated for the tokenizer, activation maps during forward passes, and the model's internal padding or alignment overheads.
3.  **Fragmentation:** In multi-GPU setups or specific library implementations, memory fragmentation can prevent the OS from allocating contiguous blocks even if total free memory appears sufficient.

**Required Quality/Performance Measurements**
Before declaring one format better than the other, the following metrics are necessary:
1.  **Maximum Sustainable Context Size:** The longest sequence length (tokens) that can be processed without triggering an OOM warning or crashing.
2.  **Tokens-Per-Second (TPS) at Target Context:** The actual inference throughput (e.g., tok/s) measured at a specific, realistic context length (e.g., 2k tokens), normalized by the time taken to generate a fixed number of tokens (e.g., 50 tokens).

*Note: Q4_K_M is not guaranteed to be faster; if the model runs out of memory and restarts frequently due to context management, Q8_0 might actually appear slower in a real-world session despite its raw speed potential on sufficient hardware.*

### Task 3 — robust aggregation

**Validation Logic**
The pseudocode below validates records by checking for success status. If a run fails, it is excluded from the median calculation but retained in the dataset to prevent masking the failure.

```python
def aggregate_decode_runs(records):
    # Initialize containers
    successful_times = []
    failed_records = []
    
    for record in records:
        # Assumption: 'record' has a 'status' (bool) and 'speed' (float)
        if record['status']:
            # Only include successful runs in the median calculation
            successful_times.append(record['speed'])
        else:
            # Keep failed run visible for analysis/reporting
            failed_records.append(record)
    
    # Compute Median for Successful Runs
    if len(successful_times) == 0:
        return {"median_speed": None, "failed_runs": failed_records}
    
    successful_times.sort()
    n = len(successful_times)
    mid = n // 2
    if n % 2 == 0:
        median_speed = (successful_times[mid - 1] + successful_times[mid]) / 2.0
    else:
        median_speed = successful_times[mid]
        
    return {"median_speed": median_speed, "failed_runs": failed_records}

# Example Usage
runs = [
    {"speed": 42.0, "status": True},
    {"speed": 41.5, "status": True},
    {"speed": 8.0, "status": False} # Contains OOM warning
]
result = aggregate_decode_runs(runs)
```

**Reporting Fewer Than Two Successful Runs**
If `len(successful_times)` is less than 2:
1.  **If 0 successful:** Report "No valid runs available for statistical aggregation. All attempts failed."
2.  **If 1 successful:** Report "Insufficient data for median calculation (requires ≥2 runs). The single valid result was [Value] tok/s, but the result is not statistically robust due to the lack of variance." Do not calculate a median; report the single value with a disclaimer.

### Task 4 — validity audit

**Four Threats to Validity**

1.  **Threat: Workload/Output Comparability**
    *   **Description:** The CPU, CUDA, and Vulkan backends may differ in how they handle floating-point precision (e.g., 32-bit vs 64-bit) or rounding modes, leading to different numerical results even on the same input. Furthermore, if the Vulkan implementation uses a different kernel optimization (e.g., fused operations) that yields different outputs than the CUDA reference, the results are not comparable.
    *   **Control/Disclosure:** Run a "determinism check" where a small subset of tokens is generated by all three backends and compared byte-for-byte. If outputs differ, the comparison must be based on *latency* rather than *accuracy*, and the output divergence must be disclosed in the methodology.

2.  **Threat: Hardware/Software Configuration Drift**
    *   **Description:** "CUDA offloads all layers" and "Vulkan offloads all layers" might imply different memory hierarchies. CUDA might utilize shared memory aggressively while Vulkan relies on global memory, affecting cache hit rates. Additionally, the "8 threads" on CPU might be oversubscribed if the GPU threads are also scaling up, causing interference.
    *   **Control/Disclosure:** Fix the number of CPU threads globally and use a tool like `nvidia-smi` to monitor active CUDA streams and Vulkan compute queues to ensure they do not contend for the same system resources during the benchmark.

3.  **Threat: Measurement Granularity (Microbenchmarks vs Macrobenchmarks)**
    *   **Description:** Measuring time per token (micro-benchmark) without accounting for initialization time (loading weights, compiling kernels) inflates the variance and makes the first few tokens unrepresentative of the stable throughput.
    *   **Control/Disclosure:** Discard the first $N$ tokens (e.g., 50-100) from every run to allow kernels to warm up and initialize caches, reporting only the "steady-state" throughput.

4.  **Threat: Statistical Insufficiency**
    *   **Description:** Running each backend only three times is statistically weak for identifying outliers (e.g., a single driver bug or transient memory spike). It increases the risk of Type I/II errors regarding performance differences.
    *   **Control/Disclosure:** Increase the number of runs to at least 10 per backend. If only three are possible due to hardware constraints, explicitly state that the results are "preliminary" and include confidence intervals based on the small sample size.

### Task 5 — user-visible latency

**Definitions and Distinctions**
*   **Time to First Token (TTFT):** The wall-clock time from the start of the prompt processing to the appearance of the first generated character. This includes prompt evaluation time + the time to compute the first output token.
*   **Prompt-Evaluation Throughput:** The speed at which the model processes the *input* tokens (2,000 in this case). This is usually a one-time cost.
*   **Decode Throughput:** The speed at which subsequent tokens are generated (200 tokens). This is the dominant factor for the total time in long-generation scenarios.
*   **Total Wall-Clock Time:** The sum of TTFT and the time taken to generate the remaining 200 tokens.

**Symbolic Equation**
Let $T_{prompt}$ be the time to evaluate the input.
Let $T_{decode}$ be the time to generate the output stream.
Total Time ($T_{total}$) = $T_{TTFT} + T_{decode}$

Where:
$T_{TTFT} \approx T_{prompt} + \frac{1}{\text{decode\_rate}}$
$T_{decode} \approx \frac{\text{num\_output\_tokens}}{\text{decode\_rate}}$

Therefore:
$T_{total} = T_{prompt} + \frac{\text{num\_output\_tokens}}{\text{decode\_rate}} + \frac{1}{\text{decode\_rate}}$
*(Note: In practice, $T_{prompt}$ is often negligible compared to $T_{decode}$ for large prompts, but $1/\text{decode\_rate}$ is the initial "cold start" lag).*

**Example of Minimal User Impact**
Optimizing prompt processing barely changes user experience if the prompt evaluation time is already negligible compared to the generation time.
*   **Scenario:** A 2,000-token prompt takes 0.5 seconds to evaluate. The generation of 200 tokens takes 20 seconds.
*   **Optimization:** Reducing the prompt evaluation time from 0.5s to 0.1s.
*   **User Experience Change:** The user waits 0.4 seconds less before seeing the first character. However, the total time still takes 20.4 seconds. The "feel" of the interaction (dominated by the 20s wait) is unchanged. The optimization only helps if the user is waiting on the *prompt evaluation* specifically (e.g., via a progress bar), not the overall response time.
