### Task 1 — quantization tradeoff

**Memory Pressure Analysis**
*   **Q8_0 (8.0 GB):** With 8.0 GB required for weights on a 6 GB GPU, the model **cannot fit entirely on the device**. To run this, the system must utilize memory offloading (swapping weights to system RAM when GPU memory is full) or rely on a very small context window where the KV cache does not significantly exceed the weight footprint, but the 8.0 GB requirement alone exceeds the 6.0 GB limit. The memory pressure is "insurmountable on-device" without aggressive offloading.
*   **Q4_K_M (4.8 GB):** This fits within the 6.0 GB GPU limit (leaving ~1.2 GB headroom for KV cache). The memory pressure is "low to moderate," allowing the model to run fully on-device provided the KV cache plus 4.8 GB does not exceed 6.0 GB.

**Why File Size is Not a Complete Runtime Estimate**
File size measures static weight storage, but runtime memory demand is dynamic:
1.  **KV Cache Overhead:** As the context length increases, the required memory for the Key-Value cache grows non-linearly. A format that fits weights + small context might exceed the limit with a larger context.
2.  **Activation Memory:** During the forward pass, temporary activation maps consume additional VRAM depending on the architecture and layer count, which is not captured by the static quantized weight file size.
3.  **Fragmentation & Overhead:** Quantized files may have internal padding or alignment overheads that affect actual usage, though this is usually minor compared to dynamic buffers.

**Required Quality/Performance Measurements**
To declare one format better, the following must be measured before assuming Q4 is universally superior:
1.  **Maximum Context Length at Target Latency:** The longest context size achievable while maintaining an acceptable generation speed (e.g., >30 tok/s) under both quantizations. Q8_0 might be better for very long contexts if offloading is acceptable, while Q4 fails completely.
2.  **Token Generation Speed at Fixed Context:** The average tokens-per-second (tok/s) generated with a representative context size (e.g., 2,048 tokens). This distinguishes if the overhead of decoding with larger weights (Q8_0) outweighs the reduced compute intensity benefits of higher precision.

*Note: It is explicitly hypothesized that Q4_K_M is generally faster due to smaller activation maps, but Q8_0 may win on accuracy-dependent tasks or specific long-context scenarios if offloading latency is managed.*

### Task 4 — validity audit

**Four Threats to Validity and Controls**

1.  **Threat: Workload/Output Comparability (Non-Technical)**
    *   *Issue:* The prompt or generation task differs between runs (e.g., one uses a complex reasoning prompt, another a creative writing prompt). Since the prompt length is fixed at 2,000 tokens but the *complexity* of the text varies, the GPU/CPU efficiency per token changes drastically.
    *   *Control/Disclosure:* Use a standardized benchmark suite with identical prompts (e.g., GSM8k for math, BigBench Hard) across all backends. Record the specific prompt ID to ensure reproducibility.

2.  **Threat: Hardware Thermal Throttling**
    *   *Issue:* Running three times on the same machine without thermal intervention may cause the CPU or GPU to throttle clock speeds after the first few runs, artificially degrading performance metrics for subsequent runs.
    *   *Control/Disclosure:* Enforce a cooling break (e.g., 30 seconds) between runs or use a thermal management tool to maintain constant clock speeds. Disclose the average CPU/GPU temperature during the run.

3.  **Threat: System Resource Contention (Software)**
    *   *Issue:* Running three times sequentially on a single machine means the second and third runs are competing for the same cache lines, file system handles, or background processes that the first run may have monopolized.
    *   *Control/Disclosure:* Isolate the runs in separate process groups or use a sandboxing tool (like `systemd-run` with separate unit files) to prevent interference. Alternatively, run them on distinct machines.

4.  **Threat: Implementation-Level Optimization Differences (Software)**
    *   *Issue:* The "CPU run" might use a different compiler optimization level (`-O3` vs `-O2`) or a newer version of the inference library compared to the CUDA/Vulkan versions, introducing a confounding variable unrelated to the architecture choice.
    *   *Control/Disclose:* Pin all build configurations and library versions to an exact commit hash or container image ID. Explicitly state the compiler flags and library versions used for each backend.

### Task 5 — user-visible latency

**Definitions and Distinctions**

1.  **Time to First Token (TTFT):**
    *   The wall-clock time from the start of the prompt input to the appearance of the first character of the generated text. This is dominated by **prompt evaluation** (processing the input) and initial warm-up.

2.  **Prompt-Evaluation Throughput:**
    *   Tokens per second used to process the 2,000-token input. This is a rate, not a latency metric, but it determines the duration of the TTFT phase.

3.  **Decode Throughput:**
    *   Tokens per second generated after the first token. This is the speed at which the model outputs subsequent characters.

4.  **Total Wall-Clock Time:**
    *   The sum of TTFT plus the time required to generate the remaining 199 tokens (assuming the first token is counted in TTFT).

**Symbolic Equation**
Let $N_{prompt}$ be the prompt length, $N_{gen}$ be the generation length, $T_{eval}$ be the time spent evaluating the prompt, and $T_{decode}$ be the total time spent decoding the output.
$$T_{total} = T_{eval} + T_{decode}$$
Where:
$$T_{eval} \approx \frac{N_{prompt} \times L_{prompt\_latency}}{R_{eval}}$$
$$T_{decode} \approx N_{gen} \times \frac{1}{R_{decode}}$$
*(Note: $L_{prompt\_latency}$ and $R_{eval}$ vary by model architecture and quantization).*

**Example of Negligible Optimization**
Optimizing prompt processing (e.g., moving from a standard tokenizer to a highly optimized one) might reduce $T_{eval}$ by 100ms.
*   **Scenario:** The prompt-evaluation throughput is 50 tok/s. For a 2,000-token prompt, $T_{eval} = 40$ seconds.
*   **Impact:** Reducing $T_{eval}$ by 100ms changes the total time from 40s + decode_time to 39.9s + decode_time.
*   **User Experience:** The user perceives the delay as "40 seconds" vs "almost 40 seconds." The subjective feeling of waiting is unchanged because 100ms is imperceptible in a multi-second wait. The optimization is mathematically significant but user-invisible.
