# Requirements and Invariants

### Inputs and Artifacts
*   **Configuration (`config.yaml`)**: Defines model aliases (path, backend, context, generation limit), workload prompts (fixed strings), and optional monitor parameters (enabled flags, intervals).
*   **Environment Variables**: `LLAMA_CPP_PATH`, `CUDA_VISIBLE_DEVICES` (if applicable), `VULKAN_ENABLED`.
*   **Runtime Inputs**: The specific model file path, backend selection, and any user-provided prompt overrides.
*   **Artifacts**:
    *   `run_<id>.json`: Atomic metadata file containing the experimental identity tuple.
    *   `response_<id>.txt`: Raw model output (stdout/stderr combined or specific stream).
    *   `metrics_<id>.json`: Performance data (tokens/sec, latency) if successfully parsed.
    *   `audit_log_<id>.txt`: Raw stdout/stderr streams preserved verbatim.

### Success and Failure States
*   **Success**: The model runs to completion, generating at least one token (or full context generation). Metrics must be present *if* a monitor is configured. If no monitor is configured, success is defined by successful token generation regardless of missing metrics.
*   **Failure**:
    *   **Model Failure**: Process exits with non-zero status code before completion (OOM, crash, segmentation fault).
    *   **Partial Generation**: Process exits with non-zero status *after* generating tokens but before completion.
    *   **Monitor Failure**: Monitor process exits or returns invalid data. This does **not** fail the run if no monitor was requested; if requested, it marks the run as "partial success" with nullified metrics.
    *   **Malformed Output**: The parser cannot extract metrics from the output file.

### Experimental Identity Tuple (EIT)
To ensure isolation, every run must generate a unique EIT string composed of:
`{model_hash}:{backend}:{hardware_label}:{context}:{gen_limit}:{prompt_hash}:{build}:{driver_env}`
*   Any change in any field invalidates results from previous runs with the same ID.
*   `hardware_label`: Derived from `nvidia-smi` (CUDA) or `vulkaninfo` (Vulkan) or `lscpu` (CPU).

### Identified Ambiguity
**Ambiguity**: "Malformed performance output" definition.
*   *Issue*: Llama.cpp output formats vary by version (e.g., `--print-tokens` vs default timing, or missing `--batching-size` headers). If a monitor is enabled but the output format changes, how do we distinguish a "broken run" from "unknown metric format"?
*   *Resolution*: The parser must attempt to parse known formats. If the output exists but cannot be parsed, the metric field in the metadata must be `null` rather than causing a runtime crash, allowing the run to succeed with zero performance data.

# State Machine

The workflow is a finite state machine (FSM) with the following states: `INIT`, `VALIDATION`, `MONITOR_LAUNCH`, `RUNNING`, `COMPLETED`, `FAILED`, `TIMEOUT`.

1.  **INIT**:
    *   Parse `config.yaml` and resolve aliases.
    *   Compute EIT. Check if EIT matches existing artifacts (if strict isolation is required, abort).
    *   Acquire hardware metadata.
2.  **VALIDATION**:
    *   Verify prompt hash matches configured workload.
    *   Verify context limit > 0.
    *   Launch Llama.cpp process (forked).
    *   **Branch A (Monitor Enabled)**: Fork/Spawn Monitor Process. Transition to `MONITOR_LAUNCH`.
    *   **Branch B (Monitor Disabled)**: Skip monitor spawn. Transition to `RUNNING`.
3.  **MONITOR_LAUNCH**:
    *   Wait for monitor process to initialize.
    *   Transition to `RUNNING`.
4.  **RUNNING**:
    *   Wait for model process to complete or timeout.
    *   **Timeout Trigger**: Send SIGKILL to model process. Transition to `FAILED`.
    *   **Normal Exit**: Transition to `FINALIZATION`.
5.  **FINALIZATION**:
    *   **Capture Outputs**: Read `stdout` and `stderr` into `audit_log_<id>.txt`.
    *   **Parse Metrics**: Attempt to parse `metrics_<id>.json` using the raw output buffer.
        *   If parse fails: Log warning, set metric fields to `null`.
    *   **Check Model Exit Code**:
        *   If Exit Code != 0: Transition to `FAILED`.
        *   If Exit Code == 0: Transition to `SUCCESS`.
    *   **Write Artifacts**: Atomic write of `run_<id>.json`.
6.  **FAILED**:
    *   Do not write `run_<id>.json` as successful.
    *   Mark `response_<id>.txt` as "incomplete" if tokens were generated.
    *   Clean up processes.

**Edge Case Handling**:
*   **OOM/Crash**: Detected via non-zero exit code. Transition to `FAILED`.
*   **Partial Output**: Detected via non-zero exit code + token count > 0. Transition to `FAILED` (but keep `response_<id>.txt` for audit).
*   **Missing Monitor Data**: If monitor process exits without data, metrics are `null`. Run status depends on model exit code (Success if model finished, Failure if model crashed).

# Auditable Design

### Component Boundaries
*   **Shell Wrapper (`run_benchmark.sh`)**: Handles process management (forking monitor, killing on timeout), file locking, and atomic writes.
*   **Python Parser (`parse_llama_output.py`)**: Pure Python logic to parse `stdout`/`stderr` strings into JSON metrics. No external dependencies beyond `json`.
*   **Metadata Generator (`gen_eit.py`)**: Generates the EIT string and populates the main JSON structure.

### Metadata Schema (`run_<id>.json`)
```json
{
  "run_id": "uuid-v4",
  "experimental_identity": "model_hash:backend:hw_label:ctx:gen:prompt_hash:build:driver_env",
  "status": "SUCCESS|FAILED",
  "model_output_path": "response_<id>.txt",
  "metrics": {
    "tokens_generated": <int|null>,
    "tokens_per_second": <float|null>,
    "latency_ms": <float|null>
  },
  "monitor_available": <bool|null>,
  "monitor_data_valid": <bool|null>,
  "exit_code": <int|null>,
  "audit_log_path": "audit_log_<id>.txt"
}
```

### Atomic Write Convention
*   To prevent corruption during inter-process communication (IPC) or partial writes:
    1.  Construct JSON object in memory.
    2.  Write to a temporary file: `run_<id>.json.tmp`.
    3.  Flush and `fsync()` the temporary file.
    4.  Rename `run_<id>.json.tmp` to `run_<id>.json` (atomic rename on POSIX).
*   **Partial File Handling**: If `response_<id>.txt` is truncated by a crash, the design assumes the truncation is the artifact. The parser will detect EOF anomalies and mark metrics as `null`.

### Preserving Stdout/Stderr
*   The shell wrapper redirects `stdout` and `stderr` of the model process to a single large file or pipes them to a buffer.
*   **Exact Prompt Preservation**: The prompt used is stored in the EIT (`prompt_hash`). The raw prompt text is included in the `audit_log_<id>.txt` header to allow manual verification against the input.

# Analysis Integrity

### Preventing Misleading Comparisons
*   **Failed Run Exclusion**: The analysis script (`analyze.sh`) must filter the `run_<id>.json` metadata. Runs where `status == "FAILED"` or `exit_code != 0` are excluded from throughput calculations, even if partial tokens were generated.
*   **Token Count Normalization**: Throughput (tok/s) must be calculated based on `tokens_generated / elapsed_time`. If `tokens_generated` is 0, the run is ignored.
*   **Variable Generated-Token Count**: The design ensures that the "base" run (same EIT) is compared only if the prompt hash matches exactly. A change in prompt hash (e.g., whitespace) invalidates the comparison entirely, forcing a new EIT generation, preventing apples-to-oranges comparisons.

### Parser Handling of Unknown Formats
*   **Fallback Strategy**: The `parse_llama_output.py` script will attempt to match patterns against known Llama.cpp versions (e.g., `Tokens: X`, `Time: Y`).
*   **Unknown Format Handling**:
    *   If the output file exists but contains no recognizable tokens or timing strings, the parser logs a `DEBUG` level warning: "Output format unrecognized or empty".
    *   It returns a JSON object with `tokens_generated: null`.
    *   It does **not** crash the main benchmark process.
    *   The `monitor_data_valid` flag in the metadata will be set to `false`.
*   **Validation**: Before returning metrics, the parser verifies that `tokens_generated` is an integer > 0. If not, metrics are `null`.

# Test Plan

1.  **Simulated Backend Failure (OOM/Crash)**
    *   *Setup*: Configure a model with insufficient heap size or inject a signal to kill the Llama.cpp process.
    *   *Expectation*: `status` = `FAILED`, `exit_code` = non-zero. `response.txt` contains partial output or empty. `metrics` = `null`. No `run_<id>.json` success flag.
2.  **Missing Monitor**
    *   *Setup*: Disable monitor in config. Run a standard workload.
    *   *Expectation*: `status` = `SUCCESS` (if model runs), `monitor_available` = `false`. `metrics` = `null` (expected), but run is not considered failed.
3.  **Prompt Containing Spaces/Newlines**
    *   *Setup*: Use a prompt from the `chat` workload that includes newlines. Ensure `prompt_hash` is calculated correctly.
    *   *Expectation*: `prompt_hash` matches the config. `audit_log` contains the raw newlines. EIT generation succeeds.
4.  **Partial Output (Crash mid-generation)**
    *   *Setup*: Configure a very short timeout (e.g., 2 seconds) on a heavy model.
    *   *Expectation*: Process killed. `status` = `FAILED` (due to non-zero exit or timeout). `response.txt` contains < 256 tokens. `metrics` = `null` (time elapsed < token count threshold).
5.  **Changed Prompt Hash**
    *   *Setup*: Run the same model/backend with a prompt that has one trailing space added.
    *   *Expectation*: `prompt_hash` differs from the baseline. EIT is different. If the system is running a "continuous benchmark", this should trigger a new run ID, ensuring previous results are not mixed.
6.  **Malformed Performance Output**
    *   *Setup*: Simulate a Llama.cpp build with a broken `--print-tokens` flag or modify the output stream to contain binary garbage.
    *   *Expectation*: `parse_llama_output.py` detects the error, sets `monitor_data_valid` = `false`, `metrics` = `null`. Main process completes successfully (if model didn't crash). `audit_log` contains the garbage.

# Pre-merge Review

### Highest-Risk Design Flaws and Fixes

1.  **Flaw: Race Condition in Atomic Writes**
    *   *Risk*: If the shell wrapper and the Python parser run concurrently or if the filesystem is under high I/O load, there is a theoretical race condition where `run_<id>.json.tmp` is written while `fsync` is in progress, or if two scripts attempt to lock the same file handle (though atomic rename mitigates this, the initial write buffer could be corrupted).
    *   *Fix*: Implement a strict file lock using `fcntl.flock()` on the temporary file *before* writing the JSON content, ensuring exclusive access during the entire generation phase.

2.  **Flaw: EIT Hash Collision or Sensitivity**
    *   *Risk*: If the `prompt_hash` calculation uses a simple `hash()` function that is not collision-resistant, two different prompts could share an EIT, mixing results. Conversely, if the hash is too sensitive (e.g., including invisible Unicode characters), a single copy-paste error generates a new EIT, breaking the "batch" nature of the experiment.
    *   *Fix*: Use a cryptographically secure hash (SHA-256) for the `prompt_hash` component and normalize the prompt string (strip trailing newlines, encode non-printable chars) *before* hashing to ensure stability.

3.  **Flaw: Metric Inflation Due to Monitor Latency**
    *   *Risk*: If the monitor process introduces significant overhead (e.g., excessive logging to disk) and calculates time based on wall-clock time including the monitor's own processing time, the `tokens_per_second` metric will be artificially low, misleading performance comparisons.
    *   *Fix*: The monitor should calculate elapsed time based on `walltime` provided by llama.cpp directly, not by subtracting walltime from the monitor's own clock. If the monitor calculates its own time, it must explicitly report `monitor_overhead_ms` in the output, which the parser must subtract from the total time to normalize the metric. (Note: If the design assumes llama.cpp handles timing, the monitor should only report *presence*, not timing, to avoid this complexity; if the monitor *must* report timing, it must use `walltime` from the command line args passed by llama.cpp).
