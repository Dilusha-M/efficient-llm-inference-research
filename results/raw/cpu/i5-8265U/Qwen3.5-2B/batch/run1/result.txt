**Why file size is not a complete runtime-memory estimate**
The file size is a static measure of the model parameters (weights), not the dynamic memory footprint at runtime.
1.  **KV Cache:** Large models require significantly more VRAM than the weights alone. The KV cache grows with sequence length and is often 2x to 10x the parameter size.
2.  **Optimizer State:** Gradients and intermediate states for quantization (e.g., Q4_K_M) are stored in memory, adding to the footprint.
3.  **Kernel Buffers:** Inference kernels (for attention, MLPs) require temporary buffers that can scale with batch size or sequence length.
4.  **Quantization Overhead:** Q4_K_M requires additional buffers for quantization operations (dequantization, scaling, rounding) compared to Q8_0, adding to the total dynamic memory.

1.  **Peak VRAM Occupancy:** Run the full pipeline (prompt + weights + KV cache + optimizer) and record the exact VRAM used. This determines if the 5.2 GB free space is sufficient for the specific batch size and sequence length.
2.  **Throughput Stability (e.g., p95/p99 tokens/s):** Compare the 240 FPS (approx) of the 8B model at Q8_0 against the 160 FPS (approx) at Q4_K_M. ### Task 3 — robust aggregation

**Pseudocode**

def aggregate_decode_speeds():
    # Define thresholds
    OOM_THRESHOLD = 5.0  # Token/s, indicates failure
    
    success_records = []
    failed_records = []
    
    # Iterate through the reported metrics
    for run_speed in [42.0, 41.5, 8.0]:
        if run_speed >= OOM_THRESHOLD:
            # Skip failed run, do not include in median
            failed_records.append(run_speed)
            # Log warning to stderr or console
            print(f"Skipping OOM run: {run_speed} tokens/s")
        else:
            # Validate success: ensure no OOM and keep as-is
            success_records.append(run_speed)
            
    # Compute median of successful runs
    if len(success_records) == 0:
        # Fewer than two runs succeed (e.g., only 1 run)
        median_speed = None
        print("Error: Fewer than two runs succeeded. Cannot compute median.")
        return median_speed
        
    sorted_success = sorted(success_records)
    median_speed = sorted_success[len(sorted_success) // 2]
    
    return median_speed

# Usage
final_result = aggregate_decode_speeds()
if final_result is None:
    print("No valid runs found.")
else:
    print(f"Robust median speed: {final_result:.1f} tokens/s")

### Task 4 — validity audit

**Threats to Validity and Controls**

1.  **Threat: Cross-Backend Latency Skew (Output Comparability)**
    *   **Description:** A benchmark might show the GPU is faster because it offloads layers, while the CPU is faster because it stays on-device. However, if the CPU backend uses a different quantization scheme (e.g., Q8 vs Q4) or a different kernel implementation (e.g., different attention strategies), the comparison is apples-to-oranges.
    *   **Control:** **Hardware Standardization.** Ensure the CPU backend uses the *exact same* quantization (e.g., Q4_K_M) and the *same* architecture (e.g., NVIDIA H100) as the GPU backend. If using different backends, explicitly report the quantization parameters and hardware models used for each.

2.  **Threat: Incomplete KV Cache Reporting**
    *   **Description:** The benchmark does not report the size of the KV cache (Context Size). Without this, you cannot determine if the GPU is actually using its full capacity or if it is being throttled by the system.
    *   **Control:** **Context Size Disclosure.** Report the sequence length (e.g., 512, 1024, 2048) used in the benchmark. A valid GPU benchmark must specify the KV cache size because the VRAM requirement is directly proportional to it.

3.  **Threat: Non-Deterministic Kernel Launching**
    *   **Description:** If the benchmark runs the CPU and GPU kernels with different kernel launch configurations (e.g., different batch sizes, different thread configurations, or different memory allocation strategies), the measured throughput will vary between runs despite the same hardware.
    *   **Control:** **Deterministic Kernel Configs.** Use identical kernel launch configurations for every backend run. Specifically, lock the `batch_size`, `num_threads`, and `device_queue_config` settings to ensure the kernel launch overhead is constant.

4.  **Threat: Mixed Workload/Output Comparability (Hardware vs. Software)**
    *   **Description:** The CPU runs on 8 threads, while the GPU offloads all layers (implying potentially a different thread count or scheduling strategy). This violates the principle of "fair comparison" where the computational unit is the sole variable. If the CPU backend is actually limited by its own CPU cores rather than the GPU, the GPU might appear faster simply because the CPU wasn't bottlenecked.
    *   **Control:** **Isolate the Bottleneck.** Ensure that in the CPU run, the CPU is also fully utilized (no other tasks running) and that the CPU backend is not constrained by other system resources. Additionally, explicitly state if the benchmark is measuring "GPU-only performance" or "Full System Performance." If full system performance is measured, the CPU backend's hardware must be known to attribute the speed difference correctly.

### Task 5 — user-visible latency

**Definitions and Distinctions**
*   **Time to First Token (TTFT):** The elapsed time from the user pressing "Enter" to the first character appearing on the screen. This reflects the latency of the initial model inference.
*   **Prompt-Evaluation Throughput:** The rate at which the model processes the *input* prompt (e.g., decoding the prompt tokens). This is often limited by the CPU speed during the initial parse.
*   **Decode Throughput:** The rate at which the model generates *output* tokens (tokens/s). This reflects the VRAM-bound inference speed.
*   **Total Wall-Clock Time:** The sum of all elapsed time from the start of the generation to the end.

**Symbolic Equation for Total Time**
Let $T_{TTFT}$ be Time to First Token, $T_{PE}$ be Prompt-Evaluation Time, and $T_{decode}$ be Decode Time.
$$ T_{Total} = T_{TTFT} + T_{PE} + T_{decode} $$

**Example where optimizing prompt processing barely changes the user's experience**
Suppose the CPU is very slow (e.g., a low-end PC) compared to the GPU.
*   Scenario: The model requires 10ms to decode 10 tokens (Decode Throughput is the limiting factor).
*   Optimization: You optimize the prompt processing by using a more efficient quantization or a faster CPU backend, reducing $T_{PE}$ from 10ms to 12ms.
*   Result: The **user-visible latency (TTFT)** remains roughly the same (e.g., 10ms + 10ms = 20ms) because the bottleneck has not shifted. The user still sees the generation taking 10ms because the GPU is slow, regardless of how fast the CPU parsed the text.
*   This demonstrates that optimizing the CPU path (Prompt-Evaluation) is largely invisible to the user if the GPU (Decode) is the bottleneck.
