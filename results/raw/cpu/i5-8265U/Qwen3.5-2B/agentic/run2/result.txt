# Requirements and Invariants

## Inputs and Artifacts
*   **Configuration File (`runner.conf`):** Defines the default environment (context size, generation limit, temperature, backend, build, driver) and the list of model aliases.
*   **Workload Definition (`workloads.yaml`):** Maps workload names to specific prompt text and optional override parameters (e.g., `context: 8192`, `temperature: 1.0`).
*   **Hardware Metadata (`hardware.json`):** A schema-matched record of the target device (GPU name, driver version, CUDA version) and its properties (e.g., `layers` count).
*   **Audit Trail:** A raw `run.log` file capturing the exact command-line arguments and environment variables used at the start of the run. This file is written atomically after the process starts, even if the process crashes mid-execution.

## Success and Failure States
*   **Success:** The runner completes the specified workload, writes the generated metrics to `metrics.json` (or `metrics.txt` for raw audit), and records a successful `response.txt` containing the response.
*   **Failure:**
    *   **Process Crash:** If the process terminates with an exit code of 128 (or 1) *before* writing the metrics file, the runner logs `status: failed` in the metadata. `metrics.json` is omitted or contains only a `metrics_written: false` flag.
    *   **Missing Monitor:** If the optional monitoring backend (e.g., `llama.cpp` `mon` module) is unavailable or cannot be initialized, the runner logs `status: partial` or `status: failed` depending on configuration, but the raw `response.txt` and `run.log` remain present for manual audit.

## Experimental Identity Tuple
The runner must use a specific tuple to ensure no two runs are conflated, even if parameters are slightly different. This tuple consists of:
1.  `model_id`: The canonical identifier of the model.
2.  `backend`: The specific backend name (e.g., `llama3-70b`, `llama3-8b`).
3.  `device`: The hardware identifier (e.g., `cuda12`, `vulkan_gpu`).
4.  `context`: The effective context size in tokens.
5.  `gen_limit`: The maximum generation length in tokens.
6.  `temperature`: The temperature value.

## Ambiguity Resolution
**Ambiguity:** How to handle the case where the `response.txt` contains multiple responses (e.g., from a chat model that supports multi-turns) versus a single deterministic response.
**Resolution:** The runner will parse the first valid response found in the file. If the file contains only one response, it is used. If the file contains multiple responses, the runner will concatenate them with a separator or treat the first one as the primary result for audit purposes. If no response is found, the run is treated as failed.

# State Machine Workflow

The workflow is strictly linear, with specific error-handling branches that prevent state leakage.

1.  **Initialization:**
    *   Read `runner.conf` and `hardware.json`.
    *   Parse `workloads.yaml` to select the target workload and retrieve the associated prompt template.
    *   Construct the `experimental_identity_tuple`.
    *   Validate that the hardware label matches the one in `hardware.json` (pre-flight check).

2.  **Validation Phase:**
    *   Check if the configuration file is valid.
    *   Check if the required backend (e.g., `llama3`, `llama2`) is installed and linked correctly.
    *   **No-Op Branch:** If validation fails, output `status: validation_failed`. Do not launch.

3.  **Launch Phase:**
    *   Start the model process using the specific prompt template.
    *   **Timeout Branch:** If the process exceeds the configured timeout (default: 30s), exit with `status: timeout`.
    *   **OOM Branch:** If the process exceeds the memory limit, exit with `status: out_of_memory`.

4.  **Monitoring Phase (Conditional):**
    *   **Monitor Available:** Attempt to start the optional monitoring backend.
        *   *Success:* Monitor collects metrics (tokens/sec, context usage, etc.) and writes them to `metrics.json` (or `metrics.txt` if JSON is not supported).
        *   *Failure:* If monitoring fails to initialize or cannot collect data, the run is marked `status: partial`. The metrics file is created but contains no data, or only a placeholder.
    *   *Note:* The presence or absence of data in `metrics.json` depends on the monitor status, not just the completion of the model.

5.  **Exit and Finalization:**
    *   **Success:** If the process exits cleanly (exit code 0) and metrics were written, write the final metrics to the output file.
    *   **Failure:** If the process exits with a non-zero code (or if the monitor failed to write), write the final metrics file containing *only* the `status: failed` flag. Do not write any generated metrics.

6.  **Cleanup:**
    *   Regardless of success or failure, close the model process and write the `run.log` atomically to ensure the exact command-line arguments are preserved for audit.

# Auditable Design

## Component Boundaries
*   **Validation Module:** Handles config parsing and hardware verification.
*   **Launcher Module:** Manages subprocess spawning, timeout handling, and OOM detection.
*   **Monitor Module:** Handles optional backend initialization and metrics collection.
*   **Finalizer Module:** Handles atomic file writing of `run.log` and the final status summary.

## Metadata Schema
The final output file (`metrics.json` or `metrics.txt`) must strictly adhere to the schema defined in `runner.conf`. The schema includes fields for:
*   `status`: "success", "failed", "timeout", "partial".
*   `model_id`, `backend`, `device`, `context`, `gen_limit`.
*   `prompt_template_hash`: A hash of the prompt used to ensure reproducibility.
*   `generated_tokens`: A count derived from the metrics.
*   `backend_version`: Version string of the backend library.
*   `device_version`: Version string of the driver/device.

## Atomic-Write and Partial-File Conventions
*   **Atomic Log Write:** The `run.log` file is written using a temporary file and `mv` (move) operation. This ensures that if the process crashes while writing the log, the log file is never corrupted.
*   **Metrics File Handling:**
    *   If the run is **successful**, the metrics file is written *after* the process exits.
    *   If the run is **failed**, **timeout**, or **partial**, the metrics file is *not* written (or written with a `metrics_written: false` flag in a secondary file if required by the specific runner implementation, but generally left empty to indicate no data).
*   **Prompt Preservation:** The full command-line arguments (including `--prompt` or equivalent) are captured in the `run.log` at the very beginning of the execution. This file is included in the final audit report alongside `metrics.json`.

# Analysis Integrity

## Preventing Misleading Throughput Comparisons
To prevent a failed run or variable generated-token count from inflating throughput metrics:
1.  **Strict Exit Code Enforcement:** The runner must enforce an exit code of 1 (or 128) for any failure state. A process that hangs or crashes but doesn't emit the proper "failed" status flag is considered "silent failure" and is treated as a success *only if* the metrics file is present and contains valid data. However, the specification requires distinguishing a failed run from missing data. Therefore, if the process crashes, the run is explicitly marked `status: failed` regardless of whether the metrics file exists.
2.  **Metrics-Only Success Condition:** A run is considered successful only if the process exits with code 0 **AND** the metrics file exists **AND** the metrics file contains non-empty data. If the process exits cleanly but the metrics file is missing (e.g., monitor failed), the run is `status: partial`. This ensures that a "failed" run is never reported as having good throughput.
3.  **Token Count Derivation:** The `generated_tokens` field in the output is not calculated *during* the run but is derived *after* the run completes by parsing the `response.txt` and `metrics.json` (or `metrics.txt`). This prevents the parser from miscounting tokens based on a truncated response stream.

## Handling Unknown Llama.cpp Output Formats
The parser must implement a robust fallback strategy:
1.  **Primary Format (JSON):** Attempt to parse the metrics file as JSON first.
2.  **Secondary Format (Text):** If JSON parsing fails or returns an empty object, attempt to parse the file as plain text.
3.  **Schema Validation:** If text parsing succeeds but the fields do not match the `runner.conf` schema (e.g., missing `status`), treat the run as a failure or malformed output and log a warning.
4.  **Parsing Failure:** If the file is completely unreadable (e.g., binary garbage), the parser logs the raw content of the file to `run.log` and reports `status: failed`. It does not attempt to extract tokens from garbage data.

# Test Plan

1.  **Simulated Backend Failure:**
    *   *Scenario:* The `llama3` backend library is not installed.
    *   *Action:* Run the benchmark with a dummy model.
    *   *Expected Result:* Runner detects missing backend, logs `status: validation_failed`, and exits without launching the process. No metrics file is created.

2.  **Missing Monitor:**
    *   *Scenario:* The optional `llama.cpp` `mon` monitoring module is compiled in but not linked to the binary.
    *   *Action:* Run a successful chat workload.
    *   *Expected Result:* Runner launches, model generates content, but the `metrics.json` file is empty or contains only a `metrics_written: false` flag. The run status should reflect the partial lack of monitor data.

3.  **Prompt Containing Spaces/Newlines:**
    *   *Scenario:* The `workloads.yaml` contains a prompt with embedded newlines or multiple spaces.
    *   *Action:* Run the `coding` workload.
    *   *Expected Result:* The runner correctly identifies the prompt template, processes the prompt through the model, and generates a valid `response.txt`. The parser must correctly handle the multi-line input and output the correct token count.

4.  **Partial Output (Model Crashes Mid-Generation):**
    *   *Scenario:* The model process creates the first line of output but crashes immediately after due to a CUDA OOM error.
    *   *Action:* Run the `world_knowledge` workload.
    *   *Expected Result:* The process exits with code 1. The `run.log` contains the exact command-line arguments (including the prompt with spaces). The `metrics.json` file is *not* created. The status is `failed`.

5.  **Changed Prompt Hash:**
    *   *Scenario:* The default prompt in `runner.conf` changes (e.g., "Hello world" to "Hello, how are you doing today?").
    *   *Action:* Run the same workload twice, once with the old prompt and once with the new prompt, ensuring other parameters remain constant.
    *   *Expected Result:* The `prompt_template_hash` field in the output reflects the new hash. The throughput metrics should be identical to the previous run because the workload parameters were identical, proving that the run identity was correctly maintained despite the hash change.

6.  **Runtime Timeout:**
    *   *Scenario:* A very large context size (e.g., 4096) is set in the config, but the workload is designed to take longer than the configured timeout.
    *   *Action:* Run a slow workload.
    *   *Expected Result:* The process is killed by the timeout handler. The runner logs `status: timeout`. The `run.log` exists, but the `metrics.json` does not, preventing a misleading high-throughput reading.
