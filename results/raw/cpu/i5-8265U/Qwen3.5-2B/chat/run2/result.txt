### 1. Lifecycle Trace: Prefill vs. Decode

In a decoder-only model, the KV cache lifecycle differs fundamentally between the **prefill phase** (prompt processing) and the **decode phase** (token-by-token generation).

*   **Prefill Phase:**
    *   **Action:** The model processes the entire prompt (e.g., 2,000 tokens) and generates the initial 300 tokens.
    *   **Traffic:** The KV cache grows from $0$ to $C_{init} = \text{tokens\_prompt} \times \text{heads} \times \text{blocks}$.
    *   **Reuse:** The entire KV cache is **recomputed** and stored. It is never reused for subsequent tokens because the model state (hidden states) is discarded after the prompt is processed.

*   **Decode Phase:**
    *   **Action:** For each of the 300 generated tokens, the model takes the current hidden state as the "context" and decodes one token.
    *   **Traffic:** The KV cache grows from $C_{init}$ to $C_{final} = C_{init} + \text{generated\_tokens} \times \text{heads} \times \text{blocks}$.
    *   **Reuse:** Only the **newly generated** KV blocks are recomputed. The previously generated blocks are **cached** and reused. The model effectively "looks back" at its own history.

**Implication:** The initial 2,000 tokens cost the full system bandwidth (prompt + full KV). The subsequent 300 tokens only cost the bandwidth required to generate the new KV blocks.

---

### 2. Hardware Stress Differentiation

*   **Prompt Processing (Prefill):** This is the **CPU-bound** operation in this scenario. The GPU computes matrix multiplications, but the CPU manages the workflow. High prompt tok/s here indicates the CPU cannot keep up with the stream of kernels.
*   **Decoding (Interactive Latency):** This is the **GPU-bound** operation. The GPU executes many small, highly parallel matrix multiplications per token. High decode tok/s here indicates the GPU is saturated with compute power, not memory bandwidth.

**Why High Prompt tok/s $\neq$ Low Interactive Latency:**
A high prompt tok/s simply means the CPU finished all prompts quickly. It says nothing about the GPU's ability to perform 1,000 small matrix multiplications per second. A system can have excellent CPU throughput (low prompt latency) while the GPU struggles to finish its 300 tokens quickly, resulting in high interactive latency.

---

### 3. Impact of Increasing Context (2k $\to$ 8k)

Increasing context from 2,000 to 8,000 tokens increases the **total** KV cache size linearly (8x).

*   **Memory Bandwidth Bottleneck:** The system reports excellent prompt throughput because the bottleneck was CPU. Increasing context linearly increases both the initial KV load (prefill) and the incremental KV load (decode). Since the system lacks VRAM, the **initial KV load dominates the prefill**. The prefill time will scale linearly with context size.
*   **Decode Latency:** During decoding, the model only needs to generate the *new* 300 tokens. The KV cache grows from 2k $\to$ 8k, but the *incremental* size is the same as before. Therefore, the **decode latency should remain roughly constant** (limited by GPU compute, not memory), assuming the initial 2k tokens are fully cached.
*   **System RAM Pressure:** Since the model fits in GPU memory, the "memory pressure" is purely a bandwidth issue. As context grows, the initial KV transfer from system RAM to GPU becomes the dominant cost, causing the initial segment of the conversation to become slow, even if the incremental decode is fast.

### 5. Proposed Measurements for Diagnosis

To pinpoint the bottleneck (Weight Bandwidth, KV Traffic, or CPU-GPU Transfer), the following controlled comparisons are required:

1.  **Measure "Weight Bandwidth" ($B_W$):**
    *   *Setup:* Run two experiments on the same hardware. One using a model with 2k context (initial load $C_1$), and one with 8k context (initial load $C_2 = C_1 \times 4$).
    *   *Metric:* Compare the **initial KV-to-GPU transfer time** ($t_{prefill}$).
    *   *Expected Result:* If $t_{prefill}$ scales linearly with context size, $B_W$ is the bottleneck.

2.  **Measure "KV-Cache Traffic" ($B_K$):**
    *   *Setup:* Measure the **GPU memory bandwidth utilization** ($\%BL$) during the *prefill* phase (loading the initial tokens) and the *decode* phase (generating the first 300 tokens).
    *   *Metric:* Compare the bandwidth utilization ratio ($\%BL_{prefill} / \%BL_{decode}$).
    *   *Expected Result:* If $B_K$ is the bottleneck, the GPU memory is saturated during the initial load, but the GPU can handle the decode load at similar rates.

3.  **Measure "CPU-GPU Transfer" ($B_{CPU}$):**
    *   *Setup:* Measure the **CPU memory bandwidth utilization** ($\%BL_{CPU}$) specifically during the first few tokens of decoding (where the KV cache is hot).
    *   *Metric:* Compare the CPU bandwidth usage against the system RAM bandwidth limit.
    *   *Expected Result:* If $B_{CPU}$ is high and $\%BL_{CPU}$ is low, the data is being moved from CPU to GPU faster than the GPU can compute it, indicating the transfer is the bottleneck.

### Numerical Example

**Assumptions:**
*   Model Size: 100M parameters.
*   KV Cache: 4KB blocks per head.
*   System RAM: 64GB (No paging).
*   GPU: 3070 (32GB VRAM).
*   Context: 2,000 tokens.

**Calculation:**
1.  **Prompt Phase (2k tokens):**
    *   Initial KV Size = $2,000 \times 4KB = 8MB$.
    *   System RAM available = 64GB (Plenty of headroom).
    *   *Time Estimate:* Fast (limited by CPU).

2.  **Decode Phase (300 tokens):**
    *   Incremental KV Size = $300 \times 4KB = 1.2MB$ (per token).
    *   System RAM available for *new* KV = 64GB - 8MB (remaining from prefill) $\approx$ 56GB (Plenty of headroom for 300 tokens).

**The "Slowdown" Scenario:**
Suppose the system RAM bandwidth is **100 GB/s**.
*   **Initial KV Transfer:**
    *   $Time = 8MB / 100GB/s = 0.00008s = 80\mu s$.
*   **Incremental Decode:**
    *   $Time = 1.2MB / 100GB/s = 0.000012s = 12\mu s$.

**Dominance Point:**
If the **CPU** can only handle a stream of 100 tokens per second (Tok/s), but the GPU can handle 1,000 tokens per second (Tok/s).
*   **Prompt Tok/s = 100** (CPU bottleneck).
*   **Decode Tok/s = 1,000** (GPU is fast).

**Result:**
The system reports **Prompt Processing Throughput** of 100 tokens/sec.
However, because the CPU is the bottleneck, the *entire* conversation is slow. The first 100 tokens take 10ms to generate. The next 100 tokens take another 10ms.
*   **Total Time for 300 tokens:** $10ms + 10ms = 20ms$.
*   **Average Latency:** 66ms per token.
*   **Perceived Latency:** "Much slower" as conversation grows, even though the *per-token* latency for the *initial* tokens might have been better.

**Conclusion:** The bottleneck is the **CPU-GPU transfer** (or CPU compute) during the prefill phase, not the KV cache. The "slowdown" is purely due to the CPU being unable to process the prompt fast enough, preventing the GPU from ever starting the generation.
