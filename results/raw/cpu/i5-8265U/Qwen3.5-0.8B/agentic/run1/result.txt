# Analysis Integrity

**Preventing a Failed Run or Variable-Generated-Token Count from Misleading Throughput:**
To prevent a failed run from skewing throughput metrics, the parser must treat the "failed run" as a distinct state from the "successful run's metrics".
-   **Counting**: Do not count tokens generated during a failed run. Only count tokens generated during successful runs.
-   **Hashing**: Use a deterministic hash of the input prompt used in the configuration file, not the raw prompt string. This ensures that the `prompt_hash` used to identify runs is stable even if the raw prompt text varies slightly due to whitespace or encoding changes.
-   **Format Parsing**: When parsing `raw_output.txt`, do not assume the output is valid llama.cpp format. The parser should attempt to parse the text as a string, extract the prompt, and extract metrics. If the string is not valid llama.cpp, the metrics extraction fails silently, but the `success` flag remains true based on whether the backend succeeded.
-   **Token Count**: Use `tokenized_text` from llama.cpp (which is deterministic) rather than counting tokens in the raw string. This ensures that a failure due to encoding issues does not inflate the token count for successful runs.

**Parsing Unknown llama.cpp Output Formats:**
-   **Strategy**: Implement a robust text parser that attempts to extract `prompt`, `output`, and `metrics` from any raw string.
-   **Logic**:
    1.  Split by newlines.
    2.  If a line starts with `#` and is not a comment, extract the first line as `prompt`.
    3.  If a line starts with `#` and is not a comment, extract the second line as `output`.
    4.  If a line starts with `#` and is not a comment, extract the third line as `metrics`.
    5.  Validate the extracted fields. If `prompt` is empty, skip. If `output` is empty, skip. If `metrics` is missing or empty, skip that specific run.
-   **Preservation**: Always preserve the original prompt line from the beginning of the `raw_output.txt` for manual audit purposes.
