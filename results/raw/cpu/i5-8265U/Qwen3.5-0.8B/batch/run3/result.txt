*   **Q4_K_M**: This quantization style allocates a small amount of RAM for the kernel layer. The 4.8 GB file represents the kernel memory footprint. If the GPU is running inference, the Q4_K_M format requires significantly less RAM for the kernel execution phase because it uses a much smaller quantization block size. **Why File Size is Not a Complete Runtime-Memory Estimate**:
File sizes are snapshots of RAM usage at a specific moment in time (e.g., when the file was written). Runtime memory usage can fluctuate based on:
1.  **I/O Latency**: The time it takes to read the file from disk to RAM before it is used.
2.  **Allocation Overhead**: The time it takes for the OS and kernel allocator to map the file to RAM.
3.  **Memory Pressure**: If the file is large enough to cause the kernel to panic or the system to pause, the file size will be higher than the actual runtime usage. Conversely, if memory is very tight, the file size may remain small even if usage is high.
**Two Quality/Performance Measurements Needed**:
Before declaring a format superior, one must compare actual inference throughput, not just file size. Specifically:
1.  **Latency**: The time required to generate the first token (prompt-to-decode latency) or the total inference latency. Faster latency is a direct measure of performance.
2.  **Throughput**: The number of tokens generated per second (tokens per second or TPS).
*Note: Declaring Q4 faster requires proving faster latency or throughput, not just smaller file size.*

    valid_records = [r for r in records if r['status'] == 'success']
    
    # Calculate median
    if len(valid_records) >= 2:

Task 4 — validity audit
**Threats to Validity**:
1.  **Hardware vs. Software Workload Parity**: A CPU can be 100% parallelized, while a GPU is 100% serial. If both run three times, one will be slower or consume more memory due to memory bandwidth differences, even if the model architecture is identical.
2.  **Hardware vs. Software Memory Usage**: If the CPU uses 8 threads and the GPU offloads all layers, the GPU will likely consume 0 RAM for the kernel layer while the CPU might consume 4x the RAM or more depending on the memory hierarchy (e.g., L3 cache vs. system RAM). Comparing the two would be invalid because the memory footprint is not comparable.
3.  **Output Validity**: If the CPU generates an output and the GPU produces an output, the outputs might differ in length, format, or semantic interpretation (e.g., a CPU text vs. a GPU image), making the comparison of "how long" or "how many tokens" meaningless.
4.  **Threat of Output Comparability**: Even if hardware is identical, the resulting output might differ (e.g., CPU processing a longer context vs. GPU offloading the context). If the task asks for "time to first token," the output length does not affect the latency directly in the same way, but the *content* of the output affects the metric if the metric is token-based. A valid control would require a "token-to-token" comparison or ensuring the output is identical (e.g., by running both on a single device).
5.  **Threat of Hardware vs. Software Memory**: As noted above, a CPU running 8 threads on 8GB RAM and a GPU using 0 GB for the kernel layer will have vastly different memory footprints. If the goal is to measure "memory pressure," this is a fatal flaw.
6.  **Threat of Software vs. Software Memory**: If both use 0 RAM for the kernel, but the CPU uses 4x the RAM or more due to threading overhead, the memory comparison is invalid.

Task 5 — User-visible latency
**Explanation**:
*   **Time to First Token (TTF)**: The time required to generate the first token. This is the "latency" phase of the inference process.
*   **Prompt-Evaluation Throughput**: The throughput achieved after the first token is generated. This is the "latency" phase for the *second* token.
*   **Decode Throughput**: The throughput achieved after the second token is generated. This is the "latency" phase for the *third* token.
*   **Total Wall-Clock Time (TWT)**: The sum of TTF, the time spent on prompt evaluation, and the time spent on decode.
*   **Symbolic Equation**:
    $$ \text{Total Wall-Clock Time} = \text{TTF} + (\text{Prompt-Evaluation Throughput} \times \text{Tokens}_{\text{prompt}}) + (\text{Decode Throughput} \times \text{Tokens}_{\text{gen}}) $$
    *(Note: Tokens in the prompt and generation sets should be explicitly defined as inputs to the evaluation and generation phases.)*

**Example where optimizing prompt processing barely changes the user's experience**:
If the user's main goal is simply "reading the response" (e.g., a blog post or chat message), the latency measured in the first three phases (TTF, prompt evaluation, decode) is negligible because the user spends virtually no time reading the generated text. If the goal is "generating a response" (e.g., writing a letter), the prompt evaluation phase takes time proportional to the length of the prompt. In this case, optimizing prompt processing (e.g., using a shorter prompt or a faster tokenizer) would change the latency significantly for the user, even if the total time to first token remains the same.
