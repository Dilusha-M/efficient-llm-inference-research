### Task 1 — quantization tradeoff
**Memory Pressure Analysis**
*   **Q8_0 (8B model):** This format requires **8.0 GB** of memory. With a 6 GB GPU having 5.2 GB *free*, the device has **2.8 GB of available block memory** to hold the model weights. Inference will trigger immediate fragmentation as the 8B model is loaded onto the 6 GB block memory. The 8.0 GB file size creates a theoretical peak memory usage of 8.0 GB, which is well above the 6 GB block memory limit, resulting in severe memory pressure that will likely cause the model to be rejected or degrade significantly due to fragmentation and cache misses.
*   **Q4_K_M (4.8B model):** This format requires **4.8 GB** of memory. With a 6 GB GPU having 5.2 GB *free*, the device has **0.4 GB of available block memory**. Inference will trigger immediate fragmentation as the 4.8B model is loaded onto the 6 GB block memory. While slightly safer than Q8_0, this model still exceeds the 6 GB block memory limit, causing severe memory pressure similar to Q8_0. However, because the file size is smaller, the risk of *total* memory exhaustion is lower, but the risk of *fragmentation* remains high if the device is under pressure.

**Why File Size is Not a Complete Runtime-Memory Estimate**
*   **Latency vs. Memory:** File size does not predict runtime memory usage because inference involves complex operations (decompression, decoding, quantization, and layout) that consume memory even before the file is fully loaded. A 10 GB file might take up 1.5 GB of RAM during decoding, leaving only 8.5 GB of free memory. Conversely, a 3 GB file might require 0.5 GB of RAM during quantization.
*   **Memory Leaks and Buffers:** The actual memory footprint can fluctuate based on the model's dynamic memory management (e.g., if the model is kept in a single file but the quantization engine manages multiple buffers).

**Required Measurements for Comparison**
Before declaring one format better, the following two metrics are critical:
1.  **Memory Pressure Index (MPI) / Fragmentation Ratio:** Specifically, the ratio of file size to the *actual* peak memory usage (including buffers, cache, and partial load). A smaller file with high fragmentation is worse than a larger file with low fragmentation.
2.  **Runtime Memory Throughput (MB/s or tokens/sec sustained):** Not the peak, but the sustained rate maintained under load. Q4_K_M might be slower at peak but maintain higher sustained throughput if it fits within a more fragmented block, whereas Q8_0 might hit fragmentation limits faster.

def validate_and_median(records):
    # 1. Validate records
    # We assume records are dictionaries containing 'success' and 'speed'

            return None, None, f"Run {i} failed to determine speed. Output: {record}"

        # Sort successful runs
        sorted_runs = sorted([r for r in records if r.get('success') == True], key=lambda x: x.get('speed', 0))

        return median_speed, sorted_runs, None
        
    # 3. Report if fewer than two succeed
    return None, None, f"No runs found to compute median. Only {len(records)} successful runs."

### Task 5 — User-Visible Latency
**Time to First Token (TTFT), Prompt-Evaluation Throughput (PET), Decode Throughput (DTP), and Total Wall-Clock (TWC)**

**Definitions and Symbolic Equations:**

Let $T_{TTFT}$ be the time to first token.
Let $N$ be the number of tokens in the prompt (2,000).
Let $N_{gen}$ be the number of generated tokens (200).
Let $P$ be the probability of generating a token given the current state.
Let $\mu$ be the mean generation rate (tokens per second).
Let $L$ be the total latency (TTFT + PET + DTP + TWC).

1.  **Time to First Token (TTFT):**
    This is the time until the first token is generated. It depends on the model's startup latency and the rate at which the model generates.
    $$ \text{TTFT} = \frac{\text{Startup Latency}}{P} $$

2.  **Prompt-Evaluation Throughput (PET):**
    This is the rate at which the model evaluates the prompt (e.g., token count per second).
    $$ \text{PET} = \frac{N}{\text{Evaluation Time}} $$

3.  **Decode Throughput (DTP):**
    This is the rate at which the model generates tokens (tokens per second).
    $$ \text{DTP} = \frac{N_{gen}}{\text{Decode Time}} $$

4.  **Total Wall-Clock Time (TWC):**
    The total time is the sum of these rates.
    $$ \text{TWC} = \text{TTFT} + \text{PET} + \text{DTP} $$
    Substituting the variables:
    $$ \text{TWC} = \frac{\text{Startup Latency}}{P} + \frac{N}{\text{Evaluation Time}} + \frac{N_{gen}}{\text{Decode Time}} $$

**Example where optimizing prompt processing barely changes the user's experience:**
Suppose the model generates 500 tokens per second ($\text{DTP} = 500$ tokens/sec) on a fast CPU. The prompt takes 0.1 seconds to evaluate ($\text{PET} = 500 \times 0.1 = 50$ tokens/sec).
*   **Optimization:** If you optimize the prompt processing significantly (e.g., by using a shorter prompt that generates 500 tokens/sec instead of 2,000), the PET drops by half.
*   **Impact:** $\text{TTFT}$ remains constant because the model starts immediately.
*   **Result:** The new PET is 25 tokens/sec (half of 50).
*   **User Experience:** The user sees a slightly slower response because the GPU is now idle while waiting for the prompt to be fully evaluated. However, the user is not "stuck" waiting. The perceived latency is reduced, but the total system throughput is halved due to the idle GPU.
