Scenario:
A 7B decoder-only model is served on a 6 GB consumer GPU with 32 GB system RAM. The model weights fit on the GPU, but the key-value (KV) cache does not always fit there. A user sends a 2,000-token prompt and requests 300 generated tokens. The system reports excellent prompt-processing throughput but becomes much slow ... (truncated)
**Executive Summary:**
The observed slowdown is driven by **re-computed KV cache calculations** in the decoding phase, not simply a lack of cache space. While the model uses 32 GB of system RAM for context, the 6 GB GPU holds only a subset of this data for the initial 2,000 tokens. As the context grows, the GPU must repeatedly compute and re-hash the same keys and values, creating a latency spike.

**1. Lifecycle of KV Cache: Reused vs. Recomputed**
In a standard autoregressive decoder (e.g., GPT-4), the cache is split into **Input** (prompt), **Key**, and **Value**.
*   **Reused:** During decoding, the model reuses the **Key** and **Value** from the **Input** cache for every new token. This is the core of the "KV cache" in your scenario.
*   **Computation:** The model only needs to compute the **Key** and **Value** for the **current** token.
*   **The Bottleneck:** When the context grows from 2,000 to 8,000 tokens, the GPU must re-calculate the **Key** and **Value** for each of the 6,000 new tokens. The system RAM holds only the keys/values for the 2,000 tokens. The CPU/GPU must compute a 6,000-element hash of the keys, then map it to the GPU, then compute the final Value. This re-computation dominates the latency.

**2. Why Prompt Processing ≠ Latency**
Prompt processing (generation) is a batch operation. It is relatively fast because the GPU is idle while waiting for the CPU to process 2,000 tokens.
In contrast, **interactive latency** is the cost of the single token generation. The 6 GB GPU is the bottleneck here. It cannot afford the repeated key-value hashing required by the large context window. The high token rate (2k/s) is irrelevant; the system is failing because it is generating 6,000 keys simultaneously.

**3. Context Growth: Prefill vs. Decode**
*   **Prefill (2,000 tokens):** The GPU handles the initial generation efficiently. The context window is fully filled in GPU memory.
*   **Decode (8,000 tokens):** The GPU must process keys for 6,000 new tokens.
    *   **Memory Bandwidth:** As the context expands, the data moves from GPU $\to$ System RAM $\to$ CPU $\to$ GPU. The memory bandwidth requirement increases quadratically with the number of keys.
    *   **Precision:** If the key-value cache is sparse (common in larger contexts), re-computing the hash of the same keys in subsequent tokens can result in wasted compute cycles.

**4. Separating True vs. False Claims**
*   **True:** The 2,000-token prompt fits on the GPU. The 8,000-token prompt overflows GPU memory.
*   **False:** Re-computing the same keys for a large context window is the primary cause of latency.
*   **Implementation Details:** The specific speedup depends entirely on:
    *   **Precision:** How many distinct key-value pairs are in the cache vs. the context window?
    *   **Offloading:** Is the KV cache fully offloaded from the GPU to the CPU for computation?
    *   **Paging:** Does the GPU use a separate page file that is flushed to RAM?
    *   **Kernel Support:** Does the framework expose a custom kernel for the specific KV cache operation?

**5. Measurement Strategy**
To distinguish bandwidth, KV-cache traffic, and CPU-GPU transfer, use the following controlled comparisons:

1.  **Memory Bandwidth Test (The "Stress Test"):** Run a prompt of exactly 2,000 tokens. Measure the total CPU/GPU throughput. If the GPU is the bottleneck, the throughput should be roughly proportional to the prompt length (e.g., $2000 \times \text{Tokens/s}$). If it is dominated by CPU-GPU transfer, the throughput will be capped at the system RAM bandwidth.
2.  **Key-Value Computation Test:** Increase the context to 8,000 tokens. Measure the time spent on key-value hashing. If this time is the dominant factor, the GPU must be doing heavy hashing. If the time is still dominated by prompt generation, the GPU is idle.
3.  **Kernel Kernel Test:** Check if there is a kernel exposed for "recompute_keys". If the latency drops when the kernel is tuned to do the hashing on the CPU (or via offloading), the bottleneck is identified as the CPU-GPU transfer or the offloading mechanism.

**Numerical Example:**
Assume the GPU handles 100 tokens/sec with 256MB RAM bandwidth.
*   **Prompt Phase:** The model processes 2,000 tokens in $2000 \times 100 = 200,000$ operations. Latency $\approx 2ms$.
*   **Decode Phase:** To generate 8,000 tokens, the GPU must execute 6,000 new key-value computations. Even if the GPU is 100 tokens/sec, the *cost* of these computations is $6,000 \times 2ms = 12ms$.
*   **Total Latency:** $2ms + 12ms = 14ms$.
*   **Result:** The 8,000-token prompt is 7x slower than the 2,000-token prompt because the system is generating 6,000 keys in parallel.
