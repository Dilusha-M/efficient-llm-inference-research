### 1. Lifecycle of the KV Cache: Reused vs. Recomputed
In a 7B model context, the KV cache is managed by a specialized memory subsystem (often a specialized memory controller or MMU) that maintains a dynamic table of cached key-value pairs.

*   **Reused Tokens:** When a token is generated from a cached key-value pair, the CPU retrieves the value immediately. The CPU does **not** perform a full lookup to the memory controller. The computation is a simple memory read/write operation.
*   **Computed Tokens:** When a token is generated from a new key-value pair (e.g., during the "decode" step), the CPU must perform a full lookup in the memory controller to find the required key-value pair. This triggers a full memory transaction.
*   **Critical Distinction:** The CPU can process millions of tokens instantly via the reusing path, but the latency of the decoding path is the bottleneck. The system is not "memory-bound"; it is **CPU-bound** by the decoding latency, even though the hardware memory is available.

### 2. Hardware Resource Allocation: Why High Prompt Tokens ≠ Low Latency
Prompt processing and decoding utilize fundamentally different memory hierarchies:

*   **Prompt Processing:** Uses the **System RAM (SRAM)**. SRAM is designed for speed but has extremely low bandwidth. It is fully saturated by the number of prompt tokens available in memory.
*   **Decoding:** Uses the **GPU Memory** (VRAM + Cache). While the GPU has massive bandwidth, it is designed for parallelism. The decoding path is a single-threaded process that must fetch and compute data from VRAM.

**The Latency Paradox:**
A high prompt token rate (e.g., 100 tokens/sec) means the CPU is waiting for SRAM to hold the prompt. However, the **decode latency is independent of the prompt rate**. It is determined by how quickly the CPU can fetch the next key-value pair from the GPU memory controller. Therefore, a conversation with 100 prompt tokens can be as slow as a conversation with 10 prompt tokens, solely because the decoding memory bandwidth is constrained by the GPU's architecture (e.g., VRAM size and bandwidth), not by the prompt volume.

### 3. Context Scaling: 2,000 → 8,000 Tokens
As context increases, the system must manage two competing resource constraints: **Prefill bandwidth** and **Decode latency**.

*   **Prefill Behavior (2k → 8k):**
    *   **2,000 tokens:** Prefilled fully. All tokens are accessed from SRAM.
    *   **8,000 tokens:** Prefilled partially. Only the first ~1,000 tokens fit in the system RAM (assuming standard 256-bit memory).
        *   *Latency Impact:* As context grows, the CPU must fetch more tokens from the GPU. This increases the total decoding latency required to finish the full context, even if the prompt processing time remains constant.
*   **Decode Behavior:**
    *   The CPU must calculate the next key-value pair. If the context is large enough, the CPU may need to fetch more tokens from the GPU than the prompt rate allows to process the full context. This creates a "race condition" where the decoding pipeline runs faster than the prompt pipeline can refill memory.
*   **Memory Bandwidth:**
    *   The **prefill phase** is heavily limited by SRAM bandwidth ($B_{prefill} \approx 10-20$ GB/s).
    *   The **decode phase** is limited by GPU VRAM bandwidth ($B_{decode} \approx 100-200$ GB/s), which is orders of magnitude faster. The bottleneck shifts from SRAM to VRAM once the prompt rate exceeds the SRAM capacity.

### 4. Distinguishing True vs. Implementation-Dependent Claims
*   **Generally True:** The system reports excellent throughput, but latency increases with context. The cache *is* reused; the issue is not cache miss overhead.
*   **Claims Dependent on Implementation Details:**
    *   **Cache Precision:** Claims about "precision" (e.g., 256-bit vs. 128-bit) affect the memory bandwidth available to the CPU, which directly impacts the prefill phase. A 256-bit cache would allow more tokens to be prefilled before GPU fetches become necessary.
    *   **GPU Offload:** Claims about "offloading" affect whether the CPU handles the memory fetches. If GPU offloading is enabled, the CPU does *not* perform the decoding step for GPU memory data, potentially reducing the effective bottleneck.
    *   **Page Faults:** Claims about "paging" depend on the kernel's memory management logic. A kernel that avoids page faults prevents the CPU from fetching data from VRAM, potentially increasing effective throughput.
    *   **Kernel Support:** Claims about "kernel support" depend on the kernel's ability to manage the specialized memory controller.

### 5. Proposed Measurements
To distinguish these bottlenecks, use the following controlled comparisons:

1.  **Prefill Bandwidth vs. GPU Decode Latency:**
    *   *Measure:* Record the CPU's CPU Frequency ($f_{cpu}$), SRAM capacity ($B_{prefill}$), and GPU VRAM bandwidth ($B_{gpu}$).
    *   *Test:* Calculate the time to prefill a 1,000-token prompt. Compare this against the time to decode the first 1,000 tokens of a larger context. If the decode time is significantly longer, the GPU bandwidth is the limiting factor.

2.  **Cache Miss Rate vs. Prompt Rate:**
    *   *Measure:* Average the ratio of Cache Misses to Prompt Tokens processed per second ($MM / PM$).
    *   *Test:* A high MM rate (e.g., >20%) indicates the CPU is constantly fetching from VRAM to look up keys, confirming the "cache miss" claim is true and the bottleneck is the lookup latency, not the cache cache.

3.  **Prefill Throughput vs. Decode Latency:**
    *   *Measure:* Average the number of tokens prefilled per second ($P_{prefill}$). Compare this against the average decoding latency ($T_{decode}$).
    *   *Test:* If $P_{prefill} < T_{decode}$, the bottleneck is the CPU's ability to keep SRAM full, not the GPU's compute power. If $P_{prefill} \approx T_{decode}$, the bottleneck is the latency of the decoding process itself.
