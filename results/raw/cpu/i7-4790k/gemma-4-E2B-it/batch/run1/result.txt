## Task 1 — quantization tradeoff

**Scenario:** 8B model weights: $8.0 \text{ GB (Q8\_0)}$, $4.8 \text{ GB (Q4\_K\_M)}$. Available free GPU memory: $5.2 \text{ GB}$.

**Memory Pressure Analysis:**

1.  **Q8\_0 (8.0 GB):** This format requires $8.0 \text{ GB}$ just for the model weights. Since the GPU has only $5.2 \text{ GB}$ free, loading the full model weights will immediately cause an Out-Of-Memory (OOM) error or significant swapping/offloading, resulting in **high memory pressure** and potential failure.
2.  **Q4\_K\_M (4.8 GB):** This format requires $4.8 \text{ GB}$ for the weights. This leaves $5.2 \text{ GB} - 4.8 \text{ GB} = 0.4 \text{ GB}$ free. This format is significantly less memory-intensive and creates **lower memory pressure**, leaving more headroom for KV cache or activation memory during inference.

**File Size vs. Runtime-Memory Estimate:**

File size is **not a complete runtime-memory estimate** because it only accounts for the static storage of the model weights. Runtime memory usage is significantly higher due to:
1.  **KV Cache:** The Key-Value cache grows linearly with the sequence length (prompt + generated tokens) and the batch size, and this memory is allocated dynamically during inference.
2.  **Activations/Overhead:** The inference process requires memory for intermediate activations, temporary buffers, and the runtime environment, which are not included in the static file size.

**Quality/Performance Measurements Needed:**

To declare one format better, the following two measurements are needed:

1.  **Inference Latency (Time to first token and total generation time):** To assess the actual speed of computation.
2.  **Per-token Throughput (Tokens/second):** To assess the efficiency of the computation relative to the output rate.

**Note on Q4 Speed:** Do not claim that Q4 is always faster. Quantization quality depends heavily on the specific task, the model architecture, the hardware, and the specific implementation (e.g., FlashAttention usage).

## Task 2 — conservative launch decision

**Scenario:** $16 \text{ GB RAM}$, $6 \text{ GB GPU}$, $2,000 \text{-token prompt}$, $512 \text{-token generation limit}$. Model weights: $5.0 \text{ GB}$ (in chosen quantization).

**Conservative Procedure for Llama.cpp:**

The goal is to maximize the chance of successful inference within the $6 \text{ GB}$ GPU memory, prioritizing the prompt context and generation limits.

1.  **Step 1: Test Minimum Viable Context:** Start by testing the absolute minimum required memory allocation.
    *   **Context Size:** Start with the minimum prompt size ($2,000$ tokens) and ensure the KV cache fits. Since the prompt is $2,000$ tokens, this context size might be too large for a $5.0 \text{ GB}$ model if the KV cache is large.

## Task 3 — robust aggregation

**Data:** Decode speeds: $42.0, 41.5, 8.0 \text{ tok/s}$. Last run logged an OOM warning (failure).

**Pseudocode for Robust Aggregation:**

```pseudocode
FUNCTION Aggregate_Decode_Speeds(Results):
    // Results is a list of tuples: (speed, status)
    
    Successful_Speeds = []
    Failed_Runs = []
    
    FOR EACH Record IN Results:
        Speed = Record.speed
        Status = Record.status // e.g., 'Success' or 'OOM_Failure'
        
        IF Status == 'Success':
            ADD Speed TO Successful_Speeds
        ELSE:
            ADD Record TO Failed_Runs
            
    // 1. Compute Median for successful runs
    IF SIZE(Successful_Speeds) >= 2:
        SORT Successful_Speeds ASCENDING
        // Median calculation (simple for demonstration)
        Median_Speed = (Successful_Speeds[FLOOR(SIZE/2) - 1] + Successful_Speeds[FLOOR(SIZE/2)]) / 2
        RETURN Median_Speed
    ELSE:
        // 2. Report based on success count
        IF SIZE(Successful_Speeds) == 1:
            RETURN Successful_Speeds[0] // Return the single successful value
        ELSE:
            // Fewer than two runs succeed (0 or 1 success)
            REPORT "Insufficient successful runs for median calculation. Successful speeds found: " + Successful_Speeds
            RETURN "N/A (Fewer than two successful runs)"
```

**Reporting Strategy (Fewer than two successes):**

If fewer than two runs succeed (i.e., zero or one successful run), the procedure should **not** attempt to calculate a median. Instead, the report must explicitly state the observed successful values or the failure condition.

*   **If 0 successes:** Report: "All runs failed (OOM or other error)."
*   **If 1 success:** Report: "Only one successful run was recorded with a speed of [Value]."

## Task 5 — user-visible latency

**Scenario:** $2,000$-token prompt, $200$ generated tokens.

**Explanation of Latency Components:**

1.  **Time to First Token (TTFT):** The time elapsed from sending the entire prompt to receiving the very first token. This is dominated by the initial prompt processing (attention calculation) and the first token generation step.
2.  **Prompt-Evaluation Throughput:** The rate at which the system processes the input prompt and prepares the initial context for the decoder. This is usually a one-time, front-loaded operation.
3.  **Decode Throughput:** The rate at which subsequent tokens are generated *after* the first token has been produced. This is measured in tokens/second ($\text{tok/s}$).
4.  **Total Wall-Clock Time:** The total time elapsed from the moment the prompt is sent until the final generated token is received.

**Symbolic Equation for Total Time:**

Let $T_{\text{prompt}}$ be the time taken for prompt processing, $T_{\text{first}}$ be the time to generate the first token, $T_{\text{gen}}(N)$ be the time taken to generate $N$ tokens, and $T_{\text{overhead}}$ be fixed setup time.

$$\text{Total Wall-Clock Time} = T_{\text{prompt}} + T_{\text{first}} + T_{\text{gen}}(200) + T_{\text{overhead}}$$

**Example Where Optimizing Prompt Processing Barely Changes User Experience:**

If the $2,000$-token prompt is already loaded entirely into the GPU memory (as is common with modern systems), optimizing the *processing* of the prompt (e.g., using a faster attention mechanism) might only reduce $T_{\text{prompt}}$ by a few milliseconds. If the generation time ($T_{\text{gen}}(200)$) is orders of magnitude larger (e.g., 10 seconds), the difference in the user experience is negligible.

**Example:** If $T_{\text{prompt}} = 100 \text{ ms}$ and $T_{\text{gen}}(200) = 10,000 \text{ ms}$, optimizing $T_{\text{prompt}}$ from $100 \text{ ms}$ to $95 \text{ ms}$ results in a $5 \text{ ms}$ improvement in total time, which is not perceptible to the user.
