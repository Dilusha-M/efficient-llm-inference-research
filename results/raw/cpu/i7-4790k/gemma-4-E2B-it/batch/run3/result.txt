## Task 1 — Quantization Tradeoff

**Given Data:**

*   8B Model: Q4\_K\_M file size = 4.8 GB
*   Available GPU Memory: 5.2 GB free

### Memory Pressure Explanation

1.  **Q8\_0 (8.0 GB):** Since the model file is 8.0 GB, loading this model *alone* will immediately exceed the 5.2 GB free memory available on the GPU, resulting in immediate memory pressure or an inability to load the model into the GPU if the entire model must reside there.
2.  **Q4\_K\_M (4.8 GB):** This file size (4.8 GB) is less than the 5.2 GB free memory. This format is more likely to fit the model weights, leaving some memory for the KV cache or activations.

### Why File Size is Not a Complete Runtime-Memory Estimate

File size (e.g., 8.0 GB vs 4.8 GB) only measures the *storage footprint* of the model weights. It does not account for the *runtime memory* required during inference, which is heavily dependent on:
1.  **Activation Memory:** The memory needed for intermediate calculations during the forward pass.
2.  **KV Cache Size:** The memory required to store the Key/Value states for the prompt and generated tokens.
3.  **Layer Offloading:** How many layers are loaded onto the GPU versus the CPU/RAM.
4.  **Inference Framework Overhead:** Memory consumed by the runtime (e.g., llama.cpp overhead).

### Two Quality/Performance Measurements Needed

To declare one format better, one must measure performance metrics that account for actual execution time and memory usage:

1.  **Inference Latency (Time to First Token / Time per Token):** Measures the speed of the actual generation process.
2.  **Peak Runtime Memory Usage:** Measures the maximum memory consumed during the entire inference process (weights + KV cache + activations).

**Note:** Do not claim that Q4 is always faster. The performance trade-off depends heavily on the specific hardware, the complexity of the task, and the specific quantization method (e.g., K-quantization vs. standard quantization).

## Task 3 — Robust Aggregation

### Pseudocode for Validation and Median Calculation

```pseudocode
FUNCTION Aggregate_Decode_Speeds(Results):
    Successful_Speeds = []
    Failed_Runs = []
    
    FOR EACH Run IN Results:
        IF Run.Status == "SUCCESS":
            Successful_Speeds.ADD(Run.Speed)
        ELSE IF Run.Status == "FAILED" OR Run.Status == "OOM":
            Failed_Runs.ADD(Run)
            
    // 1. Report Failures
    IF LENGTH(Failed_Runs) > 0:
        REPORT "Warning: " + LENGTH(Failed_Runs) + " run(s) failed or reported OOM."
        FOR EACH Run IN Failed_Runs:
            REPORT "Failed Run Details: " + Run.ID + " resulted in error/OOM."

    // 2. Compute Median for Successful Runs
    IF LENGTH(Successful_Speeds) > 0:
        SORT Successful_Speeds ASCENDING
        
        IF LENGTH(Successful_Speeds) IS ODD:
            Median = Successful_Speeds[ FLOOR(LENGTH(Successful_Speeds) / 2) ]
        ELSE:
            // Average the two middle elements for even sets
            Mid1 = Successful_Speeds[ LENGTH(Successful_Speeds) / 2 - 1 ]
            Mid2 = Successful_Speeds[ LENGTH(Successful_Speeds) / 2 ]
            Median = (Mid1 + Mid2) / 2.0
            
        REPORT "Median Successful Decode Speed: " + Median + " tok/s"
    ELSE:
        REPORT "Error: No successful runs were recorded. Cannot compute median."

END FUNCTION
```

### Reporting for Fewer Than Two Successful Runs

If fewer than two runs succeed (i.e., $0$ or $1$ successful run):

## Task 5 — User-Visible Latency

**Given Data:** Prompt = 2,000 tokens; Generated = 200 tokens.

### Explanation of Latency Components

1.  **Time to First Token ($T_{first}$):** This is the time elapsed from sending the complete prompt to the model until the very first token of the generated sequence is produced. It includes prompt processing, attention layer computation, and the initial decoding step.
2.  **Prompt-Evaluation Throughput ($TP_{eval}$):** The rate at which the model processes the input prompt (2,000 tokens) to prepare for generation. This is a measure of how quickly the initial context is processed.
3.  **Decode Throughput ($TP_{decode}$):** The sustained rate at which new tokens are generated once the generation process has started. This is usually measured in tokens per second (tok/s).
4.  **Total Wall-Clock Time ($T_{total}$):** The total time elapsed from the moment the first token is requested until the final generated token is produced (or the generation limit is hit).

### Symbolic Equation for Total Time

Assuming the process involves a fixed initial prompt processing time and a variable generation time:

$$T_{total} = T_{first} + T_{prompt\_eval} + T_{generation}$$

Where:
*   $T_{first}$: Time to generate the first token.
*   $T_{prompt\_eval}$: Time spent processing the initial 2,000-token prompt.
*   $T_{generation}$: Time taken to generate the remaining 200 tokens.

*Alternatively, using throughput:*
$$T_{total} = T_{first} + \frac{\text{Prompt Length}}{TP_{eval}} + \frac{\text{Generated Length}}{TP_{decode}}$$

### Example Where Optimizing Prompt Processing Barely Changes User Experience

**Scenario:** A user is generating a long, complex story (2,000 tokens prompt) and then asking for a short, specific summary (200 generated tokens).

**Optimization Focus:** Optimizing $T_{prompt\_eval}$ (prompt processing).

**Example:** If the prompt processing time is optimized from $1.5$ seconds to $1.4$ seconds, the change in user experience is negligible. The user perceives the delay as the time it takes to *read* the prompt, not the time it takes for the model to *digest* the prompt. If the total wall-clock time is $10.0$ seconds, reducing $T_{prompt\_eval}$ from $1.5$s to $1.4$s results in a $0.1$ second improvement, which is below the user's perceptual threshold for latency perception.
