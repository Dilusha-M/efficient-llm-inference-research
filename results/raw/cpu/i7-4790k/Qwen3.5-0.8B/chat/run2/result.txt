### 1. Lifecycle of the KV Cache: Reused vs. Recomputed
In this architecture, the KV cache operates as a **dynamic cache (L3-style)** that is distinct from the static GPU memory (`VRAM`).

*   **Reused (L1/Shared):** The system maintains a small L1 cache of the most recent 10–50 KV pairs (tokens 1–10) at the start of the prompt.
    *   *Action:* If token $T_i$ is generated, the corresponding $KV_i$ is **read from L1** and **written back** to L1 for immediate reuse in the next token generation cycle.
    *   *Constraint:* This L1 cache is physically tiny (e.g., 4–8 MB).
*   **Computationally Recomputed (L2/Shared/Shared Memory):** The system uses the GPU for the majority of the computation.
    *   *Action:* As the conversation progresses, the L1 cache is filled. The kernel iterates through the KV pairs and computes them on the GPU. These results are written to **Shared Memory** or **VRAM** for future use.
    *   *Constraint:* The GPU computes $O(N \log N)$ or $O(N^2)$ operations per token.

**The Conflict:**
For a 2,000-token prompt, the system initially computes and writes only the first 10–20 tokens to the L1 cache. The rest of the computation is deferred until the end of the conversation. When latency grows, the L1 cache is saturated, forcing the GPU to perform the remaining tokens, increasing latency but not introducing the memory overflow that would cause Out-of-Memory (OOM) errors.

### 2. Stress Differences: Prompt Processing vs. Interactive Latency
Prompt processing and decoding are fundamentally different tasks:

*   **Prompt Processing:** This is a **one-shot task** (usually 50–100 tokens) executed by a CPU kernel. It has negligible latency (microseconds) and does not depend on interactive interaction.
*   **Interactive Latency:** This is the **token-by-token latency** (usually milliseconds) experienced by the model while the user types and generates new tokens. This is the bottleneck.

**Why High Prompt Token/Count $\neq$ Low Latency:**
The prompt-to-token ratio (e.g., 50 tokens/second) is a measure of throughput, not latency. Latency scales exponentially with context depth due to the **exponential memory cost** of the KV cache (as shown in Section 1). If you only have 100 tokens in L1, the GPU must run the entire 8,000-token sequence in parallel. The latency for the last 7,900 tokens is 100x worse than the 100 tokens at the start.

### 3. Effects of Context Scaling (2k $\to$ 8k)
Moving from 2,000 to 8,000 tokens changes the cache dynamics drastically:

*   **Prefill Behavior:**
    *   **2,000 tokens:** The system computes the first 2,000 tokens to the L1 cache. Latency is dominated by the GPU's ability to process the first 2,000 tokens.
    *   **8,000 tokens:** The system computes **no more** than 2,000 tokens. The remaining 6,000 tokens are **computed on the GPU** for the entire duration of the conversation.
*   **Memory Bandwidth:**
    *   **Prefill Phase:** Bandwidth is dominated by **GPU VRAM** and **Shared Memory**.
    *   **Decode Phase:** Bandwidth becomes the bottleneck. The GPU must transfer the massive data set (6,000 tokens) from Shared Memory to VRAM for the decode kernel. If VRAM is saturated or bandwidth is throttled, the entire conversation may timeout or fail to finish.

### 4. Distinguishing Claims (True vs. Implementation-Dependent)
*   **True Claims:**
    *   "The system will never OOM if the prompt size stays below the KV cache threshold."
    *   "Latency increases exponentially with conversation length."
    *   "Prefill latency is often the dominant factor in high-throughput scenarios."
*   **Implementation-Dependent Claims:**
    *   **"Does the cache ever fit?"** No. Even with a small cache (e.g., 512 tokens), the model must compute the first 512 tokens before writing them to the cache. The *efficiency* of the cache depends on the specific kernel launch strategy (e.g., how many tokens per kernel launch).
    *   **"Does offloading help?"** No. Offloading the *first* 512 tokens is safe and necessary for correctness. Offloading the *rest* of the tokens requires the GPU to process the entire sequence, which is inefficient.
    *   **"Is there a fixed bandwidth limit?"** No. Bandwidth depends on the specific implementation (e.g., is the kernel moving data via PCIe, NVLink, or shared memory bandwidth?).

### 5. Recommended Measurements for Bottleneck Identification
To isolate the specific resource consuming the model, run these controlled experiments:

1.  **Prefill Latency vs. Decode Latency Ratio:**
    *   **Metric:** `AvgLatencyDecode / AvgLatencyPrefill`.
    *   **Goal:** Determine if the model is stuck in the "Prefill-only" phase of the decode kernel, causing the decay in latency.
2.  **Cache Hit/Cache Miss Ratio by Context Size:**
    *   **Metric:** `MemBurst / TotalTokens` vs. `MemBurst / TokensPerKernel`.
    *   **Goal:** If the system consistently misses the last 3,000 tokens of the 8,000-token prompt, the latency is dominated by the decode kernel's memory bandwidth, not the CPU prefetch.
3.  **GPU VRAM Burst vs. Shared Memory Burst:**
    *   **Metric:** `VRAM_Burst / SharedMem_Burst`.
    *   **Goal:** If VRAM is saturated or bandwidth is the limiting factor, the bottleneck shifts to memory transfer rather than GPU computation.
