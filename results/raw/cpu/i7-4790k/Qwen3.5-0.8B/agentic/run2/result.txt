# State Machine Workflow

The lifecycle transitions as follows:

1.  **Validation Phase**:
    *   **Input Parsing**: Read `model_config.yaml` and `workload_config.json`. Validate that `workload_config` is not empty.
    *   **Environment Check**: Verify GPU layer count matches `gpu_layers` in config, and check if CUDA driver version is valid (optional, per spec).
    *   **Metadata Generation**: If no monitor is specified in `monitor_config.json`, generate a default entry `monitor_metadata.txt`.
    *   **Result Determination**: If all checks pass, set `status` to `success`.

2.  **Launch Phase**:
    *   **Process Initiation**: Start llama.cpp backend.
    *   **Task Execution**: Run the specified workload (`chat`, `batch`, `coding`, etc.).
    *   **Timeout Detection**: If `timeout` in config is reached, terminate process with `SIGTERM` and set `status` to `failed`.
    *   **OOM Detection**: If memory limit is exceeded, terminate with `SIGKILL` and set `status` to `failed`.
    *   **Monitor Check**: Attempt to access a monitor. If the monitor file is missing or sample is 0, set `monitor_status` to `failed` and skip monitoring in the result.

3.  **Process Exit Phase**:
    *   If the backend exits with code 0, set `process_exit_code` to 0.
    *   If the backend exits with code 1 or the process is killed, set `process_exit_code` to 1.

4.  **Finalization Phase**:
    *   **Output Generation**: Write `response.txt` containing the model's final response. Ensure exact prompt hash is preserved.
    *   **Metadata Writing**: Write `monitor_metadata.txt` with available/failed monitor info.
    *   **Raw Output Preservation**: Write `raw_output` (binary stream) to the filesystem.
    *   **Result Package**: Combine all metadata, process exit code, and raw output into `benchmark_result.json`.

# Auditable Design

**Component Boundaries:**
*   **`config_loader.py`**: Handles reading YAML/JSON configs, validating keys, and extracting numerical/enum values.
*   **`workload_runner.py`**: Orchestrates the llama.cpp process and manages the task execution loop.
*   **`benchmark_executor.py`**: Manages the monitoring system, file I/O for raw output, and generates the final JSON structure.
*   **`audit_engine.py`**: Handles parsing the `response.txt` for human-readable metrics and the raw binary for structural integrity.

**Metadata Schema:**
*   Each run is identified by a tuple `(model_alias, backend, context_kb, generation_limit, temperature, gpu_layers, workload, process_exit_code, raw_output_binary, monitor_status, monitor_metadata)`.
*   `monitor_status`: `{"available": bool, "sampled": float, "metadata": {"status": "ok", "samples": [...]}}`.
*   `monitor_metadata`: List of dictionaries with `name`, `status`, and `sample_value`.

**Atomic Write Conventions:**
*   **Filesystem**: Use `AtomicFile` or `partial_write` to ensure data is written to disk in chunks without overwriting previous partial writes.
*   **Output File**: Use `partial_write` to write `response.txt` incrementally. The final write ensures the exact prompt hash is preserved byte-for-byte.
*   **Binary**: `raw_output` is written as a binary stream directly to disk, preserving line endings and character encoding exactly as the model outputs them.

**Preserving Stdout/stderr:**
*   Do not redirect `stdout` and `stderr` to temporary files.
*   If the process fails, ensure `stderr` is logged to a separate `audit_log.txt` for debugging purposes, while keeping the main benchmark JSON clean.

# Analysis Integrity

**Preventing Variable Generated-Token Count from Misleading Throughput:**
*   **Mechanism**: The `performance_metrics` array should be empty or contain a default value (e.g., `{"speed": 0.0, "latency": 0.0, "errors": 0.0}`) rather than a computed variable.
*   **Reasoning**: Throughput is defined as `Total Output Size / Time` or `Speed`. Since the model's internal token count is not directly observable without a reference token generator, and the prompt hash is fixed, the only variable that can affect "tokens per second" is the *generation length*. By hardcoding the metric to 0.0, the system ensures the throughput calculation is robust against variations in generation length or temperature, preventing false positives in throughput comparisons across different model versions or prompt hashes.

**Parsing Unknown llama.cpp Output Formats:**
*   **Strategy**: Implement a strict regex parser for llama.cpp output.
*   **Action**: If the parser encounters text that does not match any known llama.cpp output format (e.g., an unexpected line ending, non-standard JSON structure, or specific formatting instructions), it should:
    1.  Flag the output as malformed.
    2.  Do not append it to the `performance_metrics` array.
    3.  Log a warning to `audit_log.txt` and set `raw_output` to an empty string or a placeholder marker so the JSON structure remains valid.
