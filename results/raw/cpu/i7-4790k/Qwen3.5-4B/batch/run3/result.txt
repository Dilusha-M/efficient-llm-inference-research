### Task 1 — quantization tradeoff

**Memory Pressure Analysis**
*   **Q8_0 (8.0 GB):** This format requires 8.0 GB of VRAM to load. With 5.2 GB free on a 6 GB GPU, this leaves only **0.2 GB (200 MB)** of headroom for the Key-Value (KV) cache, attention masks, and intermediate activations. The memory pressure is extremely high; any increase in context window or any spike in activation memory (e.g., due to layer normalization implementation variance) will likely cause an Out-Of-Memory (OOM) crash immediately upon generating the first few tokens.
*   **Q4_K_M (4.8 GB):** This format requires 4.8 GB of VRAM. This leaves **0.4 GB (400 MB)** of headroom for the KV cache and activations. While still tight for large contexts, it provides a safety buffer of roughly 2x the headroom of Q8_0, making it significantly less likely to crash under variable load conditions.

**Why File Size $\neq$ Runtime Memory Estimate**
File size represents only the static weight storage requirement. It does not account for:
1.  **KV Cache Growth:** The memory required to store attention keys and values scales linearly with context length. A 2,000-token context can consume hundreds of MBs, potentially exceeding the free space even if the weights fit.
2.  **Activation Memory:** During the forward pass, the GPU must store temporary tensors for each layer's output, gradients (if using certain optimizers), and attention matrices. These are not included in the model file size.
3.  **Quantization Noise Overhead:** While Q4_K_M has higher numerical noise (lower precision) than Q8_0, it does not inherently consume more VRAM; the trade-off is accuracy, not memory usage per se. The "pressure" comes from the total working set (Weights + KV + Activations), not just the model file.

**Required Measurements**
Before declaring one format better, the following two metrics must be measured under identical context lengths:
1.  **Maximum Sustainable Context Length:** The largest context size (e.g., in tokens) at which the system runs for 1 minute without an OOM error. This is the definitive measure of "fit" for a specific hardware constraint.
2.  **Per-Token Latency (p99):** The 99th percentile time to generate a single token. This measures whether the quantization-induced drop in precision causes slower inference speeds (due to additional micro-op instructions or numerical instability) that outweigh the benefits of fitting a larger context.

### Task 3 — robust aggregation

**Pseudocode**
```python
# Assume records is a list of dicts: {'speed': float, 'status': 'success'|'fail', 'tokens': int}
records = [...] 

successful_runs = []
failed_runs = [] # Keep visible for debugging

for r in records:
    if r['status'] == 'fail' or r['speed'] <= 0: # Treat OOM warning as fail
        failed_runs.append(r)
    else:
        successful_runs.append(r['speed'])

# Compute median
if len(successful_runs) == 0:
    report_median = None
elif len(successful_runs) == 1:
    report_median = successful_runs[0]
    warning_msg = "Only 1 successful run; median is unreliable."
else:
    successful_runs.sort()
    mid = len(successful_runs) // 2
    report_median = successful_runs[mid] # Python even/odd handling logic
    warning_msg = None

# Handle < 2 runs case explicitly
if len(successful_runs) < 2:
    final_report = f"Insufficient data ({len(successful_runs)} successful runs). "
    final_report += f"Median cannot be statistically validated. "
    if failed_runs:
        final_report += f"Note: {len(failed_runs)} run(s) failed (see logs)."
else:
    final_report = f"Median Decode Speed: {report_median:.1f} tok/s"
    if warning_msg:
        final_report += f". {warning_msg}"

return final_report, failed_runs
```

**Reporting Rule for < 2 Runs**
If fewer than two runs succeed, the median cannot be calculated statistically (requires at least 2 values to find a center point, or 1 value which is trivial but prone to outlier bias). The result should **not** be a single number. Instead, the system must report:
1.  **Data Insufficiency:** State clearly that fewer than two valid runs exist.
2.  **Failure Visibility:** List the failed runs with their error messages (e.g., "Run 3: OOM on context size N").
3.  **No Median:** Explicitly state that no median speed is reported. If only one run succeeded, it should be flagged as a "single sample" rather than a median, and the result should be treated as a potential outlier until validated.

### Task 4 — validity audit

**Four Threats to Validity**

1.  **Threat: Workload/Output Comparability**
    *   *Description:* The prompt text sent to the CPU vs. CUDA vs. Vulkan backends might differ slightly due to buffering differences, or the generation might stop at different token counts if the backends handle the `stop` sequence differently (e.g., CPU might stop one token earlier than Vulkan due to loop logic).
    *   *Control/Disclosure:* Use an identical, pre-formatted prompt string passed via a standardized API (e.g., `llama_generate` with identical parameters) for all backends. Log the exact number of tokens generated (`n_tokens`) and the exact byte offset of the generated text to ensure the output is byte-for-byte identical.

2.  **Threat: Hardware Thermal Throttling**
    *   *Description:* The CPU and GPU may react differently to sustained load. The GPU might throttle faster than the CPU (or vice versa) due to power limits (TDP), causing the decode speed to drop mid-benchmark unrelated to the algorithm.
    *   *Control/Disclosure:* Monitor CPU/GPU temperatures and power draw (via `sensors` or `nvtop`) and record them alongside speed. If temperature exceeds a threshold (e.g., 80°C), discard the data point or apply a thermal derating correction factor.

3.  **Threat: Kernel Launch Overhead Variance**
    *   *Description:* CUDA and Vulkan have different kernel launch overheads compared to CPU threads. If the prompt is short, the overhead dominates, and if the generation is long, it dominates. If the benchmark mixes short and long generations, the results are incomparable.
    *   *Control/Disclosure:* Ensure all runs use the **same generation length** (e.g., exactly 1024 tokens) and warm up the engines (run a dummy 1000-token pass before timing) to stabilize kernel caches. Report the "warm-up" phase duration.

4.  **Threat: System Interference (OS Scheduling)**
    *   *Description:* The OS scheduler might prioritize the Vulkan worker differently than the CPU threads or CUDA process, or background tasks (defrag, updates) might spike latency.
    *   *Control/Disclosure:* Run the benchmark in a **cgroup-controlled environment** with CPU affinity set to dedicated cores (e.g., `taskset -c 0-3`) and disable background services. Record the system load average (`uptime` output) during the run.

### Task 5 — user-visible latency

**Definitions**

1.  **Time to First Token (TTFT):** The wall-clock time from the moment the prompt is received until the first character of the generation is displayed. This includes prompt evaluation time + initial decode time.
2.  **Prompt-Evaluation Throughput:** The rate (tokens/sec) at which the model processes the input prompt. Since the prompt is static, this is a one-time cost, not a sustained throughput.
3.  **Decode Throughput:** The rate (tokens/sec) at which the model generates new tokens *after* the prompt is evaluated. This is the sustained speed during the generation phase.
4.  **Total Wall-Clock Time:** The sum of TTFT + (Number of Generated Tokens / Decode Throughput).

**Symbolic Equation**
Let $T_{prompt}$ be the time to evaluate the prompt.
Let $T_{decode}$ be the time to decode $N_{gen}$ tokens (where $N_{gen}=200$).
Let $R_{decode}$ be the decode throughput (tok/s).
$$T_{total} = T_{prompt} + \frac{N_{gen}}{R_{decode}}$$
*(Note: $T_{prompt}$ is often small compared to $T_{decode}$ for long generations, but dominates TTFT).*

**Example of Minimal Impact Optimization**
*   **Scenario:** A user asks a 2,000-token question. The model generates 200 tokens.
*   **Optimization:** Reducing the prompt evaluation time from 500ms to 400ms (a 20% improvement in prompt processing).
*   **Impact:** The TTFT improves from ~500ms to ~400ms. The user waits 100ms less for the *first* word. However, the total time for the 200 generated tokens (assuming 20 tok/s) is $10$ seconds. The total time changes from 10.5s to 10.4s.
*   **Conclusion:** Optimizing prompt processing barely changes the user's experience because the **decode phase dominates the total time** (the "bottleneck"). The user perceives the delay as "waiting for the answer," which is determined by the slow generation of 200 tokens, not the fast processing of the 2000-token question.
