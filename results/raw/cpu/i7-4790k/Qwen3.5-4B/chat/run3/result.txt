### 1. KV Cache Lifecycle: Reuse vs. Recomputation

The lifecycle of the KV cache in a decoder-only transformer follows a strict spatial-temporal pattern:

*   **Prefill Phase (Prompt Processing):**
    For an input sequence $N_{prompt}$, the model computes the entire set of Key-Value pairs from token $0$ to $N_{prompt}$. Unlike subsequent steps, **no KV cache is reused** from a previous conversation. Every attention head computes a full dot-product against the previous hidden state. This phase saturates the GPU's tensor cores and global memory bandwidth simultaneously.
    *   *Memory Behavior:* The entire KV matrix (Shape: $N_{prompt} \times N_{heads} \times D_{model}$) is allocated in VRAM (or RAM if offloaded).

*   **Decode Phase (Token Generation):**
    For each generated token $t$, the model attends only over the *existing* KV cache (tokens $0$ to $t-1$).
    *   **Reused:** The KV states for all prior $t-1$ tokens are loaded once into registers/SMs and reused for every subsequent step.
    *   **Recomputed:** Only the KV pair for the *current* token $t$ is computed using the new hidden state and the previous KV context.
    *   **Memory Behavior:** As $t$ grows, the active KV matrix grows in size. If $N_{prompt} + N_{generated}$ exceeds VRAM capacity, the system must spill the overflow to System RAM, introducing a PCIe bus transfer latency before every decode step.

### 2. Prefill vs. Decode: Hardware Stress & Throughput Illusion

**Hardware Stress Disparity:**
*   **Prefill** is **compute-bound** (initially) and **memory-bound** (sustained). It requires massive parallelism to process $N_{prompt}$ tokens in parallel, maximizing the utilization of Tensor Cores. It consumes high bandwidth but does not necessarily hit the latency ceiling of the memory subsystem unless context is massive.
*   **Decode** is **latency-bound**. It relies on the reuse mechanism. The bottleneck is not computing the new token, but **fetching** the relevant portion of the KV cache and **transferring** data between memory tiers (VRAM $\leftrightarrow$ HBM $\leftrightarrow$ DDR4/5).

**Why High Prompt tok/s $\neq$ Low Latency:**
A high prompt throughput ($tok/s$) indicates the GPU is efficiently processing the *initial* batch. However, latency is dominated by the **prefill time + the first few decode steps**.
1.  If $N_{prompt}$ is large, the initial $tok/s$ drops naturally as $N_{prompt}/\text{latency}$ increases.
2.  If the KV cache spills to RAM (due to 32GB RAM vs 6GB VRAM), the first decode step incurs a PCIe transfer latency (~100–200 $\mu$s) that is orders of magnitude higher than VRAM access (~10–20 $\mu$s).
3.  Consequently, you can have a system that "preflights" 100 tokens in 50ms (4000 tok/s) but takes 200ms to generate the first output token because the KV cache was offloaded to RAM.

### 3. Scaling Context: 2k $\to$ 8k Tokens

Increasing context from 2,000 to 8,000 tokens impacts both phases non-linearly:

*   **Prefill Behavior:**
    *   **Compute:** Theoretical peak FLOPs increase by $\approx 4\times$. Since Tensor Cores saturate, the time roughly scales linearly with $N_{prompt}$.
    *   **Memory:** The KV matrix size grows by $4\times$. If the 2k context barely fits in VRAM, the 8k context will likely force a complete spill to System RAM, creating a persistent memory wall for the entire generation.

*   **Decode Behavior:**
    *   **Reuse Efficiency:** The fraction of reused tokens increases. The first few generated tokens recompute 2k or 8k of KV history respectively.
    *   **Bandwidth Impact:** As generated tokens ($N_{gen}$) approach $N_{prompt}$, the system must fetch a larger and larger slice of the KV matrix.
    *   **The Spill Wall:** With 6GB VRAM, an 8k context requires $\approx 16\text{--}24$ GB of KV cache (assuming 16-bit FP16 weights + overhead). This forces the system to keep a "hot" window in VRAM and a massive "cold" window in RAM, causing every decode step to wait for a CPU-RAM-GPU sync or a slow HBM-to-DDR copy.

**Numerical Example:**
Assume 16-bit precision.
*   **KV Cache Size per Token:** $\approx 128 \text{ MB}$ (conservative estimate for 8k heads, 4096 dim).
*   **Scenario A (2k Context):**
    *   KV Size: $240 \text{ MB}$. Fits in 6GB VRAM.
    *   Prefill Time: $10 \text{ ms}$.
    *   Decode Latency (per token): $2 \text{ ms}$ (GPU bound).
    *   **Total for 300 tokens:** $10 \text{ ms} + (300 \times 2 \text{ ms}) \approx 610 \text{ ms}$.
*   **Scenario B (8k Context):**
    *   KV Size: $1 \text{ GB}$. Fits in VRAM (still).
    *   Prefill Time: $\approx 40 \text{ ms}$ (4x compute).
    *   Decode Latency (per token): $\approx 2.5 \text{ ms}$ (slightly higher due to larger register pressure).
    *   **Total for 300 tokens:** $40 \text{ ms} + (300 \times 2.5 \text{ ms}) \approx 760 \text{ ms}$.
*   **Scenario C (12k Context - Spill):**
    *   KV Size: $1.5 \text{ GB}$. **Spills to RAM**.
    *   Prefill Time: $\approx 50 \text{ ms}$ (Memory-bound fetch dominates).
    *   Decode Latency (per token): $\approx 15 \text{ ms}$ (PCIe transfer + CPU overhead).
    *   **Total for 300 tokens:** $50 \text{ ms} + (300 \times 15 \text{ ms}) \approx 4.5 \text{ seconds}$.

*Conclusion:* Moving from A to C increases total time by $\approx 7\times$ despite generating the same number of tokens, primarily due to the decode latency spike.

### 4. General Truths vs. Implementation Dependencies

| Feature | General Truth (Architectural) | Implementation Dependency |
| :--- | :--- | :--- |
| **Prefill Complexity** | Prefill complexity is $O(N_{prompt}^2)$. | Optimization: FlashAttention (reduces to $O(N_{prompt})$ space) vs. standard Attention ($O(N^2)$ space). |
| **Decode Mechanism** | Decode reuses previous KV; recomputes only current token. | Precision: FP16 vs. INT8 quantization affects memory footprint and compute speed. |
| **Memory Spill** | Spilling to RAM increases latency due to PCIe bandwidth limits. | Offload Policy: Aggressive offloading (all KV) vs. Streaming (keep only recent $N$ in VRAM). |
| **Latency Floor** | Decode latency is bounded by memory access time + kernel launch overhead. | Kernel Support: CUDA vs. ROCm vs. DirectML affects occupancy and warp utilization. |

### 5. Diagnostic Measurements & Controlled Comparisons

To isolate the bottleneck (Weight BW vs. KV Traffic vs. CPU/GPU Transfer), perform these three tests:

**Test A: Isolate KV Cache Traffic (VRAM vs. RAM)**
*   **Setup:** Keep $N_{prompt}$ fixed (e.g., 2k). Keep $N_{gen}$ fixed (e.g., 10).
*   **Method:** Force KV cache to stay in VRAM (via quantization or offload settings) vs. allowing spill to RAM.
*   **Metric:** Measure per-token latency ($L_{gen}$).
*   **Expected:** If $L_{gen}$ jumps by $>10\times$ with RAM, **KV cache memory access** is the bottleneck. Check if the jump correlates with PCIe throughput limits.

**Test B: Isolate Weight Bandwidth (Prefill Dominance)**
*   **Setup:** Keep $N_{gen}$ = 0 (batch inference) or very small.
*   **Method:** Increase $N_{prompt}$ from 2k to 8k. Monitor GPU Utilization vs. Memory Bandwidth utilization.
*   **Metric:** Throughput ($tok/s$) vs. Prefill Time.
*   **Expected:** If throughput degrades significantly and GPU utilization drops below 50%, **Weight/Activation bandwidth** is the bottleneck (likely due to large KV matrix filling HBM2/HBM2e).

**Test C: Isolate CPU-GPU Transfer (Prefill Dominance)**
*   **Setup:** Run with massive $N_{prompt}$ that forces full KV spill to RAM.
*   **Method:** Measure the time spent in `torch.cuda.synchronize()` or inspect the `cudaEvent` logs for the kernel launch *before* the first decode step.
*   **Metric:** Time taken to load the full KV matrix into GPU memory.
*   **Expected:** If the time is proportional to the size of the KV matrix and limited by PCIe Gen3/4 bandwidth ($\approx 20\text{--}30 \text{ GB/s}$), **CPU-GPU transfer** is the bottleneck.

**Recommendation for Engineering Decision:**
Given the 6GB VRAM constraint and 32GB RAM, **do not rely on full KV offloading** for interactive use. Implement a **streaming KV cache** (e.g., `llama-streaming` or custom logic) that keeps only the last $N \approx 2000$ tokens in VRAM and streams the rest from RAM on-demand, or use quantization (INT4/INT8) to fit more context in VRAM, accepting a trade-off in precision for reduced memory bandwidth pressure.
