# Requirements and Invariants

### Inputs
*   **Configuration File (`config.yaml`):** Defines model aliases, paths, backend selection (CPU/CUDA/Vulkan), and optional workload parameters (context, temp, threads).
*   **Model Binary:** The `.gguf` file corresponding to the alias.
*   **Workload Definition:** Specifies the prompt template, generation limit, and specific flags (e.g., `--batch-size`, `--n-predict`).
*   **System Environment:** Host hardware metadata (CPU model, GPU driver version, available VRAM), build environment (llama.cpp commit/hash).

### Artifacts
*   **Raw Output Directory:** Contains the exact `stdout`/`stderr` streams and generated `response.txt` for every invocation.
*   **Metadata File (`run_<hash>.json`):** A single JSON file per run containing:
    *   The experimental identity tuple.
    *   Timestamp and duration.
    *   Hardware and build metadata.
    *   Configured parameters (context, temp, backend).
    *   Status flags (Success, Timeout, OOM, ParseError, MonitorError).
    *   Raw metric values if available.
*   **Validation Log:** A separate log for pre-launch sanity checks.

### Success/Failure States
*   **Success:** Process exits with code 0, `response.txt` exists and is non-empty, and optional metrics are successfully parsed (or marked as "unavailable" if sparsely sampled).
*   **Model Failure:** Process exits with non-zero code OR `response.txt` is empty/malformed. This is distinct from monitor failure.
*   **Monitor Failure:** Process succeeds, but optional monitoring data (e.g., VRAM usage curves) is missing or partial. The run is still valid but marked with a `monitor_status: "partial"` flag.
*   **Timeout/OOM:** Process killed by external signal (124 for timeout, 137/138 for OOM/Kill).

### Experimental Identity Tuple
A run is uniquely identified by the tuple:
`(Model_Path, Backend, Hardware_Label, Context, Generation_Limit, Prompt_Hash, Temperature, GPU_Layers, Build_Hash, Driver_Version)`
If any element in this tuple changes, the result is invalid for comparison with previous runs.

### Ambiguity Resolution
*   **Ambiguity:** The specification states "Monitors may be unavailable or sampled sparsely," but does not define the exact output format of the monitoring tool (e.g., Prometheus exposition, CSV, JSON).
*   **Resolution:** The design must treat the monitor as an external, optional subsystem. The parser must implement a "Best Effort" strategy: if the expected monitor port/socket/file is missing, log a `MonitorUnavailable` warning in the metadata but proceed to run the model. If the monitor is active but outputs partial data, the metadata must explicitly list which samples were received and which were missed, rather than failing the whole run. The specific monitoring format must be hardcoded in the agent's internal logic (or configurable via a strict schema extension) before implementation.

# State Machine

The workflow follows a strict lifecycle from validation to finalization.

### States & Transitions
1.  **IDLE:** Initial state.
2.  **VALIDATION:**
    *   *Check Config:* Validate YAML syntax and required fields.
    *   *Check Model:* Verify model file existence and format (`.gguf`).
    *   *Check Backend:* Verify driver availability (e.g., `nvidia-smi` for CUDA) and build flags.
    *   *Compute Identity:* Generate the Experimental Identity Tuple hash.
    *   *Transition:* If validation fails, go to **FINALIZE** with `status: "validation_error"`. If passed, go to **LAUNCH_PREP**.
3.  **LAUNCH_PREP:**
    *   Prepare the command line based on config/workload.
    *   Ensure atomic write directory exists.
    *   Transition to **RUNNING**.
4.  **RUNNING:**
    *   Spawn the llama.cpp process.
    *   Capture `stdout`/`stderr` to a temporary buffer.
    *   Start optional monitoring threads/sockets.
    *   Monitor for process exit (normal or signal).
    *   *Timeout Event:* If duration exceeds limit, send SIGKILL. Transition to **EXITED**.
    *   *OOM Event:* If SIGKILL received, transition to **EXITED**.
5.  **EXITED:**
    *   Read exit code and signal number.
    *   Read `response.txt` (if generated) and metrics.
    *   Attempt to parse metrics.
        *   If metrics parseable -> Extract throughput/tokens.
        *   If metrics malformed/unavailable -> Mark as "unavailable" (do not fail run).
    *   If monitor data was promised but missing -> Mark `monitor_status: "partial"`.
    *   If model failed (empty response/crash) -> Mark `run_status: "model_failure"`.
    *   If model succeeded -> Mark `run_status: "success"`.
6.  **FINALIZE:**
    *   Write atomic metadata file (`run_<id>.json.tmp` -> `mv` -> `run_<id>.json`).
    *   Append entry to validation log.
    *   Transition to **IDLE**.

### Error Handling Specifics
*   **Malformed Performance Output:** The parser attempts regex extraction. If the pattern fails, the metric field in metadata becomes `null` or `"parse_error"`, but the run status remains based on the process exit code and response file validity.
*   **Monitor Failure:** If the monitor crashes or disconnects, the state machine logs the disconnect but continues to read the model process output. The final metadata reflects the disconnect time but preserves the model run's success/failure state.

# Auditable Design

### Component Boundaries (Shell/Python)
*   **Shell Script (`runner.sh`):**
    *   Responsible for environment setup (loading paths, setting variables).
    *   Constructs the exact command string for llama.cpp.
    *   Executes the process and captures streams to temporary files.
    *   Handles the atomic move of the metadata file.
    *   Does **not** contain parsing logic.
*   **Python Component (`parser.py` / `analyzer.py`):**
    *   Invoked by the shell script via `python3`.
    *   Reads the temporary stdout/stderr and response files.
    *   Computes the Experimental Identity Tuple hash.
    *   Parses performance metrics (tokens/sec, time) using robust regex.
    *   Handles "unknown output formats" by falling back to raw text logging instead of crashing.
    *   Writes the final JSON metadata.

### Metadata Schema (JSON)
```json
{
  "id": "<unique_run_id>",
  "timestamp": "<ISO8601>",
  "identity_tuple": {
    "model_path": "...",
    "backend": "...",
    "hardware_label": "...",
    "context": <int>,
    "generation_limit": <int>,
    "prompt_hash": "<sha256>",
    "temperature": <float>,
    "gpu_layers": <int>,
    "build_hash": "<commit>",
    "driver_version": "<version>"
  },
  "execution": {
    "start_time": "<ISO8601>",
    "end_time": "<ISO8601>",
    "duration_sec": <float|null>,
    "exit_code": <int>,
    "exit_signal": <int|null>
  },
  "outcome": {
    "status": "success" | "timeout" | "oom" | "model_failure" | "validation_error",
    "monitor_status": "complete" | "partial" | "unavailable"
  },
  "metrics": {
    "tokens_generated": <int|null>,
    "tokens_per_second": <float|null>,
    "total_time_sec": <float|null>,
    "parse_notes": "<string|null>"
  },
  "raw_artifacts": {
    "response_file": "response.txt",
    "stdout_file": "stdout.txt",
    "stderr_file": "stderr.txt"
  }
}
```

### Atomic-Write & Partial-File Conventions
*   **Atomic Writes:** The metadata file is always written to a `.tmp` extension path first. Only after successful completion of the write is the file renamed to the final name using `mv` (atomic on POSIX). If the process is killed during write, no partial JSON file remains visible.
*   **Raw Artifacts:** `response.txt`, `stdout.txt`, and `stderr.txt` are written to disk immediately upon flush (buffered I/O with `fsync` or equivalent in Python). Even if the process crashes mid-generation, these files will contain whatever data was flushed, ensuring raw auditability.
*   **Prompt Preservation:** The exact prompt string used is saved in the metadata (escaped JSON string) alongside its SHA256 hash. This prevents ambiguity regarding whitespace or newline differences.

### Preserving Stdout/Stderr
The runner redirects the process's standard streams to specific temporary files before execution. No buffering is skipped; the files act as a verbatim transcript of the model's runtime behavior.

# Analysis Integrity

### Preventing Misleading Throughput Comparisons
1.  **Identity Tuple Enforcement:** The analysis logic strictly filters results. If the `identity_tuple` of a new run differs from a baseline run (e.g., different build hash, different driver version, or different prompt hash), they are treated as incompatible datasets. Aggregation tools must reject mixing these results.
2.  **Token Count Normalization:** Throughput (tokens/sec) is calculated using `tokens_generated` and `duration_sec`. If `tokens_generated` is missing (e.g., model crashed before finishing), the throughput is set to `null`. The analysis script must exclude `null` throughput values from averages unless a specific "partial run analysis" mode is requested (which requires explicit flagging).
3.  **Variable Generation Handling:** If a run generates significantly fewer tokens due to early stopping (not OOM/Timeout), the metadata must include a flag `early_stop_reason`. The analysis pipeline should weigh these runs lower or exclude them from "steady-state" performance benchmarks unless the early stop was intentional.

### Handling Unknown Output Formats
The parser must assume the primary metric source is the standard llama.cpp progress bar or JSON output.
*   **Strategy:** Use a "Try-Hard-Fail-Safe" approach.
    *   **Try:** Parse expected regex patterns for `n-predict` completion or JSON stats.
    *   **Fail-Safe:** If parsing fails, do not crash. Log a `parse_notes` field in the metadata indicating "Unknown format detected; raw output preserved."
    *   **Audit Trail:** The `stdout.txt` file guarantees that an engineer can manually inspect the raw output to understand why parsing failed. The design never claims a metric is "available" if the parser couldn't extract it; it claims it is "unavailable" or "unknown".

# Test Plan

1.  **Test: Valid CPU Run (Baseline)**
    *   *Setup:* Single-threaded CPU build, small model, `chat` workload.
    *   *Action:* Run with default context (4096) and limit (256).
    *   *Expectation:* Metadata shows `status: "success"`, `monitor_status: "complete"`, and valid throughput. Raw files contain full response.

2.  **Test: Simulated Backend Failure (CUDA Driver Missing)**
    *   *Setup:* Config requests `backend: "cuda"`, but `nvidia-smi` returns failure or driver is not installed.
    *   *Action:* Attempt launch.
    *   *Expectation:* Validation state catches the missing driver. Metadata shows `status: "validation_error"` or `model_failure` depending on if the fallback logic exists (spec says distinguish failure, so likely validation error). No model binary is loaded.

3.  **Test: Missing Monitor**
    *   *Setup:* Run with a configuration that enables monitoring, but the monitor port/socket is explicitly blocked or the monitor binary is missing.
    *   *Action:* Execute model run successfully.
    *   *Expectation:* Model runs to completion (`status: "success"`). Metadata shows `monitor_status: "unavailable"` or `"partial"`. No crash occurs. Raw output remains intact.

4.  **Test: Prompt Containing Spaces and Newlines**
    *   *Setup:* Workload prompt includes multi-line instructions and special characters (e.g., `User: Hello\n\nSystem: ...`).
    *   *Action:* Run benchmark.
    *   *Expectation:* Metadata `prompt` field stores the exact string with escaped newlines. `prompt_hash` changes correctly if the string changes. Model generates correct response.

5.  **Test: Partial Output (Crash Mid-Generation)**
    *   *Setup:* Configure a very high generation limit that causes an OOM or force a crash after 10 tokens using a specific flag.
    *   *Action:* Run until crash.
    *   *Expectation:* Metadata shows `status: "model_failure"` (or `oom`). `tokens_generated` is low. `response.txt` contains the partial output (not empty). `monitor_status` reflects if monitor survived the crash.

6.  **Test: Changed Prompt Hash (Identity Violation)**
    *   *Setup:* Run identical model/backend/config, but append a space to the prompt.
    *   *Action:* Run and compute identity.
    *   *Expectation:* The `prompt_hash` in the metadata changes. The experimental identity tuple is unique. Aggregation logic treating this as a duplicate of the previous run must be prevented by checking the tuple hash.

# Pre-merge Review

### Three Highest-Risk Design Flaws
1.  **Flaw: Silent Monitor Dependency**
    *   *Risk:* The design assumes if a monitor is "enabled," its data is critical. If the monitor fails, the whole run might be discarded, violating the requirement to distinguish model failure from monitor failure.
    *   *Fix:* Implement a strict "Monitor-Optional" flag. The state machine must never transition to `model_failure` solely because `monitor_status` is `partial` or `unavailable`. The metadata schema must explicitly decouple `run_status` from `monitor_status`.

2.  **Flaw: Ambiguous Identity Tuple Construction**
    *   *Risk:* The specification lists many variables for the identity tuple. If the "Hardware Label" is derived from a system call that behaves differently across OS versions (e.g., Linux vs. Windows), runs on the same machine but different OS might be treated as incompatible, or vice versa, breaking auditability.
    *   *Fix:* Define the "Hardware Label" strictly as a string concatenation of the OS name, CPU Model, and GPU Model (from lscpu/nvidia-smi) rather than a generic UUID. Ensure the "Build Hash" includes the specific compilation flags (e.g., `-DCUSTOM_FLAG`) to ensure binary compatibility checks are rigorous.

3.  **Flaw: Raw Output Corruption on Atomic Writes**
    *   *Risk:* If the shell script writes `stdout.txt` and then the process crashes immediately after, the file might be truncated. While atomic writes are used for metadata, raw logs are often append-only. If the log rotation or buffering logic isn't perfect, a crash could result in a missing last line of `stdout.txt`, making manual audit impossible for the final token.
    *   *Fix:* Force line-buffered output for the model process (`-f` flag or Python `flush=True`) and use `fsync` on the file descriptor immediately after every write. Ensure the atomic move logic only applies to the *metadata* file, while raw logs are flushed to completion before the process is allowed to exit or be killed.
