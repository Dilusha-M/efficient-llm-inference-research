### Task 1 — Quantization Tradeoff

**Assumptions & Fact Distinction:**
*   **Fact:** The Q8_0 file size is 8.0 GB; the Q4_K_M file size is 4.8 GB.
*   **Fact:** The GPU has 6.0 GB total VRAM with 5.2 GB currently free.

*   **Explicit Limitation:** We do not know the overhead required for KV cache, activations, or the CPU-side context buffer. We do not know the specific architecture of the model (e.g., whether it requires specific kernel optimizations for Q4 vs Q8).

**Analysis of Memory Pressure:**
1.  **Q8_0 Format:**
    *   **Weights Only:** Requires 8.0 GB.
    *   **Current Free VRAM:** 5.2 GB.
    *   **Immediate Deficit:** The weights alone exceed available VRAM by 2.8 GB. Even if the system offloads layers to system RAM (CPU), the GPU must hold *some* layers to accelerate inference. If the strategy is to load *all* weights on GPU, this format is impossible without swapping or offloading. If a hybrid approach is used, the "pressure" is high because the GPU must be reserved for both weights and the KV cache (which grows with context).
2.  **Q4_K_M Format:**
    *   **Weights Only:** Requires 4.8 GB.
    *   **Current Free VRAM:** 5.2 GB.
    *   **Immediate Deficit:** The weights fit within free VRAM with a slack of 0.4 GB *before* accounting for KV cache or activations.

**Why File Size is Not a Complete Runtime Memory Estimate:**
File size represents the static weight storage. Runtime memory pressure includes:
1.  **KV Cache:** Stores attention keys and values; size scales linearly with context length and batch size.
2.  **Activations:** Intermediate computations during the forward pass.
3.  **Execution Engine Overhead:** Context buffers, allocator structures, and thread-local data.
4.  **System RAM Offload Buffer:** If VRAM is full, the system needs contiguous space in system RAM to swap layers, which adds latency and requires managing the bandwidth between CPU and GPU.

**Required Quality/Performance Measurements:**
Before declaring one format better, these two metrics are essential:
1.  **Per-Token Latency (TTFT + Decode):** Measure the time to generate the first token and the average time per subsequent token. A lower-bit format might be faster due to memory bandwidth savings, even if slightly less accurate.
2.  **Semantic Similarity Score (e.g., ROUGE or BERTScore):** Compare the output of both models against a gold-standard reference to quantify the quality loss introduced by quantization. A format is only "better" if it meets the quality threshold while offering superior speed/memory efficiency.

function aggregate_results(speeds_list, warnings_list):
    # 1. Validate Records
    valid_runs = []
    failed_runs = []

            })

            valid_runs.append(speed)
            
    # 2. Compute Median for Successful Runs
    if len(valid_runs) < 2:
        return {
            "status": "insufficient_data",
            "message": f"Only {len(valid_runs)} successful runs. Median cannot be statistically calculated.",
            "valid_runs": valid_runs,
            "failed_runs": failed_runs
        }
        
    valid_runs.sort()
    n = len(valid_runs)
    if n % 2 == 1:
        median = valid_runs[n // 2]
    else:
        median = (valid_runs[n // 2 - 1] + valid_runs[n // 2]) / 2
        
    return {
        "median_speed": median,
        "success_rate": f"{len(valid_runs)}/{len(speeds_list)}",
        "failed_runs": failed_runs, # Explicitly report failures
        "data": valid_runs
    }

### Task 4 — Validity Audit

**Threat 1: Thermal Throttling / Hardware Frequency Shift**
*   **Threat:** Running CUDA and Vulkan backends (which are often compute-bound) may cause the GPU to heat up faster than the CPU benchmark, leading to frequency scaling down during the second or third run, artificially lowering throughput.
*   **Control/Disclosure:** Run all three backends on the same hardware instance but interleave them randomly (e.g., CPU -> Vulkan -> CUDA -> Vulkan -> CUDA) to average out thermal effects. Disclose that benchmarks were run in a short sequence without thermal stabilization periods between the three runs.

**Threat 2: Memory Bandwidth Contention (NUMA or Shared Memory)**
*   **Threat:** The 8-thread CPU benchmark might contend with background OS processes or the GPU drivers for shared PCIe bandwidth or CPU cache coherency traffic, whereas the GPU runs might saturate the bus differently, skewing results.
*   **Control/Disclosure:** Pin CPU threads to specific cores and disable non-essential background services during testing. Disclose the exact core affinity settings used.

**Threat 3: Workload/Output Comparability (Semantic Drift)**
*   **Threat:** Different backends may have slight numerical precision differences (FP16 vs BF16 internal casting) or ordering of operations (fused kernels vs. split kernels) leading to different logits. If the model uses a deterministic tie-breaking mechanism or a small vocabulary where floating point noise changes the chosen token, the **output text will differ** between CPU and GPU runs. Comparing "speeds" is valid, but comparing "quality" or "consistency" is invalid if the outputs don't match.
*   **Control/Disclosure:** Force deterministic execution flags where possible. For the validity claim, **only report latency/throughput**, not accuracy, unless the outputs are identical. Explicitly disclose that even minor numerical differences can lead to different generated text, making cross-backend quality comparison invalid without a fixed seed and identical computation graph.

**Threat 4: Driver/Kernel Initialization Overhead**
*   **Threat:** The first run of a backend (especially Vulkan) often involves heavy driver initialization and shader compilation (cold start). If the three runs are not warmed up, the first run is an outlier, and averaging three runs (including the cold start) biases the result downward for that backend.
*   **Control/Disclosure:** Discard the first run as a "warm-up" and average only the last two runs, or ensure a significant warm-up workload (e.g., running the model once with dummy data) before starting the measurement. Disclose that the reported mean includes the initialization cost if warm-up was omitted.

### Task 5 — User-Visible Latency

**Concept Definitions:**
1.  **Time to First Token (TTFT):** The time from pressing "Generate" until the first character appears on screen. This includes processing the entire 2,000-token prompt and starting the first generation step.
2.  **Prompt-Evaluation Throughput:** The rate at which the model processes the input prompt tokens (e.g., 10 tokens/sec). It is a measure of how fast the model "reads" the prompt.
3.  **Decode Throughput:** The rate at which new tokens are generated after the first token (e.g., 40 tokens/sec). This is the steady-state speed.
4.  **Total Wall-Clock Time:** The total duration from pressing "Generate" until the last token of the 200-token response is displayed.

**Symbolic Equation for Total Time:**
Let $T_{proc}$ be the time to process the prompt (inverse of prompt-throughput).
Let $N_{prompt}$ be the number of input tokens (2,000).
Let $N_{gen}$ be the number of generated tokens (200).
Let $R_{decode}$ be the decode throughput (tok/s).
Let $T_{first}$ be the TTFT (which depends on prompt processing plus the latency of the first generation step).

$$ T_{total} = T_{proc} + T_{first} + \frac{N_{gen} - 1}{R_{decode}} $$

*Note: $T_{proc}$ is often the dominant factor in TTFT. $T_{first}$ includes the time to compute the logit for the first token after the prompt is processed.*

**Example of Minimal Impact Scenario:**
**Scenario:** A user has a very fast GPU where prompt processing takes 0.5 seconds ($T_{proc} = 0.5s$) and decode throughput is 40 tok/s.
**Optimization:** The user upgrades their CPU or network to reduce prompt processing time to 0.2 seconds (a 60% improvement in prompt stage).
**Experience:**
*   Original Total Time: $0.5s + T_{first} + (199/40)s \approx 0.5 + 0.1 + 4.975 \approx 5.57s$.
*   Optimized Total Time: $0.2s + T_{first} + (199/40)s \approx 0.2 + 0.1 + 4.975 \approx 5.27s$.
**Conclusion:** The user perceives a difference of only 0.3 seconds. However, if the original prompt was huge (e.g., 10,000 tokens), $T_{proc}$ might be 10s. Optimizing that to 1s would save 9s, drastically changing the experience. In the 2,000-token case, the decode phase (approx 5 seconds) dominates the total time, so optimizing the prompt processing (which is fast) barely changes the user's perceived wait time for the full response. Optimizing **decode throughput** (e.g., from 40 to 60 tok/s) would reduce the 5s wait to ~3.3s, which is a much more visible change.
