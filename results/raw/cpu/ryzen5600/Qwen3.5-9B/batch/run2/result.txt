**Memory Pressure Analysis:**
1.  **Q8_0 Format:**

    *   **Runtime Pressure:** Even before processing a single token, the system needs 8.0 GB + KV Cache + Context Overhead.

2.  **Runtime Overhead:** CUDA context, allocator buffers, and fused kernel arguments.

### Task 2 — conservative launch decision

**Assumptions:**
*   The 5.0 GB weight figure is strictly for model parameters (W), excluding the Key-Value (KV) cache.
*   The 16 GB system RAM is available for CPU offloading if VRAM fills up.

**Conservative Procedure:**

**1. What to Try First (The "Safe Fit" Strategy):**
*   **Step A: Minimize Context Window:** Do not start with 2,000 tokens. Start with a smaller context (e.g., 512 or 1024 tokens) to minimize KV cache footprint.
*   **Step B: GPU-Only Initialization with Monitoring:** Launch with `--n-gpu-layers 64` (all layers on GPU) but set `--ctx-size` to a conservative value (e.g., 256 or 512).
*   **Step C: Dynamic Offloading:** If the GPU fills, do not immediately assume CPU offloading is stable. Instead, reduce `--n-gpu-layers` gradually (e.g., try 32, then 16) until the model loads without OOM.
*   **Command Flag Logic:** Use `--main-gpu 0` and ensure `--n-gpu-layers` is set explicitly. Do not rely on automatic heuristics without telemetry.

**2. Telemetry to Record:**
*   **Peak VRAM Usage (`--verbose 3` or `--metrics`):** Monitor the exact peak memory during the *first prompt processing*, not just the average. The peak usually happens when loading weights + initializing the KV cache for the full prompt.
*   **Swap/Pagefile Activity:** Monitor if the system starts swapping to the 16 GB RAM. Swapping kills performance (latency spikes).
*   **Batch Size Impact:** Record how changing `--batch-size` affects peak memory. A small batch (1) is safer for conservative testing than batching.

**3. Unsafe or Misleading Success Scenarios:**
*   **The "First Prompt" Illusion:** The model appears to run fine on a short test prompt (e.g., "Hello") but crashes on the actual 2,000-token prompt because the KV cache grows non-linearly with context length. *Unsafe:* Declaring success based on a short test.

*   **Partial Offload Instability:** Setting `--n-gpu-layers` to a value that leaves exactly 0 MB free buffer. Any slight increase in KV cache will cause an immediate OOM. *Unsafe:* No headroom for the OS or allocator overhead.

### Task 3 — robust aggregation

**Assumptions:**
*   The 8.0 tok/s run is a valid measurement despite the warning, but it represents a degraded state (likely swapping or severe thrashing).
*   "Median" is the preferred statistic for robustness against outliers, but the dataset is tiny (N=3).
*   The goal is to distinguish between a "failed" run (OOM) and a "slow" run.

**Pseudocode:**

```python
def validate_and_aggregate(results):
    """
    results: List of tuples (speed_toks_per_sec, status_code, run_id)
    status_code: 'success', 'oom', 'error'
    """
    successful_runs = []
    failed_runs = []
    
    # 1. Validation: Separate successful from failed
    for run in results:
        speed, status, run_id = run
        if status == 'success':
            # Validate numeric range (optional sanity check)
            if speed > 0:
                successful_runs.append((run_id, speed))
            else:
                failed_runs.append(run) # Treat non-positive speed as invalid even if status says success
        elif status in ['oom', 'error']:
            failed_runs.append(run)
        else:
            # Unknown status, treat as failed for safety
            failed_runs.append(run)
            
    # 2. Handling the "Fewer than two runs succeed" case
    if len(successful_runs) < 2:
        # Cannot compute a meaningful median or mean
        return {
            "status": "INSUFFICIENT_DATA",
            "message": f"Only {len(successful_runs)} successful runs recorded. Median cannot be computed reliably.",
            "successful_runs": successful_runs,
            "failed_runs": failed_runs,
            "recommendation": "Re-run experiment. The 8.0 tok/s value is an outlier driven by OOM behavior."
        }
    
    # 3. Extract speeds from successful runs
    speeds = [s for _, s in successful_runs]
    
    # 4. Compute Median
    speeds.sort()
    n = len(speeds)
    if n % 2 == 1:
        median_speed = speeds[n // 2]
    else:
        median_speed = (speeds[n // 2 - 1] + speeds[n // 2]) / 2.0
        
    # 5. Reporting
    return {
        "status": "SUCCESS",
        "median_speed": median_speed,
        "successful_runs": speeds,
        "failed_runs": failed_runs, # Keep visible
        "note": "Failed run(s) excluded from median calculation but retained in logs for debugging."
    }

# Usage Example
raw_data = [
    (42.0, "success", "run_1"),
    (41.5, "success", "run_2"),
    (8.0, "oom", "run_3") # The failed run with warning
]

final_report = validate_and_aggregate(raw_data)
```

**Reporting Logic for < 2 Successes:**
If fewer than two runs succeed (e.g., only the 42.0 and 41.5 runs succeed, or only the 8.0 run succeeds), you **cannot** report a statistical median. You must report the **count of successful runs** and explicitly state that the result is **unstable** or **inconclusive**. Do not average the failed run (8.0) into the metric, as it represents a system failure state, not a performance baseline. The report should highlight the instability of the hardware/software stack.

### Task 4 — validity audit

**Assumptions:**
*   The "CPU" refers to a specific CPU configuration with exactly 8 threads pinned.
*   "Offloads all layers" implies the GPU is used solely for the matrix multiplications, but other kernels (like attention or normalization) might still be CPU-bound or hybrid depending on the backend implementation.
*   The comparison assumes identical model weights and identical prompts.

**Four Threats to Validity:**

1.  **Threat: Kernel Launch Overhead & Warm-up Differences**
    *   *Description:* CUDA and Vulkan have different initialization costs and "warm-up" requirements. Running only 3 times may not account for driver initialization latency or memory cold-cache effects.
    *   *Control/Disclosure:* Include a mandatory "warm-up" phase (e.g., 50 dummy tokens) before timing starts. Explicitly disclose the number of iterations and whether the first run was excluded from the average.

2.  **Threat: Memory Bandwidth Saturation vs. Compute Bound Distortion**
    *   *Description:* CUDA with all layers offloaded might saturate memory bandwidth differently than Vulkan or CPU due to how each handles memory coalescing and the specific memory allocator (e.g., CUDA's `cudaMallocAsync` vs. Vulkan's `vkCmdAllocateBuffer`). The CPU (8 threads) might be compute-bound, while the GPU backends are memory-bound, making the comparison unfair regarding algorithmic complexity.
    *   *Control/Disclosure:* Report the theoretical FLOPS utilization for each backend. Disclose if one backend is memory-bandwidth bound while another is compute-bound, as this invalidates a direct "speed" comparison without normalizing for operation count.

3.  **Threat: Precision Rounding and Determinism Drift (Workload Comparability)**
    *   *Description:* CUDA (FP16/FP32) and Vulkan (often FP16 with different rounding modes) or CPU (AVX2/AVX-512) may produce slightly different floating-point results due to operation ordering (associativity errors). If the model uses logits for sampling, tiny differences in the hidden state can lead to different token probabilities, changing the *actual* output text or the *effective* workload if the generation path diverges.
    *   *Control/Disclosure:* Force deterministic execution (e.g., set `deterministic` flags) or fix the random seed strictly. Disclose any bit-differences in the final logits. If the outputs differ, the "workload" (the specific sequence of tokens generated) is not comparable.

4.  **Threat: Context Scheduler Interference (Workload Comparability)**
    *   *Description:* The CPU backend running on 8 threads might contend with the OS scheduler or other background processes differently than the GPU backends, which often bypass the CPU scheduler for compute kernels. Furthermore, if the CPU backend runs attention logic on the CPU while others run it on GPU, the *nature* of the workload (memory access patterns) differs fundamentally, not just the hardware.
    *   *Control/Disclosure:* Pin the CPU threads to specific cores to avoid scheduler thrashing. Disclose which specific kernels (e.g., `flash_attn` vs `sdpa` vs standard matmul) are executed on which device for each backend. If the backend implementation changes the *location* of different sub-kernels (e.g., CUDA does everything on GPU, CPU does everything on CPU, Vulkan does a hybrid), this constitutes a workload architecture change, not just a hardware change.

### Task 5 — user-visible latency

*   "Throughput" is measured in tokens/second (tok/s).

**Definitions & Differences:**
1.  **Time to First Token (TTFT):** The wall-clock time from the start of inference (prompt submission) until the first generated token is ready. This includes the time to process the entire 2,000-token prompt.
2.  **Prompt-Evaluation Throughput:** The speed at which the model processes the input prompt to reach the first token. It is calculated as `Length of Prompt / TTFT`. High throughput here means the prompt was processed quickly.
3.  **Decode Throughput:** The speed at which the model generates tokens *after* the first token. It is calculated as `Number of Generated Tokens / (Total Time - TTFT)`. This is usually stable and high (e.g., 40-50 tok/s).
4.  **Total Wall-Clock Time:** The sum of TTFT and the time taken to generate all 200 tokens. `Total Time = TTFT + (200 tokens / Decode Throughput)`.

**Symbolic Equation for Total Time:**
Let $T_{prompt}$ be the time to process the prompt (TTFT).
Let $T_{decode}$ be the time to decode $N$ tokens at rate $R_{decode}$.
$$ T_{total} = T_{prompt} + \frac{N}{R_{decode}} $$
Where:
*   $T_{prompt} = \frac{L_{prompt}}{R_{prompt}}$ ($L_{prompt}$ = 2000 tokens, $R_{prompt}$ = prompt throughput).
*   $N$ = 200 tokens.
