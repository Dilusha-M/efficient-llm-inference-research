### Executive Summary: The Bottleneck Shift
The system exhibits the classic **Prefill-Decode Mismatch**. During the 2,000-token prompt (prefill), the GPU is saturated with compute and memory bandwidth, hiding the cost of fetching weights and processing the massive batch. However, during the 300-token decode phase, the workload shifts to strict latency-bound execution where every token requires reading the entire previous history (KV cache). Since the KV cache exceeds 6 GB, it spills to RAM. The resulting CPU-GPU transfer latency and reduced effective bandwidth per token cause the interactive latency to spike, while the "excellent" prompt throughput remains a misleading metric because it ignores the sequential, latency-bound nature of autoregressive generation.

---

### 1. Lifecycle of the KV Cache: Reuse vs. Recomputation

*   **Prefill Phase (Prompt Processing):**
    *   **Weights:** Loaded once from VRAM (if resident) or RAM.
    *   **KV Cache:** Initialized to zeros. As the model processes each token in the 2,000-token prompt, it computes new Key and Value vectors for every layer and head. These are appended to the growing cache.
    *   **Resource Profile:** Compute-bound and bandwidth-bound (reading weights + writing new cache). The GPU can overlap reading weights with computing, masking the cost of filling the cache.
*   **Decode Phase (Token-by-Token Generation):**
    *   **Weights:** Remain static in VRAM; accessed sequentially for attention scoring.
    *   **KV Cache:** **Critical Reuse.** To generate the next token, the model must attend to *all* previous tokens. This requires reading the entire accumulated KV cache from the last step to the current position.
    *   **Resource Profile:** Memory-bound (reading historical cache) and latency-bound (waiting for data). No new cache is computed until the next prompt token arrives (if any).

**Distinction:** The prefill rewrites the cache $N$ times in parallel; the decode reads the same cache $N$ times in strict sequence.

### 2. Hardware Stress & The Latency Throughput Paradox

*   **Prefill Stress:** Dominated by **VRAM Bandwidth** (reading weights) and **Compute Throughput**. A 6 GB VRAM card can saturate its memory bus reading weights quickly. The GPU hides memory latency by processing many tokens simultaneously.
*   **Decode Stress:** Dominated by **Memory Latency** and **Data Movement**. When the KV cache spills to system RAM (32 GB), the PCIe bandwidth (typically 32–64 GB/s) is orders of magnitude slower than VRAM bandwidth (900+ GB/s). Furthermore, PCIe introduces high latency (microseconds vs. nanoseconds).
*   **The Paradox:** High prompt tokens/second (tok/s) does not imply low latency because:
    1.  Prompt processing is **throughput-oriented**; you can move massive data fast if you have enough parallelism.
    2.  Decoding is **latency-oriented**; you are limited by the slowest link (PCIe) for every single token. A system can process a 2k prompt in 0.5s (high throughput) but generate the 300th token 50ms after the 299th (high latency).

### 3. Impact of Context Expansion (2k $\to$ 8k Tokens)

Increasing context from 2,000 to 8,000 tokens exacerbates the bottleneck through two mechanisms:

1.  **Prefill Overhead:** The prefill phase must now compute and store 4x more KV entries. This increases the initial VRAM usage and the time to fill the cache, potentially pushing the GPU further into memory-bandwidth saturation during the first few seconds.
2.  **Decode Degradation (The Critical Factor):**
    *   **Cache Volume:** The decode phase must read 4x more historical data (4x the KV cache size) for every single generated token.
    *   **Bandwidth Saturation:** If the cache is on RAM, reading 8k tokens of cache requires moving significantly more data over the PCIe bus. Since PCIe is the bottleneck, doubling the context length roughly doubles the time per decode token ($T_{token} \propto \text{Context Length}$).
    *   **Memory Pressure:** An 8k context on a 6 GB GPU will likely force even more aggressive swapping or require quantization of the cache (e.g., from FP16 to INT8/FP8) to fit, further complicating the latency profile.

### 4. General Truths vs. Implementation Dependencies

| Claim Type | Statement | Context/Dependency |
| :--- | :--- | :--- |
| **General Truth** | Autoregressive decoding latency scales linearly with context length when the KV cache resides in slower memory (RAM). | True across architectures; physics of data movement. |
| **General Truth** | High prefill throughput does not correlate with low decoding latency. | True; different optimization goals (batched vs. single-token). |
| **Implementation Dependent** | The exact latency penalty of spilling KV cache to RAM. | Depends on PCIe generation (Gen3 vs Gen4), CPU overhead for paging, and kernel efficiency. |

### 5. Diagnostic Measurements & Controlled Comparisons

To isolate the bottleneck, perform these three controlled experiments:

1.  **Isolate KV-Cache Traffic (Bandwidth Bottleneck):**
    *   *Method:* Run a synthetic benchmark using a "dummy" model where weights are already loaded, but force a massive, artificial KV cache (e.g., 4k tokens of dummy data) to reside entirely in RAM.
    *   *Metric:* Measure time-per-token. If latency scales linearly with the size of this dummy cache, the bottleneck is **KV-cache memory bandwidth** on the PCIe bus.
2.  **Isolate CPU-GPU Transfer Overhead (Latency Bottleneck):**
    *   *Method:* Measure the latency difference between a 2,000-token prompt and an 8,000-token prompt with identical total token counts (e.g., 2k prompt vs. 0 prompt + 2k dummy history). Alternatively, use a tool that allows disabling PCIe compression or forcing synchronous PCIe flushes.
    *   *Metric:* Look for constant overhead added to the decode step. If the latency jump is disproportionate to the data size increase, **PCIe setup latency** or **CPU interrupt handling** during page faults is the culprit.
3.  **Isolate Weight Bandwidth (Baseline Check):**
    *   *Method:* Compare the time-to-compute a single token with a "frozen" KV cache (no new tokens in context) vs. a dynamic cache. Then, swap the GPU to one with higher memory bandwidth (if available) or use a different VRAM size to see if prefill times change disproportionately.
    *   *Metric:* If prefill time changes significantly with VRAM size but decode time does not (once cache is on RAM), the baseline confirms weights were the original bottleneck, and now the cache is the new bottleneck.

### Numerical Example: Dominance of Decode Latency

**Assumptions:**
*   GPU VRAM Bandwidth: $900$ GB/s.
*   System RAM + PCIe Bandwidth: $30$ GB/s (conservative estimate including overhead).
*   Model Weights: $2$ GB.
*   KV Cache (2k tokens): $4$ GB.
*   KV Cache (8k tokens): $8$ GB.
*   Compute time per token (negligible for this comparison): $0.05$ ms.

**Scenario A: 2,000 Token Prompt (Prefill Only)**
*   Data to move: Weights ($2$ GB) + New Cache ($4$ GB) = $6$ GB.
*   Time $\approx 6 \text{ GB} / 900 \text{ GB/s} = 0.0067 \text{ s} = 6.7 \text{ ms}$.
*   *Result:* Extremely fast. High tok/s is achievable.

**Scenario B: 1 Token Decode (Context = 2,000 tokens, Cache in RAM)**
*   Data to move: Entire Historical Cache ($4$ GB).
*   Time $\approx 4 \text{ GB} / 30 \text{ GB/s} = 0.133 \text{ s} = 133 \text{ ms}$.
*   *Result:* Latency dominated by RAM read.

**Scenario C: 1 Token Decode (Context = 8,000 tokens, Cache in RAM)**
*   Data to move: Entire Historical Cache ($8$ GB).
*   Time $\approx 8 \text{ GB} / 30 \text{ GB/s} = 0.266 \text{ s} = 266 \text{ ms}$.

**Conclusion:** Even though the prompt processing (Scenario A) takes only $6.7$ ms, the interaction latency (Scenario B/C) jumps from $133$ ms to $266$ ms purely due to context expansion. The total response time is entirely dominated by the decode phase's memory traffic, not the prompt processing speed.
