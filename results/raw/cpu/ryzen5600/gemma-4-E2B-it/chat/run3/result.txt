Scenario:
A 7B decoder-only model is served on a 6 GB consumer GPU with 32 GB system RAM. The model weights fit on the GPU, but the key-value (KV) cache does not always fit there. A user sends a 2,000-token prompt and requests 300 generated tokens. The system reports excellent prompt-processing throughput but becomes much slow ... (truncated)
This scenario points to a classic resource contention issue in large language model (LLM) serving, specifically concerning memory access patterns and the trade-off between computational throughput and memory bandwidth.

## Analysis and Investigation

### 1. Lifecycle of the KV Cache

The KV cache stores the intermediate attention states required for the next token prediction, indexed by the sequence history.

*   **Prompt Processing (Prefill):** The entire 2,000-token prompt is processed. The full attention mechanism is computed across all prompt tokens. The resulting $K$ and $V$ matrices for these tokens are computed and stored in the KV cache. **All tokens in the prompt are read and written.**
*   **Token-by-Token Decoding (Decoding):** As tokens are generated sequentially (300 tokens), the system reuses the previous context. For each new token, the model only computes the attention for the *new* token against the *entire* existing KV cache (Prompt + previously generated tokens). **The prompt's $K/V$ states are reused (read), and new $K/V$ states for the newly generated tokens are computed and appended (written).**

### 2. Resource Stress Disparity

*   **Prompt Processing (Prefill):** This phase is **compute-bound**. It involves large, parallel matrix multiplications across the entire input sequence. Since the weights are on the GPU, this phase heavily stresses the **GPU's Tensor Core/ALU throughput** and its ability to feed data from global memory.
*   **Decoding (Autoregressive):** This phase is often **memory-bound**. While the computation is sequential, the bottleneck shifts to **memory bandwidth** because the model must repeatedly fetch and write the growing KV cache from memory to the processing units for every single token. A high prompt tokens/s (throughput) is achievable because the initial large computation is fast, but the subsequent latency is dominated by memory access latency and bandwidth for the growing cache.

### 3. Effect of Increasing Context ($2\text{k} \to 8\text{k}$ Tokens)

Increasing the context length significantly amplifies the memory footprint of the KV cache, impacting both phases:

*   **Prefill Phase:** The computational complexity scales quadratically with sequence length ($O(N^2)$) during the self-attention computation, meaning longer prompts take significantly longer. The GPU must process larger input sequences, increasing the time spent in the initial computation.
*   **Decoding Phase:** The KV cache size increases linearly with context length ($L$). Since the memory is now larger, the time spent reading/writing the KV cache (memory bandwidth) becomes a more dominant factor, especially on constrained systems where the bottleneck shifts from raw compute to memory bandwidth. The system becomes slower because the memory accesses for the growing cache dominate the per-token latency.

### 4. Claim Separation

| Category | Claim | Status |
| :--- | :--- | :--- |
| **General Truths** | Prompt processing is compute-bound; decoding is memory-bound. | True |
| **Implementation Dependent** | KV-cache size directly dictates memory bandwidth saturation. | Depends on implementation (e.g., block size, memory layout). |
| **Implementation Dependent** | Moving KV cache to system RAM introduces latency due to PCIe/memory transfer overhead. | Depends on interconnect speed and offload strategy. |
| **Implementation Dependent** | The exact bottleneck depends on the specific memory access pattern (e.g., sequential vs. random access). | Depends on the specific hardware memory hierarchy. |

### 5. Proposed Measurements

To distinguish the bottleneck, we need to isolate the time spent in computation versus time spent in data movement (memory I/O).

1.  **Weight Bandwidth Measurement (Compute Bottleneck):**
    *   **Measurement:** Measure the time taken for the **Prefill Phase** (processing the 2,000-token prompt only) while keeping the KV cache size fixed (or very small).
    *   **Goal:** Establish the baseline computational throughput of the GPU, isolating it from memory contention.

2.  **KV-Cache Traffic Measurement (Memory Bottleneck):**
    *   **Measurement:** Measure the time taken for the **Decoding Phase** (generating 300 tokens) while using the full 2,000-token context. Simultaneously, measure the total **memory bandwidth utilization** (GPU VRAM read/write rate) during this phase.
    *   **Goal:** Determine if the latency increase scales linearly with the growing cache size and correlates with memory bandwidth saturation.

3.  **CPU–GPU Transfer Measurement (Interconnect Bottleneck):**
    *   **Measurement:** Measure the time taken for the **full transfer** of the 2,000-token prompt weights and the initial KV cache (after prompt processing) to the system RAM, and subsequently the transfer of the generated output tokens back.
    *   **Goal:** Quantify the overhead introduced by moving the large KV state between the GPU and the CPU system memory, isolating the PCIe/bus latency component.

**Numerical Example (Illustrative):**

Assume the following hypothetical, simplified time breakdown for a 100-token prompt and 10 generated tokens:

*   **Prefill Time ($T_P$):** $10 \text{ms}$ (Compute Bound)
*   **Decode Time ($T_D$):** $90 \text{ms}$ (Memory Bound)

If the system is heavily memory bound due to the KV cache growth, the total time $T_{\text{total}}$ for the 10 generated tokens might be:
$$T_{\text{total}} = T_P + T_D = 10 \text{ms} + 90 \text{ms} = 100 \text{ms}$$

If the system were purely compute-bound (e.g., if memory bandwidth was infinite), $T_D$ might be $10 \text{ms}$, leading to $T_{\text{total}} = 20 \text{ms}$. The difference highlights that increasing the context pushes the system from a compute-limited regime to a memory-limited regime.
