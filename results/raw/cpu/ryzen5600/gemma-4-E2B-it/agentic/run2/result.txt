* **Failure (Model/Process):** The underlying `llama.cpp` process fails (e.g., OOM, internal error).
* **Failure (Data Integrity):** Missing required monitoring data or malformed performance output.

**Experimental Identity Tuple:**
The tuple defining a unique run must be: (Model Alias, Backend, Hardware Label, Context, Generation Limit, Prompt Hash, Workload, Run Timestamp).

**Ambiguity to be Resolved:**
The specification states that the runner must distinguish a failed model run from missing optional monitoring data. ## State Machine

**State 1: Initialization & Validation**
1. Load configuration from the alias file.
2. Validate all required inputs (Model, Backend, Workload).
3. Initialize default parameters (Context=4096, Limit=256, Temp=0.7, Threads=1).
4. Calculate the Run Identifier (Identity Tuple).

**State 2: Pre-Execution Check**
1. Check for availability of monitoring hooks/environment for required metrics.
2. If monitoring data is expected but unavailable, set failure flag for monitoring data absence (potential soft failure, depending on ambiguity resolution).

**State 3: Execution Launch**
1. Construct the specific command line arguments for `llama.cpp` based on inputs.
2. Launch the model process, redirecting stdout/stderr to separate files for auditing.

**State 4: Monitoring & Waiting**
1. Start asynchronous monitoring of the process (CPU, Memory, Time).
2. Wait for process termination or timeout.
3. Handle process termination events:
    * **Normal Exit:** Proceed to State 5.
    * **Timeout:** Terminate process forcefully and record timeout failure.
    * **OOM/Signal Failure:** Record process failure and associated error codes.

**State 5: Post-Execution Processing & Validation**
1. Aggregate raw output and performance metrics.
2. Validate Performance Output format. If malformed, mark run as failed (Data Integrity Failure).
3. Validate presence of required monitoring data. If missing, mark run as failed (Monitoring Data Failure).
4. Finalize the Run Metadata file.

**State 6: Finalization**
1. Archive raw output (for manual audit).
2. Record the definitive success/failure status based on validation checks.
3. Mark the Run as complete.

## Auditable Design

**Component Boundaries:**
1. **Configuration Loader:** Reads and parses the model alias file.
2. **Command Builder:** Generates the precise execution command and parameter set.
3. **Execution Engine (Wrapper):** Manages the lifecycle of the external `llama.cpp` process, handles process spawning, and manages timeouts.
4. **Monitor Agent:** Hooks into the execution environment to capture hardware/process metrics.
5. **Output Handler:** Manages file I/O for raw response and performance data.
6. **Metadata Writer:** Assembles and writes the final Run Metadata file.

**Atomic-Write / Partial-File Conventions:**

If validation fails, the system must record the failure in the metadata, but the partial file should not be considered a valid run.

**Preserving stdout/stderr and Prompt:**
* **Prompt:** The exact prompt used must be stored as a string within the Run Metadata file, preferably hashed for integrity checks.
* **Stdout/Stderr:** The raw output stream from `llama.cpp` must be captured immediately upon generation. Since the requirement is to keep the raw output available for manual audit, the full stream must be written to a designated file (`response.txt`) before any parsing or aggregation occurs.

## Analysis Integrity

**Preventing Misleading Throughput Comparison:**
Throughput comparison must be anchored to a single, verifiable metric derived from the raw output, not just token counts.
1. **Token Count Verification:** The token count must be explicitly extracted from the *valid* output stream (e.g., by parsing the output structure generated by `llama.cpp` or using a secondary, trusted tokenizer). If the output format is unknown, the system must default to recording the raw token count reported by the process, flagging it as potentially untrusted.
2. **Failure Weighting:** If the run is marked `FAILURE` (due to process error or data corruption), the calculated throughput should be excluded from aggregate performance comparisons, or marked with a special error value (e.g., $\text{NaN}$ or $-\infty$), ensuring failed runs do not skew averages.

**Handling Unknown Llama.cpp Output Formats:**
If the parser encounters an output format that does not match expected structures (e.g., missing expected headers, corrupted token counts):
1. **Strict Parsing Failure:** The parser must fail the validation step for that specific run, setting the `failure_reason` to `OUTPUT_MALFORMED`.
2. **Raw Preservation:** The raw output file (`response.txt`) must *always* be preserved.
3. **Fallback Metric:** If token counts cannot be reliably extracted, the system must rely solely on timing metrics (`time_ms`) for relative performance comparison, explicitly flagging that token-based throughput is unavailable for that specific run.

## Pre-merge Review

**Highest-Risk Design Flaw 1: Ambiguous Failure Handling (State Machine)**
* **Flaw:** The ambiguity regarding whether monitoring failure implies process failure, or vice versa, could lead to incorrect error reporting, masking true causes.
* **Fix:** Strictly enforce the hierarchy: Process Failure (OOM/Signal) is primary. Monitoring Failure is secondary (absence of optional data). The State Machine must explicitly define that *any* failure to collect *required* data results in a failure status, regardless of the process outcome.

**Highest-Risk Design Flaw 2: Data Integrity vs. Raw Output Preservation**
* **Flaw:** Balancing the need for strict, verifiable performance metrics against the requirement to keep the raw output available for audit. If parsing fails, the system must decide whether to discard the run or keep the raw output.
* **Fix:** Adopt the principle: **Raw output is immutable and always saved.** Performance metrics and validity are derived *from* the output. If parsing fails, the failure reason must be `OUTPUT_MALFORMED`, but the raw file must remain. This separates auditing (raw file) from quantitative comparison (metadata).

**Highest-Risk Design Flaw 3: Non-Atomic Metadata Writing**
* **Flaw:** Writing the final metadata file concurrently with the process completion risks leaving an inconsistent state if the system crashes between writing performance data and finalizing the status.
* **Fix:** Implement a two-phase commit for metadata: 1. Collect ALL data (raw, metrics, status) into temporary memory structures. 2. Only when all data is verified and complete, write the entire Run Metadata file atomically to disk (e.g., write to a temporary file, then rename/move to the final location).
