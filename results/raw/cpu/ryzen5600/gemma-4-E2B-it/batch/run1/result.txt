## Task 1 — quantization tradeoff

**Given Data:**

*   8B Model: Q4\_K\_M file size = 4.8 GB
*   GPU Memory: 6 GB total, 5.2 GB free before inference.

**Explanation of Memory Pressure:**

1.  **Q8\_0 (8.0 GB):** Since the file size (8.0 GB) is larger than the available free memory (5.2 GB), loading this model will immediately cause an **Out-of-Memory (OOM)** error or severe swapping/paging pressure, as $8.0 \text{ GB} > 5.2 \text{ GB}$.
2.  **Q4\_K\_M (4.8 GB):** This file size (4.8 GB) fits within the available free memory (5.2 GB). However, the actual memory required during inference will be significantly larger due to activations, KV cache, and runtime overhead, potentially exceeding the remaining free memory.

**Why File Size is Not a Complete Runtime-Memory Estimate:**

File size only estimates the *storage footprint* of the weights. Runtime memory usage depends critically on:
1.  **Quantization Scheme:** Different formats (like Q4\_K\_M vs. Q8\_0) imply different internal data structures and potential memory overheads during computation.
2.  **Activation Memory:** The memory required for intermediate activations during the forward pass is not included.
3.  **KV Cache:** The memory allocated for the Key-Value cache, which scales with the sequence length (prompt + generated tokens), is a dynamic runtime cost.

**Two Quality/Performance Measurements Needed for Comparison:**

1.  **Inference Latency (Time-based):** Measure the wall-clock time required to generate the full sequence (e.g., time to generate the first token, time to generate $N$ tokens). This measures actual performance.
2.  **Peak Memory Usage:** Measure the maximum amount of GPU memory utilized during the entire inference process. This directly assesses the risk of OOM errors on the target hardware.

**Note on Speed:** We cannot claim Q4 is always faster. While smaller file size suggests less data movement, the actual computation speed depends on the hardware utilization and the specific implementation efficiency of the quantization scheme (e.g., how much computation is performed on the compressed data vs. dequantization).

FUNCTION Aggregate_Decode_Speeds(Results):
    // Results is a list of (speed, status) tuples. Status is 'SUCCESS' or 'FAILURE'.
    Successful_Speeds = []
    Failed_Runs = []
    
    FOR EACH Run IN Results:
        SPEED = Run.speed
        STATUS = Run.status  // e.g., 'SUCCESS', 'OOM_WARNING'
        
        IF STATUS == 'SUCCESS':
            Successful_Speeds.APPEND(SPEED)
        ELSE:
            Failed_Runs.APPEND(Run)
            
    // 1. Compute Median for Successful Runs
    IF SIZE(Successful_Speeds) >= 2:
        SORT(Successful_Speeds)
        // Median calculation (for even/odd counts)
        IF SIZE(Successful_Speeds) is odd:
            Median = Successful_Speeds[FLOOR(SIZE(Successful_Speeds) / 2)]
        ELSE:
            Median = (Successful_Speeds[SIZE(Successful_Speeds)/2 - 1] + Successful_Speeds[SIZE(Successful_Speeds)/2]) / 2
        
        RETURN {
            "median_speed": Median,
            "successful_count": SIZE(Successful_Speeds),
            "failed_runs": Failed_Runs
        }
    ELSE:
        // 2. Handling Insufficient Successes
        IF SIZE(Successful_Speeds) == 0:
            RETURN {
                "error": "No successful runs found.",
                "failed_runs": Failed_Runs
            }
        ELSE: // Exactly one success
            RETURN {
                "median_speed": Successful_Speeds[0],
                "successful_count": 1,
                "failed_runs": Failed_Runs,
                "note": "Only one successful run recorded."
            }

## Task 5 — user-visible latency

**Scenario:** Prompt = 2,000 tokens; Generation = 200 tokens.

**Definitions:**

1.  **Time to First Token (TTFT):** The time elapsed from sending the entire prompt to the model until the very first token of the generated response is produced. (Primarily prompt processing and initial forward pass).
2.  **Prompt-Evaluation Throughput:** The rate at which the system processes and evaluates the input prompt itself (often measured in tokens/second or time per prompt).
3.  **Decode Throughput:** The rate at which new tokens are generated during the autoregressive decoding phase (e.g., tokens/second).
4.  **Total Wall-Clock Time:** The total elapsed time from the moment the prompt is submitted until the final generated token is received.

**Symbolic Equation for Total Time:**

$$\text{Total Time} = \text{TTFT} + \text{Time}_{\text{Decoding}}$$

Where:
$$\text{Time}_{\text{Decoding}} = \frac{\text{Generated Tokens}}{\text{Decode Throughput}}$$

**Example Where Optimizing Prompt Processing Barely Changes User Experience:**

**Scenario:** Optimizing Prompt Processing (improving Prompt-Evaluation Throughput) barely changes the user experience.

*   **Context:** 2,000-token prompt.
*   **Optimization:** Improving the efficiency of the initial prompt processing (e.g., by using a faster attention mechanism or better batching for the prompt encoding).
*   **Outcome:** The **Time to First Token (TTFT)** might decrease by $50 \text{ ms}$, but if the actual generation time (which dominates the total experience) is $10$ seconds, the user perceives **no change** in the overall wait time. The improvement is absorbed by the larger decoding phase.
