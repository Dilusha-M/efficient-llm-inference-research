### System Behavior Analysis: 7B Decoder on Hybrid Memory

#### 1. KV Cache Lifecycle: Prefill vs. Decode
The behavior you observe is a classic manifestation of the **prefill-decode asymmetry** in Transformer inference.

*   **Prompt Processing (Prefill):** For a 2,000-token prompt, the model performs a parallel computation. Every token in the prompt is processed to compute its hidden state and update the Key-Value (KV) cache.
    *   *Reuse:* None. All 2,000 positions are computed from scratch.
    *   *Memory Access:* High parallelism; the GPU computes a massive block of weights against a growing scratchpad until the KV cache fills up or memory limits are hit.
*   **Decoding (Autoregressive):** For the requested 300 tokens, the model is autoregressive.
    *   *Reuse:* Only the **most recent** $N$ tokens (typically the context window size, here 2,000) are needed. The model reuses the KV cache for all previous tokens except the current one.
    *   *Computation:* To generate token $t$, the model computes activations only for the new attention heads and the current token's hidden state, then updates the KV cache for position $t$.
    *   *The Bottleneck:* As the conversation grows beyond the GPU's 6GB limit, the system must **page** the KV cache to system RAM (32GB). The GPU must constantly read from the slower CPU memory (DRAM) to update the cache for the next token, creating a serial dependency chain.

#### 2. Hardware Stressors: Throughput vs. Latency
*   **Prompt Processing Stress:** Dominated by **compute-bound** operations on the GPU. The GPU's Tensor Cores process the 2,000 tokens in parallel. High throughput (tok/s) here indicates the GPU compute units are saturated.
*   **Decoding Stress:** Dominated by **memory-bound** operations. The bottleneck is fetching the updated KV cache, not computing new weights.
*   **The Misleading Metric:** A high prompt tok/s does not imply low interactive latency because:
    1.  Prefill and decode use different memory paths. High parallelism in the prefill hides latency in the decode phase.
    2.  Interactive latency is determined by the *slowest* step in the decode loop (usually the GPU waiting for DRAM or the CPU waiting for the GPU). If the KV cache is paged, the decode loop becomes serial and CPU/GPU-bound, regardless of how fast the prefill was.

#### 3. Scaling Effects: 2,000 to 8,000 Tokens
Increasing context from 2,000 to 8,000 tokens exacerbates the memory pressure:
*   **Prefill Behavior:** Computation scales linearly with tokens (2,000 vs. 8,000). The total prefill time increases, but the *relative* impact on total latency drops if the prefill is fast compared to decode.
*   **Decode Behavior & Memory Bandwidth:**
    *   **GPU Limit:** If the KV cache exceeds 6GB, the GPU cannot update the cache efficiently.
    *   **Paging Penalty:** When paging occurs, the system must read ~2KB–4KB of KV data per token from DRAM to update the GPU cache.
    *   **Bandwidth Constraint:** DRAM bandwidth (~20–30 GB/s) is orders of magnitude lower than the GPU's memory bandwidth (hundreds of GB/s). As context grows, the time spent fetching KV data from RAM dominates the token generation time.
    *   **Result:** Latency grows roughly linearly with context size once paging is active, as the decode loop becomes a simple "read memory, compute new token, write memory" loop.

#### 4. Truth vs. Implementation Dependency
*   **Generally True:**
    *   Prefill is compute-bound; decode is memory-bound.
    *   KV cache paging increases per-token latency significantly (often by 5x–10x depending on bus speed).
    *   Increasing context size linearly increases the memory footprint of the KV cache.
*   **Implementation-Dependent:**
    *   **Cache Precision:** Using FP16/BF16 for weights vs. FP8/INT8 quantization changes the effective KV cache size (e.g., 7B @ FP16 is ~28GB, not 6GB). If the model is quantized, the "KV cache does not fit" claim might be an illusion.
    *   **Kernel Support:** Some GPUs support efficient `pageable` kernels that minimize CPU overhead; others require explicit CPU-side buffering.
    *   **Paging Strategy:** Is the system using `torch.cuda.empty_cache()` aggressively (causing thrashing) or a custom heap allocator?
    *   **Kernel Support:** Does the GPU support native sparse attention or continuous batching, which could mitigate the linear latency growth?

#### 5. Diagnostic Measurements & Comparisons
To isolate the bottleneck, perform these three controlled experiments:

1.  **Isolate KV Cache Traffic (GPU vs. RAM):**
    *   *Setup:* Keep context at 2,000 tokens. Force the KV cache entirely onto System RAM (using `torch.cuda.empty_cache()` and offloading layers if necessary, or simulating a smaller GPU).
    *   *Metric:* Measure per-token latency.
    *   *Interpretation:* If latency is 5x higher than on GPU, the bottleneck is **GPU–DRAM memory bandwidth**, not compute.

2.  **Isolate Weight Bandwidth:**
    *   *Setup:* Keep context at 2,000 tokens. Inject artificial latency into the weight loading phase (e.g., by simulating a slow NVMe drive or using a model with significantly larger weights while keeping KV cache size constant).
    *   *Metric:* Measure prefill throughput vs. decode latency.
    *   *Interpretation:* If prefill time dominates total time significantly, the system is **compute-bound** (weights are the bottleneck). If prefill is negligible compared to decode, weights are not the bottleneck.

3.  **Isolate CPU–GPU Transfer:**
    *   *Setup:* Keep context at 2,000 tokens. Run a control where the KV cache fits entirely on GPU (no paging). Compare with a scenario where the cache is paged.
    *   *Metric:* Measure the variance in decode time.
    *   *Interpretation:* If the variance correlates directly with the size of the portion of the cache on RAM, the bottleneck is **CPU–GPU synchronization/transfer overhead**, not just raw bandwidth.

#### Numerical Example: Latency Dominance
Assumptions:
*   Model: 7B Decoder (7 parameters).
*   Precision: FP16 (Weights: 28GB, but assume we are using a quantized version or partial offload scenario where we focus on the active context).
*   Context: 2,000 tokens.
*   GPU: 6GB VRAM.
*   System RAM: 32GB (DRAM).

**Scenario A: Full GPU (2,000 tokens fit in 6GB)**
*   **Prefill:** 2,000 tokens $\times$ 2ms/token (compute bound) = **4,000ms**.
*   **Decode:** 300 tokens $\times$ 5ms/token (GPU compute + small memory access) = **1,500ms**.
*   **Total:** 5,500ms (1.45s per output token).

**Scenario B: Partial Paging (KV cache exceeds 6GB)**
*   **Prefill:** Still **4,000ms** (GPU compute is fast).
*   **Decode:** The GPU must read 2KB of KV data from DRAM for every token.
    *   DRAM Bandwidth limit: ~20 GB/s $\approx$ 2,000 MB/s.
    *   Time per token fetch: 2,000 bytes / 2,000,000,000 bytes/s = 1$\mu$s (negligible).
    *   *However*, the overhead of page table management, CPU-GPU sync, and kernel launches dominates. Let's assume the effective latency jumps to 50ms/token due to synchronization stalls.
    *   **Decode:** 300 tokens $\times$ 50ms/token = **15,000ms**.

**Observation:** Even though the prefill time (4s) remains constant, the decode time jumps from 1.5s to 15s.
