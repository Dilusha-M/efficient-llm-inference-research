### Explanation of Algorithm and Design

**1. One-Pass, O(1) Extra Space**
The algorithm iterates through the input `lines` exactly once. For each line, it creates a dictionary `keys_in_line` to track keys found *within that specific line*. This dictionary size is bounded by the number of unique keys in a single log line (typically very small, like `event`, `tps`, `latency`), satisfying the O(1) space requirement relative to the input size. We do not store the list of all valid records or all lines; we only maintain `count`, `total`, `min_tps`, and `max_tps` as scalar accumulators.

**2. Why Naive Substring Matching Fails**
Naive approaches often use `if 'event=decode' in line and 'tps=' in line:`. This is dangerous for two reasons:
*   **Wrong Event:** A line like `event=decode tps=50 event=ping` might pass the substring check, but logically it's ambiguous or malformed depending on strictness. More critically, a line like `event=decoded` (containing the substring `decode`) would incorrectly match if not split by whitespace first. Tokenization (`split()`) ensures we are looking at actual tokens, not substrings.
*   **Malformed Duplicates:** A naive check might see `tps=50` and `tps=60` and just pick the last one or average them. The prompt requires treating duplicates as **malformed** (invalidating the record). Tokenization and subsequent key counting in a map allows us to detect if a key appears more than once within the same line before validating the value.

**3. Empty-Result Policy**
The prompt specifies returning `None` for `min_tps`, `max_tps`, and `avg_tps` when there are no valid records. My implementation initializes these to `None` and only updates them if a valid record is found. If `count` remains 0, the division `total / count` is avoided, and `None` is returned.
