### 1. Lifecycle of KV Cache: Reused vs. Recomputed
The lifecycle of the KV cache on consumer GPUs is strictly bounded by the **VRAM (Video RAM)** capacity.

*   **Reused:** In the early stages of decoding, the model's **forward pass** (training weights) is computed and stored in the VRAM. The **KV cache** (weights for the current batch of tokens) is also stored here. These are immutable; once loaded, they cannot be overwritten.
*   **Recomputed:** As the **forward pass** completes and the model generates new tokens, the new weights must be computed. Crucially, if the **KV cache is not fully loaded in VRAM**, the model must **recompute** the weights on the host (CPU/GPU). This is why the latency spikes as the conversation grows; the model must "fetch" the next batch of weights from the system RAM to the VRAM during inference.

### 2. Resource Stress and Latency Mechanics
**Prompt Processing vs. Interactive Latency:**
Prompt processing (the encoder generation phase) is a **write-through** operation. The entire sequence of text is pushed onto the host CPU and stored in VRAM before execution begins. This creates a massive **write latency** and bandwidth bottleneck because the host CPU must process thousands of tokens simultaneously.

**Latency vs. Throughput:**
A high **token/s** rate (e.g., 3,000 tokens/sec) represents **throughput**, not latency. Latency is the time spent waiting for the next token. If the prompt takes 10 seconds to generate, but the subsequent decoding takes 1 second per token, the total latency is 11 seconds, even though throughput is 100 tokens/sec. The prompt processing overhead dominates the total execution time.

### 3. Context Scaling (2k → 8k Tokens)
Increasing context from 2,000 to 8,000 tokens changes the decoding strategy from **prefill-only** to **prefill-decode** or **prefill-decode-reuse** depending on GPU VRAM.

*   **Prefill vs. Decode:**
    *   **Prefill:** The model generates the initial 2k tokens and holds them in VRAM.
    *   **Decode:** As the model generates the remaining 6k tokens, it must compute the new weights.
*   **Memory Bandwidth:**
    *   If VRAM is small (e.g., 16GB), the model must constantly "fetch" the next 2k weights from the host. The **write bandwidth** of the host CPU becomes the limiting factor.
    *   If VRAM is large (e.g., 64GB), the model can fully prefill the 8k tokens. The bottleneck shifts to **compute bandwidth** (GPU compute cycles) and **memory bandwidth** (moving 8k weights to VRAM).
*   **Latency Spike:** As the context grows, the ratio of **Recompute Latency** to **Write Latency** increases. The host CPU spends more time fetching new weights to VRAM, causing the per-token latency to climb sharply.

### 4. Separating Claims by Implementation Detail
*   **Generally True:**
    *   VRAM is a memory bottleneck, not a compute bottleneck.
    *   Latency is dominated by write latency, not compute latency.
    *   Context size increases compute latency only if the model is forced to recompute weights (e.g., small VRAM).
*   **Depends on Implementation:**
    *   **Cache Precision:** If the kernel uses a 256-bit or 128-bit cache, the write bandwidth is significantly higher than a 64-bit cache.
    *   **GPU Offloading:** If the GPU offloads the KV cache computation to a separate accelerator, the write latency drops, potentially relieving the bottleneck.
    *   **Page Faults:** If the system is configured to page cache to disk, write latency increases linearly with context size.

### 5. Proposed Measurements (Controlled Comparisons)
To isolate the specific bottleneck, run three distinct comparisons:

1.  **Write Bandwidth vs. Compute Bandwidth:**
    *   **Metric:** `Latency = Write Latency / Tokens/sec`.
    *   **Action:** Measure latency at 2k vs. 8k tokens while keeping the prompt fixed.
    *   **Result:** If `Write Latency` dominates, the bottleneck is the host CPU writing to VRAM. If `Compute Latency` dominates, the bottleneck is the GPU compute cycles.

2.  **Prefill vs. Decode Latency:**
    *   **Metric:** `Total Latency = (Prefill Latency) + (Decode Latency)`.
    *   **Action:** Measure latency at 2k tokens (prefill-only) vs. 8k tokens (prefill-decode).
    *   **Result:** If total latency increases linearly with context, the bottleneck is memory access. If it plateaus, the bottleneck is compute.

3.  **Kernel Cache Size Effect:**
    *   **Metric:** `Write Latency` (measured with 128-bit cache vs. 64-bit cache).
    *   **Action:** Keep the same context size but change the kernel's cache granularity.
    *   **Result:** A significantly smaller cache size will show a more dramatic increase in write latency, proving the write bandwidth is the critical path.
