### 1. Lifecycle of the KV Cache: Reused vs. Recomputed

In this architecture, the `KV` cache acts as a "compute proxy." It is a **shared, non-sequential memory block** on the GPU that holds a view of the query's key-value pairs. The lifecycle proceeds as follows:

*   **Pre-prompt (Reused):** As soon as the prompt is received, the GPU fetches the `KV` cache entry for the current key. This entry is a snapshot of the *previous* token's state. If the `KV` size fits within the 32 GB RAM, this entry is **reused** immediately. If it overflows, the system must evict the old entry and load a new one.
*   **Token-by-Token (Recomputed):** Once a token is generated, the `KV` cache entry must be **recomputed** for that new token. The GPU calculates the new key-value pairs based on the new prompt. Because this data is not cached in memory but computed on the fly, it consumes **compute cycles (FLOPs)** rather than memory bandwidth.
*   **Lifetime:** A new `KV` entry is only recomputed when the prompt changes. If the prompt is identical to the previous one, the `KV` entry is reused.

**Key Distinction:** The 32 GB RAM holds the *reused* snapshots. The 6 GB GPU holds the *current* computed values for the active prompt. The 2,000 token prompt likely contains a mix of previously computed entries and new recomputed entries, causing the bottleneck to appear only when the new recomputed entries exceed available RAM.

### 2. Resource Separation: Prompt vs. Decoding

Prompt processing and token-by-token decoding stress distinct hardware layers:

*   **Prompt Processing (The 7B Model):** This is a heavy **inference** task. The 7B model requires massive **compute cycles** and **memory bandwidth** to process the text. Even with 32 GB RAM, the 7B model is too large for the cache, forcing it to hold a single large `KV` entry.
*   **Token-by-Token Decoding (The 300 Tokens):** This is a **workload** task. It is light on compute and memory compared to the prompt. However, it is extremely **bandwidth intensive**. Generating 300 tokens from scratch requires massive data movement and processing power.

**Why High Prompt Tokens $\neq$ Low Latency:**
A high `prompt tok/s` rate is only a fraction of the total latency. Latency is determined by the **slowest path** in the pipeline. If the system is bottlenecked by the generation of 300 tokens, the latency will skyrocket regardless of how fast the prompt processing is. The prompt processing speed cannot slow down a generation bottleneck.

### 3. Context Shift Effects (2,000 → 8,000 Tokens)

Increasing context from 2,000 to 8,000 tokens changes the load profile:

*   **Prefill Behavior (Reused Entries):**
    *   **2,000 Tokens:** The system might use all 32 GB for the first 2,000 tokens. By the 2,001st token, the 32 GB might overflow, forcing a new eviction. This creates a small number of "expensive" `KV` entries.
    *   **8,000 Tokens:** The 32 GB will be fully utilized for the entire 8,000 tokens. All 8,000 entries are **reused**, meaning the GPU spends negligible cycles computing the key-value pairs. Latency becomes dominated by the 6 GB memory bandwidth required to fetch and store the full context.
*   **Decode Behavior (Recomputed Entries):**
    *   The 300 tokens generated during the 8,000-token context will generate a massive number of new recomputed `KV` entries. The GPU will compute these new entries, likely exceeding its 6 GB RAM capacity.
*   **Memory Bandwidth:** The transition creates a massive spike in **memory bandwidth** requirements. Fetching 8,000 full `KV` entries simultaneously (or repeatedly evicting and re-fetching) will saturate the 32 GB RAM, causing the system to timeout or freeze.

### 5. Benchmarking Strategy

To isolate the true bottleneck, run the following comparisons:

1.  **Memory Bandwidth (The "KV" Test):**
    *   *Metric:* `Memory Bandwidth Required / Time Consumed`.
    *   *Action:* Simulate a 7B model running with a 2,000-token prompt. Measure how much RAM bandwidth is needed to cache the `KV` entries for the 2,000 tokens (assuming they fit in 32GB). Then, simulate the same prompt with an 8,000-token prompt. If the bandwidth requirement increases significantly (due to needing more RAM for the larger context), the bandwidth is the cause.

2.  **Compute Cycle Count (The "Prompt" Test):**
    *   *Metric:* `Total FLOPs / Prompt Length`.
    *   *Action:* Run the prompt with a 2,000-token prompt and 8,000-token prompt. Calculate the total FLOPs spent on the GPU for the prompt. If the 8,000-token prompt incurs significantly more FLOPs than the 2,000-token prompt, the prompt processing is the bottleneck.

3.  **Kernel Throughput (The "Generation" Test):**
    *   *Metric:* `Tokens Generated / Token Time`.
    *   *Action:* Measure the throughput of the 7B kernel under the 2,000-token prompt. Compare this to the throughput of the same kernel under the 8,000-token prompt. If the kernel cannot process the 8,000 tokens, the generation bottleneck exists regardless of the RAM.

**Numerical Example:**
Assume the 2,000-token prompt fits in 32 GB. The system runs at a constant `prompt tok/s` (e.g., 50 tokens/s).
*   **Scenario A (Prefill):** The GPU holds 2,000 reused `KV` entries. Latency = `prompt tok/s` + `compute cost per token`.
*   **Scenario B (Decode):** The GPU holds 8,000 reused `KV` entries. Latency = `prompt tok/s` + `compute cost per token`.

If the 32 GB is fully utilized in Scenario B, the latency is dominated by the **memory bandwidth** needed to hold 8,000 entries (typically 64 GB/s for 32-bit float64). If the 32 GB is insufficient to hold 8,000 entries (e.g., only 12 GB available), the system will time-out during the decode phase. The key is measuring the **memory bandwidth cost** for the context size.
