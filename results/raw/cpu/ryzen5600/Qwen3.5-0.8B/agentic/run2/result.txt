## 1. Requirements and Invariants

### Inputs and Artifacts
The system receives the following inputs for every benchmark run:
*   **Configuration**: Model name (alias), backend type (CPU/CUDA/Vulkan), hardware label (e.g., `m400`, `nvidia-a100`), context size, generation limit (256), temperature (0.7), thread count (1).
*   **Workload Prompt**: A specific prompt string (e.g., `chat`, `batch`, `coding`) defining the task.
*   **Environment Metadata**: The default context, generation limit, temperature, and CPU thread count.
*   **Hardware Metadata**: A string identifying the specific GPU or CPU architecture (e.g., `gpu:ml400`, `cpu:1`).
*   **Model File**: The source code path or file ID of the model to run.
*   **Backend Info**: The internal backend class or identifier (e.g., `backend:llama`).
*   **Driver Environment**: OS driver details (e.g., `driver:linux`).
*   **Output**: The raw `response.txt` (text output only) and performance metrics.

### Success/Failure States
*   **Success**: The model successfully completes the workload execution, generating text output, and metrics are written to `performance.json` and `response.txt`.
*   **Failure**: The model fails to complete the workload execution due to internal error or hardware failure, or the system exits early due to timeout/oom. The `response.txt` remains empty or contains a generic error message.

### Experimental Identity Tuple
*   **Identity**: `(ModelAlias, Backend, DeviceType, ContextSize, GenLimit, Temperature, ThreadCount, OutputPath, RunId)`

### Ambiguity to Resolve
**Ambiguity**: "Fixed workload prompts".
*   **Constraint Violation**: The specification states "Workloads are `chat`, `batch`, `coding`, `summarization`, `agentic`, and `world_knowledge`". However, the prompt might vary.
*   **Resolution**: The runtime environment must support **runtime prompt override**. The configuration file (e.g., `config.yaml`) should allow users to specify a dynamic prompt string for a specific run. This ensures that even if the static list is incomplete, a valid prompt can be injected for any specific request.

## 2. State-Machine Workflow

The system lifecycle is defined as follows:

1.  **Validation**:
    *   Check `config.yaml` for required fields.
    *   Verify model file exists.
    *   Parse configuration for constraints (context, temp, threads).
    *   Validate hardware label against supported device types (e.g., `m400` supports `gpu:ml400`).
    *   **Exit on Failure**: If model not found, hardware mismatch, or required config missing, return `RUNNING_STATUS_FAILED`.

2.  **Launch**:
    *   Initialize backend context (default context 4096, gen limit 256, temp 0.7, threads 1).
    *   Instantiate `llama.cpp` backend class.
    *   Execute workload: `run_workload(prompt, model_path, context, gen_limit, temp, threads)`.
    *   **Exit on Failure**: If workload fails, set `RUNNING_STATUS_FAILED`.

3.  **Monitoring (Sampling)**:
    *   If `monitor` is enabled and sampling is active, wait for the next sampling cycle.
    *   **Exit on Failure**: If monitoring fails or the sampling rate is 0, set `RUNNING_STATUS_FAILED`.

4.  **Process Exit**:
    *   **Timeout**: If the backend waits for the next sampling cycle but no new sample is received, return `RUNNING_STATUS_TIMEOUT`.
    *   **OOM**: If the backend detects OOM error or memory exhaustion, return `RUNNING_STATUS_FAILED`.
    *   **Partial Output**: If the backend returns partial output (e.g., only 100 bytes for a 256 token limit), the system must handle this gracefully.
    *   **Monitor Failure**: If `monitor` is unavailable, set `RUNNING_STATUS_FAILED`.
    *   **Exit**: Return `RUNNING_STATUS_DONE` with the full `response.txt` and metrics.

5.  **Finalization**:
    *   Write `performance.json` with raw metrics and `response.txt`.
    *   Mark `RUNNING_STATUS_DONE`.

## 3. Auditable Design

### Shell/Python Component Boundaries
*   **Python Layer**: Handles configuration parsing, model initialization, backend instantiation, and orchestration of sampling cycles.
*   **Shell Layer**: Manages environment variables, handles file I/O for `performance.json`, and orchestrates the "run" process.
*   **Output**: `stdout` is redirected to `response.txt` by the Python layer; `stderr` is ignored or logged to the shell for debugging.

### Metadata Schema
*   **Run Metadata**: A JSON object containing:
    ```json
    {
      "uuid": "uuid-001",
      "model_alias": "model_alpha",
      "backend": "llama.cpp",
      "device_type": "gpu:ml400",
      "context": 4096,
      "gen_limit": 256,
      "temperature": 0.7,
      "threads": 1,
      "prompt": "chat",
      "hardware_label": "m400",
      "output_path": "/tmp/benchmark_results.json",
      "run_id": "12345",
      "status": "completed"
    }
    ```

### Atomic-Write or Partial-File Conventions
*   **Partial Output**: If `response.txt` is smaller than `gen_limit`, the system does not crash. Instead, it logs a specific status note in `performance.json` (e.g., `"status": "partial"`). The `response.txt` is still available for manual audit.
*   **Metadata**: The `run_id` and `status` are atomic writes to disk.
*   **Cleanup**: A cleanup phase occurs upon `RUNNING_STATUS_DONE` to delete temporary metadata files.

## 4. Analysis Integrity

### Preventing a Failed Run
*   **Token Count Mismatch**: A parser should track the *actual* generated tokens (excluding system overhead) to compare against the fixed `generation limit`.
*   **Variable Token Count**: If the parser uses a fixed counter, it will incorrectly flag a partial completion as failure if the actual tokens > limit.
*   **Fix**: The parser must parse the `response.txt` content to count real tokens. It should compare this count against the limit. If the count is less than the limit, the output is truncated (handled in State Machine). If it exceeds, the status must be recorded as `RUNNING_STATUS_FAILED`.

### Unknown Output Formats
*   **Parser Strategy**: The parser must implement a fallback mechanism for unknown llama.cpp output formats.
*   **Action**: If the parser cannot determine the structure of `response.txt`, it should treat the entire file as raw metadata, parse it into a structured format (e.g., key-value pairs for metrics), and record the file size and header.
*   **Result**: The system will not crash, but it will record the raw data. In a production scenario, this might be a "truncated output" error that requires manual investigation.

## 6. Pre-merge Review: Risk Flaws and Fixes

### 1. Ambiguity Resolved: "Fixed Workload Prompts"
**Flaw**: Hardcoding a static list of workloads without runtime override capability.
**Fix**: Replace the static list with an environment variable or runtime argument mechanism (`LLEMBENCHMARK_WORKFLOW` env var). The code must parse this environment variable to decide which workload to execute. If the environment variable is missing, the code defaults to `chat`, maintaining backward compatibility.

### 2. Token Count Inaccuracy
**Flaw**: Using a fixed token counter for performance output without validating actual token generation.
**Fix**: Integrate a custom tokenizer (or use llama.cpp's built-in tokenization) to parse `response.txt` and count actual tokens. Update the `generation_limit` in the configuration to reflect the *actual* output size rather than the hardcoded limit. This ensures throughput comparisons are accurate (e.g., 1000 tokens / 100MB = 10 tokens/s) rather than arbitrary units.

### 3. Hardware Label Inconsistency
**Flaw**: Hardcoding a specific hardware string (e.g., `m400`) instead of allowing the system to infer it from the `device_type` (e.g., `gpu:ml400`).
**Fix**: In the hardware metadata parsing logic, map the `device_type` (e.g., `gpu:ml400`) to the correct hardware label (e.g., `m400`). This ensures the system can distinguish between a generic GPU and a specific model card, preventing errors when loading specific model files for that device.
