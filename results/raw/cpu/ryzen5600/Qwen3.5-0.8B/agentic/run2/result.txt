## 1. Requirements and Invariants

### Inputs

### Artifacts
*   **Raw Output File:** `response.txt` containing the full text of the prompt-prompt response (including internal monolog).
*   **Performance Metrics:** A structured text file or JSON containing `duration_ms`, `tokens_processed`, `tokens_generated`, `errors_count`, and `monitor_events` (if present).
*   **Process ID (PID):** The PID of the running llama.cpp process.
*   **Failure State:** A boolean flag (`is_failed`) indicating if the process terminated due to an exception or clean exit.

### Success/Failure States
*   **Success:** Process completes with exit code 0. `response.txt` is present and readable. `is_failed` is `false`.
*   **Failure:** Process exits with non-zero code. `response.txt` may be absent or contain partial/invalid text depending on the crash point. `is_failed` is `true`.

### Experimental Identity Tuple
*   `Identity = (ModelAlias, Backend, ContextLimit, GenLimit, Temperature, ThreadCount, MetadataFile, MonitorList)`
*   *Note: The Identity tuple is the set of all parameters required to construct the benchmark runner. If any parameter changes, the identity tuple must update to reflect the new architecture state.*

### Ambiguity to Resolve
**Ambiguity A: The Definition of "Failed Model Run" vs. "Monitor Failure" vs. "Runtime Error"**
*   The specification states: *"A model process may fail after creating partial output."*
*   **Resolution:** The distinction between a process exit due to a model error vs. a monitor failure (e.g., a missing monitor definition) must be explicit in the logic.
    *   *Example:* If the monitor is missing, the process should still terminate normally (likely with a fatal error in llama.cpp), but the runner should record a `monitor_events` entry with a "Monitor Not Found" event.
    *   *Example:* If the monitor exists but is not running, the process might exit cleanly or hang. The runner must distinguish between a "Missing Monitor" state (which is usually fatal) and a "Monitor Not Running" state (which might be recoverable).
    *   *Specific Fix:* Implement a check in the `process_exit()` handler: `if monitor_events is not None and monitor_events.get("type") == "monitor_not_found": raise RuntimeError("Monitor not found: <name>");`

### Invariants (Hard Constraints)

## 2. State Machine Workflow

The lifecycle of a benchmark run is defined as follows:

1.  **Validation Phase:**
    *   Load `.llamaconfig`.
    *   Load `.metadata_file` (if present).
    *   Check for required metadata fields.
    *   Verify environment flags do not override config defaults (e.g., `CUDA_VISIBLE_DEVICES` must not overwrite the specified GPU list).
    *   **Result:** If validation fails, exit with `is_failed = True` and no output.

2.  **Launch Phase:**
    *   Construct the llama.cpp command string: `llama.cpp --model <model_alias> --config <config_path> --task <workload_prompt> --config <config_path> --context <context> --gen-limit <gen_limit> --temperature <temp> --threads <thread_count>`.
    *   Spawn the process.
    *   **Result:** If the process crashes before spawning, `is_failed = True`, `response.txt` is missing, and `is_failing` flag is set.

3.  **Execution Phase:**
    *   llama.cpp executes the workload and generates text.
    *   llama.cpp prints internal monolog, which goes to `stdout`.
    *   **Result:** `response.txt` contains the output. If `is_failing`, `response.txt` is missing.

4.  **Monitoring Phase (Conditional):**
    *   llama.cpp sends a message to the configured monitor (if present) or sends a signal to stop it.
    *   llama.cpp waits for the monitor to complete.
    *   **Result:**
        *   If monitor stops: `is_failing = True`.
        *   If monitor finishes: `is_failing = True` (unless monitor was missing).
        *   If monitor is never started: Monitor events recorded. `is_failing = True`.

5.  **Process Exit Phase:**
    *   llama.cpp exits with code 0 or non-zero.
    *   **Result:** `is_failing` flag is set. If `is_failing`, `response.txt` is missing.

6.  **Finalization Phase:**
    *   Gather metrics.
    *   Check for errors in `response.txt`.
    *   Write `response.txt` to disk.
    *   Write `performance_metrics.json` (or similar).
    *   Write `metadata_file` to disk.
    *   **Result:** Success only if `response.txt` exists and is valid. Failure if any artifact is missing or corrupted.

### Special Scenarios
*   **Timeout:** llama.cpp may timeout. The process exits with code 128 or similar. `is_failing = True`. `response.txt` is missing.
*   **OOM:** llama.cpp may hit memory limits. `is_failing = True`. `response.txt` is missing.
*   **Malformed Performance Output:** If `tokens_processed` does not match `tokens_generated`, the parser flags this.
*   **Monitor Failure:** If the monitor is not running, it might exit gracefully (if config allows) or crash. The logic must distinguish between "Monitor Failed to start" (terminate) and "Monitor Failed to complete" (record event).

## 3. Auditable Design

### Shell/Python Component Boundaries
*   **Python Component (Runner):**
    *   Reads `.llamaconfig` from a dedicated file (e.g., `/app/config/llamaconfig.yaml`).
    *   Reads `.metadata_file` from a dedicated file (e.g., `/app/metadata/monitor_config.json` or `metadata.txt`).
    *   Parses command-line arguments.
    *   Spawns the process.
    *   **No direct access to stdout/stderr of llama.cpp.**
    *   Collects `response.txt` and `performance_metrics.json`.
*   **Shell Wrapper (Optional):**
    *   Handles argument parsing for specific task types (`chat`, `batch`, etc.) to ensure the prompt string is correct.
*   **No Direct Memory Access:** The runner must not pollute the memory of llama.cpp or the monitor process.

### Metadata Schema
The `metadata_file` must be a valid JSON object structure, adhering to the schema below. The schema is generated automatically based on the `.metadata_file` content.

```json
{
  "hardware": {
    "name": "NVIDIA A100",
    "gpu_version": "24.0",
    "gpu_layers": ["cuda", "mps", "nvcc"],
    "thread_count": 384
  },
  "monitor_config": {
    "name": "monitor_alpha",
    "enabled": true,
    "sample_rate": 10,
    "timeout_ms": 30000
  }
}
```

### Atomic-Write and Partial-File Conventions
*   **Atomic Writes:** The `performance_metrics.json` file is written atomically using `f.write()` followed by `f.flush()` and `f.sync()`. This ensures that if `response.txt` is partially written before `performance_metrics.json` is written, `performance_metrics.json` will be valid and readable.
*   **Partial File:** If `response.txt` is missing but `performance_metrics.json` is present, the runner cannot proceed to the next run unless it can recover the missing content.
*   **Metadata File:** The `metadata_file` is read once, stored, and never modified. Changes must be applied via a "Rebuild" command or by re-reading the file.

### Preservation of Output
*   **stdout/stderr:** The raw output of llama.cpp is written to `stdout` (via `log_message`). This is preserved in `response.txt` by the runner.
*   **Prompt:** The exact prompt string (`<prompt>`) is written to `response.txt` and is immutable.

## 4. Analysis Integrity

### Preventing Variable Generated-Token Count Misleading Throughput
A common pitfall is comparing `tokens_generated` with `tokens_processed`. If the model generates tokens but the prompt has a trailing newline that llama.cpp ignores, `tokens_processed` might be lower than `tokens_generated`.
*   **Fix:** The parser must count **all** characters in the response, including newlines.
    *   Formula: `tokens_processed = len(response_text.split('\n').join('\n'))`.
    *   If the prompt ends with a newline, that newline must be counted in the total.
*   **Unknown Output Formats:** If llama.cpp outputs a structure like `{"output": "text"}` instead of plain text, the parser must strip the JSON wrapper and count the resulting text.
    *   *Parser Logic:*
        ```python
        raw = reader.read()
        # Strip JSON if present
        # Remove leading/trailing newlines
        # Split by newlines, join with newlines
        processed = raw.split('\n').join('\n')
        # Calculate token count
        ```

### Handling Missing or Sampled Monitors
If a monitor is not running, the process might exit cleanly (if config allows) or hang. The runner must distinguish these.
*   **Detection:** Check `monitor_events` in `performance_metrics.json`.
*   **Logic:**
    *   If `events` is empty and `monitor_name` is defined -> Record `monitor_not_found` event.
    *   If `events` is not empty -> Record `monitor_not_found` event.
    *   If `events` is `[]` -> Record `monitor_not_found` event.
*   **Result:** `is_failing` remains `True` regardless of the monitor's health status, but the performance metrics accurately reflect that the monitor was not running.

## 5. Test Plan

1.  **Backend Failure (Model Error):**
    *   *Scenario:* Define a model alias that does not exist in the config file.
    *   *Expected:* Process crashes immediately. `is_failing = True`. `response.txt` is missing. `performance_metrics.json` is missing. `metadata_file` is missing.

2.  **Missing Monitor:**
    *   *Scenario:* Define a monitor name in `.metadata_file` but do not include it in the `monitor_config` section.
    *   *Expected:* Process terminates (likely with fatal error or graceful stop depending on config). `is_failing = True`. `response.txt` is missing. `performance_metrics.json` has a `monitor_events` list with `type` set to `"monitor_not_found"`. `metadata_file` is missing.

3.  **Prompt Containing Newlines:**
    *   *Scenario:* The `workload_prompt` contains embedded newlines.
    *   *Expected:* `response.txt` must contain the prompt exactly as written, including newlines. The parser must handle splitting by newlines correctly. `tokens_processed` should include all characters.

4.  **Partial Output:**
    *   *Scenario:* `response.txt` is empty or truncated (e.g., monitor stopped early).
    *   *Expected:* The parser checks for completeness. If truncated, it should still report the missing monitor event. `is_failing = True`. `response.txt` is missing.

5.  **Changed Prompt Hash:**
    *   *Scenario:* Change the prompt string in `.llamaconfig` without updating the actual prompt string in the run.
    *   *Expected:* `response.txt` contains the old prompt, not the new one. The parser validates that `response.txt` matches the prompt in the config. If it doesn't, the runner should fail.

6.  **Changed Prompt Hash (via Rebuild):**
    *   *Scenario:* Change the prompt in `.llamaconfig` and re-run the benchmark.
    *   *Expected:* `response.txt` reflects the new prompt. `metadata_file` must reflect the new config. The "Changed Prompt" test ensures that a change in config is tracked and reflected in the output.

## 6. Pre-merge Review: Risks and Fixes

### 1. The Ambiguity Resolution: Failed Model Run vs. Monitor Failure
*   **Risks:** Ambiguity in determining if a monitor failure is recoverable or fatal. If a monitor is missing, does the runner report a failure or just a missing monitor event?
*   **Fix:** Introduce a specific flag `monitor_status` in the metadata file. If `monitor_name` is present and `monitor_status` is `missing`, the process should exit with a fatal error and `is_failing = True`. If `monitor_status` is `running` or `stopped`, the process may exit cleanly. The runner must check `monitor_status` before declaring a failure.

### 2. The Token Count Ambiguity
*   **Risks:** Difficulty in comparing throughput if the prompt has newlines or if llama.cpp omits them.
*   **Fix:** Implement a strict parser that explicitly counts all characters. Do not rely on `len(response.txt)`. Ensure the count includes newlines found in the prompt. Use a fixed-size buffer or line-by-line parser to be precise.

### 3. The Metadata File Corruption Risk
*   **Risks:** If the `.metadata_file` is modified after a run (e.g., by a script), the runner must re-read and re-apply the changes. If the runner cannot read the file, it fails.
*   **Fix:** Enforce a "Rebuild" command on the filesystem before the runner starts a new run. The runner must check if the file exists and read it. If not, it should fail with a clear error message, preventing silent corruption. Additionally, implement a "Reload" flag in config that triggers a re-read of the metadata file.
