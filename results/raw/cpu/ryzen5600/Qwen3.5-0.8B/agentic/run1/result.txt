# State Machine Workflow

**Lifecycle:**
1.  **Validation**: Parse `config.yaml`. Validate model/backend/config constraints.
2.  **Launch**: Execute `llama.cpp` with the determined `backend` and `model_name`.
3.  **Processing**:
    *   **Wait**: Monitor `llama.cpp` process status.
    *   **Generate**: Run the model (or fallback).
    *   **Wait**: Monitor process status.
    *   **Parse**: Decode `response.txt`.
4.  **Metrics**: Extract tokens/sec, calls, vars from `response.txt`.
5.  **Hardware Check**: Verify GPU layers/IDs against `metadata.json`.
6.  **Finalization**:
    *   **Success**: Write `metadata.json` + `metrics.json` + `response.txt` to disk.
    *   **Failure**: Log error to `logs/run_*.txt`. Write `response.txt` to disk (if not failed process) + `metadata.json` (if monitor failed).

**Events:**
*   **Timeout**: Model waits > 30 seconds without completion. `process_status` becomes "timeout". `metrics` are calculated based on partial output.
*   **OOM**: Process crashes. `process_status` becomes "oom". `metrics` are discarded.
*   **OOMKilled**: Process killed by OS. `process_status` becomes "oomkilled". `metrics` are discarded.
*   **Monitor Failure**: Monitor service restarts or fails. `metrics` are missing/0.
*   **Malformed Output**: `response.txt` contains errors (e.g., `# Invalid`, `# Mismatched`).
*   **Partial Output**: Model stops before hitting generation limit. `response.txt` is truncated.
*   **Failed Process**: `response.txt` is empty or truncated.

**Special Handling:**
*   **Monitor Sampling**: If a monitor is defined but not running, the "metrics" field in `response.txt` is ignored or set to `null`.
*   **Partial Run**: If the model generates < 256 tokens, the `generation_limit` is not enforced in the metric calculation. The parser treats the output as a valid response within the limit, but metrics reflect only the generated text.

# Auditable Design

**Component Boundaries:**
1.  **CLI Interface (`runner.py`)**:
    *   **Read Config**: Reads `config.yaml`, validates model/backend compatibility, computes `prompt_hash` (using hardcoded string if missing, or parsing `config.yaml` if provided).
    *   **Launch**: Uses `llama.cpp` with `--model` and `--backend`.
    *   **Monitor**: Uses `llama.cpp` monitor API.
    *   **Parse**: Reads `response.txt`, validates format, extracts tokens/sec/calls/vars.
2.  **Metadata Generator (`meta_generator.py`)**:
    *   **Writes**: Writes `metadata.json` (model, backend, hardware, context, limit, temp) + `metrics.json` (if valid).
3.  **Logger (`logger.py`)**:
    *   **Writes**: Writes `logs/run_*.txt` only on success/failure.
    *   **Preserves**: Captures `stdout` and `stderr` on success (or captures `response.txt` on failure) to avoid modifying the raw output.

**Metadata Schema:**
*   **`metadata.json`**:
    ```json

      "temperature_override": 0.7,
      "gpu_layers": 4,

        "model": "llama.cpp",

        }

    }
    ```

**Atomic-Write Convention:**
*   **Files**: Write `metadata.json`, `metrics.json`, and `response.txt` to a dedicated `/run/` directory using `atomic_write` (or `flock` with atomic mode).
*   **Log Files**: Write `logs/run_*.txt` using `atomic_write`.
*   **Prompt**: Write `prompt.txt` containing the raw prompt string using `atomic_write` (or `flock`).

**Preserved Output:**
*   **Success**: `stdout` is redirected to `stdout.txt` (or `stdout.txt` if `response.txt` is empty). `stderr` is logged separately to `logs/`.
*   **Failure**: `stdout` is discarded (or captured in `stdout.txt` if `response.txt` is empty). `stderr` is logged separately.

# Analysis Integrity

**Variable Generated-Token Count:**
*   **Risk**: If `tokens_per_sec` is calculated as `total_tokens / time`, and the model generates less tokens than the generation limit (e.g., 200 vs 256 limit), the throughput metric will artificially inflate.
*   **Mitigation**: The parser must check if the model generated fewer than the `generation_limit` tokens. If so, the `tokens_per_sec` value must be capped at a reasonable baseline (e.g., 100 tokens/sec) or treated as "partial". The specification requires distinguishing a failed run from missing metrics, implying metrics should be robust. To prevent misleading comparisons, the `tokens_per_sec` metric should be calculated only if the response length exceeds a threshold (e.g., 100 tokens).

**Unknown Output Formats:**
*   **Risk**: If `response.txt` contains garbage, `# Invalid`, or an unexpected number of lines, the parser cannot reliably extract `# Tokens: <N>`.
*   **Mitigation**: The parser must perform a strict format check. If the count is missing, the `tokens_per_sec` metric must be set to `null` or `0`, and the `tokens_per_sec` value in `metrics.json` must be absent (null/empty object). The parser should not attempt to parse `# Tokens: 1500` if it doesn't know how to parse the model's specific format.

# Pre-merge Review

**Three Highest-Risk Design Flaws:**

1.  **Ambiguous Prompt Hash Calculation**: As noted, the specification requires hashing the prompt, but the absence of a defined hash source makes the parser unable to distinguish between a new prompt run and an old one (or modify the old one).
    *   *Fix*: Hardcode a static, unique, pre-computed SHA256 hash of the prompt used in the first successful run of the agent (e.g., generated from the prompt in `config.yaml` directly if missing, or a fixed string if explicitly defined).

2.  **Dynamic Capping of Tokens Per Second**: The design implies that if the model generates fewer tokens than the generation limit, the throughput metric should reflect that limitation. However, if the model generates more tokens than the limit (e.g., 300 vs 256), the metric becomes misleading, potentially overestimating performance.
    *   *Fix*: Add a guard clause in the parser: Calculate `tokens_per_sec` only if the generated response length exceeds a safe baseline (e.g., 100 tokens). If the response is shorter than this baseline, set the metric to `null` or `0` to prevent misleading comparisons.

3.  **Hardcoded `stdout.txt` Capture**: The design specifies that stdout/stderr must be preserved on success. While this is good for debugging, if the `llama.cpp` binary is updated or modified, the exact prompt used to generate `response.txt` changes, requiring `stdout.txt` to be updated. If `stdout.txt` is not updated, it becomes an audit trail issue for the agent.
    *   *Fix*: Modify the architecture to capture `stdout` and `stderr` (or `response.txt`) from the `llama.cpp` process **before** writing metadata. Use `log_capture` or `popen` with `stdout` redirected to a temporary file before writing the final report. Ensure that even if `response.txt` is empty, the `stdout` captured from the process is preserved in the metadata.
