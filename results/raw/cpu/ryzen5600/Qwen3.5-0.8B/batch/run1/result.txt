## Task 3 — Robust Aggregation
**Assumptions:**

*   "Out-of-memory warning" indicates failure in the last run.

def robust_aggregate_decodes():
    # 1. Initialize a set to track failed runs to ensure visibility
    failed_runs = set()
    
    # 2. Gather data from all runs
    data = []
    for i in range(3):
        # Simulate the run
        run_id = i + 1
        # Simulate successful decode: 42.0, 41.5, 8.0 tok/s
        # The OOM warning indicates this specific run failed
        success_count = 3
        avg_speed = (42.0 + 41.5 + 8.0) / 3
        data.append({
            "run_id": run_id,
            "success": True,
            "speed": avg_speed
        })
    
    # 3. Filter out failed runs
    successful_runs = [d for d in data if d["success"]]
    
    # 4. Compute Median
    if len(successful_runs) < 2:
        # If fewer than 2 runs succeed, the median cannot be computed.
        # We must explicitly state this.
        print(f"Error: Not enough successful runs ({len(successful_runs)}) to compute the median.")
        return None
    
    successful_runs.sort(key=lambda x: x["speed"])
    median_speed = successful_runs[len(successful_runs)//2]["speed"]
    return median_speed

# Example Usage

## Task 4 — Validity Audit
**Assumptions:**
*   CPU: 8 threads (likely 2 threads per thread).
*   CUDA: Offloads all layers.
*   Vulkan: Offloads all layers.
*   Context: Run 3 times.

**Threats and Controls:**

1.  **Hardware-Software Concurrency Conflict:**
    *   **Threat:** CUDA offloading all layers to the GPU means the GPU handles the computation. However, the CPU might still be processing 8 threads (or the system scheduler might queue these threads). If the CUDA kernel is large and the CPU is busy, the GPU might not get the necessary memory bandwidth to match the CPU's throughput, leading to latency spikes or underperformance.
    *   **Control:** Monitor the **CPU-to-GPU bandwidth ratio** during inference. If the GPU is saturated but the CPU cannot feed it enough data, performance drops. Verify that the GPU memory bandwidth is sufficient relative to the CPU's maximum throughput.

2.  **Latency vs. Throughput Misalignment:**
    *   **Threat:** The prompt asks for "time to first token" vs "decode throughput." If the CPU processes 8 threads and the GPU processes layers, the system might be running at the CPU's full 8x throughput, but the "decode throughput" might be artificially high if the GPU is idle while the CPU is busy. Conversely, if the system is stuck waiting for data from the CPU when the GPU is ready, the perceived latency is higher than true throughput.
    *   **Control:** Compare **Average Latency** vs. **Throughput**. A scenario where the CPU is fully utilized but the GPU is underutilized (e.g., GPU offloading all layers while CPU is idle) will cause high latency but low throughput. Conversely, a scenario where the CPU is idle but GPU is full will cause low latency but high throughput. Measure both metrics to isolate the true latency.

3.  **Output Comparability (The "Prompt-Jump" Issue):**
    *   **Threat:** If the CPU processes a 2,000-token prompt (via 8 threads) and the GPU processes a 500-token prompt (via 2 threads), the GPU might be able to generate the prompt but fail to generate the remaining 1,500 tokens (due to generation limits or the need for prompt generation).
    *   **Control:** **Ensure prompt length matches the generation limit.** If the CPU generates a long prompt that exceeds the GPU's generation limit, the GPU must generate the rest. This creates a bottleneck where the CPU does the heavy lifting but the GPU cannot finish the job, resulting in "late" or "skipped" outputs.

4.  **Output Validity (False Positives from GPU Offloading):**
    *   **Threat:** The prompt asks to compare CPU vs. CUDA. If the GPU is offloading *all* layers, it is effectively optimizing for speed. If the GPU is offloading *only* some layers, the model might be underperforming compared to the CPU because it is not using the GPU's best capabilities (e.g., if the GPU has a higher CUDA CUDA thread count or better kernel code).
    *   **Control:** **Compare GPU Offloaded vs. CPU Offloaded.** If the GPU is offloading the *same* layers as the CPU, the latency should be comparable. If the GPU is offloading only a subset of layers, the CPU might be underutilized. Use metrics like **Latency per Token** to ensure the GPU is actually working on the target workload.

## Task 5 — User-Visible Latency
**Assumptions:**
*   Prompt: 2,000 tokens.
*   Tokens Generated: 200.
*   Context: "User-visible latency" is defined by the total time from the moment the user presses Enter until the model finishes.

**Difference Explanation:**
*   **Time to First Token (TTFT):** The time the user sees the first character appear on screen. This is determined by the CPU's rendering queue and the GPU's display buffer. It depends on the CPU's ability to render 8 threads at their maximum speed.
*   **Prompt-Evaluation Throughput:** The average speed at which the GPU can generate tokens while the CPU is actively processing them. It depends on the GPU's GPU bandwidth relative to the CPU's RAM bandwidth.
*   **Decode Throughput:** The speed at which the model successfully produces tokens *after* the prompt has been fully generated. This is determined by the GPU's ability to complete the generation once the prompt is ready.
*   **Total Wall-Clock Time:** The sum of the three above phases, often including a small delay for the CPU to render the first token if the GPU is not immediately responsive.

**Symbolic Equation for Total Time:**
Let $T_{TTFT}$ be the time to first token.
Let $T_{PE}$ be the time to evaluate the prompt (assuming prompt-generation time is negligible compared to the model latency).
Let $T_{Decode}$ be the time to generate the 200 tokens.
Let $T_{Total}$ be the total wall-clock time.

$$T_{Total} = T_{TTFT} + T_{PE} + T_{Decode}$$

*Note: $T_{PE}$ represents the time the GPU is busy generating the prompt but the CPU is not yet free to process the output. This is the "prompt-jump" delay.*

**Example where Optimizing Prompt Processing Barely Changes the User's Experience:**
*   **Scenario:** The user types a 2,000-token prompt. The CPU processes it instantly. The GPU immediately starts generating the first 200 tokens.
*   **Optimization:** Ensure the GPU has enough **free memory** to hold the 200 generated tokens *while* the CPU is still processing the prompt.
*   **Why it barely changes:** If the CPU finishes the prompt instantly (8x speed) and the GPU has ample memory to generate the 200 tokens, the GPU will be idle. The user sees the first 200 tokens instantly and then waits for the GPU to finish generating the remaining 180 tokens. The total duration increases by roughly 180 tokens / speed, which is a small fraction of the 2,000-token prompt.
*   **Example:** If the GPU has 20 GB of free memory, and the CPU generates 200 tokens in 10ms (1,000 tokens/sec), the GPU takes 200 tokens in ~20ms. Total time = 10ms + 20ms + 20ms = 50ms.
*   **Comparison to Optimization:** If the GPU only had 10 GB of free memory, generating the 200 tokens would take 200 tokens / 1,000 tokens/sec = 0.2 seconds. Total time = 10ms + 20ms + 200ms = 230ms.
*   **Result:** In the scenario above, optimizing prompt processing (providing more free memory) only delays the total time by 20ms (the generation time of the first batch), whereas if the prompt generation itself was the bottleneck (e.g., CPU was slow), a 100ms delay would be more noticeable.
