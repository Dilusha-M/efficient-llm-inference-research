### Task 1 — quantization tradeoff
**Memory Pressure Analysis:**
The **Q8_0** format (8-bit quantization) creates the most severe memory pressure. The file size is 8.0 GB. When running on an 8B model with an 8.0 GB Q8_0 file, the model must load the entire file into the device before processing, resulting in a memory footprint of approximately 15–16 GB (excluding the 8B model itself).
The **Q4_K_M** format (4-bit quantization) creates significantly less pressure. The file size is 4.8 GB, requiring about 1.2 GB for the quantization file. For an 8B model, this leaves approximately 6.4 GB of free memory before inference.

**Why File Size is Not a Complete Runtime-Memory Estimate:**
File size is only an initial static estimate. During inference, memory usage is dynamic based on:
1.  **Inference Overhead:** The model execution itself consumes memory (activation buffers, attention states, etc.).
2.  **Backends & Buffers:** Different quantization formats vary in their internal buffers (e.g., Q8_0 often has larger attention buffers than Q4_K_M).
3.  **Hardware Limits:** GPU memory constraints (e.g., the 5.2 GB free before inference) may be saturated by the quantization file alone, regardless of the file size.

**Required Measurements for Comparison:**
To declare one format "better," one must compare the **actual memory usage at runtime** and **latency performance** (which is not directly comparable to raw file size). Two specific measurements are required:
1.  **Peak Memory Footprint:** The maximum memory consumption observed during the inference window for each format.
2.  **Latency Performance (or Average Latency):** The time to generate the first token (Prompt-to-End latency) for each format. *Note: Q4_K_M is generally faster on GPU for 8B models due to better memory layout and fewer operations, but it cannot be assumed to be faster everywhere.*

### Task 2 — Conservative Launch Decision
**Procedure for Context Size and GPU Layer Offload:**
Given a machine with **16 GB RAM**, a **6 GB GPU**, a **512-token prompt**, and a **500-token generation limit** (200 prompt + 300 generation), the conservative procedure involves balancing memory efficiency against latency constraints.

1.  **Context Size Selection:**
    *   **Strategy:** Start with a small context size to ensure the model only loads the most relevant tokens (the prompt) and avoids loading the entire 500-token window if the prompt is short.
    *   **Action:** Begin with **100 tokens**. If the model processes this quickly and the latency is acceptable, proceed to **200**. If the latency spikes, consider reducing to **50**.
    *   **Why:** Loading more context than the prompt can process increases latency and memory usage.

2.  **GPU Layer Offload:**
    *   **Strategy:** Offload the most computationally expensive layers (typically the first 25–30 layers for 8B models) to the CPU to utilize the GPU's memory bandwidth.
    *   **Action:** Offload layers 1–25. Keep layers 26–50 on the GPU to ensure the GPU is utilized for the longer, more stable generation phase.
    *   **Why:** CPU offloading reduces VRAM usage and lowers latency, but it does not necessarily improve generation speed if the GPU is saturated by the first layers.

3.  **Telemetry to Record:**
    *   **Context Length:** The actual context size loaded (e.g., 100 tokens).
    *   **Latency:** The time to generate the first token.
    *   **Memory Footprint:** The peak memory usage observed during inference.
    *   **Generation Latency:** The time to generate the second token (to distinguish prompt processing from generation).

4.  **Unsafe or Misleading Success:**
    *   **Incorrect Context Size:** Choosing a context size larger than the prompt (e.g., 1000 tokens) results in a massive context window load, causing latency spikes, GPU out-of-memory errors, and poor inference quality.
    *   **Ignoring Latency:** Offloading heavy layers to the GPU while keeping the first layers on the CPU might cause the GPU to become saturated before the second generation token is generated, leading to a "fast but unreliable" or "stuttering" generation experience.
    *   **Static Assumption:** Claiming the 5.0 GB weight figure is "safe" if the actual generated tokens exceed the 500-token limit or if the GPU memory is fully saturated by the quantization file alone without adequate context.

### Task 5 — User-Visible Latency
**Explanation of Latency Components:**
The provided metrics differ in what they measure.

*   **Time to First Token (Prompt-to-End Latency):** The elapsed time from the moment the user sends the prompt until the first token is generated. This is the primary metric for *how long it takes to read the prompt*.
*   **Prompt-Evaluation Throughput:** The number of tokens generated per second (tokens/s). This is a throughput metric, not latency, but it indicates efficiency.
*   **Decode Throughput:** The number of tokens generated per second (tokens/s). This is the *same as Prompt-Evaluation Throughput* but refers to the token generation process.

**Symbolic Equation for Total Time:**
$$ T_{total} = T_{prompt} + \underbrace{\text{Latency}_{generation}}_{\text{Time for the model to process and output the final token}} $$
Where:
*   $T_{prompt}$ is the time to first token.
*   $\text{Latency}_{generation}$ is the time required for the model to process the prompt and generate the final token.

**Example where optimizing prompt processing barely changes the experience:**
*   **Scenario:** A user types "Hello" and presses enter. The system must wait for the prompt to be fully read and validated before the first token can be generated.
*   **Optimization:** If the system can process a 200-token prompt in less than 1 second (e.g., by offloading the first 25 layers to the CPU), the time to first token ($T_{prompt}$) becomes negligible (e.g., < 0.1 seconds).
*   **Result:** Since the prompt-to-end latency is already < 1 second, optimizing the *prompt processing speed* has a **minimal effect** on the total user experience. The user perceives the time as constant. Only if the prompt-to-end latency were significantly higher (e.g., > 5 seconds) would optimization of prompt processing change the perceived experience substantially.
