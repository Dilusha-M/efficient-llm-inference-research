### Task 1 — Quantization Tradeoff
**Assumptions:**
*   **Hardware:** A 6 GB GPU (e.g., 8x8-bit or similar) with 5.2 GB free before inference (i.e., available for 16G contiguous memory).
*   **Model:** 8B context size (1024 tokens).
*   **Quantization:** Q8_0 (full precision, 8 bits per channel) vs. Q4_K_M (int8 or float16, 4 bits per channel).
*   **Runtime Memory Estimate:** Inference time is a direct function of memory bandwidth and occupancy. Assuming the 8B model fits in 8G contiguous memory and the 4.8 GB Q4_K_M file contains the model weights and potentially some KV cache (which depends on the specific quantization method and context), we must distinguish between the file size and actual runtime.

**Memory Pressure Analysis:**
*   **Q8_0 File (8.0 GB):**
    *   **Pressure:** The file size is **not** a direct runtime-memory estimate; rather, the file size is a **static resource constraint**. A 8.0 GB file cannot fit in 5.2 GB free memory unless the memory is heavily fragmented or if the file includes significant overhead (like intermediate layers).
    *   **Pressure Source:** The file itself requires contiguous 8-bit storage. If the GPU has 5.2 GB free, it is likely **overloaded** by the file size itself, not just the model. If the GPU is not fully utilized by the file, the file is "wasted" memory.
*   **Q4_K_M File (4.8 GB):**
    *   **Pressure:** This file size is a **runtime-memory estimate**. Inference time is driven by the actual bytes of the model weights and KV cache. A 4.8 GB file implies the model weights occupy roughly 4.8 GB. If the 8B model fits in 8G, the file size is a reasonable proxy for the actual memory footprint.
    *   **Pressure Source:** It creates pressure if the file is large enough to saturate the 5.2 GB free bandwidth, or if the file includes unnecessary overhead.

**Why File Size is Not a Complete Runtime Estimate:**
1.  **Overhead vs. Content:** A 8.0 GB file includes metadata, headers, and potentially large intermediate activations if the model is not fully quantized. A 4.8 GB file might exclude these.
2.  **Fragmentation:** Memory is often fragmented. A 8.0 GB file might fit in 5.2 GB of contiguous memory, but the actual memory usage during inference depends on where the 8-bit data is stored, not just the total file size.
3.  **Model Size Variance:** The actual runtime depends on the model's capacity (8B vs. 4B). If the Q8_0 file is slightly larger due to more complex quantization, the pressure would be higher than the 4.8 GB file, even if the Q4 file is smaller.

**Quality/Performance Measurements Needed:**
Before declaring one format better, two measurements are required:
1.  **Quantization Efficiency / Memory Footprint:** The ratio of actual runtime memory usage to the file size (e.g., $Memory_{runtime} / FileSize_{file}$). A 64-bit float file is far more memory-intensive than a 4-bit file, regardless of the model size.
2.  **Latency / Throughput (Token Rate):** The ratio of tokens generated per second ($Tokens_{generated} / Time_{inference}$) for both formats. This distinguishes between "cost" (memory) and "performance" (speed).

**Important Note:** Q4 is not always faster. Q8_0 is faster at **cost** (lower memory pressure and faster memory bandwidth utilization). Q4K_M is faster at **speed** (higher throughput) but incurs higher memory pressure. The optimal choice depends on whether the GPU bandwidth is a bottleneck (where Q4K_M wins) or memory pressure is the bottleneck (where Q8_0 wins).

### Task 5 — User-Visible Latency
**Explanation of Differences:**
*   **Time to First Token (t_1):** This is the latency when the user types the first character. It is dominated by **prompt processing**. The GPU is typically idle or at a very low load while waiting for the prompt, so this time is roughly identical across all backends.
*   **Prompt-Throughput (t_p):** The latency when the user types the entire prompt and the model begins generating. This is the **primary bottleneck** for all backends. It depends on the GPU's compute capability, memory bandwidth, and the efficiency of the offload layer.
*   **Decode Throughput (t_d):** This is the latency when the model **decodes** the first token after the prompt is generated. This is where the **difference** is most apparent. The CPU (with 8 threads) is more efficient at parallelizing the decoding process compared to the GPU (which has fewer threads by default and has higher memory bandwidth). Thus, t_d is typically lower on the CPU.
*   **Total Wall-Clock Time (t_total):** The sum of these phases: $t_{total} = t_{prompt} + t_{t_1} + t_p + t_d$.

**Symbolic Equation:**
$$t_{total} = t_{prompt} + t_{t_1} + t_{prompt} + t_{decode}$$
$$t_{total} = 2 \cdot t_{prompt} + t_{t_1} + t_{decode}$$

**Example of Optimizing Prompt Processing:**
*   **Scenario:** A user types a long prompt (e.g., 2,000 tokens).
*   **Optimization:** Instead of typing the prompt immediately, the system runs a **prompt processing pipeline** (e.g., using a specialized inference engine or a smaller, faster model) to generate the first 500 tokens, and then submits the full prompt to the GPU for decoding.
*   **Result:** While the total wall-clock time for the full generation increases slightly due to the extra CPU processing, the **user's perceived experience** remains unchanged because they can type and input the prompt much faster than they can wait for the GPU to start decoding the entire prompt.
