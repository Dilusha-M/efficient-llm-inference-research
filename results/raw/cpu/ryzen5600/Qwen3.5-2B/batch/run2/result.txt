### Task 1 — quantization tradeoff

**Memory Pressure Analysis**
*   **Q8_0 (8.0 GB):** With 8.0 GB of weights on an 8.0 GB GPU and only 5.2 GB of free memory, the model has **0 GB** of free memory. The model is running out of RAM.
*   **Q4_K_M (4.8 GB):** With 4.8 GB of weights on a 6 GB GPU and 5.2 GB of free memory, the model has **0.4 GB** of free memory.
    *   *Assumption:* The 8.0 GB Q8_0 file represents the *entirety* of the model weights at inference time.
    *   *Assumption:* The 4.8 GB Q4_K_M file represents the *entirety* of the model weights at inference time.

**Why file size is not a complete runtime-memory estimate**
The runtime memory footprint is not simply the file size because:
1.  **KV Cache:** Large language models generate context that is significantly larger than the weights. The prompt tokens (2,000 in the second task, but hypothetical in this context) plus generated tokens can easily exceed the weights in size, potentially requiring 10–20 GB of VRAM depending on the generation length.
2.  **Activation History:** For long generation sequences, the stack of activations can grow significantly larger than the weights, pushing memory usage well beyond the file size.
3.  **Quantization Overhead:** Even with `Q4_K_M`, there is overhead for the quantization engine, precision types (floats), and kernel launch overheads.

**Two quality/performance measurements needed**
Before declaring one format better, one must evaluate:
1.  **Latency (Time to First Token / Token Generation Time):** Measures the wall-clock time per token, which is the most critical user-facing metric. A lower value indicates better throughput.
2.  **Memory Efficiency (VRAM Utilization):** Measures the ratio of model size to actual VRAM used (e.g., $8.0/8.0 = 100\%$ vs $4.8/6.0 = 80\%$), or more specifically, the VRAM required for the *effective* generation (Weights + KV Cache).

**Conclusion**
Q8_0 creates 100% VRAM utilization (critical risk), while Q4_K_M creates 80% VRAM utilization. Therefore, Q4_K_M is the safer choice *if* the generation length is short enough that KV Cache overhead remains below the 0.4 GB free margin. However, if the generation length causes the KV cache to exceed 0.4 GB, the user will experience OOM, regardless of the quantization. Thus, **Q4_K_M is not universally faster**; it is only faster if the generation length fits within the available free memory.

### Task 3 — robust aggregation

**Pseudocode for Robust Aggregation**
```python
def robust_aggregate_decodes(
    successes: list, 
    failures: list,
    threshold: float = 0.0
) -> float:
    """
    Validates records, keeps failed runs visible, and computes median 
    without silently treating failures as zero.
    """
    
    # 1. Validation: Keep failed runs visible
    for i, run in enumerate(failures):
        print(f"Run {i+1} ({run.get('task_id', 'Unknown'))} FAILED: {run.get('error_message', 'Unknown Error')}")
    
    # 2. Validation: Keep successes visible
    for i, run in enumerate(successes):
        # Determine the phase (prompt_eval or decode) to include in the summary
        phase = run.get('phase')
        print(f"Run {i+1} ({run.get('task_id', 'Unknown'))} SUCCESS: {run.get('metrics', {}).get('tok/s', 'N/A')} tok/s ({phase})")
    
    # 3. Computation: Calculate Median
    total_tokens = sum(r.get('metrics', {}).get('tok/s', 0) for r in successes)
    n = len(successes)
    
    if n == 0:
        raise ValueError("No successful runs found to compute median.")
    
    # Sort for median calculation
    sorted_sums = sorted([r.get('metrics', {}).get('tok/s', 0) for r in successes])
    
    if n % 2 == 1:
        # Odd number of runs
        median = sorted_sums[n // 2]
    else:
        # Even number of runs
        median = (sorted_sums[n // 2 - 1] + sorted_sums[n // 2]) / 2.0
    
    return median
```

**Reporting if fewer than two runs succeed**
If fewer than two successful runs exist (i.e., `len(successes) < 2`), the function cannot compute a meaningful median because a median is the middle value of a dataset, requiring an even or odd count where the middle element is defined.
*   **Action:** Report the count of successes and failures.
*   **Example Output:** "Only 1 successful run found. Cannot compute median." or "Median undefined (insufficient data)."
*   **Rationale:** A median is statistically the robust estimator of central tendency, but it requires a sample size of at least 2 (or $n$ where $n$ is odd). With $n=1$, the dataset is trivially skewed; with $n<2$, no central point exists.

    *   *Control:* Use **exact floating-point precision** for validation runs (e.g., float32) to establish a baseline against which the quantized results are measured.

### Task 5 — user-visible latency

**Difference Between Metrics**
For a 2,000-token prompt and 200 generated tokens:
1.  **Time to First Token (TTFT):** The wall-clock time from the start of the generation process (after prompt evaluation) until the very first generated token is output. This is the most immediate user-perceived latency.
2.  **Prompt-Evaluation Throughput:** The throughput of the model processing the input prompt to produce the output logits. This is a measure of how fast the *model* can process the input, not necessarily how fast the output leaves the host.
3.  **Decode Throughput:** The throughput of the model processing the KV cache and generating output tokens. This measures the model's raw generation capability.
4.  **Total Wall-Clock Time:** The sum of TTFT and the time spent generating the 200 tokens.

**Symbolic Equation**
Let $t_0$ be the start time, $t_{TTFT}$ be time to first token, $t_{eval}$ be time for prompt evaluation, and $t_{gen}$ be the time for the 200 tokens.
$$ \text{Total Time} = t_0 + t_{TTFT} + t_{eval} + t_{gen} $$
*(Note: Often $t_0$ and $t_{TTFT}$ are merged, simplifying to $\text{TTFT} + t_{eval} + t_{gen}$)*

**Example where optimizing prompt processing barely changes user experience**
Consider a scenario where the user types a very long, complex prompt (e.g., "Explain the quantum entanglement phenomenon in the context of string theory and compare the results to standard model outputs.").
*   **Action:** Optimizing the prompt processing (e.g., parsing the prompt faster, reducing tokenization latency, or improving the decoding pass) might reduce the **Prompt-Evaluation Throughput** by 10%.
*   **Result:** The **Time to First Token** might increase by 0.1 seconds because the system waits longer for the prompt to be fully parsed and processed.
*   **User Experience:** To the user, the experience is **unchanged**. They type their prompt, hit enter, and receive the first character almost immediately. The delay is negligible compared to the typical 200-token generation latency (which could be 2–5 seconds). The optimization only saves time *after* the first token has been generated, which is invisible to the user.
