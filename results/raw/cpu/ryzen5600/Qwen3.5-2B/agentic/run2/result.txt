# Project: Llama-CPP Benchmark Runner Specification

## 1. Requirements and Invariants

**Inputs:**
*   **Configuration File (`benchmark.yaml`):** Defines base parameters (context size, generation limit, temperature) and optional overrides for specific workloads.
*   **Model Assets:** `.bin` or `.safetensors` files representing the Llama model.
*   **Metadata File:** A single line in `metadata.json` containing `model_path`, `backend`, `hardware_label`, `build`, `prompt_hash`, and `generated_token_count`.
*   **Hardware Description:** File listing supported GPUs/Directories (e.g., `devices.txt`).

**Artifacts:**
*   **`response.txt` / `raw_response.txt`:** The raw stdout/stderr captured from the `llama.cpp` process.
*   **`metrics.txt` / `perf_output.txt`:** The formatted performance metrics (tokens/s, VRAM usage, etc.).
*   **`audit_log` (in-process):** A temporary buffer capturing the raw stdout/stderr stream before file creation.

**Success vs. Failure States:**
*   **Success:** The runner completes all monitored workloads within the timeout limit, produces valid `metrics.txt` for each, and the resulting `metadata.json` is valid JSON containing the `generated_token_count`.
*   **Failure:**
    *   **Model Load Fail:** The process cannot start or cannot load the model file.
    *   **Monitor Fail:** The monitoring component cannot start or its socket connection drops.
    *   **Process Crash:** The `llama.cpp` process exits abruptly (e.g., OOM, segmentation fault) without producing a complete metrics block.

**Experimental Identity Tuple:**
To ensure results are comparable, the runner must capture the following tuple for every run:
```json
{
  "context_size": 4096, // Default, or override via config
  "gen_limit": 256, // Default, or override via config
  "temperature": 0.7, // Default, or override via config
  "backend": "cpu" | "cuda" | "vulkan",
  "hardware_label": "NVIDIA/Hardware-Brand", // String identifying the device
  "build_info": "LLAMA-2-7B-INT4", // Version from config
  "prompt_hash": "sha256(...)", // Hash of the fixed prompt string
  "generated_token_count": <int> // Only present if successful
}
```

**Ambiguity to Resolve:**
**Ambiguity:** What constitutes a "failed model run"?
**Resolution:** A run is considered failed if the `llama.cpp` process terminates with a non-zero exit code *before* the `metrics.txt` file is fully written to disk. The runner must treat any non-zero exit code during the "launch" phase as a failure, even if the process later times out. If the process times out (wall-clock limit exceeded) without writing any metrics, it is treated as a failure, not a success with missing data.

## 2. State-Machine Workflow

The system operates as a state machine with the following transitions:

1.  **Initialization (`START`):**
    *   Parse `benchmark.yaml` to set defaults.
    *   Scan `devices.txt` to populate `hardware_label`.
    *   Validate that all required assets (model files, config) exist. If not, transition to `ERROR`.

2.  **Validation (`VALIDATE`):**
    *   Verify `backend` and `build` match the current system state (or accepted overrides).
    *   Check that the default context (4096) and gen limit (256) are not overridden by the user in a way that violates known tool constraints (e.g., context > 4096 unless overridden).
    *   *Note:* If overrides conflict with known constraints, raise an error rather than silently ignoring them, as this violates the "no mixing" invariant.

3.  **Launch (`LAUNCH`):**
    *   Spawn `llama.cpp` subprocess.
    *   Capture raw `stdout` and `stderr` into an internal buffer (`audit_log`).
    *   Define a timeout (e.g., 60s) based on the `gen_limit`.
    *   Transition to `MONITORING`.

4.  **Monitoring (`MONITORING`):**
    *   Attempt to establish a connection to a monitoring socket.
    *   **Scenario A (Monitor Available):** Read metrics every N tokens. Write to `metrics.txt`.
    *   **Scenario B (Monitor Missing):** Do not write metrics. Continue running.
    *   **Timeout:** Wait for the `gen_limit` generation count.
    *   **Partial Output:** If the process writes metrics but the file is truncated or corrupted, stop the run and log a `PERF_OUTPUT_FAILURE` state.

5.  **Process Exit (`EXIT`):**
    *   **Normal Exit:** If the process terminates normally, write the final metrics to `metrics.txt` (atomic write).
    *   **Failure Exit:** If the process crashes or exits with error, do *not* write the metrics file. Instead, write a `PERF_OUTPUT_FAILURE` entry to the `audit_log` indicating the exit reason.

6.  **Finalization (`FINISH`):**
    *   Clean up process.
    *   If `PERF_OUTPUT_FAILURE` state was reached, generate a `metadata.json` containing only the fixed fields (model, backend, hardware, build, prompt_hash) *without* the `generated_token_count`.
    *   If normal state reached, append the `generated_token_count` to `metadata.json`.
    *   Write the raw `response.txt` to `raw_output.txt` for manual audit.
    *   Transition to `DONE`.

**Exceptions:**
*   **OOM:** If memory allocation fails during `LAUNCH`, the process is killed, and the run fails.
*   **Malformed Output:** If the process writes garbage to `metrics.txt` (e.g., non-numeric tokens), the runner must detect this (e.g., via regex pattern matching) and treat it as a failure to prevent misleading throughput.

## 3. Auditable Design

**Component Boundaries:**
*   **`ConfigManager`:** Loads YAML/JSON config, validates constraints, and populates the `benchmark.yaml` file.
*   **`BenchmarkRunner`:** Orchestrates the subprocess lifecycle, manages timeouts, and handles the state machine logic.
*   **`PerformanceMonitor`:** (Optional) A separate process or subprocess that listens on a Unix domain socket for metrics updates. If unavailable, `BenchmarkRunner` acts as the fallback monitor.
*   **`AuditWriter`:** A low-level helper that writes to the `audit_log` buffer rather than the final output files to ensure the raw stream is preserved.

**Metadata Schema (`metadata.json`):**
```json
{
  "model_path": "path/to/model.bin",
  "backend": "cuda",
  "hardware_label": "NVIDIA-A100-SXM4-80GB",
  "build": "Llama-2-7B-INT4",
  "prompt_hash": "0x..." // SHA256 of the exact prompt string used
  // The following keys are ONLY present if the run was successful:
  "generated_token_count": 1024
}
```

**Atomic-Write Conventions:**
*   **Metrics File (`metrics.txt`):** Must be written using `f.write("metrics...")` or `file.write()` to ensure the file is either fully written or completely empty.
*   **Raw Stream:** The `audit_log` must be a Python `string` containing the raw stdout/stderr bytes as a single string, preserving line breaks and whitespace exactly as they appeared.
*   **Output Files:**
    *   `raw_output.txt`: Appended to the end of the `audit_log` after the run completes.
    *   `metrics.txt`: Created by the runner only if the run was successful.
    *   `metadata.json`: Only written if `generated_token_count` was present. If missing, the file is created but empty (or omitted from the final summary).

**Prompt Preservation:**
The `audit_log` buffer captures the command line arguments of `llama.cpp` *before* execution. The exact prompt string is reconstructed from this captured text or passed as a command-line argument to the subprocess. This ensures that even if the prompt string is long or contains special characters, it is preserved in the audit log for the auditor's reference.

## 4. Analysis Integrity

**Preventing Misleading Throughput:**
To prevent a failed run or one with variable generated-token counts from skewing throughput comparisons (e.g., comparing 10 tokens/s on a 100 token run vs 20 tokens/s on a 200 token run):
1.  **Strict Mode Enforcement:** The runner calculates expected throughput (`tokens_generated` / `wall_clock`).
2.  **Threshold Check:** If `generated_token_count` is significantly lower than the configured `gen_limit` (e.g., < 5% of limit), the run is marked as "insufficient data" and the output is ignored.
3.  **Format Validation:** A parser checks the `metrics.txt` structure. If the format deviates from the expected Llama-CPP standard (e.g., missing header, non-integer token count), the run is marked as "malformed output" and excluded from the final report, preventing garbage data from being averaged into the final throughput score.

**Parser for Unknown Formats:**
The parser should implement a fallback strategy:
1.  Attempt to parse the standard header (e.g., `# Llama.cpp Benchmark`).
2.  If that fails, attempt to parse the raw stream for a specific signature (e.g., `tokens_per_second`).
3.  If both fail, the token count is derived *only* from the `generated_token_count` field in `metadata.json`.
4.  If `generated_token_count` is missing or zero, the run is automatically excluded from the "Success" category, ensuring the final report only aggregates valid, comparable data.

## 5. Test Plan

1.  **Simulated Backend Failure:**
    *   *Scenario:* The `devices.txt` file lists a non-existent GPU, or the `benchmark.yaml` specifies a backend that doesn't exist.
    *   *Action:* `llama.cpp` fails to load the device.
    *   *Verification:* Check that `metrics.txt` is not created and `metadata.json` contains the `backend` field but no `generated_token_count`.

2.  **Missing Monitor:**
    *   *Scenario:* The monitoring socket is missing or the connection drops immediately.
    *   *Action:* Run the benchmark with a low `gen_limit` (e.g., 10 tokens) to avoid timeout.
    *   *Verification:* Ensure `metadata.json` has the `generated_token_count` field populated correctly despite no monitoring data being collected.

3.  **Prompt Containing Spaces/Newlines:**
    *   *Scenario:* The `benchmark.yaml` overrides the prompt to include a newline or spaces (e.g., `prompt: "Hello\nWorld"`).
    *   *Action:* Ensure the `audit_log` in `raw_output.txt` contains the exact prompt string including newlines, and `metadata.json`'s `prompt_hash` reflects the new hash.

4.  **Partial Output:**
    *   *Scenario:* The process crashes while writing to the metrics file (e.g., `SIGSEGV`), leaving the file truncated.
    *   *Action:* The `llama.cpp` process exits with a non-zero code.
    *   *Verification:* No `metrics.txt` file is generated. The `audit_log` indicates a `PERF_OUTPUT_FAILURE` state.

5.  **Changed Prompt Hash:**
    *   *Scenario:* The `benchmark.yaml` changes the prompt to a 2000-character string.
    *   *Action:* The hash of this new string is calculated.
    *   *Verification:* The `metadata.json` `prompt_hash` field must update to reflect the new hash, proving the system tracks prompt identity.

6.  **Timing Consistency:**
    *   *Scenario:* Two runs with identical configs and hardware, but different `gen_limit` values (e.g., 20 vs 100 tokens).
    *   *Action:* Run both.
    *   *Verification:* Both runs must be marked as "Success" and have `generated_token_count` populated. The throughput values should reflect the actual time taken to generate that specific token count.

## 6. Pre-Merge Review

**Highest-Risk Design Flaws and Fixes:**

1.  **Flaw 1: Inconsistent Handling of Missing Monitors.**
    *   *Risk:* If the monitoring component is missing, the runner might still write a `metrics.txt` file, leading to a false "Success" state where the user sees a valid report even if no data was actually collected.
    *   *Fix:* Explicitly conditionally write `metrics.txt` inside `MONITORING`. If the monitor is unavailable, write nothing to the file. Only write to the file if the monitor is successfully connected. This requires a check in `MONITORING` state before file writing begins.

2.  **Flaw 2: Ambiguity on "Partial Output" Definition.**
    *   *Risk:* If `llama.cpp` writes a partial metrics file that is later truncated by disk I/O while the process is still running, the final run might be marked "Success" because the file exists, but the data is corrupted.
    *   *Fix:* Define "Partial Output" strictly as "Process exited with non-zero code *before* metrics file was fully written to disk". If the file is written, it must be fully written (no truncation) or the process must have terminated cleanly. The state machine must verify `metrics.txt` integrity (e.g., by checking file size vs. expected size based on `gen_limit`) before marking the run as "Success".

3.  **Flaw 3: Inability to Distinguish "No Metrics" from "Failed Output".**
    *   *Risk:* If the process generates valid metrics but the `metadata.json` generation logic incorrectly omits the `generated_token_count` field when it shouldn't, the user cannot determine if the benchmark failed due to a crash or simply because the monitoring component was missing.
    *   *Fix:* Ensure the `FINISH` state logic explicitly checks the `audit_log` for `PERF_OUTPUT_FAILURE` markers. If such a marker exists, the runner must skip the `metadata.json` generation entirely, ensuring the distinction between "failed run" (no metrics file) and "missing monitor" (valid metrics file but missing token count) is maintained.
